# 方案总览与关键决策

> 本文是产品方向和关键权责的唯一决策摘要。它先回答“工作台是什么”，再说明知识、Skill、Git、WeKnora、SkillHub 和 DeepSeek Harness 如何协作。

## 1. 产品定义

这是一个面向团队的**知识与 Skill 创作发布工作台**，以可进入 DSH Desktop Workbench 市场的 `team-knowledge-workbench` 作为产品交付形态。

`team-knowledge-workbench` 是可复用的 Workbench 产品/插件包；`team-knowledge-asset` 是独立的团队资产域。不同团队可以安装同一个 Workbench，但必须分别绑定自己的资产 Git 仓库、WeKnora space、权限、steward、审核策略和下游分发目标。工作台不复制 DeepSeek Harness 的会话运行时，也不把发布后的任务执行作为自己的主产品模块。

工作台的主要工作单元是 **Creation Session（创作会话）**。首页提供两个启动动作：从资料创建知识、从工作流创建 Skill；启动动作会创建独立的草稿和会话，用户在会话内完成梳理、确认、测试、提交和发布。多个会话可以并行，但各自隔离上下文、草稿、异步操作和回调。

```text
资料入口：材料 → Agent 梳理/讨论 → Knowledge → Git/MR/CI
  → protected main merge → merge event → Workbench outbox/worker
  → WeKnora ingest/read-back → published knowledge
能力入口：工作流 → Agent 追问/建模 → Skill + 测试 → Git/MR/CI
  → protected main merge → package/digest → SkillHub release/read-back
  → pinned digest
发布交接：SkillHub pinned digest → TeamAI distribution/read-back
  → DSH handoff/discovery/load read-back
反馈回流：Harness/业务反馈引用 → 知识复核或 Skill 回归 → 新版本发布
```

`merge event` 只是异步发布的触发事实。只有下游真实状态读回，才能推进 `published`、`released`、`installed` 或 `loaded`；HTTP 200、任务入队和 provider 接受请求都不构成业务成功。

## 2. 系统职责

| 层 | 解决的问题 | 主要职责 |
|---|---|---|
| 知识/Skill 创作发布工作台 | 我们应该知道什么，以及如何稳定完成一类工作？ | 首页入口、Creation Session、梳理、讨论、建模、测试、审核、提交、发布和反馈候选 |
| Git/CI、WeKnora、SkillHub、TeamLab | 如何保存、索引、协作和分发已批准资产？ | 各自维护 canonical source、知识检索、内部协作或 Skill release；通过受控 adapter 共用服务接入，不共用团队资产授权 |
| DeepSeek Harness 会话工作台 | 如何消费已发布能力完成一次会话任务？ | Workspace、Session、Skill discovery/load、工具、权限、人工批准、恢复和运行观测 |
| 业务系统/SPC 后端 | 业务事实和生产状态是什么？ | 计算、告警、工单、业务写入和真实结果 |

## 3. 首期必须证明的两条生产线

### 知识链

```text
会议纪要/资料
  → 从资料创建知识
  → Knowledge Creation Session
  → 材料 → 梳理 → 确认 → 提交 → 发布
  → Knowledge Draft
  → Git/MR/CI/审核
  → protected main merge
  → Git merge event
  → Workbench outbox/worker
  → WeKnora ingest
  → document/version/source/ACL read-back
  → 带来源和版本的可检索知识
```

### Skill 发布链

```text
重复工作流
  → 用户自然语言描述
  → Agent 追问输入、步骤、判断、例外、输出和成功标准
  → Workflow Draft
  → Skill Draft（说明、资源、脚本、契约、测试集）
  → 样例试跑和评测
  → Git/MR/CI/审核
  → protected main merge
  → package + immutable digest
  → SkillHub release/read-back
  → pinned digest
```

### 分发链

```text
SkillHub pinned digest
  → TeamAI distribution request
  → target workspace install/pull
  → TeamAI installed revision/digest read-back
  → DSH handoff
  → DSH profile/loaded digest read-back
  → 下游 Harness 消费
```

TeamAI 不重新决定 Skill 版本，也不从 `latest` 构建或拉取；它只分发 SkillHub 已确认的固定 digest。SkillHub、TeamAI 或 DSH 不可用时，可以走管理员 fallback，但必须保留相同的 package、digest、target、profile、读回和回滚证据。

### 下游消费，不是本项目生产线

```text
approved Skill/Knowledge release
  → SkillHub 确认 Skill package/digest（知识仍由 WeKnora 索引）
  → TeamAI pinned digest distribution（如启用）
  → DeepSeek Harness handoff/discovery/load
  → Harness Workspace/Session 消费
  → 结构化 feedback reference 回到本项目
```

工作台可以验证一个发布版本是否具备下游交接所需的 metadata，也可以接收下游反馈；但不实现完整 Session、Run、Tool Call、运行时人工 gate 或业务任务状态机。

## 4. 核心决策

| 决策 | 当前结论 |
|---|---|
| 产品主语 | 知识和 Skill 的创作、测试、审核与发布工作台 |
| Knowledge | 有来源、适用范围、owner、版本和复核信息的正式知识 |
| Workflow | 对一类工作的步骤、判断、例外、输入、输出和人工节点的结构化描述；是 Skill 生成的中间对象 |
| Skill | 可复用、可测试、可版本化和可发布的任务能力包；不等于一段 Prompt |
| Git | knowledge-assets、Skill 源码、契约、测试、metadata 和评审的 canonical source |
| WeKnora | 已批准知识的 Wiki/索引/检索层；不负责 Skill 管理和事实审批 |
| SkillHub | Skill package 的注册、不可变版本/digest 和 release read-back；不替代 Git/CI、质量评测、人工审核或 TeamAI 目标安装 |
| TeamAI | 消费 SkillHub 已确认的 pinned digest，负责目标 workspace 分发、同步和安装读回；不负责 Skill 审批或 release |
| 工作台控制面 | 保存草稿、协作会话、确认、测试、发布状态、outbox/worker、交接记录和反馈候选；当前复用 DSH Desktop 认证上下文；PostgreSQL 保存过程状态、权限映射、Job、幂等、对账和审计 |
| DeepSeek Harness | 消费已发布资产，负责 Workspace、Session、Skill load、工具、权限和运行时状态 |
| 业务系统/SPC 后端 | 负责业务事实、动态状态、计算、告警、工单和生产运行 |
| Plugin | 后续独立资产域，负责受控工具/外部系统能力；DSH Desktop Workbench package 是本项目的产品交付包，不等同于业务 Plugin asset |

## 5. 四条不可破坏的原则

1. **创作工作台先于运行时**：用户先看到材料、草稿、差异、测试结果和发布下一步；任务执行交给 DeepSeek Harness。
2. **双资产、一套治理底座**：Knowledge 与 Skill 分开管理，都具备来源、owner、版本、审核、权限、反馈和回滚。
3. **一类对象一个权威写入面**：Git 保存正式知识和 Skill；WeKnora 做知识索引；SkillHub 做批准 Skill 的分发；Harness 做会话运行。
4. **自动化降低成本，不替代责任**：模型负责梳理、追问和起草；脚本负责确定性门禁；人负责事实、范围、风险和发布。

## 6. 关键状态不能混淆

```text
knowledge candidate / approved / published
skill draft / tested / approved / released
workflow draft / confirmed
git submitted / ci passed / review approved
weknora indexed / stale / failed
skillhub published / unavailable
dsh handoff requested / verified / unknown
harness loaded / running / succeeded / failed
```

其中最后一组属于下游 Harness；工作台只能保存交接请求和结构化验证/反馈引用，不能把下游状态伪装成自己的运行状态。一次 Agent 说“已经完成”，不代表 Git 已提交、WeKnora 已索引、SkillHub 已发布或 Harness 已加载。

## 7. 阶段顺序

| 阶段 | 要证明的结果 |
|---|---|
| P0 | 工作台信息架构、两条生产线、资产模型和 Harness 边界；腾讯云非生产验证环境、PostgreSQL/对象存储、现有 WeKnora 测试空间、DSH/SkillHub 部署可行性、DSH auth adapter 和 Workbench Plugin 包契约 |
| P1 | 会议纪要可生成知识并进入 Git/WeKnora；一个工作流可生成 Skill 草稿并完成样例试跑；至少两个团队/asset space 可安装同一 Workbench 且数据隔离 |
| P2 | Skill 可通过测试、审核并发布到 SkillHub；发布版本具备下游交接 metadata；知识目录与 WeKnora 映射可回读 |
| P3 | 目标 DeepSeek Harness 环境可验证发现/加载已发布 Skill；运行反馈能回流到知识复核或 Skill 回归 |
| P4 | 在有真实需求时建设受控 Plugin、连接器、凭据和运行时隔离 |
| P5 | 通用 SaaS 多租户控制面、独立业务 Plugin Marketplace、跨团队 Agent 联邦和高风险生产写入 |

阶段由退出证据推进，不按日历自动升级。

## 8. MVP 成功标准

- 非程序员不操作 Git，也能从会议纪要生成、讨论并确认知识草稿；
- 确认后的知识确实进入 Git，并在 WeKnora 中可检索、可引用；
- 用户能通过自然语言完善一套工作流，并得到包含说明、资源/脚本、契约和测试集的 Skill 草稿；
- 用户能用脱敏样例试跑 Skill，看到输入、输出、差异、失败原因和评测结果；
- 确认后的 Skill 确实提交 Git，并在 SkillHub 具备可查询的固定版本或明确的管理员 fallback 证据；
- 工作台能生成目标 Harness 可消费的版本、digest、package metadata 和依赖引用；
- 下游 Harness 或业务系统的结构化反馈能明确回到知识复核、Skill 回归、分发故障或平台故障。

北极星指标：**经过审核并被下游实际消费、随后能产生可行动反馈的知识/Skill 发布版本数**。对 Skill 还必须能够按实际 version/digest 查看调用次数、活跃用户数、分层成功次数和 Badcase；这些是下游消费事实的聚合，不是把工作台扩展成完整运行时。
