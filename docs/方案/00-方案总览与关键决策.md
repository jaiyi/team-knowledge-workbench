# 方案总览与关键决策

> 本文是当前方案范围和关键权责的决策摘要。它先回答“工作台是什么”，再说明知识、Skill、Git、WeKnora、SkillHub 和 DeepSeek Harness 如何协作。想先理解组织知识工程为什么值得做、难在哪里，以及 Workbench 打算怎样帮忙，请读[产品说明](../产品/README.md)；其中未验证的用户假设不自动成为已证实的方案收益。

## 1. 产品定义

这是一个面向团队的**知识与 Skill 创作发布工作台**，以可进入 DSH Desktop Workbench 市场的 `team-knowledge-workbench` 作为产品交付形态。

`team-knowledge-workbench` 是可复用的 Workbench 产品/插件包；`team-knowledge-asset` 是独立的团队资产域。不同团队可以安装同一个 Workbench，但必须分别绑定自己的资产 Git 仓库、WeKnora space、权限、steward、审核策略和下游分发目标。工作台不复制 DeepSeek Harness 的会话运行时，也不把发布后的任务执行作为自己的主产品模块。

Workbench 面向用户有五个一级入口：「我的工作台」「提炼知识&经验」「打磨可复用的技能」「连接业务数据源」「团队业务资产大盘」，默认首页先提供个人 Inbox 的主动暂存入口，再展示本人有权的使用、反馈和下一步；原生 DSH 对话属于宿主。只有明确正式创作或修订、经服务端核对空间/来源或基线/动作权限后，才以 **Creation Session（创作会话）**及独立草稿作为可恢复工作单元；查阅、核证、单独反馈、沿用旧版或回宿主任务不自动建会话。会话内完成梳理、确认、测试、提交与发布，并行会话隔离上下文、草稿、异步操作和回调。工程映射与待验证集成详见[开发工程设计](11-开发工程设计与集成基线.md)。

```text
资料入口：有权材料/旧版 → 明确正式创作/修订并由服务端授权 → Knowledge Session/Draft
  → Agent 梳理/讨论/逐项确认 → Git MR/CI/指定审核人
  → protected merge → Workbench outbox/worker → WeKnora 索引及授权检索读回
  → published knowledge（合成材料可先在隔离非生产空间验证，再由大盘有权读回）
能力入口：有权工作流/Skill 候选 → 明确正式创作/修订并由服务端授权
  → Skill Session/Draft + 测试 → Git MR/CI/指定审核人 → 审核中
  → canonical Git 受保护 main 经审核合并 → 已发布 Skill
  → 固定 merge commit 的 package/digest
发布交接：选用且验证通过的 Registry release 或有期限管理员固定包 fallback
  → TeamAI 优先验证的多端分发或受控目标安装 → 逐目标安装读回
  → DSH profile discovery/load digest 读回 → 实际消费
反馈回流：独立 Feedback Candidate → 受理/分流/补证/回访
  → 仅正式知识/Skill 修订决定及授权后关联新 Session
```

上图分别标识 Git 正式审核与固定包必经链、条件性的 Registry/管理员 fallback、优先验证的 TeamAI/受控目标安装及 DSH 独立加载；不是目标环境已接通的拓扑。DSH 与 WeKnora 为必接组件，分发选型和管理员路径见[工程设计第 7 节](11-开发工程设计与集成基线.md#7-skillhub-与-teamai-的角色评估及选择门)。入口④的标准 Tool/MCP 契约及合成只读 Demo、入口②至入口⑤的合成知识真实非生产链见[工程设计 5.5–5.6](11-开发工程设计与集成基线.md#55-数据中台-toolmcp-标准接入契约与真实-demo拟议)；演示数据、非生产真实集成和生产真实能力不能互相代替。Skill 的正式 `已发布` 仅由 canonical Git 受保护 main 上经 MR/CI/指定审核人批准的 merge commit 证实；合并前仍为 `审核中`，包括仅批准而未合并的修订。固定包和管理员 fallback 不会自行使 Skill 已发布；Registry registration/release read-back、TeamAI installed、DSH loaded 和业务结果另列独立证据。知识的 `published` 仍须通过 WeKnora 指定版本/source/ACL 读回及授权检索验证，不因 Git merge 自动推进。`merge event` 只是后续异步操作的触发事实，不能单凭 webhook/PG 回执代替受保护 commit 与审核校验。HTTP 200、任务入队和 provider 接受请求都不构成相应外部步骤成功。

个人暂存的 `InboxItem` 在 PostgreSQL 私有保存，仅引用本人获准来源；必要正文才经授权写入加密对象存储。保存或打开知识页不创建会话、草稿或正式资产，也不自动写 Git/WeKnora 或触发 DSH 任务；显式授权提交最小团队候选仅取得独立 `submission_id`/受理回执，仍不建会话。随后明确决定正式创作时重新核验来源、目标空间、基线及动作权限，获准才建立 Knowledge Session/Draft。待决工程风险与验证门见[未决工程风险与决策记录](12-未决工程风险与决策记录.md)。

## 2. 系统职责

| 层 | 解决的问题 | 主要职责 |
|---|---|---|
| 知识/Skill 创作发布工作台 | 我们应该知道什么，以及如何稳定完成一类工作？ | 首页入口、Creation Session、梳理、讨论、建模、测试、审核、提交、发布和反馈候选 |
| Git/CI、WeKnora、SkillHub、TeamLab | 如何保存、索引、协作和分发已批准资产？ | 各自维护 canonical source、知识检索、内部协作或 Skill release；通过受控 adapter 共用服务接入，不共用团队资产授权 |
| DeepSeek Harness 会话工作台 | 如何消费已发布能力完成一次会话任务？ | Workspace、Session、Skill discovery/load、工具、权限、人工批准、恢复和运行观测 |
| 业务系统/SPC 后端 | 业务事实和生产状态是什么？ | 计算、告警、工单、业务写入和真实结果 |

## 3. 首期必须证明的两条生产线

### 知识链

```text
有权材料/旧版 → 明确正式新建/修订 + 服务端授权
  → Knowledge Creation Session / Draft
  → 材料 → 梳理 → 确认 → 提交 → 发布
  → Knowledge Draft
  → Git/MR/CI/审核
  → protected main merge
  → Git merge event
  → Workbench outbox/worker
  → WeKnora ingest
  → document/version/source/ACL read-back
  → 带来源和版本的可检索知识
```

### Skill 审核与固定包链（必经）

```text
稳定且可测试的工作方式／获准 Skill 候选
  → 明确需要正式创作／修订 → Workflow/Skill Draft
  → 契约、golden/regression/security 测试与 DSH 目标格式校验（能力待实测）
  → Git MR/CI + 指定审核人批准（合并前仍审核中）+ canonical protected main merge（Skill 已发布）
  → 从固定 merge commit 构建 package + immutable digest
  → 固定包及审核、测试证据可追溯
```

### 发布与分发链（按选型条件分支，目标读回分层）

```text
已审固定包/digest
  ├─ 经 ADR 选用的 SkillHub/等价 Registry → release/version/digest 读回
  └─ 未选 Registry → 有期限、可审计的管理员固定包 fallback（不得称 Registry released）
  → TeamAI（优先验证多端分发，启用时）或经验证的受控目标安装
  → 逐 target installed file manifest/digest 读回
  → DSH 指定 profile 的 discovery/load/digest 读回
  → 实际消费与业务结果分别取证
```

DSH 自带 Skill 校验、发现/加载和资产展示的目标能力须按确切版本和权限分别实测；Workbench 可复用已证实能力展示证据，但仍需汇总 Git、WeKnora、分发和反馈状态，不把页面可见当成资产已加载或质量合格。

在**受控发布路径**中，TeamAI 不重新决定 Skill 正式版本或从 `latest` 生成新包：只分发已审 Git/CI 固定包/digest，若选用 SkillHub 则先读回对应 release；否则独立标注管理员固定包 fallback，不能写成 SkillHub 成功。TeamAI 上游默认会在目标客户端下一次受支持会话启动时拉取团队仓库更新，**并非天然固定在某个 commit**；是否可按 commit/tag pin 以及目标 DSH 是否触发 Hook、实际落盘/加载哪些文件，都须按部署模式和目标版本验证。生产可用门禁要求读回安装文件与批准 digest 的映射；如无法防止未审核/漂移版本生效，则阻断真实目标安装。SkillHub、TeamAI 或 DSH 不可用时，可以走有范围、有期限的管理员 fallback，但必须保留同一固定包、digest、target、profile、读回和回滚证据。

### 下游消费，不是本项目生产线

```text
受审 Skill/Knowledge 正式源和固定 Skill package/digest
  → 选用时核 SkillHub/等价 Registry release；否则记录管理员固定包 fallback
  → TeamAI 优先验证的多端分发（启用时）或受控目标安装及逐目标读回
  → DSH 指定 profile discovery/load 的真实读回
  → Harness Workspace/Session 实际消费（独立于加载）
  → 最小反馈引用与业务结果证据分别回到本项目
```

工作台可以验证一个发布版本是否具备下游交接所需的 metadata，也可以接收下游反馈；但不实现完整 Session、Run、Tool Call、运行时人工 gate 或业务任务状态机。

## 4. 核心决策

| 决策 | 当前结论 |
|---|---|
| 产品主语 | 知识和 Skill 的创作、测试、审核与发布工作台 |
| Knowledge | 有来源、适用范围、owner、版本和复核信息的正式知识 |
| Workflow | 对一类工作的步骤、判断、例外、输入、输出和人工节点的结构化描述；是 Skill 生成的中间对象 |
| Skill | 可复用、可测试、可版本化和可发布的任务能力包；不等于一段 Prompt |
| Git | knowledge-assets、Skill 源码、契约、测试、metadata 和评审的 canonical source |
| WeKnora | 已批准知识的 Wiki/索引/检索层；不负责 Skill 管理和事实审批 |
| SkillHub（候选） | 暂定 Skill package 的注册、不可变版本/digest 和 release read-back；目标环境未验证，若不适用需 ADR 决策替代或受控管理员固定包 fallback；不替代 Git/CI、质量评测、人工审核或目标安装 |
| TeamAI（候选） | 暂定消费已确认 pinned digest，负责可选目标 workspace 分发、同步和安装读回；只有能证明等价 registry/release 契约才可评估独立替代 SkillHub |
| 工作台控制面 | 保存草稿、协作会话、确认、测试、发布状态、outbox/worker、交接记录和反馈候选；计划复用经后端验证的 DSH Desktop 认证上下文（目标机制待 Spike）；PostgreSQL 保存过程状态、权限映射、Job、幂等、对账和审计 |
| DeepSeek Harness | 消费已发布资产，负责 Workspace、Session、Skill load、工具、权限和运行时状态 |
| 业务系统/SPC 后端 | 负责业务事实、动态状态、计算、告警、工单和生产运行 |
| Plugin | 后续独立资产域，负责受控工具/外部系统能力；DSH Desktop Workbench package 是本项目的产品交付包，不等同于业务 Plugin asset |

## 5. 四条不可破坏的原则

1. **创作工作台先于运行时**：用户先看到材料、草稿、差异、测试结果和发布下一步；任务执行交给 DeepSeek Harness。
2. **双资产、一套治理底座**：Knowledge 与 Skill 分开管理，都具备来源、owner、版本、审核、权限、反馈和回滚。
3. **一类对象一个权威写入面**：Git 保存正式知识和 Skill；WeKnora 做知识索引；Skill release 暂按 SkillHub 的待验证候选契约设计（未通过时使用明确标记的管理员固定包 fallback，替代选型须 ADR）；Harness 做会话运行。
4. **自动化降低成本，不替代责任**：模型负责梳理、追问和起草；脚本负责确定性门禁；人负责事实、范围、风险和发布。

## 6. 关键状态不能混淆

```text
knowledge candidate / approved / published
skill draft / tested / 审核中（含批准未合并） / 已发布（canonical protected main 经审 merge）
skill package built / registry released（选用且读回） / fallback_only（非发布依据）
workflow draft / confirmed
git submitted / ci passed / review approved
weknora indexed / stale / failed
skillhub published / unavailable
dsh handoff requested / verified / unknown
harness loaded / running / succeeded / failed
```

其中最后一组属于下游 Harness；工作台只能保存交接请求和结构化验证/反馈引用，不能把下游状态伪装成自己的运行状态。一次 Agent 说“已经完成”，不代表 Git 已提交、WeKnora 已索引、SkillHub 已发布或 Harness 已加载。

## 7. 阶段顺序

| 阶段 | 要证明的结果 |
|---|---|
| P0 | 五入口信息架构、两条资产生产线、权限及接口/状态基线；腾讯云非生产验证环境、PostgreSQL/对象存储、现有 WeKnora 测试空间、DSH 目标安装/身份交换可行性、SkillHub/TeamAI 职责与部署可行性 Spike |
| P1 | 知识从材料经 Git/WeKnora 完成真实读回；Skill 在同一 MVP 周期具备草稿、契约、测试、固定包/digest、明确标记的管理员/真实发布与最小消费证据；至少两个团队/asset space 使用同一 Workbench 而数据隔离 |
| P2 | Skill 的候选 registry release（若通过真实选型门）和固定包读回，或有期限和责任人的管理员 fallback；知识目录与 WeKnora 映射可回读 |
| P3 | 目标 DeepSeek Harness 环境可验证发现/加载已发布 Skill；运行反馈能回流到知识复核或 Skill 回归 |
| P4 | 在有真实需求时建设受控 Plugin、连接器、凭据和运行时隔离 |
| P5 | 通用 SaaS 多租户控制面、独立业务 Plugin Marketplace、跨团队 Agent 联邦和高风险生产写入 |

阶段由退出证据推进，不按日历自动升级。

## 8. MVP 成功标准

- 非程序员不操作 Git，也能从会议纪要生成、讨论并确认知识草稿；
- 确认后的知识确实进入 Git，并在 WeKnora 中可检索、可引用；
- 用户能通过自然语言完善一套工作流，并得到包含说明、资源/脚本、契约和测试集的 Skill 草稿；
- 用户能用脱敏样例试跑 Skill，看到输入、输出、差异、失败原因和评测结果；
- 确认后的 Skill 经 MR/CI/指定审核人批准并合入 canonical protected main 后才标已发布，且可从该 commit 构建不可变固定包；若 SkillHub 真实选型门通过则另核其 release/version/digest，否则保留明确标记的管理员 fallback 证据；
- 工作台能生成目标 Harness 可消费的版本、digest、package metadata 和依赖引用；
- 下游 Harness 或业务系统的结构化反馈能明确回到知识复核、Skill 回归、分发故障或平台故障。

北极星指标：**经过审核并被下游实际消费、随后能产生可行动反馈的知识/Skill 发布版本数**。对 Skill 还必须能够按实际 version/digest 查看调用次数、活跃用户数、分层成功次数和 Badcase；这些是下游消费事实的聚合，不是把工作台扩展成完整运行时。
