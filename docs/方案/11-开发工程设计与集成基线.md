# 开发工程设计与集成基线（待技术验证）

> 本文把[现行产品逐页设计](../产品/界面功能设计/README.md)和[可视化原型](../产品/可视化原型/index.html)映射为待开发的工作包、边界和接口草案。原型是静态内存演示，不是可以直接部署的插件或真实平台联调证据。本文件是[08 实施路线与验收](08-MVP实施、验证与验收.md)的详细设计输入，不能取代其阶段门禁、证据清单和 Go/No-Go。下述 HTTP 路由、事件字段和时序是**建议的 Workbench 内部契约**，不是 DSH、WeKnora、SkillHub 或 TeamAI 已证实的官方 API。目标版本、部署环境、SDK 和权限模型未验证前，状态保持 `pending`。

## 1. 设计决定、范围和待决问题

- **产品入口**：五个 Workbench 一级入口是「我的工作台」「提炼知识&经验」「打磨可复用的技能」「连接业务数据源」「团队业务资产大盘」。默认先看本人有权的使用与反馈；DSH 原生对话属于宿主。入口只是导航，不强制每次都创建资产；仅在明确决定正式知识/Skill 创作或修订、服务端验证空间/来源或基线/动作权限后，创建独立 Creation Session 和草稿。原[09 信息架构](09-工作台信息架构与核心对象.md)中标注的历史首页线框不作为现行五入口验收；Creation Session 的并发和证据规则仍有效。
- **必须接入**：DSH Desktop Workbench 宿主和目标 DSH/Harness 消费端、WeKnora 知识索引/检索；Git/MR/CI 是两类正式资产的源头。DSH 认证交换、Workbench 安装和 Skill load 的目标契约，WeKnora 的 ACL、版本、来源和可检索读回都需要非生产实测；不能以“必接”代替“已接通”。
- **统一前端、分权后端**：普通用户在 DSH Workbench 完成有权限的导入、核对、评论、修订、审核、发起提交、查进展与反馈回访；无需日常在 Git、WeKnora 或 Skill 平台切页。但 Git 的保护分支、外部审批策略和 DSH 运行时 gate 仍各自拥有权威；若 Provider 不支持受控 API 审批，Workbench 显示有明确责任人的待办及经授权的外部审批入口，完成后**读回**，绝不冒充站内审批。
- **Skill 审核与组件选型**：Git MR/CI、指定审核人批准及 canonical protected main 经审 merge 是正式 Skill `已发布` 的必经判定，合并前（含已批准未合并）仍 `审核中`；从固定 merge commit 构建 package/digest 是独立制品步骤，不推进 Git 发布状态。目标 DSH 的 Skill 合格校验、发现/加载和资产可视化须按目标版本实测，不能替代审核或业务测试。TeamAI 优先验证多端分发；只有独立 Registry 契约确有必要且目标验证通过，才选用 SkillHub/等价 Registry；否则使用有期限、可审计的管理员固定包 fallback，fallback 不使 Skill 已发布。见第 7 节的选择门；选型改变时以 ADR 更新 Provider 契约和验收范围，不能把可选节点改写为必经节点。
- **首期边界**：Knowledge-first，但 Skill 必须在同一 MVP 周期交付草稿、契约、测试、固定包/摘要、明确标记的安装/发布 fallback 与最小消费验证；真实 Skill Registry/TeamAI 自动化可以分期。**DSH 必接不等于 P1 已真实 loaded**：fake/admin 的最小消费仅满足契约和 MVP 开发门，目标 DSH 装载/read-back 是后续真实 Provider/Pilot/Stable 的独立门禁；不能把 fake load 写成真实消费者已用。业务 Tool **真实生产目录/审批/调用不在首期承诺**，但版本化标准接入契约及隔离非生产的可调用只读合成 Demo Tool 属于首期验证；复杂运行追踪、业务写入、通用 Plugin Marketplace、跨团队资产流通不在首期。
- **范围张力**：现行逐页产品设计从单团队原型起步，不设计跨团队资产流通；08 要求两个 asset-space 安装/隔离，是后端与插件安装的安全验收，不意味着上线跨团队共享资产、跨空间搜索或默认聚合视图。只有单团队演示通过不能替代两个空间的隔离负向测试。

## 2. 五入口到工程能力的映射

这里的 P0=设计、非生产 Spike、工程骨架和隔离；P1 双资产 MVP=08 的阶段 3–7、N0–N4 中的相应能力验收（包含真实知识链、合成知识进入大盘、只读合成 Tool Demo 与明确标记的 Skill fallback）；N5/阶段 8 验证目标 Skill Provider，N6/阶段 9 验收发布候选与试点，不把 N0–N6 误作 P1 的阶段编号。P2 的反馈与指标演进、P3 的目标 Skill Provider 验证及后续生产业务数据源/高级诊断分别按 08 门禁执行。不是把原型中的虚构按钮在 P0 全部接成真实按钮。每个待办都需由服务端按当前授权返回对象、状态、责任人和可执行动作。

| 入口/内页 | 当前原型的意图和拟实现任务 | MVP 的服务端数据、证据与动作 | 后续/阻断边界 |
|---|---|---|---|
| 我的工作台（默认） | 看本人可核对的使用、报告具体问题、返回准确版本/负责人；个人 Inbox 暂存获准来源定位/少量笔记；不是强制创作首页 | 授权资产/独立反馈候选/经指派的本人待办和最小消费引用，缺覆盖率即显示“不可计算”；`InboxItem` 个人 PG 私有保存（必要时获准加密对象引用）；保存/回访/打开知识页均不抓取链接，打开知识页不写入，明确获准分享时独立 `submission_id` 仅受理最小候选，另行正式创作并重鉴权后才建会话；不自动写 Git/WeKnora；报告→去重/核验→分流/补证/关闭→仅正式创作或修订决定且授权后关联新会话→回访 | 宿主真实会话引用无契约时允许本人手填最小疑点、标待核验；不能据此声称真实调用、成功率或业务结果；无指派不生成个人待办；未来 IM 收件需另行授权验证，不默认启用 |
| 提炼知识&经验：导入来源 | 本地获准材料/来源定位与完整性；原型可展示合成材料 | 在入口明确选择使用链接且当前主体、来源/用途/目标空间获准、目标受限获取能力已验证后，可临时抓取固定原件并解析供只读梳理，不因抓取自动建会话或团队候选；正式创作会话绑定资产空间、来源 ACL、同意/用途、固定原件版本/hash、形成/生效/截止与复核时间；逐页/段/工作表或单元格锚点、已读/未读/排除范围及原因；获准原件默认保留在原系统，创作时仅按许可临时处理并保存最小定位/锚点；必要的加密对象副本须另核用途、留存和撤权 | 首期格式×大小×语言/版式及时效规则待 owner 冻结和 parser 实测；链接抓取另须来源/目标 allowlist、逐跳/实际地址和内容安全验证，未通过只留定位；越界、关键内容无锚点、漏页漏表或时效不明仅留有权最小待人工核对线索，阻断可送审正式候选；无来源权不抓取/假装全文，扫描件/复杂表格不预先承诺 |
| 同入口：事实梳理、经验总结 | 当前项的来源、已有事实/知识精确版对照、评论、分歧及责任 | 会话内候选与草稿修订，WeKnora 经授权查询返回准确 source/version/ACL 与不可得原因；事实/推断标注；有权 steward 逐项确认 | Tool 未授权不做实时数字核验；来源和检索权未知不能写“无已有内容” |
| 同入口：加入知识库（第四步） | 来源、事实、经验、规则、报表/计划的去向树预览 | 对正式 Knowledge 去向按 taxonomy/owner/ACL 建规范 Git change package、MR/CI/审核；merge→WeKnora index+read-back+检索后才 published；非知识去向留原来源/业务系统 | 预览不等于已入库；拒绝或证据不足不产生正式资产 |
| 同入口：优化已有 Skill（可选第五步） | 具体稳定可测缺口才关联 Skill；可以跳过 | 固定来源候选和已有 Skill 基线的最小关联，经授权跳 Skill 核对/会话 | 原型合成示例不是试跑；不因此自动创建或发布 Skill |
| 打磨可复用的技能：引入 Skill→自动校验→具体修改与复测→审核提交 | 团队准确旧版或外部获准候选的核验、对照与必要的复用/修订 | 先核来源/分享资格/ID/version/digest；无稳定任务则回知识或人工；按 Workflow、Skill Draft、测试 fixture、确需时的固定知识查询说明与失败核实路径、风险与审查建立会话；CI→merge→固定包/digest→真实 release 或显式 admin fallback | 外部缺契约可作为候选，不可直接送审；DSH 建议或虚构样包不能充当正式测试、包或审核；release、install、load 分列 |
| 连接业务数据源：可发现/待申请 | 按业务域读授权目录、看 schema、受控试参条件、记录申请意向；原型虚构 Tool 须标明 | 冻结版本化 Tool/MCP 标准接入契约；在隔离非生产环境以**真实可调用的只读合成 Demo Tool**走通发现→详情→权限/环境检查→受控试参→带来源结果→审计/失败回执。未接入 Provider 不伪造目录；申请意向与 Provider 真实批准分列 | 生产数据中台目录、字段授权、审批和使用统计须逐 Provider/宿主验证，Demo 不能代替生产授权；不支持的能力显示“未知/未提供” |
| 团队业务资产大盘：最新进展/全局概览/智能诊断、候选能力地图 | 有权资产详情和准确版本，区分使用、分发与价值；诊断只作建议 | 隔离空间合成材料经入口②**真实**草稿/审核/Git protected merge/worker/WeKnora 测试索引和 ACL 检索读回→大盘；按资产 ID/版本去重，项目×产品线正交关联、权限过滤和具体文档深链；失败/撤权/旧版残留显示真实状态 | 真实扫描方能称智能诊断（范围/批次/来源/unknown），预置线索仅称 fixture；合成链不证明正式业务授权、知识质量或业务价值 |
| 内页：内容讨论→修订提议→修订核对 | 锚定具体段落及版本、建议改法、由有权者确认 | Workbench 按空间/条目/固定草稿修订先持久化获权评论与状态；目标宿主提供可核 comment/turn/reply/终态时才由服务端 CAS 创建新待核稿；从评论 fork 草稿并比对 base revision，审查者逐项限定范围/拒绝/补证/暂缓，记录身份、修订和理由 | 无可靠 DSH 回合关联/完成回执则只保存评论和人工改写；旧/迟到回复不得覆盖新稿，原型本地报告或示意卡片不是正式受理/审批，跨团队无权不得看评论原文 |
| DSH 原生任务/任务复盘 | 宿主内执行任务，主动复盘并把最小线索引回 Workbench | 仅接获授权、可签名或可读回的 session/asset/version 引用；WorkBench 持反馈候选和回访状态 | 不复制 DSH Session/Run/Tool Call 或完整 Prompt/trace；不能把 DSH 宿主示意视为运行证据 |

导航显示可始终保持五入口，但某入口的动作由 `disabled_reason/provider_status` 明示不可用；不能以隐藏入口、填假数据掩盖 P1 尚未建设的能力。团队资产隔离是生产首期前置门禁；产品原型当前只示例单团队、不自动证明多团队正确。

## 3. 部署和权威数据流

```text
DSH Desktop / Workbench host (安装、路由、受限宿主上下文)
  └─ Workbench client (五入口、草稿差异、证据和任务回访；无 provider secret)
        │  已验证宿主身份 → 短期后端会话交换（契约待 Spike）
        ▼
Team Knowledge Backend（模块化单体；授权、绑定、会话、审核、API、审计）
  ├─ PostgreSQL：principal/membership、binding、个人 InboxItem、草稿、approval、operation、outbox、审计
  ├─ 加密对象存储：单独获准的来源处理副本/大 fixture；短期签名读取+敏感级别
  ├─ Git adapter：受控 MR/CI/审查+protected merge webhook 校验
  ├─ Tool Provider adapters：版本化目录/权限/试参契约；隔离合成 Demo 非生产真实调用
  └─ persistent worker：租约、幂等、provider adapters、读回与对账
        ├─ WeKnora space（批准知识的 index/retrieval/ACL）
        ├─ Skill Registry 候选（SkillHub 或经验证的等价注册能力 / admin 固定包）
        ├─ TeamAI 可选分发/同步（或其他经验证的目标适配器）
        └─ DSH/Harness profile/load（下游权威；Worker 不代替 Runtime）
```

控制面只保留过程状态；Git protected merge commit 是已审知识/Skill 源码的 canonical source：Skill 指定版本经 MR/CI/指定审核人批准且合入 canonical protected main 后为 `已发布`，合并前仍 `审核中`。WeKnora 授权索引和检索读回仍是知识 published 的独立事实；Skill CI 从固定 commit 构建 package 和不可变 digest 不改变其 Git 发布状态；Registry release、目标 install、DSH loaded 与业务结果是逐层独立事实，管理员固定包 fallback 也不使 Skill 已发布。Workbench 插件自身 market 安装/重启只说明 UI 可用，不代表资产可用。若用户跳到原生 DSH 会话，返回 Workbench 时按授权 `team/asset/version` 重读原状态而非沿用本地缓存。

**部署提案**：非生产一套 Backend+独立 Worker+PostgreSQL+对象存储+测试 Git repo+WeKnora 独立 space；DSH Desktop 使用隔离 profile/fresh install。每个 asset space 持独立稳定 repository identity、受保护 ref、CODEOWNERS、WeKnora space、密钥 binding、审查和发布策略；跨团队复用代码包，不复用可变草稿、查询缓存或 Token。生产拓扑、托管区域和备份参数以阶段 0/1 决定，不能推断当前已经部署。

### 3.1 多人安装后的配置与管理员入口（拟议）

同一签名/固定 digest 的 Workbench 插件可安装在多位成员的 DSH Desktop；**每台电脑不配置共享 Git/WeKnora/PostgreSQL/TeamAI 服务凭据**。如启用 TeamAI 且目标 CLI 需要从私有团队仓库拉取，成员仍须按授权完成各自的目标端 `init` 和最小只读 Git 身份配置；这不是在 Workbench 插件中填入或复制团队共享密钥。插件仅从受信任的安装/部署配置取得环境标识及 Backend 地址；服务端验证来源、TLS 和目标环境后再完成 DSH 身份交换，返回当前用户可访问的团队空间和配置状态。Backend 地址的分发与信任锚采用何种宿主机制须在 DSH Bundle Spike 中验证：不得通过未校验的深链、普通成员可修改的远端配置或随意填写 URL 把登录凭据送往错误服务；地址/环境不匹配则停止交换。服务端无绑定时显示“尚未开通该团队空间”、责任人和申请途径，不允许客户端临时填写 Provider URL 绕过绑定。

| 配置层 | 负责人与存放位置 | MVP 中如何操作 |
|---|---|---|
| 部署/平台 | 平台运维在受控部署配置与 Secret Manager 中管理 Backend、PostgreSQL、对象存储、TLS、备份、Webhook 来源、密钥引用 | 数据库连接串、主密钥、生产 Provider Token 不进入插件/团队配置页；运维以受控部署和审计变更，恢复演练后才开放 |
| 团队资产空间 | 平台 owner 预置或批准 `team_id/asset_space_id` 与角色；对应 asset owner 按策略维护 Git 仓库稳定 ID、受保护 ref、知识目录/WeKnora space、steward、review policy、可选 Registry/分发 target 和服务身份绑定 | **站内仅管理员可见的「团队空间与连接」子页**完成受限绑定、验证、激活、停用和状态诊断；不是新增第六个普通用户一级入口，也不允许选择未批准的任意 repo/space/target |
| 个人 | 每位成员的已验证 DSH 身份映射与可选本地偏好 | 选择服务端返回的有权空间、查看本人任务/连接不可用提示；不填写或回显共享密钥，不把插件安装视为获得团队访问权 |

**页面最小信息架构**：空间概览展示环境、配置版本、当前成员有权看到的空间、负责人和总体就绪度；连接卡分别展示 Git（仓库稳定 ID/受保护 ref/审核策略）、WeKnora（目标 space/ACL/检索读回）、候选 Skill Registry（仅选用时）、TeamAI/其他分发（仅启用时：团队仓库、目标 workspace/profile、拉取模式、首次引导、固定版本/目标安装回执，详见 3.2）、DSH 目标（仅有经验证的 profile/loader 契约时）。卡片按角色显示非敏感目标、`provider_mode`、`integration_status`、上次检查时间、最后可信读回及证据引用、故障责任人与下一动作；缺失的选项标记“未接入/待验证”，不生成假的健康绿灯。平台运维另有**部署诊断**，只显示 Backend/Worker/PostgreSQL/存储的健康、备份和迁移结果，不回传数据库地址、密码或内部网络细节给普通成员。普通用户五入口内只看与自身操作有关的阻断原因、申请/联系入口，不能看他空间的连接清单。

**配置生命周期**：部署时通过受控流程引导首位 platform owner 并创建待启用的空间绑定；不得依赖客户端自报管理员或默认管理员密码。管理员在站内选择已有获批资源、填写非敏感引用或发起由服务端密钥管理承接的凭据登记/轮换，页面始终不回显明文；先保存版本化配置草案，按当前授权与资源唯一性、仓库 ref/目标空间/service identity 作用域进行校验，再用脱敏非生产 fixture 按 Provider 真实能力做最小权限连接测试和读回。连接测试仅面向服务端预先允许的 Provider 端点和网络范围，拒绝任意 URL、重定向越界及 DNS/地址变更导致的 SSRF。**网络连通/HTTP 200 不等于配置就绪**：Git 查保护分支/仓库 ID 与 webhook、WeKnora 查目标空间及 ACL/检索边界，Skill/DSH 则分别按选型契约读回固定 digest/目标，不能仅凭配置页的测试写 `published/released/installed/loaded`。测试成功由有权角色复核后激活配置版本；失败保留旧有效版本、owner、错误、下一检查时间和回滚入口。无权或未配置的空间不能跑真实发布；TeamAI 未选型时无需提供其配置或必填字段。

**变更与隔离**：配置写入使用 `If-Match`/版本与幂等审计，平台 owner 与 asset owner 按策略分别批准危险变更。已受理 operation 固定创建时的 `config_version`、空间/repo/target/service identity；切换目标、解绑、撤销成员或轮换凭据时，暂停尚未外调的旧操作并重新授权，已提交且结果未明的操作先按**原目标/固定版本**读回再对账，不自动拿新凭据或新空间重放。配置历史、凭据引用版本、操作者/复核人、真实读回和回滚记录按空间保留；删除连接不能抹去先前的审批与发布证据。空间 A 管理员无法查询/测试/更改空间 B 的绑定；仅改变本机偏好不能修改服务端配置。

### 3.2 TeamAI 配置与成员设备引导（仅选用时，拟议）

[TeamAI 官方 README](https://github.com/Tencent/teamai-cli/blob/main/README.md)、[Getting Started](https://github.com/Tencent/teamai-cli/blob/main/docs/guide/getting-started.md)及[Distribution mechanism](https://github.com/Tencent/teamai-cli/blob/main/docs/guide/distribution.md)描述的是 Git-backed 团队资源：`teamai push → 分支/PR → 审核合并`；成员**先在目标 workspace/user scope 执行 `teamai init`**，安装 SessionStart Hook，此后已支持的 AI 工具在下次会话启动时触发 `teamai pull`。这属于“首次授权/初始化后、在会话边界自动拉取”，不是 Git 合并瞬间远程推送到在线设备，也不保证打开的旧会话立即更新。官方示例的 `pull --team-ref <commit/tag>` 只适用于其规定的独立 Git 团队仓库 workspace 条件，不适用于 HTTP 或单仓模式；不能以 `main/latest` 代替固定版本门禁。上述仅为上游文档描述，不是本项目 DSH Desktop/目标 TeamAI 版本已实测的下发能力。用户已在讨论中贴出千问分享内容，补足了先前无法从分享页读取的正文；其中关于 DSH 落盘路径、Hook 触发、WeKnora MCP 等具体断言仍须以对应上游源码和目标环境实验分别核对，不能以分享总结本身作为实现或授权依据。

| 配置层 | Workbench 站内该配置什么 | 谁负责、哪些不能自动完成 |
|---|---|---|
| 平台受控部署 | 允许的 TeamAI CLI/Hook 目标版本、来源、兼容的 DSH profile、签名/升级策略；Git 访问代理/凭据仅在服务端 Secret Manager 引用；允许的网络、安装根目录、回滚和诊断策略 | 平台 owner 批准工具与 Hook 权限；不能将团队 Git 写 Token/脚本或 CLI 全局安装无提示地推到成员本机 |
| 团队空间连接卡 | `distribution_mode=disabled|teamai_session_pull|managed_target`（后两者须 Spike 后启用）、`team_repo_identity/ref`、其与 canonical Skill Git 仓库的关系、受保护 MR 策略、目标 namespace/project/role、目标 workspace/profile、Skill 格式/manifest 映射、期望固定 commit/digest、目标读回契约、检查/停用/回滚状态 | asset owner + 平台 owner 只从已批准 repo/目标/凭据引用中选择；不能把 TeamAI repo 链接到任意其他团队或让管理员子页代替 Git 审核；启用后仍按目标声明 `pending/blocked/real_verified` |
| 成员设备或运行目标 | 服务端仅显示该主体有权目标的“待初始化/待授权/已初始化/待拉取/已拉取待验证/已装载/过期或离线”，提供受控安装说明与检查入口 | 每台实际需要接收 Skill 的机器/DSH profile 首次须**经授权**安装/初始化（除非经实测支持的受控托管目标），获该目标最小只读 Git 访问权；用户不逐机填写 PostgreSQL/WeKnora/共享写密钥，但不能因此推断 TeamAI 已在该机初始化或有本机 Hook 执行许可 |

**两种下发模式不可混用状态**：①`teamai_session_pull`：成员/管理员首次按受控流程 `init`，后续 Hook 在受支持会话启动时拉取；离线、已有会话、Hook 缺失或用户本地修改均可能延迟/阻止更新，可供用户明确请求“检查/同步”，但仍须目标端执行并读回。②`managed_target`：只有证明 Backend/受控代理持有合法目标安装通道、明确授权和目标路径，才能由发布操作触发定向同步并读取该目标回执；Backend 的分发请求不是“所有成员本机已安装”，更不是 DSH loaded。两种模式都必须保留每目标的 `target_id,scope,team_repo_commit,pinned_source_digest,installed_file_manifest,installed_digest,hook_or_pull_at,readback_at,profile,client_version`；TeamAI CLI 如果重写文件或不能返回可靠 installed revision/digest，则由获授权的目标代理计算文件清单、digest 与原包映射，无法独立验证时保持 `unknown/fallback_only`。

**权限不是靠 TeamAI 资源筛选实现**：官方 distribution 文档说明角色默认可自选、无主角色的成员可能收到全部资源，标签只增加订阅，`manifest/members.yaml` 的审查约束也不能抵挡该用户进程主动改本地配置。TeamAI namespace/role/project/tag 是投递过滤与易用性机制，**不是机密 Skill 的强访问控制**；敏感包必须由 Git 仓库/目标只读权限、单独空间和 DSH profile/tool policy 双重限制。统一 Workbench 后端的 DSH 身份授权不能自动换成 TeamAI CLI 的 Git 身份；成员首次 `init` 若须 Git 登录，使用本人经批准的独立凭据，不由插件静默注入共享密钥。禁用 Hook、撤权或离线后已经落盘的副本需要设备回执/清理或明确升级为无法立即撤回，不能只在 PG 改成 `revoked`。

### 3.3 WeKnora 知识与 DSH 会话查询的接入边界（拟议）

Workbench 站内对照与检索走 Backend→WeKnora adapter，后端按用户/资产空间鉴权和结果过滤，记录 `knowledge_id,version,source_commit,document_id,ACL` 与真实检索引用；不能靠某个安装在成员本机的 TeamAI Skill 绕开这条治理链。DSH 原生会话如需在任务中查知识，优先验证目标 WeKnora 是否提供有权限和来源读回的**只读**接口，并在目标 DSH 验证官方 Plugin/MCP 或受控 Workbench 查询工具之一的加载/调用契约；请求主体、查询范围与权限须由被调用的服务端验证，不能仅由本地 Skill 声称已授权。TeamAI 只可分发指导 Agent 何时查询的 Skill，不分发知识正文或凭据。

若选 DSH MCP 路线，先分别验证 WeKnora 端点/工具 schema、DSH 客户端/profile 与配置格式、用户/空间身份传递和工具结果引用，再验证目标请求的 ACL 拒绝、撤权后的负向查询与故障状态。团队仓库可放**不含密钥的接入说明或配置模板**，但不能将模板直接覆盖成员的 DSH profile 文件或把 Token 放进 `.teamai/`、Git、Skill、MCP YAML；配置需经受控、最小权限的目标端安装/诊断并独立读回，避免合并或破坏既有 profile。`teamai pull`、`dsh web` 启动、回答“有哪些 Skill”、WeKnora MCP 服务可访问，各自都不足以证明用户有权检索或 DSH 加载了某个固定版本。若目标 MCP 机制不满足权限或版本引用要求，保留 Workbench 授权检索入口，不开放 DSH 直连为生产知识入口。

### 3.4 DSH 原生会话观测与 OpenTelemetry 选择门（拟议）

**已知与未知**：上游 `deepseek-ai/deepseek-harness` 的 `dsh-v0.2.0-rc.2`（commit `639ed015397290b3745d163aafe02ffee4aa3f84`）[Session 事件文档](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/subsystems/session.md#L1200-L1274)和[Session Query 文档](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/docs/subsystems/session-query.md#L373-L486)提供结构化生命周期事件/查询线索；[Session Telemetry OTel README](https://github.com/deepseek-ai/deepseek-harness/blob/639ed015397290b3745d163aafe02ffee4aa3f84/packages/session/session-telemetry-otel/README.md#L30-L72)描述其反馈相关用途。**这只证明上游有候选能力**：目标 Desktop/Host 插件权限、事件可靠性、Skill 实际执行及固定包 digest 归因、知识真实引用/版本、业务回执均未在本项目环境验证；Desktop 的 session ownership metadata 不是有权事件订阅。MCP Tool 不能绕过宿主权限监听 Session，Skill 发现、目录变更或显式加载也不是实际消费。

优先试验经平台/数据 owner 批准的 **Host 侧观测适配器**（仅目标版本正式允许的 Plugin 事件订阅或有权 Session Query；如均不可用，则不自动声称原生会话使用）。宿主侧按授权空间/环境提取实际开始、完成、尝试/重试、Skill 固定版本与装载包 digest、知识查询/检索/实际引用及必要的会话关联；在**出宿主之前**做字段白名单、去敏、作用域校验。Workbench 只接收方案/01 的版本化最小领域事件、可失效的受控 trace 引用和业务系统另发的结果回执；Backend 对来源服务身份/签名、事件时间窗、team/asset-space/asset ACL、固定版本、幂等键、乱序/迟到、撤权和读回再次核验。按独立宿主开始事件或经授权的查询底账核覆盖率与漏投；不可靠、缺版本/权限、无可信底账时分别降级为仅观测样本或“不可计算”。UI 不提供抓取任意用户完整 Session 的通道，用户手填反馈仍可受理但标未核消费。

**原生评论回复是独立待验证契约（R-05）**：Workbench 服务端在当前身份、空间、条目和固定 `draft_revision_id/state_version` 下先持久化有权评论和 `comment_id`，回执与再次查询由自身负责；评论成立不取决于 DSH 是否接受请求，不复制未经许可的来源正文给宿主。只有目标 DSH Desktop/Host Plugin 提供经授权的评论投递、唯一 `turn_id`、可持久查询的 `reply_id` 与明确 `completed|failed|cancelled|timeout` 终态，且可绑定同一 `comment_id`/会话/主体/空间/固定草稿版本并在刷新后读回，才开启自动生成待核稿。投递/回调走固定作用域的幂等键和可查询状态；`accepted`、流式片段或通知不是完成。结果仅在成功终态、回复与评论唯一关联、仍有权且目标草稿 `state_version` 未变时通过 CAS 创建新待核稿；重复回执只返回既有修订，迟到回复、并发改稿、撤权或关联不明只留有权可查的冲突/待核记录，不能覆盖当前稿或自动重放到新基线。超时先读回而非盲目重发；响应敏感内容仅在明确允许范围保存，审计只留最小 ID、状态和证据引用。若目标宿主缺这条链，首期仍由 Workbench 保存评论/人工改写，自动回复显示未接通；原型预置回复不算真实回执。此契约与 3.4 的**消费遥测**不同，不能靠 OTel span 推断回复终态。

**OpenTelemetry（OTel）Trace/OTLP 不是成功率的硬依赖。**Backend→Worker→Git/WeKnora/Provider 的技术排障可选 OTel span/correlation（例如 `operation_id`、阶段、耗时、错误码、固定版本的非敏感引用）；如果已有获批的 Collector/可观测平台且需要跨服务故障定位，可优先复用 OTel；首期仅做成功率则优先落地可信领域事件与对账。是否采用其 SDK、Collector、OTLP 或目标 DSH 官方 Session Telemetry，由单独 ADR 根据目标版本、授权与故障成本决定。OTLP 是传输/观测格式，不是可信消费领域事件、不可变资产注册表或业务成功判定器；trace 的采样、反馈触发、丢包/重试和多端时钟差都可能使其无法提供完整分母。即使 OTel 能发出 span，也必须有可信、未采样或可对账的最小消费底账与业务结果回执，不能用采样 span 数计算调用/引用总量或拿 span `OK` 当业务成功。若启用 DSH Session telemetry，先核对其模式/触发条件、字段、采样和脱敏保证，不能将反馈导出的原始 Session 日志视为持续可靠或默认安全的实时事件源。

OTel/exporter/collector 和 Workbench 指标两侧均采用字段白名单与数据分类审查：禁止 Prompt/回答原文、Tool 参数/结果正文、业务文件、用户密钥或完整 Tool Call trace 进入跨系统长期存储；屏蔽自由文本 span attribute、事件 body、异常消息及自动 instrumentation 可能携带的敏感值。限制宿主本地追踪访问、导出端点、传输身份、接收端 ACL、留存期与审计，注入敏感测试样本验证拒收而非只依赖 Collector 末端清洗。安全审批未通过则只做合成离线契约验证，不部署生产 trace exporter。详见[方案/01 消费事件及报表](01-问题、用户与产品范围.md#343-最小消费事件和版本归因)及[方案/08 阶段 2、6/8 的门禁](08-MVP实施、验证与验收.md#阶段-2外部契约与技术-spike)。

## 4. 身份、权限与团队隔离

**信任起点**：DSH Desktop 身份上下文只有在后端能验证签发方、签名/证明、受众、有效期、nonce 和会话撤销的情况下可交换成受限 Workbench 会话；确切宿主可用机制需 Spike，若无法安全验证就阻断真实资产写入，不把 renderer 自报身份、DSH ownership metadata 或 launch token 当 API/worker 通用凭据。Backend 从 `dsh_subject` 映射 `principal_id`，再查成员、资产空间绑定、资源 ACL、操作权限；工作台安装本身不授予团队资产权限。管理员显式绑定服务身份和目标资源；Worker 按 operation 固定的资产空间取限定 scope 的短期凭据，调用前复核当前绑定和权限撤销策略，不能借用用户 Token。`requested_by/approved_by/released_by/reconciled_by` 是人的责任，`executed_by/service_identity_id` 是技术执行；审计均保留。

| 动作/对象 | 允许的最小角色（最终由绑定策略定义） | 服务端额外检查与拒绝 |
|---|---|---|
| 看本人待办/有权资产、按来源检索 | 有权团队成员 | session/asset/source ACL、检索结果二次过滤和版本范围；无权限/未绑定与空结果分开 |
| 本人 InboxItem：创建/列出/更改/删除 | 已验证 principal，本人且当前有权的上下文 | owner 由服务端确定，不接受客户端指定；逐条重鉴权、来源引用范围/用途、对象读取签名 URL 与当前权限，禁止跨主体/跨空间列举、分享或用 Inbox ID 绕过来源授权 |
| 创建或改草稿/评论、导入来源 | contributor/asset owner | 资源、来源/用途授权、敏感等级、会话成员和 `state_version`；不得引用他空间 ID |
| 确认事实、判断适用范围/复核来源 | 指定 steward/受托专家 | 绑定候选+修订+审核范围；贡献者意见不自动变审批 |
| 提交 MR/请求试跑 | contributor/asset owner，受限 tester | 新版本、无冲突、目标路径、fixtures/依赖授权；仅 server-assigned repo/target。对未经批准的 Skill Draft，静态检查不执行候选代码或 Tool；可执行试跑另要求经安全准入并用无害/恶意 fixture 验证的隔离非生产 Runner、最小权限/无生产凭据、网络/文件/进程边界、跨空间拒绝、资源及成本配额、超时终止与审计。Runner 未通过、撤权或额度不足则拒绝执行并保持真实测试门禁未满足，不改走 DSH、CI 或通用 Tool 绕过 |
| 审核并允许 merge/发布 | review policy 指定 reviewer/asset owner | 本人不能自动代替另一审批角色；Git CODEOWNERS/CI/protected merge 独立门禁 |
| 配空间、凭据、Provider、回滚/对账 | platform owner + 对应 asset owner 的策略授权 | 双人批准可由策略要求；限定环境、target、旧 digest、撤销与复核；敏感操作留理由 |
| 看聚合使用/业务结论 | 被授权的负责人/业务结果 Owner | 小样本抑制、无权限筛选拒绝，业务成功必须由业务 Owner/系统确认 |

在 PostgreSQL 使用复合 `(team_id,asset_space_id,resource_id)` 约束及 RLS 或等效强制查询边界；worker/outbox/callback/对象存储 URI/缓存键均固定作用域，日志不得以未经筛选的 provider 结果泄露跨空间数据。撤权后已开的页面重新鉴权，未执行的 job 暂停；已提交到不可撤回外部步骤的 job 转 `unknown/reconciling` 并由有权 owner 核对，绝不在后台拿旧用户授权无条件续跑。来源/WeKnora 的查询也使用服务端可验证的 ACL 映射；若 Provider 不支持必要的 per-document ACL/引用版本读回，应通过物理隔离加服务端过滤的实验证明同等拒绝能力，否则阻断正式检索可用声明。

个人 Inbox 作为独立 PG 私有记录建议最小字段 `inbox_item_id,owner_principal_id,origin_space_id?,source_ref?,source_kind,note_excerpt?,object_ref?,sensitivity,purpose,status,state_version,created_at,updated_at,expires_at`；`status=saved|removed|expired` 只说明暂存，不复用 asset/feedback/release 状态。服务端绑定 owner 与可选来源空间，按 principal + 来源作用域强制查询边界（RLS 或等效），不得用 team 成员角色替代私人所有权；对象读取仅对当前有权主体签发短期 URL。默认保存来源定位/摘要而非 Prompt/业务正文；保存、回访及导航到知识入口不排队抓取或解析外部链接，链接仅为有权待核定位。获数据 owner 准许需要存正文时，仅在加密对象存储放允许内容并在 PG 留引用/hash，使用单独的短期访问授权、加密密钥与配额，日志、审计及消费事件不拷贝正文。私有删除或到期清理须覆盖 PG 对象引用、对象本体、过期 URL 与缓存，审计仅保留非敏感删除事实；备份与法定留存例外、期限/分类由数据 owner 在阶段 1 冻结，未通过前不保存真实敏感输入。个人 Inbox 不被 WeKnora 检索或 Git 扫描，也不能因工作台安装、反馈提交或 DSH Session 产生而自动填充。打开「提炼知识&经验」仅传经重鉴权的来源定位/待核提示，不执行写入；若用户明确选择分享最小内容，另建 `submission_id` 的独立团队待核候选（不复用个人 Inbox ID 或 Feedback Candidate ID），按目标空间限制查看/受理，不能把提交回执视为正式知识草稿；只有再明确正式创作并重新核权才走 Session 创建。未来 IM connector 的主体绑定、消息/附件同意、群聊 ACL、重复投递和撤权/删除回执单独过安全与数据准入门，默认关闭。

**材料解析与送审边界（拟议内部契约）**：材料/知识 owner 先批准格式×大小×语言/版式支持矩阵、关键内容及覆盖判定、形成/生效/截止与复核规则，parser 目标能力须由脱敏原件实测，不能因上传成功、HTTP 200 或模型有输出即称完整。导入获准来源时固定 `source_id,source_version,source_hash,source_acl,origin_ref,observed_at,formed_at,effective_at,expires_at,last_verified_at`；对每个区块记录 `segment_id,source_hash,anchor(page/paragraph/sheet/cell),coverage_status,unread_or_excluded_reason`，含附件、跨页和未读范围。字段名和状态是 Workbench 提案，不是外部 parser API；原文默认留在有权原系统；只有来源 owner 单独批准复制/处理用途、期限和清理范围，才可使用受控对象存储保留必要副本，控制面始终只存最小引用和证据。需要跨次阅读原文时，只有目标 WeKnora 已独立托管该指定来源文档且可核 ID/版本、文档级 ACL 和真实深链，才展示跳转并由目标重新鉴权；无映射时回有权原系统定位/人工核对。正式知识文档的 WeKnora 读回不证明原件已托管，Workbench 不提供持久原文阅读或独立来源全文索引。仅保存私人 Inbox、打开页面或受理最小来源候选不启动解析/建 Session；用户在知识入口明确选择链接用于梳理且服务端核过当前身份、来源 ACL、用途、目标空间及受限获取范围后，可在不建 Session 的只读阶段临时抓取并逐区块解析已验证支持的固定原件；抓取本身不受理团队候选、建 Draft 或保存全文。用户另行明确正式创作且重新鉴权后，服务端再次对固定原件逐区块核支持范围、关键锚点、覆盖和时效。解析失败、漏页漏表、关键内容不可定位、来源过期/时效不明或权限不足时 fail-closed：在获权范围只记录最小「待人工核对」线索、缺失原因与责任人，不产出可送审的正式知识候选，现有 Draft 不得绕过此门；补证/人工复核须绑定固定版本重新核门，不能用模型置信度或人工点击跳过原件缺口。解析覆盖、业务事实核证和 WeKnora 正式发布分别取证，互不代替。

**用户材料链接受限获取（R-09，独立于管理员连接检查）**：仅对知识入口中成员明确选定的来源执行服务端获取；先核当前主体对来源的访问/处理资格、用途与团队目标，再由服务端受控连接器解析来源对象或允许的固定来源系统/域名与路径，不把任意 URL 当可请求的代理地址。逐跳限制重定向和协议，重新解析域名并核 DNS、实际连接 IP/目的地及最终来源身份，拒绝私网、回环、链路本地、云元数据地址和越界目标；每次转跳与重试都不得跳过授权/网络边界。限制下载字节、时长、文件类型/实际内容，隔离扫描和解析器，拒绝恶意或损坏输入，最小化错误/拒绝审计且不外传凭据、正文或内部网络响应。固定原件版本/hash 与来源 ACL/时效按上述逐区块合同核对；失败只留获权的最小待核定位，已取片段不得绕过送审门。目标连接器、allowlist、parser 隔离与正负例须按来源逐项验证；管理员连接测试通过、用户贴出链接、原系统浏览器可打开或静态原型可本地读文件，均不证明此路径安全可用。

## 5. 站内 API 与回传契约草案

客户端只调用 Backend 的版本化业务 API；写入中**创建/提交/测试/发起外部操作**须有 `Idempotency-Key`，**修改已有对象/推进状态**须有 `If-Match: <state_version>`（或等价请求字段），兼有两种语义的操作两者都要；首次创建以服务端检查绑定、权限和 source/base revision 代替尚不存在的对象版本。服务端作用域包括 principal、asset_space、对象、动作，负载摘要绑定 key；相同 key+相同负载返回原操作，不同负载拒绝 `409 IDEMPOTENCY_CONFLICT`。失去权限 `403 FORBIDDEN`、不可确认身份 `401 AUTH_UNVERIFIED`、旧版 `409 STALE_REVISION`、绑定缺失 `409 BINDING_REQUIRED`；外部结果未知由已建立的 operation 查询返回 `unknown`（首次异步请求用 `202 queued` 并给查询位置），不可将 `unknown` 解释为可立即重试的失败。读请求也以资源 ID 重新鉴权；客户端 team 参数仅是选择意图。

### 5.1 异步事务与事件

建议 merge webhook 包含 `provider_event_id,repository_identity,protected_ref,merge_commit_sha,changed_paths,provider_actor,event_time,signature`。验证签名/时间窗/仓库稳定 ID/受保护 ref、查实际 merge commit **及其最终审核/CI 事实**和允许路径后，**同一个数据库事务**写 receipt（唯一 `provider+event_id` 和防重 `repository_identity+commit+asset-kind+path`）、operation、outbox 和初始审计，再响应 webhook；未经 Git 实际治理事实验证不得生成可执行 outbox，不能因 webhook body 自称已合并就发布。数据库提交失败不确认 receipt；重复 webhook 返回已有 ID；不同 payload 重复 ID 则拒绝并告警。对一个 commit 的多资产 changed paths 必须按每个资产的 canonical identity 展开，只有稳定 repo+commit+asset-kind+规范 path 确实唯一时才使用该防重键；资产迁移、删除和重命名按 5.2–5.3 的稳定 `asset_id+change_kind+target` 拆分处理。provider 不支持完整 webhook 时通过有凭据的受控 reconciliation 拉取受保护分支增量，仍以固定 merge commit 驱动。

```text
approved MR + protected Git merge
  → verified merge receipt/transactional outbox（queued）
  → worker lease + scoped credential + recheck binding（running）
  → provider upsert/register by immutable source key（waiting_readback）
  → poll/read-back document or release + version/source/ACL/digest match
  → verified success / explicit failure / unknown→reconciling
  → asset status CAS + audit + task notification（刷新页面读回）
```

建议 `operation` 至少存 `operation_id,kind,change_kind?,team_id,asset_space_id,asset_id?,session_id?,draft_revision_id?,source_commit?,from_path?,to_path?,expected_state_version,blocked_epoch?,config_version,provider_mode,integration_status,idempotency_key,correlation_id,provider_operation_id?,provider_target?,actor_id,service_identity_id,state,last_verified_step,readback_ref?,attempt,lease_expires_at?,next_check_at?,error_code?,created_at,updated_at`；连接检查 operation 可无 asset_id/source_commit，但必须有空间、连接/配置版本、目标和执行身份。`expected_state_version` 固定创建时前置条件；operation 自身版本与正式 asset revision 各自 CAS，不允许旧 operation 反写新正式版本。每次 callback 必须验签、校验 event ID、provider operation ID、scope、目标固定 digest/commit 与状态版本，重复事件去重、迟到旧版只记审计不覆盖新版本。provider 无幂等支持时超时**先查固定 source key 和目标读回**，不盲发第二次；无法证实即 `unknown`，进入对账/人工手动判定并保留理由。worker 重启通过租约到期恢复，按固定 source key 做至少一次投递+应用侧幂等；超预算进 dead-letter/人工接管。撤回/回滚另开操作并记录前后版本、受影响目标和读回，不删除旧证据。

**知识实例**：`knowledge_id+source_commit+asset_space` 固定输入，worker 从已审 Git 路径读取 metadata/source/ACL，将映射传 WeKnora adapter；只有 read-back 的 document ID、version、source_commit、repo_path、ACL 与实际有权检索命中均与期望一致，才使该版本 `published`。部分索引失败/ACL 漂移保留旧已验证版本的审计证据；**只有旧版仍获授权且内容有效时**才继续对外提供旧版，否则先停止服务端查询并处理所有直连入口，新版本为 `index_unknown/stale`，不把旧版替换成新成功。

### 5.2 Knowledge 增改、退役与权限变更契约（拟议）

一次站内保存只在 PG 事务内写 `draft_revision`、CAS 版本和审计；必要时写对象存储获准材料的 hash/引用。它不修改正式 Git、PG 的已发布版本指针或 WeKnora。提交生成固定 `asset_id/canonical_key/base_revision/change_kind/target_path/expected_acl/source_digest` 的受审 change package；Git branch/MR/CI 与人工批准是外部治理步骤，不与草稿保存共用 ACID 事务。合并后按第 5.1 节同事务登记 verified receipt、operation/outbox；由固定 commit 的内容/变更类型驱动 Worker，读回后 CAS 更新当前可用指针。前端分别显示「草稿已保存」「待审核」「Git 已合并／索引中」「检索已生效」「待对账」与具体版本，不把其中任一步直接叫同步完成。Git 受保护分支 commit 是正式内容权威；PG 保存各版本工作流与服务端可用性指针，WeKnora 只保存索引事实。

| 变更 | 提交前检查与 Git 表达 | 合并后目标、成功门槛与失败处理 |
|---|---|---|
| 新增 | 服务端分配不可变 `asset_id` 与空间内唯一 `canonical_key`；无正式 base revision，检查来源/路径、owner、ACL 和目标 space；同一申请的重试沿用同一 asset ID/MR | 固定 commit 与规范 path 建 `weknora_mapping`；以 `space+asset_id+commit+change_kind` 为操作幂等键，索引读回 ID/version/source/path/ACL 与授权检索命中后才设置该版本 `published`；失败保持 `publishing/index_unknown`，不出现假资产 |
| 修改 | 草稿必须携带现有 `base_revision` 与 `state_version`；提交与合并前重新读 Git 目标 head/资产版本并校验范围、权限、来源和 ACL；过期返回 `revision_conflict` 并由人合并 | 新 commit 生成**新** `asset_revision` 与索引操作，读回新版本且检索命中后才原子切换 PG 当前可用指针；旧映射/索引是否继续可访问按旧版授权和保留策略核查。ACL 收紧、旧内容失效时须先阻断旧入口并逐目标验证旧版不可检索；不能以“保留旧版”作安全回退 |
| 普通退役／撤回 | 有权 owner 发起并经相应审核；Git 合并显式 tombstone/退役 metadata（稳定 asset ID、退役理由引用、上一个内容 commit、期望旧索引目标），不直接删除历史 commit；禁止把 path 删除误认为意图已获批准 | 接受合并后立即从 Workbench 检索和展示候选中隐藏并标 `retiring`，停止新的索引；对固定 WeKnora 文档/所有关联旧版执行**经目标验证**的下架、删除或查询阻断及负向检索读回。确认所有受控检索入口不再命中、直连入口已有等效封锁/证据后才将当前可用指针置空并标 `deprecated`；否则为 `withdrawal_unknown/manual_required`，不可声称已彻底不可检索。Git 历史、PG 审批/审计和留存义务独立保留 |
| 移动／重命名 | 固定 `asset_id` 不变；显式 `from_path→to_path`、旧目标 document IDs、base revision 和新 ACL；两条路径唯一性及目标空间策略校验；跨空间迁移另走授权/数据迁移审批，不能仅改 path | 先对新 path/版本索引及读回，再对旧路径/所有受影响旧索引按保留策略撤回或隔离，核对新旧目标的同一身份映射、ACL 和检索结果后更新路径指针；旧路径可能暴露错误或敏感信息时先阻断旧入口。任何旧索引残留标 `migration_unknown/manual_required`，不以新路径已命中冒称迁移完成 |

退役是**新审核事件**而非把历史记录从 Git/PG/审计物理擦除；数据删除请求如涉及法定清除期限、备份或外部索引，由数据 owner 单列清除工单和验证范围，不用 `deprecated` 代替数据已被物理删除。旧 `published` 版本的历史证据仍保留，但其历史状态不意味着当前仍可访问。任何路径删除、旧版可检索或未识别的 Git diff 均先进入隔离/人工确认；不能把 WeKnora upsert 的 200 当作旧索引清理成功。WeKnora 是否支持按 ID/版本下架、ACL 读回、负向检索与直连禁用须阶段 2 实测；若做不到可验证撤回，阶段 5 不开放该范围的正式退役完成声明或无法保证的直连入口。

**紧急撤权**独立于普通 Git 审核流：接获经验证的成员撤权、来源 ACL 收紧或敏感数据暴露事件，Backend 先在 PG 事务记录原因、范围、责任人、阻断 epoch/审计和待办，并**立即**在受控 API/查询缓存/待执行 job 对该主体或资产拒绝服务、清除缓存与撤销会话；不等待 MR、Webhook 或索引完成才阻断。平台/数据 owner 随即按原目标核查并收紧 WeKnora ACL、共享链接、直连 API、已下发副本及 Git/对象存储访问策略，发起独立的受审更正/退役 MR 和索引操作。若任一外部访问路径无法立即阻断或负向读回，升级安全事件并暂停受影响空间/目标访问，标 `revocation_unknown/manual_required`；仅 Backend 拒绝成功不代表外部已撤权。只有所有声明范围内的入口按被撤主体/旧索引做负向检索或明确拒绝读回，且原目标权限复核完成，才标撤权已生效；事后补齐 Git 治理记录，不允许事后 MR 取代即时阻断。Worker 在外调前复核阻断 epoch/配置版本，迟到的旧 ingest 或 callback 一律隔离/对账，不能重新开放已撤权限。

### 5.3 Git／PG／WeKnora 对账与补偿（拟议）

服务端定期对每个有权 `asset_space+repository_identity+protected_ref` 扫描**已验证的**受保护分支 commit 区间，核对 PG merge receipt/outbox/资产版本指针及 WeKnora 目标的 document ID/version/source/path/ACL/检索可见性；并对每个 `unknown`、租约过期、迁移/退役中、权限撤销中的操作安排更短的到期检查。增量游标和上次完成的 commit/检查时间持久化，频率、回扫窗口、分页、超时、负载预算及保留期限在阶段 1 按环境确定；定期做覆盖旧索引和 tombstone 的全量/抽样校验，窗口不等于安全边界。对账只读取允许范围的元数据与脱敏证据，不复制敏感正文到日志；目标不可用、扫描不完整或权限不足时游标不前移，告警并维持 `unknown`。

| 差异 | 处置权威及可恢复动作 |
|---|---|
| Git 存在已审核 merge、PG 漏 receipt（含 webhook 漏投、绕过工作台的合规 Git 提交） | 验证仓库/ref/commit 祖先链、CI/审核策略、资产身份、路径和目标空间；从 Git 固定 commit 合成唯一 receipt+outbox 并审计 `source=reconciliation`。无法证明审核/归属或意外路径的外部变更隔离 `manual_required`，不得自动索引 |
| PG 已入队而 WeKnora 缺失、部分成功或读回不符 | 固定 `asset_id+commit+target` 查询原 operation 与所有旧 document ID/可见性；确认无未明外部写入后按幂等键安全重试或由 owner 指定修复；不改 Git 内容来掩盖索引故障，旧版可否继续服务需单独 ACL/有效性判断 |
| WeKnora 有孤儿索引、旧路径/旧版仍可检索、ACL 被放宽 | 先隔离受控检索并告警，核源、来源及外部直连；经 owner 授权按目标能力撤回/隔离，做正负向读回，不从 WeKnora 反写 Git 当正式内容；无法安全清理时维持人工接管及安全事件 |
| PG 指针落后、迟到旧 event/callback 或当前 Git head 不含该 commit | 按资产稳定 ID、commit 在受保护分支的拓扑顺序和当前审核版本比对；仅为缺失且仍适用的版本补 operation，旧版本证据只入审计。修复 PG 指针也须检查真实检索与授权后 CAS 更新；不能让旧事件覆盖已发布新版本或复活已退役资产 |

三方对账不是“最终一致即自动成功”：记录 `reconciliation_id,scope,git_ref/from_to_commit,asset_id,expected_revision,provider_target,observed_document_ids,observed_versions,acl_digest,visibility_probe,drift_kind,decision,actor/service_identity,next_check_at,evidence_ref`；按空间和差异类型生成 owner 待办、告警及失败预算，人工修复须授权、理由、原目标读回、幂等键及回滚证据。Webhook、定时扫描和人工对账统一用 `space+repo_identity+commit+asset_id+change_kind+target` 去重，退役/迁移对所有历史目标建独立补偿步骤，避免“当前版本已成功”掩盖旧索引残留。不同源时钟/乱序先比 commit 祖先与当前资产版本，不按 webhook 到达时间决定新旧；不可确认时维持 `reconciling`，前端展示最后可信版本、受影响检索范围、责任人和下一次检查，不展示虚假的绿色完成态。

**Skill 实例**：Git MR/CI/指定审核人批准后直到核实 canonical protected main merge 仍为 `审核中`；核实受审 merge commit 后该 Skill 版本 `已发布`。CI 从 fixed merge commit 构建 package、digest、SBOM 是后续独立步骤；Registry（若选 SkillHub）必须读回相同 release/version/digest 才 `registry_released`，失败/未知不抹除已核实的 Git 发布，但阻断依赖该 release 的分发；TeamAI 仅在选用时按 3.2/5.4 的**固定源包→可拉取仓库版本→逐目标实际 pull/安装**分别留证，目标读回 target、installed revision、文件 digest 后才 `installed`；DSH 目标 profile/tool policy 与 loaded digest 确认后才 `loaded`。若选择管理员 fallback，不写 SkillHub released，而写 `release_mode=admin,fallback_only` 与操作者/固定包/目标/回滚证据，fallback 本身不使 Skill 已发布；没有 DSH 真实 load/read-back 时同样不写 `loaded`。合并 event 丢失/审核或 commit 归属未知时先对账受保护 main 与审批，不凭 webhook、PG receipt、package 或 fallback 晋级；任何 `latest` 解析、未知凭据或目标 digest 不同均阻断进入“目标可用”。

**反馈实例**：接受用户在 Workbench 输入的最小问题及有权的 `asset_id/version/source_commit|digest`、可选经校验 `invocation_id/attempt_no`；下游事件通过可信来源验签和同空间版本关联后才计入消费聚合；无引用也可创建待核候选。可独立受理、去重、分流、补证、关闭和回访；仅决定正式知识/Skill 创作或修订且通过服务端授权后，才关联新 Creation Session/Draft，权限、分发或原业务流程问题不必转资产创作。反馈不直接修改 Git 或覆盖旧审批，敏感原文和完整 trace 不落反馈表。

### 5.4 Skill 上传与 TeamAI 分发状态（仅选用时，拟议）

Workbench 的“上传 Skill”不是把草稿从 Desktop 直接 `teamai push` 到正式 TeamAI 仓库：有权贡献者提交固定 draft revision→Git 受控 MR/CI/人工审查→受保护 merge→从**该 commit** 构建 package/digest 并读回选定 Registry release（或标注 admin 固定包 fallback）。若 TeamAI 使用**同一个已批准 canonical repo**，需验证其 `teamai.yaml`、`skills/` layout 与项目 `skills/<domain>/<name>/` 包/依赖可一一映射，并核实 TeamAI 只拉获准固定 commit；若另有 TeamAI 团队仓库，Backend 以固定批准包生成镜像变更包，凭限定服务身份在**目标仓库另开 MR/CI/审核并合并**，对比源 commit/package digest 与镜像文件 manifest，不得借 `teamai push` 创建第二条未经审核的正式发布链。上游文档 `teamai push` 适用于其自身团队仓库的资源贡献流程，不等于已实现本项目的 SkillHub release 或本地 DSH 安装；如目标版本能直接消费经验证的 Registry 固定包而不经 Git 镜像，须单独 Spike/ADR 冻结该适配方式。

建议分列 `review_pending/approved_unmerged`（Git 尚未合并，Skill 审核中）、`git_published`（核实 canonical protected main 经审 merge commit）、`packaged`（digest）、`registry_released|fallback_only`（选用的 Registry 读回或仅管理员操作证据）、`team_repo_merged`（若另仓，目标 commit/manifest）、`distribution_available`（仅目标仓库版本可拉）、`target_pull_pending`、`target_installed`（逐目标文件清单/固定 digest read-back）、`dsh_loaded`（逐 profile 实际装载读回）、`consumed`（实际运行引用），且各阶段分别保留 `provider_mode/integration_status`。Git 已发布版本不得因 Registry/目标失败被当成未发布，反之不能凭 fallback、注册请求、包或镜像仓合并使 canonical Git 未合并 Skill 已发布；Knowledge published 仍待 WeKnora 授权读回。TeamAI 的 Git commit hash 与 Skill package digest **不是同一种 hash**：必须记录 `source_commit→package_digest→team_repo_commit→target_file_manifest/digest` 的可验证映射；目录可见、MR 已合并、某一台电脑拉取、Hook 被安装或 HTTP 成功均不能将所有目标写为 installed。SessionStart 是目标侧拉取触发器：管理员发布只令目标有资格在下次会话获取，并不触发打开中会话或离线机器的即时安装。用户在 Workbench 看指定目标的 pending/上次拉取时间/下一步，可请求经授权的目标主动 `pull`，但没有可验证目标端代理时只生成操作指引，不由 Backend 代答成功。

同步异常（Git 镜像失败、目标未初始化、Hook 未触发/不支持 DSH、用户本地修改文件、目标离线、pull 失败/冲突、包摘要不符）逐目标进入 `unknown/reconciling`，原安装版本在仍安全时保留，不盲目覆写用户文件；撤回/角色变化也需读取每个目标的版本/残留并让目标按实际机制清理，离线目标保留未撤回风险和 owner。只有受控环境的脱敏 fixture 实测 TeamAI 目标 CLI/Hook、DSH 安装根目录/loader、目标 digest 与回滚后才能标该路径 `real_verified`。如果 target 没有 DSH 兼容 Hook 或 loader，允许经审核的管理员固定包安装 fallback 并明确列出未覆盖设备，不得声称 TeamAI 自动无感分发已落地。

### 5.5 数据中台 Tool/MCP 标准接入契约与真实 Demo（拟议）

先冻结 Workbench 自己的版本化 `tool_provider_contract_version`、能力声明和 adapter mapping，再选一个**获准的隔离非生产 Provider**实现一项只读、低风险、只返回合成记录的 Demo Tool。可用自建受控 Demo Provider 验证标准契约，不冒称已对接真实数据中台；MCP 只是候选传输之一，HTTP/其他 Provider 也通过同一标准语义接入。Provider 自己负责目录/执行能力与其权限事实，数据责任方负责数据/字段准入与真实审批，DSH 宿主负责目标 Tool/profile policy；Workbench 仅做已授权目录聚合、申请途径展示、代理受控试参、证据和审计，不能凭目录可见或 MCP 握手授予调用权。不同 Provider 的字段权限、申请状态、审批主体和错误码须在 adapter 映射表逐项声明；缺失能力填 `unsupported|unknown` 并显示“未提供/未知”，不能转成“已授权/已批准”。

| 标准能力（建议 schema v1） | 最小输入/输出与权威 | 拒绝与证据 |
|---|---|---|
| 目录发现/详情 | 服务端强制 space/principal/environment，Provider 稳定 ID、tool ID/version、业务域、只读标志、描述、分页游标、schema/字段分类和 `capabilities`；目录展示范围由 Provider 与 Backend 授权交集决定 | 目录空、未接入、无权、Provider 不可用分列；记录目录版本/查询时间，不泄露隐藏项 |
| 权限与环境检查 | 分别查询 `discoverable`, `callable`, 字段可见范围、环境、DSH profile/policy、申请途径和审批回执是否支持；映射实际 Provider subject 与 service identity | 不把目录可见、Backend 连接检查、申请意向当作可调用/已批准；无可靠主体映射或字段级授权时 fail-closed |
| 受控测试调用 | 固定 `tool_id/version, environment, schema_version, fixture_ref, selected_fields, request_id`；服务端重新鉴权、验证 JSON Schema、只读 allowlist、合成数据域、时间/结果/次数预算，使用最小权限凭据，禁止自由 URL/生产租户/写入 effects | 请求带幂等键；Provider 接受后超时为 `unknown` 并凭 request ID 查读回，不盲重试；越权字段、注入、重定向越界、超额及写操作明确拒绝 |
| 结果/失败/审计 | 结构化合成结果带 provider/tool version、环境、fixture/source ID、字段可见性、调用/审计 ID、时间及截断标记；失败返回可核验 code、责任方、下一动作和查询 operation | 仅保留脱敏摘要/hash 和必要引用，不保留敏感正文或完整 Tool Call trace；无法取得 Provider 审计时标 `unknown`，不写测试通过 |

建议 `GET /v1/spaces/{space}/tools?cursor=...`、`GET /v1/spaces/{space}/tools/{id}`、`POST /v1/spaces/{space}/tools/{id}/checks`、`POST /v1/spaces/{space}/tools/{id}/test-invocations` 和 `GET /v1/operations/{id}`；这是 Backend API 草案，非 Provider 原生 API。`checks` 不授予权限，试参只接受目录固定的 schema/参数和已批准的测试环境，写入审计及 operation/outbox。申请仅登记 intent、责任人、Provider 申请入口/真实回执引用及 `pending|unknown|approved|rejected` 的**可证**来源；无法读回外部审批时不填 `approved`。适配器应给每项能力独立 `supported/unsupported/unknown`、`provider_mode`、`integration_status`、目标版本、契约兼容结果、证据与失效时间；标准接口兼容不表示所有 Provider 可提供相同字段权限。原型虚构目录=`fake/fixture`，真实 Demo 调用=`real` 且限定**非生产合成目标**，生产数据中台能力另需生产授权/字段 ACL/调用审计/撤权和 DSH 目标验证，不能因为 Demo `real_verified` 自动晋级。

Demo 的验收走发现→详情/schema→有权/无权及字段级检查→受控只读调用→结果来源→审计/失败回执→撤权后拒绝；同时测试未知能力、Provider 超时、重复/重放、无效参数、跨空间访问、写指令、未知审批与审计不可用。固定 fixture digest、实际请求/读回脱敏摘要、目标版本/环境、主体/权限、执行与复核人、失败和回滚进入 evidence manifest；无可授权非生产 Provider 时只交契约/fixture，明确 `blocked`，不称“Tool 跑通”。

### 5.6 合成知识经真实链路进入资产大盘（拟议）

在隔离非生产空间创建**明确标“合成”**的材料、已有知识基线、项目和产品线的独立多对多关系及两组权限主体；fixture 有版本、生成规则、摘要、保留/销毁责任人，不包含真实产品 ID 或敏感数据。使用入口②已授权的正式创作路径而非直接向 WeKnora 灌入预置索引：选择材料/基线和去向→服务端授权创建 Knowledge Session/Draft→逐项确认与受审 change package→指定审核人/Git MR/CI/protected merge→持久 outbox/worker→真实 WeKnora **测试空间** index、document/version/source commit/ACL read-back 和有权检索。入口⑤从授权资产 read model 读取发布事件、版本、来源与检索证据：详情深链指向**具体有权的文档 ID/版本**并在打开时重新鉴权，不以聚合卡片或 Git 路径猜文档 URL。只有各层真实读回才显示“非生产真实集成”；静态预置卡标“演示数据”，真实生产空间另行验收。

大盘的“最新进展”按事件 ID/asset ID/version/operation 去重并区分草稿、已审合并、索引中、检索可用、失败/待对账；“全局概览”以稳定 asset ID+revision 去重，项目和产品线分别为查找轴，同一资产关联多个轴时总数不重复累加，所有计数附授权范围/时间窗/最后刷新时间与 unknown；权限过滤先于聚合，防跨空间、无权深链和小样本反推。“智能诊断”只有确实运行已授权扫描时才给扫描批次、范围、覆盖率、来源、时间窗、未读/unknown 和待核候选；人工配置线索一律标 fixture，不称“AI 已巡检”。不以合成使用事件、发布量或索引命中推断知识质量/业务价值。

同一合成资产至少跑新增→修订（旧版仍有效或应阻断）→索引半成功/超时并读回/人工对账→成员撤权和旧版残留负向检索：检查 PG 指针、Git commit、WeKnora 新旧 document IDs、缓存/直连入口及大盘状态相互一致；失败不得展示“已发布/已撤权”绿色结论，恢复不能由迟到事件复活旧版。记录 fixture digest、merge/review/CI、worker attempts、检索正负向、ACL、链接点击的鉴权拒绝与复核人。此技术纵向链只能证明隔离环境的工程可行性，不证明真实业务材料的授权、知识准确性、实际采用或业务结果；后者保留 Pilot Beta/生产独立门禁。

## 6. 可靠性、安全与开发前需冻结的契约

- **数据库**：先冻结状态字典、唯一约束、CAS 迁移、租约/超时/retry budget、审批签名和错误码；PostgreSQL 控制面备份/恢复演练、审计 append-only 或等价防篡改策略、对象存储生命周期和销毁策略在阶段 1 定稿。不得靠页面状态保证发布。
- **Provider**：每个适配器输出 `provider_mode: fake|admin|real` 和 `integration_status: pending|blocked|fallback_only|contract_verified|real_verified|deprecated`、目标版本/环境、请求/读回证据及最后检查时间。fake/admin 只能证明对应契约或受控人工操作；真实可用必须按确切目标 Provider 读回验证。故障率/延迟阈值、SLO 和轮询上限由试点负载/运维 Owner 确定，不先捏造数字。
- **安全与数据最小化**：获准输入、来源 ACL、敏感级别及最短保存期限决定是否落库；对象存储加密、短期授权读取、密钥管理；LLM 调用最小化内容且不在日志/审计复制 Prompt 和 Tool Call trace；对来源文档的指令视为数据、不能授予 publish/tool 权限；固定测试 fixture 脱敏和 secret scan。保留原型警示：“请勿输入真实产品 ID 或敏感数据。”
- **观测**：用 correlation ID 串起 UI→API→Git commit→outbox/attempt→Provider read-back→用户待办，指标至少含排队/等待时长、unknown 积压和年龄、版本不一致、ACL 拒绝、重试/死信、不同 provider mode 的成功数；日志不含生产 Token、原文或敏感字段。告警指向有权 owner 与可查询 operation。
- **反例必须实现**：重复/乱序 Git event、伪造 webhook、旧修订覆盖、两空间同名 ID、撤权后 worker/缓存/检索、WeKnora 索引部分成功、Worker 崩溃、Provider 接受后超时/回执丢失、callback 迟到、Skill digest 漂移、禁用/回滚后旧 loaded 状态、业务成功未经 Owner 确认。这些不能只在 UI 提示“稍后再试”。

## 7. SkillHub 与 TeamAI 的角色评估及选择门

现有方案曾以 SkillHub 注册固定 release + TeamAI 分发为候选拓扑；现行的**正式审核权威是 Git MR/CI/指定审核人/protected merge**，两项 Provider 不构成同一类能力或首期硬依赖。[验证材料](../验证/README.md)仅说明目标自动能力尚待实测。此表是**待取证的判定规则**，不是目标部署通过结论：

| 要证明什么 | SkillHub（注册候选） | TeamAI（分发候选） | 判定/失败后的去向 |
|---|---|---|---|
| 固定批准 commit 的 package 登记、不可变 version/digest 和撤回 | 优先取证目标版本 API/包制品、注册→release→查询→撤回读回 | 只有若能证明等价不可变 registry/release 契约才可替代，不能因支持 `pull` 就认定有 release | 两者皆无时 Git/CI 固定包 + 管理员审计 fallback；目标 real release 未经读回不得称 SkillHub released |
| 指定团队/目标/profile 的包安装、摘要和旧版回滚 | Registry 不自动证明目标安装；检查是否自带分发且能读回 | 验证首次 init（成员权限）、同仓/镜像仓映射、SessionStart Hook 在 DSH 的兼容性、下次会话 pull 与主动 pull 区别、离线目标的固定版本安装/清理和逐目标文件摘要；不把角色/tag 当 ACL | 可仅用 SkillHub+受控管理员目标安装；不能靠目录可见或 Hook 已注册代替 installed/loaded |
| DSH loader 和权限兼容 | 注册包需与目标 DSH schema/loader 对齐 | 分发输出需与 DSH profile 的 digest/权限对齐 | 不管用谁，DSH discovery/load 与 profile/tool policy 独立实测；无法对齐则阻断目标可用 |
| 团队隔离、service identity、ACL/审计 | 查 registry 是否支持每资产空间 namespace 与最小写/读权限 | 查 workspace/target 身份、跨团队 pull 拒绝与审计 | 隔离失败不能投入真实团队；回到单团队受控手工验证不伪造多团队 Ready |
| 稳定运营成本与复杂度 | 部署、版本兼容、备份、升级、可观测、失败补偿 | 同左；额外镜像同步、配置漂移、冲突与重复供应链节点 | 如果 TeamAI 不带来明确真实需求且增加失败面，MVP 不引入；随 N5 决定后续扩展 |

**优先验证次序**：①Git MR/CI、指定审核人/protected merge 与固定 package/digest，以及目标 DSH 校验/loader 契约；②TeamAI 的首次 init、目标 Hook、固定版本映射、逐目标安装/撤回是否满足多端分发；③仅当独立 Registry 契约确有需求时验证 SkillHub/等价方案的不可变 release、查询和撤回，否则不将其列入首期硬依赖；④未通过的非必选 Provider 不伪造状态，按范围、期限和责任人采用已审固定包的受控管理员安装 fallback。Git 的正式审核不依赖 SkillHub，SkillHub release 不能代替目标安装，DSH 校验/加载也不能代替 Git 批准或真实业务测试。DSH、WeKnora 仍为必接边界：关键契约不足时阻断对应真实链，整改/升级目标环境，不以 fake/管理员操作替代真实读回。

每个评估产出 `目标 commit/version, API/部署制品证据, 环境, 操作主体和权限, fixture/package digest, 正向命令与退出码, read-back 原文的脱敏摘要, 负向隔离/超时/回滚, owner, review_at, evidence_digest`。不引用开源文档或本地 mock 直接下结论 `real_verified`。

## 8. Spike、依赖和验收映射（沿用 08）
