# 系统架构与权威边界

## 1. 当前推荐拓扑

```text
Git protected main
  ├─ knowledge merge event
  │    → event receipt / outbox
  │    → persistent worker
  │    → WeKnora ingest
  │    → document/version/source/ACL read-back
  │
  └─ Skill merge
       → package builder
       → immutable digest
       → SkillHub release
       → release/digest read-back
       → pinned digest
       → TeamAI distribution adapter
       → target install/digest read-back
       → DSH handoff/load read-back
```

Workbench PostgreSQL 保存 event、outbox operation、job/lease、provider operation、read-back 和 reconciliation；worker 只从 Git merge commit 读取 canonical 内容，不把 webhook 请求本身当成发布结果。

`team-knowledge-workbench` 是可被多个团队安装的产品包，`team-knowledge-asset` 是团队独立绑定的内容和治理资产域。Workbench 安装状态不等于资产发布状态；DSH Desktop host state、Session ownership 和 market install record 不是共享团队控制面，也不是正式资产的权威来源。

第一版只有一个新增创作发布控制面，负责 Creation Session、知识和 Skill 的草稿、资产生产、审核、发布和反馈分流。它必须按 `team_id`、`asset_space_id` 和 `session_id` 隔离检索范围、草稿和异步 job，拒绝过期 `state_version` 的回调，不复制 DeepSeek Harness 的完整 Runtime。异步动作先用数据库任务表、租约、幂等键、重试、读回和人工补偿。

## 2. 权威边界

| 对象 | 权威来源 | 负责什么 | 不负责什么 |
|---|---|---|---|
| Workbench package/market | DSH Desktop Workbench catalog/install/restart/uninstall 记录 | 插件包、版本、digest 和宿主安装状态 | 决定团队资产是否批准或发布 |
| team-knowledge-asset | 每个团队独立的 Git + WeKnora space + 治理配置 | 知识正文、Skill 源码、目录、版本、ACL 和审核 | 不能被另一个团队安装的 Workbench 直接读取 |
| Team/asset-space binding | Team Knowledge backend 的服务端配置和授权 | 将 Workbench 实例绑定到团队资产域 | 不能由客户端任意切换或扩大范围 |
| 正式知识 | Git + MR/CI/人工审核 | 正文、来源、差异、版本、回滚 | 下游直接修改 |
| 知识检索 | WeKnora | 索引、ACL、查询、引用 | 决定批准或管理 Skill |
| 正式 Skill | Git + MR/CI/人工审核 | 源码、契约、测试、依赖、版本 | 运行时自行改写 |
| Plugin package | Git + CI + package digest（P4 起） | manifest、工具 schema、适配器、依赖和权限声明 | 直接获得运行权限 |
| Plugin 注册/安装 | Plugin registry/管理员记录（P4 起） | package、digest、安装、启停、撤回和兼容性 | 决定业务任务质量 |
| Skill 注册/发布 | SkillHub | package、不可变 version/digest、release、beta/stable、撤回和真实 release read-back | 不负责 TeamAI 目标安装、知识事实或运行权限 |
| TeamAI 分发/同步 | TeamAI distribution adapter | 消费 SkillHub pinned digest，目标 workspace 映射、pull、安装和 digest read-back | 不负责审批、SkillHub release、知识索引或运行权限 |
| TeamLab 分发/协作 | Git 批准版本 + TeamLab adapter 运行记录（验证后） | 固定 package/digest 进入目标协作空间、目标绑定、release read-back、撤回和协作反馈 | 审批知识/Skill、管理知识索引、决定 Plugin health 或授予运行权限 |
| Agent Manifest | Git + CI + 人工审核（后续） | 多个 Skill、知识 profile、模型/工具策略的组合和分发描述 | 替代依赖资产的 owner、审核、ACL 或回归 |
| 执行和工具权限 | DeepSeek Harness profile/policy + Plugin runtime/tool registry（下游） | 会话装载、工具、人工确认和运行 | 改变 canonical source |
| 运行反馈 | Harness/业务系统的反馈引用 | 归因、质量和候选任务 | 直接发布资产 |
| Git merge event | Git provider 的合并事实 | repository、protected ref、merge commit、changed paths、actor 和 event id；触发异步操作 | 不能证明下游发布成功 |
| Workbench outbox/worker | PostgreSQL + worker | 事件落库、幂等、租约、重试、provider operation、read-back、reconciliation 和人工补偿 | 不能成为知识或 Skill canonical source |
| WeKnora ingest/read-back | WeKnora adapter/provider | 知识 document、index/version、source、repo_path、ACL 和实际可检索状态 | 不能审批知识或管理 Skill |
| Skill package/digest | Git/CI 构建产物 | 从固定 merge commit 生成不可变 package 和内容完整性标识 | 不能授予运行权限 |
| SkillHub release/read-back | SkillHub | 注册 package、release/version/digest、晋级/撤回和真实 release 状态 | 不负责 TeamAI 目标安装 |
| TeamAI distribution/read-back | TeamAI adapter | 消费 SkillHub pinned digest，分发到目标 workspace，读回 installed revision/文件清单/digest | 不负责 Skill 审批、release 或 DSH runtime |
| DSH handoff/load/read-back | DeepSeek Harness | 目标 profile、handoff、实际 loaded digest 和运行前状态 | 不改变 Git canonical source |


## 3. 组件职责

### Plugin 管理（P4 起）

Plugin 提供工具能力或外部系统适配，不提供业务任务方法。Plugin catalog/registry 管理 manifest、版本、digest、兼容性、安装、启停、健康、撤回和权限授予；Plugin runtime/gateway 负责隔离执行、凭据注入、超时/重试/幂等、tool registry 和真实状态读回。Skill 通过 profile 使用 Plugin 工具，但 Plugin 管理不替代 Skill 管理。

进入 P4 的触发条件包括：出现第二个外部系统或重复适配、多个 Skill 复用同一工具、需要集中权限/凭据治理、需要沙箱/进程隔离，或模块化单体无法接受地管理安装和运行。

### 工作台控制面

提供业务人员的统一创作发布入口和平台 owner 的控制面：工作台首页、Creation Session、session-scoped source/retrieval、知识/Skill 草稿、变更包、审核、测试、发布状态、事件接收、outbox operation、worker lease/retry、下游 read-back、交接记录、反馈、对账和审计。

会话上下文、Draft 和外部发布操作必须使用不同标识；回调必须校验 session、draft revision、expected state version 和 correlation id。它不存放未经治理的正式正文，不绕过下游真实状态，也不承载 Harness 的 Session/Run 控制。

### Git/CI

Git/CI 保存知识、Skill、Plugin manifest/适配器、schema、测试、metadata、依赖锁定、CODEOWNERS 和变更历史。执行格式、secret、契约、权限冲突、链接、依赖和回归门禁，并提供可验证的 protected main merge commit。merge event 至少要能关联 `asset_repository_id`、稳定 repository identity、repository、protected ref、merge commit、changed paths、actor、event id、签名和时间；事件接收方还必须校验 webhook source、`team_id`/`asset_space_id` 绑定以及 changed paths 是否位于允许的 `knowledge/` 或 `skills/` 根目录。

### WeKnora

只接收批准后的知识，提供权限过滤、检索、来源和版本引用。工作台必须保存 ingest/index job 和 document/version/source/repo_path/ACL read-back；只有实际可检索状态确认后才能将知识标记为 published。它不能管理 Skill 的契约、测试、发布或运行权限。

### TeamLab 分发/协作适配层（验证后）

TeamLab 只负责将已批准、固定版本的知识/Skill 交接到目标团队协作空间或内部消费入口，并读回目标绑定、版本/digest、协作状态和撤回结果。它可以复用内部服务接入配置，但不能改变 Git canonical source、WeKnora 索引事实、Skill 审批或 Harness 运行权限；TeamLab service identity、目标 workspace/space 和操作审计必须按 team/asset-space 隔离。能力未确认时回到管理员或 fake provider fallback。

### TeamAI 分发适配层（可选，验证后）

TeamAI 只负责已由 SkillHub 确认 pinned digest 的团队 AI 资产分发和本地同步：仓库镜像、`init`、变更分支上的 `push`、`pull`、版本切换、目标 workspace 映射/注入和安装读回。它必须返回 target、installed revision、文件清单和实际 digest；不能重新解析 `latest`、从另一份源码构建或决定 release。它可以承载 Skills、Rules、Agent Manifest 和受控 Plugin manifest 的分发，但不负责知识事实审批、Skill 业务质量、WeKnora 检索、Plugin runtime、权限授予或统一 run 的最终归因。

自动同步不等于自动批准或自动生效。实际运行前必须确认 target、profile、installed revision、pinned digest 和权限状态；不可用时必须回到 SkillHub 固定包或管理员 fallback。

### SkillHub

提供 Skill package 的注册、不可变 version/digest、release、晋级/撤回和真实状态读回。SkillHub 是 Skill release 的事实来源，不负责 TeamAI 目标安装；能力未验证时由管理员流程保证同样的 package、digest、审批、装载和回滚语义。

### OpenCSG 运行层（验证后）

参考方案将 OpenCSG 定位为模型推理、Agent 编排、AI Gateway 和多 Agent 协作运行层；本项目只把它作为待验证 provider，不因外部方案描述而视为已集成。其资产托管、AgenticHub、CSGClaw 或本地模型能力必须分别验证，不能替代工作台、Git、WeKnora、Skill 分发或 Plugin 治理。

### DSH Desktop Workbench Plugin

DSH Desktop 的 Workbench Host 是本地插件/UI/Session ownership 机制，不是 Team Knowledge 的共享团队控制面。`team-knowledge-workbench` 应按 dsh-desktop 的 Workbench 标准提供 server entry、构建后的 client module、canonical repository identity 和最小宿主 patch；通过宿主 ownership service 获取只读 Session 元数据，不把它当作授权。市场 catalog、安装、重启、启停和卸载读回只证明插件到达目标 Desktop，不证明任何团队资产已发布、WeKnora 已索引或 Harness 已加载。

Workbench 后端必须使用独立的身份、团队/asset-space ACL 和 worker credential。DSH launch token 只用于宿主启动交换，不能作为通用 API credential 转发给 Team Knowledge API 或后台 worker。Renderer 继续遵守 sandbox、context isolation、禁用 Node integration 和窄 IPC；不得用 preload DOM 注入或宽泛 patch 绕过安全边界。

### Team Knowledge Backend 与资产域

Team Knowledge Backend 负责团队绑定、DSH 身份映射、Creation Session、Draft/Revision、目录治理、审核、Git/MR/CI、Git merge event 接收、outbox/worker、WeKnora、SkillHub、TeamLab、TeamAI、handoff、反馈和审计。PostgreSQL 是过程控制面，保存用户/服务身份映射、会话、草稿、审批、Job/lease、事件、幂等键、provider read-back、对账和审计；对象存储保存加密的原始材料、附件和大型测试 fixture。正式知识和 Skill 仍分别以 Git 为 canonical source，WeKnora、SkillHub、TeamLab 和 TeamAI 通过受控 adapter 读写，不能直接写 WeKnora 内部数据库。

当前不以公司统一身份系统接入作为 P0 前提。Workbench 复用 DSH Desktop 的认证上下文，但后端必须重新验证可用的 `principal_id`、`team_id`、`asset_space_id` 和资源 ACL。`desktopWorkbenchOwnership` 仅是宿主元数据，DSH launch token 不是 Team Knowledge、Git、WeKnora、SkillHub、TeamLab 或 Worker 的通用 credential。Git、WeKnora、SkillHub 和 TeamLab 可以复用内部服务接入配置，但每个 asset-space 的资源范围、服务身份授权和审计必须独立。

每个团队的 `team-knowledge-asset` 至少独立拥有 Git repository、protected branch/CODEOWNERS、WeKnora space、ACL、taxonomy、steward 和 release policy。Workbench 可以被多个团队安装，但不能因为安装相同插件而共享可变草稿或权限。

### 知识与 Skill 的 canonical repository layout

默认逻辑结构如下，路径相对于 `asset_repository` 的 repository root：

```text
<asset_repository root>/
├── README.md
├── taxonomy/v1.yaml
├── knowledge/<domain>/<topic>/<knowledge-slug>/
├── skills/<domain>/<name>/
├── profiles/
└── CODEOWNERS
```

P1 默认由同一个 canonical repository 同时承载 `knowledge/` 和 `skills/`。Knowledge 和 Skill 是同一 `team_id`/`asset_space_id` 下的两类并列一等资产：前者由 WeKnora 索引和检索，后者构建为 Skill package 并发布到 SkillHub。Skill 不复制 Knowledge 正文，只在 `skill.yaml` 中通过固定 ID/version 声明 `knowledge_dependencies`；SkillHub、TeamAI 和 DSH 的 package、安装和加载状态不能替代 Knowledge 的 Git/WeKnora 权威。`team-knowledge-asset` 是该团队资产域的逻辑名称，不要求 repository 内再嵌套同名目录。

P1 一个 `asset_space` 只允许一个 active canonical `asset_repository`；如未来因规模或权限需要拆分 Knowledge repository 与 Skill repository，必须通过控制面显式绑定 `team_id`、`asset_space_id`、`repository_kind: knowledge | skill`、稳定 `repository_identity`、`repository_url`、`canonical_path`、`protected_ref`、CODEOWNERS policy、release policy、ACL 和 steward/owner，不能通过目录名、客户端参数或 `latest` 推断归属。

### 知识目录与 WeKnora 映射

默认知识目录如下，路径是知识 canonical identity 的一部分：

```text
knowledge/<domain>/<topic>/<knowledge-slug>/
├── KNOWLEDGE.md
├── metadata.yaml
├── sources.yaml
└── CHANGELOG.md
```

Workbench 在知识 Creation Session 中要求或建议 domain/topic，预览最终 repo path，执行 taxonomy、slug、重复 canonical key、owner 和敏感级别校验；Agent 不能随意在根目录平铺或创建未经治理的分类。WeKnora 允许使用不同的物理 collection/index，但必须携带 `asset_space_id`、`knowledge_id`、`repo_path`、`domain`、`topic`、`version`、`source_commit`、`sensitivity`、`status` 和 ACL，使 Git 路径与 WeKnora 展示路径可双向追溯。移动、合并和退役必须由 Git MR 驱动，并进行索引迁移、旧路径 alias/redirect 或退役记录和读回对账。

### DeepSeek Bot

可选的 DSH 协作层，提供 Bot、Group、Memory 和交接；不能替代资产治理、SkillHub、Git、WeKnora 或企业审批。

## 4. 当前不引入的层

完整 Integration Gateway、Plugin Registry/Runtime、Console Plugin、MCP 高风险工具、多 provider、服务端 Bot Host 和 TeamAI 自动分发不是 P1 的硬依赖。腾讯云非生产部署、现有 WeKnora 测试空间、DSH/Harness、SkillHub 和 TeamLab 的可部署性验证属于 P0；如果目标制品/API 未确认，则保留 fake provider 或管理员 fallback。TeamAI 先只做能力侦察或可选 adapter，只有双资产稳定且出现真实分发触发证据后才进入 P3；业务 Plugin 只有出现外部系统复用、集中权限或运行时隔离需求后才进入 P4。

DSH Desktop Workbench market 是本项目产品包的分发渠道，不等同于本项目建设一个独立业务 Plugin Marketplace。正式市场准入、catalog、公开仓库、构建产物、安装重启、启停和回滚应按 DSH 宿主规则单独验证。

这不影响知识和 Skill 管理是当前产品核心；延后的是 TeamAI 自动分发、Plugin 等更重的实现层，不是 Skill 资产能力。

## 5. 不可混淆的边界

- WeKnora 是知识检索，不是 Skill 管理；
- SkillHub/TeamAI 是分发实现，不是知识事实审核；
- TeamAI 的 pull 成功不等于 Skill stable、Plugin enabled 或运行成功；
- DSH 是执行面，不是资产 canonical source；
- MCP 是调用协议，不是异步控制面；
- Webhook/event 到达不等于 worker 成功；
- outbox job 成功调用 provider 不等于 read-back 成功；
- WeKnora ingest 不等于知识 published；
- SkillHub release 不等于 TeamAI installed；
- TeamAI installed 不等于 DSH loaded；
- DSH handoff request 不等于 handoff completed；
- `installed_revision` 不等于 `package_digest`；
- HTTP 200 不等于任何一个业务状态成功；

- 一个 Agent 的成功回答不是通用规则；
- 一个统一页面不等于系统统一。
