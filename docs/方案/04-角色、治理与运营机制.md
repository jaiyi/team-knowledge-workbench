# 角色、治理与运营机制

## 1. 三类责任

```text
模型：提取、摘要、分类、起草、发现冲突、生成测试候选
脚本/CI：校验 schema、权限、依赖、secret、回归和差异
人：确认事实、范围、任务边界、风险、批准发布和高风险动作
```

在原有角色之外，平台 owner 负责可复用的 `team-knowledge-workbench` 产品包和宿主市场交付；team asset owner 负责本团队 `team-knowledge-asset` 的 Git/WeKnora/ACL/taxonomy；WeKnora space admin 负责索引空间和权限读回；distribution/runtime owner 负责 DSH/SkillHub/TeamLab 交接。多个团队可安装同一 Workbench，但不能共享可变草稿、资产授权或审计上下文。当前用户身份通过 DSH Desktop 认证上下文进入工作台；后端负责映射 `principal_id`、团队成员和角色，并重新校验 asset-space ACL。

### 首期试点的三类核心角色

首期产品不以“所有团队成员”作为目标用户，而以一个明确业务流程中的三类角色作为试点边界。三类角色描述的是业务价值责任，不取代平台 owner、asset owner、steward、Skill owner、审核人和 distribution/runtime owner 等治理角色；早期可以由同一人兼任，但必须在记录中分别标明。

| 角色 | 定义 | 首要责任 | 不能由什么替代 |
|---|---|---|---|
| **第一用户** | 负责把业务资料和经验转化为正式 Knowledge 或 Skill 的领域专家/Knowledge steward/Workflow owner | 创建、确认、维护资产；确认事实、范围、例外、契约、测试和复核日期；处理知识或 Skill Badcase | 不能由平台管理员或模型单独替代；平台可降低 Git/Provider 操作成本，但不能替代领域判断 |
| **第一推动者** | 对具体业务流程的效率、质量或交付结果负责，并愿意为试点投入人员和时间的业务流程 Owner | 选择场景、提供人工基线和目标、指定第一用户与审核人、调配试点资源、确认继续/调整/停止 | 不能只由平台 owner 或技术负责人承担；技术团队可以推动交付，但不能单独证明业务价值 |
| **第一受益者** | 在真实业务流程中消费已发布 Knowledge 或 Skill，并因此减少查找、沟通、处理时长或返工的一线执行者 | 实际消费、反馈问题、提供结果引用和任务结果；验证消费后的效率、质量和一致性改善 | 不能用发布次数、安装次数、加载次数或作者主观满意度替代 |

三类角色形成闭环：

```text
第一推动者：这个场景值得投入，并且我对结果负责。
第一用户：我负责把业务经验做成高质量、可维护的资产。
第一受益者：我使用这个资产，并且我的实际工作结果得到改善。
```

第一推动者必须能够明确：

- 首个业务场景和不包含的范围；
- 当前人工基线、目标改善和统计窗口；
- 愿意投入的第一用户、审核人和第一受益者；
- 允许的审核、发布和人工介入成本；
- 试点停止条件、业务结果确认人和最终 Go/No-Go 决策人。

第一用户必须能够完成：

- 将材料或工作流整理为可审查的 Knowledge/Skill 草稿；
- 确认事实、来源、范围、例外、输入输出、权限和成功标准；
- 在不直接操作 Git、CI、WeKnora 或 Provider 命令的情况下完成提交和维护；
- 根据消费反馈创建修订、复核或回归任务。

第一受益者必须能够完成：

- 在声明的目标流程中消费固定版本的 Knowledge/Skill；
- 区分结果正确、需要人工修订、运行失败和无法判断；
- 通过最小反馈引用报告问题，不提交原始业务敏感内容；
- 提供可核验的任务耗时、返工、错误或一致性结果。

平台 owner、Provider 管理员和 Harness/DSH runtime owner 属于支撑角色，不作为首期业务价值的唯一证明人。发布、安装、加载和技术成功不能替代第一受益者的业务结果，也不能由资产作者单独确认。

### 首期试点分布与最小配置

首期试点先按一个明确的低风险、高频、可回放业务流程组织，不按“全公司用户”铺开。推荐最小配置如下：

| 角色 | 建议人数 | 试点职责 | 主要证据 |
|---|---:|---|---|
| 第一推动者：业务流程 Owner | 1 | 选定场景、提供人工基线和目标、调配资源、确认业务结果、决定继续/调整/停止 | 场景说明、基线、目标、样本量、停止条件、Go/No-Go 记录 |
| 第一用户：领域专家/Knowledge steward/Workflow owner | 2–3 | 创建、确认、审核前修订和维护 Knowledge 或 Skill；处理事实、契约、测试和复核任务 | 草稿修订、确认记录、MR/发布证据、维护耗时、返工和复核关闭时间 |
| 审核人 | 1 | 审核事实、风险、权限、契约、依赖和发布范围 | 审核意见、批准记录、例外和回滚决定 |
| 第一受益者：一线消费者 | 5–8 | 在真实或受控低风险流程中消费固定版本，反馈并提供任务结果 | 消费事件、结果引用、任务耗时、首次成功、返工、Badcase 和业务确认 |
| 平台/分发支持 | 1–2 | 提供 Workbench、Git、WeKnora、Provider、身份、故障和证据支持 | 部署、read-back、对账、恢复、权限和安全证据 |

5–8 名高频使用者应优先定义为第一受益者，而不是默认定义为资产作者；如果其中部分人员同时参与创作，仍需在试点记录中区分其消费和资产维护行为。

试点不要求每个角色由不同人员承担，但以下责任不能因为兼任而合并为不可区分的状态：

- 创建/维护 Knowledge 或 Skill 的责任；
- 审核和发布责任；
- 业务结果确认责任；
- 平台技术执行和 Provider read-back 责任；
- 最终 Go/No-Go 和风险例外责任。

### Knowledge-first 与 Skill-first 的角色映射

两类资产的第一用户和证据重点不同：

| 试点主线 | 第一推动者 | 第一用户 | 第一受益者 | 首期重点证据 |
|---|---|---|---|---|
| Knowledge-first | 业务流程 Owner | 领域专家/Knowledge steward | 需要查询规则、资料和流程的一线执行者 | 从材料到可用知识的耗时、引用/检索质量、过期率、查找和返工下降 |
| Skill-first | 流程自动化 Owner | Workflow owner/Skill owner | 重复执行该流程的一线操作人员 | 输入输出契约、回归通过率、首次成功率、人工纠正率、处理时长和业务结果 |

Knowledge steward 主要对事实、来源、适用范围、例外、敏感等级和复核负责；Skill owner 主要对任务边界、输入输出、effects、测试、运行归因和回滚负责。两者不能只使用一个泛化的“贡献者”角色替代。

当前默认推荐 Knowledge-first：先验证“团队是否愿意持续维护正式知识资产，以及知识消费是否改善一线工作”，再将稳定、高频、边界清晰的流程固化为 Skill。Skill 可以在 P1 保留数据模型、契约和测试能力，但不应把 SkillHub、TeamAI、DSH 分发和 Harness 业务执行同时作为首个业务价值闭环的必要条件。

### 三类角色的试点验收问题

| 角色 | 必须回答的问题 | 可量化证据 |
|---|---|---|
| 第一用户 | 每周花多少时间整理资料或回答重复问题？哪些内容必须人工确认？愿意多久维护一次？是否能不操作 Git 完成发布？ | 从材料到可用资产耗时、人工修订次数、确认率、发布返工率、复核按时率、过期率 |
| 第一推动者 | 要改善哪个业务结果？人工基线是什么？愿意投入哪些人员？允许多长时间看不到结果？什么情况停止试点？谁确认业务成功？ | 目标、基线、改善幅度、样本量、试点周期、维护成本、停止条件 |
| 第一受益者 | 在什么任务中消费？以前如何完成？是否减少查找和沟通？结果是否更快、更一致？遇到错误是否知道如何反馈？ | 任务完成时长、首次成功率、人工返工率、重复提问次数、业务错误率、反馈提交率 |

没有三类角色的独立证据，不能仅凭平台安装、资产发布、Skill load 或调用次数判断试点成功。
## 2. RACI

| 活动 | 平台 owner | Distribution/runtime owner | 贡献者 | 知识 steward | Skill owner | Plugin/integration owner | 审核人 |
|---|---|---|---|---|---|---|---|
| 模板和门禁 | A/R | C | C | C | C | C | I |
| 提交资料/工作流需求 | I | I | R | C | C | C | I |
| 生成知识/Skill 草稿 | A | C | C | C | C | C | I |
| 确认知识事实和范围 | I | I | R | A/R | C | I | C |
| 确认 Skill 契约和预期结果 | I | C | C | C | A/R | C | C |
| 权限/effects/兼容性审核 | A/R | C | I | C | R | C | A |
| CI、安全和回归检查 | A/R | C | I | I | C | C | I |
| 发布知识/Skill | C | R | I | R | R | R | A |
| DSH 交接与能力验证 | C | A/R | I | C | R | C | I |
| 反馈分流 | R | R | C | A（知识） | A（Skill） | A（Plugin/平台） | C |
| 退役/回滚 | R | R | I | A（知识） | A（Skill） | A（Plugin/分发） | A |

merge event、outbox/worker、provider read-back 和 TeamAI/DSH 安装读回由平台 owner/Distribution owner 分别承担技术执行责任，业务 steward/Skill owner 仍承担内容和质量责任。任何 read-back 不完整时，不能由平台 owner 单方面将状态改为 published、released 或 loaded。

早期一人可以兼任多个角色，但知识责任、Skill 责任和分发责任必须分别明确，不能因为同一个人兼任就把审核、发布和安装读回混为一类。

### Creation Session 责任

每个会话必须有明确的 `owner_id`。owner 负责会话目标、输入材料、草稿推进、暂停/恢复、分叉和提交动作；协作者只能在授权范围内编辑当前会话。会话权限与正式资产权限分开：能编辑 Draft 不等于能批准 Asset Revision，能批准资产也不等于能批准下游 Harness 运行。

- **Session owner**：管理会话上下文、成员、待确认项和会话状态；
- **Session collaborator**：在会话范围内补充材料、修改草稿或运行测试；
- **Knowledge steward / Skill owner**：对正式知识事实或 Skill 契约、测试和质量负责；
- **Reviewer / publisher**：审批正式修订和发布；
- **Distribution/runtime owner**：负责 handoff 读回和下游能力验证；Harness runtime approval 由下游负责。

同一正式资产的并行会话发生 `base_revision` 冲突时，由 owner/steward 或 Skill owner 人工合并；不能由平台按最后写入者覆盖。


### 知识

事实、来源、适用范围、例外、敏感等级、跨域可见性、复核日期和是否足以形成通用规则。

### Skill

任务是否值得固化、输入输出是否完整、失败态和例外、知识依赖是否正确、工具/effects 是否必要、风险等级、测试结果、profile 兼容性、beta/stable、撤回和回滚。

### Plugin

Plugin owner 必须确认工具 manifest、外部系统边界、权限和凭据需求、宿主兼容性、依赖/SBOM、沙箱或进程隔离、超时/重试/幂等、health、禁用和回滚。Plugin 只能声明能力需求，不能自行授予权限或把 provider 响应变成系统指令。

### 分发

TeamAI 或其他 distribution adapter 的目标仓库、分支保护、版本 pin、SkillHub release/digest 一致性、profile 兼容、secret 扫描、Hook 限制、删除清理、安装读回、回滚和审计。平台 owner 还必须人工确认 merge commit、WeKnora read-back、SkillHub release digest、TeamAI target/installed digest 和 DSH profile/loaded digest 是否分别与批准版本一致。Agent Manifest 必须逐项引用已批准的 Skill、知识 profile 和工具权限，不能用组合包绕过任何依赖资产门禁。

### 共同

任何生产写入、不可逆动作、对外发送、权限扩大和数据范围扩大。发布交接也必须经过批准版本、目标范围确认和实际状态读回。下游 Harness 的运行时人工批准由 Harness/业务系统负责。

## 3. 审核与责任边界

业务责任人与技术执行人必须分开记录。`created_by`、`confirmed_by`、`approved_by`、`released_by` 和 `owner_id` 指向真实 DSH 用户或团队角色；`executed_by` 和 `service_identity_id` 指向实际执行 Git、WeKnora、SkillHub 或 TeamLab 外部调用的受控服务身份。Git bot 可以作为 commit author/committer，但 MR、commit trailer、asset metadata 和审计必须关联真实提交人、审核人和发布人。Agent 可以起草、测试和解释结果，不能作为唯一批准人，也不能使用个人长期 Token。

Git、WeKnora、SkillHub 和 TeamLab 可以复用内部服务接入配置，但每个团队的 asset-space、资源 ACL、操作范围和审计记录必须独立。DSH launch token 和 `desktopWorkbenchOwnership` 不能替代后端授权或作为其他组件的通用 credential。

## 4. 风险等级与 gate

| 级别 | 示例 | 默认控制 |
|---|---|---|
| L0 | 只读检索、证据卡片 | 可自动执行，记录审计 |
| L1 | 摘要、候选、草稿 | 可自动执行，标记未验证 |
| L2 | 隔离环境计算和回放 | 限资源、网络和数据范围 |
| L3 | 创建任务、修改临时状态 | 范围校验和可恢复记录 |
| L4 | 敏感读取、业务写入 | 人工确认、最小权限、读回比对 |
| L5 | 生产、不可逆或现场动作 | 强制 gate、双人审批、急停和回滚 |

Skill 只能声明能力需求，实际权限由 DSH profile、tool policy、用户、workspace、环境和运行时授权共同决定。

## 5. 产品成熟度与发布门禁

产品成熟度不只表示“功能是否能运行”，还表示业务价值、用户采用、平台可靠性、安全治理和 Provider 证据是否达到对应阶段。统一使用三个阶段：

```text
Contract Beta → Pilot Beta → Stable
```

成熟度必须绑定适用范围，而不是对整个产品作无条件承诺：

```text
asset_type + asset_space + provider_mode + target + profile + package_digest
```

### 5.1 Contract Beta

定义：

> 产品和集成契约可以在受控环境运行，但尚未证明真实业务价值，也不代表真实 Provider 已完成接入。

进入条件：

- 核心对象、状态机和权限边界已冻结；
- Git、控制面、审计和身份契约通过；
- fake provider 或 admin fallback 可以运行；
- schema、幂等、重试、read-back、unknown/reconciling 和回滚路径通过；
- 无未关闭的 Critical 安全问题；
- 未完成真实 Provider 验证的 Provider 必须标记为 `pending`、`blocked`、`fallback_only` 或 `contract_verified`；只有真实 Provider read-back 通过后才能标记 `real_verified`；
- 可靠性指标至少能够记录 merge-to-index、read-back、retry、backlog、unknown 和 digest mismatch。

允许范围：

- 非生产环境；
- 脱敏 fixture；
- 受控回放；
- 内部技术验证；
- fake/admin contract test。

禁止表述：

```text
SkillHub 已正式接通
TeamAI 已完成真实分发
DSH 已完成真实加载
系统已具备生产能力
```

### 5.2 Pilot Beta

定义：

> 产品已在一个明确的低风险真实场景中被真实用户使用，但仍处于受控试点阶段。

进入条件：

- 已确定具体业务场景和业务结果 Owner；
- 至少一个团队完成真实创作、审核和消费；
- 用户无需直接操作底层 Git、Provider 或运行时系统；
- 有人工基线、目标指标、统计窗口和样本记录；
- 开始采集采用指标，并至少有一个真实低风险场景的价值指标；
- 技术完成、契约成功、业务成功、失败和 unknown 分层记录；
- 有人工复核、回滚、故障接管和反馈分流机制；
- fake/admin fallback 与 real Provider 状态明确区分。

Pilot Beta 允许存在：

- 人工发布；
- Provider fallback；
- 人工业务结果确认；
- 受控的未知状态；
- 低风险场景下的有限人工介入。

但必须满足：

- fallback 不得绕过 protected main、CI、人工审核或权限门禁；
- fallback 结果不得伪装为真实 Provider 成功；
- 所有 fallback 操作必须有独立审计记录和有效期；
- 高风险业务写入仍然禁止；
- `unknown` 超过最大存续时间或积压超过阈值时，必须停止扩大试点并进入对账。

### 5.3 Stable

定义：

> 在声明的资产类型、Provider 路径、目标环境和运行 profile 范围内，产品具备可重复使用、可恢复和可运营能力。

Stable 不是全局承诺，必须明确适用范围和对应证据。进入条件：

1. **价值证据**
   - 业务结果 Owner 已确认目标指标；
   - 相对于人工基线有可解释的改善；
   - 价值指标不是由技术完成状态推导；
   - Badcase 率和人工返工率处于约定范围。

2. **采用证据**
   - 真实用户持续使用；
   - 发布版本被实际复用；
   - 反馈能够进入维护队列；
   - 资产 Owner 和 steward 有明确维护责任。

3. **可靠性证据**
   - 真实 Provider read-back 通过；
   - outbox、retry、reconciliation 和 rollback 已验证；
   - unknown 在约定阈值内；
   - 关键 SLO 达标；
   - backup/restore 和 worker restart 已完成演练。

4. **安全和治理证据**
   - 跨团队隔离通过；
   - Secret、Webhook、路径穿越、内容注入和权限边界测试通过；
   - 供应链来源和 package digest 可验证；
   - 审计记录完整；
   - Critical/High 风险均已关闭或经过正式例外批准。

5. **运营证据**
   - 审核、Badcase、unknown 和 Provider 故障均有 SLA；
   - 有明确升级路径；
   - 有维护预算和容量；
   - 有回滚和停止使用条件。

Stable 不要求首期支持高风险生产写入，但必须声明边界，例如：

```text
stable_for: low-risk assisted workflow
```

不能将其表述为：

```text
stable_for_all_production_workflows
```

### 5.4 Provider 验证状态

Provider 状态与产品成熟度分开记录，统一使用：

| 状态 | 含义 |
|---|---|
| `pending` | 尚未完成验证 |
| `blocked` | 存在阻塞问题，当前不可使用 |
| `fallback_only` | 只能通过 fake 或 admin fallback 使用 |
| `contract_verified` | 契约、状态机和失败路径已验证，但不代表真实 Provider 接通 |
| `real_verified` | 目标版本、目标环境和真实 Provider read-back 已验证 |
| `deprecated` | 不再作为推荐依赖 |

同时记录：

```text
provider_mode: fake | admin | real
```

最终状态不能只写 `released`、`loaded` 或 `succeeded`，必须能够回答：由哪个 Provider、以什么模式、在什么版本、对应哪个 source commit 和 package digest、是否经过 read-back、是否有真实业务结果。

### 5.5 Skill 治理门禁

一个 Skill 进入 Contract Beta 前必须有：契约、知识依赖、effects/权限声明、golden cases、回归结果、owner、固定版本和非生产 profile。

进入 Pilot Beta 前还必须有：低风险真实场景、业务结果 Owner、采用事件、人工复核、反馈分流和 fallback 标记。

进入 Stable 前还必须有：真实任务证据、价值基线和目标、失败和人工纠正记录、依赖和 SBOM、digest、运行归因、回滚 pin、下一次复核日期、SLA 和明确批准。

禁止：模型自动标 stable、相似度自动合并 Skill、Skill 自行增加工具、用一次成功运行替代回归、用 `latest` 代替固定版本。

## 6. Plugin 治理门禁（P4 起）

一个 Plugin 进入 `enabled` 前必须有：manifest、工具 input/output schema、最小权限和数据范围、Secret Manager 引用、依赖/许可证/SBOM、宿主兼容性、health/readback、安装审计、失败清理和回滚 pin。涉及敏感数据、网络写入或不可逆动作时，必须增加沙箱、人工确认、限流、幂等和读回比对。

Skill 质量治理与 Plugin 运行时治理分开：Skill 关注任务结果、知识依赖和回归；Plugin 关注工具安全、外部系统兼容性和运行可靠性；分发治理关注版本到达、目标一致性和交接证据。下游 Harness 负责会话运行和运行时权限，本工作台只接收必要反馈引用。

## 7. 运营节奏


知识 steward 检查事实/范围；Skill owner 检查契约/测试/effects；Plugin owner 检查 manifest/权限/兼容性/health；平台 owner 检查 CI、权限和发布证据。

### 每周复核队列

分别处理知识错误/过期/引用失效、Skill 失败/纠正率/契约冲突、Plugin API/health/权限/兼容性问题、profile 权限异常、索引/装载失败、merge event 丢失、outbox backlog、SkillHub release unknown、TeamAI digest mismatch、DSH handoff failure 和人工补偿任务。

### 每月质量回顾

同时看三层指标：

- **价值指标**：业务任务完成率、首次成功率、人工返工率、平均处理时长、业务错误率、已确认 Badcase 率和相对于人工基线的目标业务指标改善；
- **采用指标**：有效调用次数、执行尝试次数、活跃用户数、发布版本消费率、版本复用率、反馈覆盖率、资产维护及时率；
- **平台可靠性指标**：merge-to-index 时延、package build 成功率、Provider read-back 成功率、outbox backlog、retry rate、unknown 数量和持续时间、digest mismatch、回滚成功率、provider error rate。

消费指标必须按实际 `skill_id/version/package_digest` 统计，并同时展示统计窗口、分母、unknown 数量、数据覆盖率、最后同步时间和最后对账时间。Skill owner 解释 Skill 质量和 Badcase；平台/分发 owner 解释版本、安装和交接数据；业务结果 Owner 负责业务成功事实。不能把 SkillHub release、TeamAI install、DSH load 或无反馈推断为 Skill 使用或成功。

Contract Beta 重点观察可靠性和契约证据；Pilot Beta 开始观察采用和真实低风险场景价值；Stable 必须同时满足三层指标可统计、版本/digest 可追溯和约定阈值达标。

## 8. 反馈分流

| 反馈 | 进入的治理任务 |
|---|---|
| 事实、范围、引用错误 | 知识复核/MR |
| 输入输出不匹配 | Skill 契约修订 |
| 步骤或结果质量错误 | Skill 回归/MR |
| Plugin API、凭据、健康或兼容性错误 | Plugin 禁用/回滚和平台故障 |
| 分发同步、版本漂移、安装读回或删除清理错误 | 分发故障、回滚和人工对账 |
| 业务规则变化 | 知识和依赖 Skill 联合复核 |
| 运行基础设施失败 | 平台故障和补偿 |

反馈不直接覆盖正式知识或 Skill。试点先选择 5–8 名高频使用者和一个知识域/任务，证明双资产闭环有价值后再扩展。
