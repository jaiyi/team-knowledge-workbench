# 端到端工作台工作流

> 本文描述用户如何在工作台中把资料变成知识、把工作方式变成 Skill，并把已发布资产交给 DeepSeek Harness。工作台不承载发布后的会话执行。

## 1. 一张总图

```text
DSH 原生任务（宿主）或 Workbench「我的工作台」（默认）
  → 核本人有权记录、原系统/有权联系人和准确旧版
  ├─ 已解决／现有资产适用 → 回原任务；不强迫创建或沉淀
  ├─ 具体疑点 → 独立 Feedback Candidate → 核验／分流／回访
  ├─ 提炼知识&经验 → 读获准来源 → 核事实与经验 → 去向预览
  │    └─ 明确新建／修订正式知识且通过服务端权限核验
  │         → Knowledge Creation Session + Draft → Git 审核 → WeKnora 读回
  ├─ 打磨可复用的技能 → 核候选／准确旧版 → 沿用或停止
  │    └─ 明确创作／修订且通过服务端权限核验
  │         → Skill Creation Session + Draft → Git 审核 → 固定包／目标读回
  ├─ 连接业务数据源 → 有权目录与申请指引；实际调用由受控宿主/提供方核权
  └─ 团队业务资产大盘 → 只读进展／关系／诊断候选 → 显式继续处理

已发布资产 → DSH 目标按固定版本发现/装载 → 宿主任务实际消费
  → 最小反馈引用回 Workbench；只有确认需正式修订时才关联新创作会话
```

五个入口按当次问题选择，并非顺序完成；查看来源、核证旧版、只读详情、提交反馈均不自动创建会话或草稿。只有用户明确选择正式新建／修订知识或 Skill，且服务端核过资产空间、来源／基线版本和动作权限，才创建该类型独立的 Creation Session、Draft 和后续异步操作；知识与 Skill 会话可并行，不能共享可变上下文。Feedback Candidate 有自己的核验、分流、回访和关闭路径，误报、权限／分发故障或原业务流程问题不必转创作。工作台的 Creation Session 不等于下游 Harness Session。

## 2. 生产线一：会议/资料到知识

### 2.0 团队资产空间与目录上下文

用户进入 Workbench 后，服务端先根据身份和宿主配置确定当前 `team_id`、`asset_space_id`、资产 Git repository 和 WeKnora space。客户端不能仅凭 URL 或表单参数切换团队资产空间；切换必须经过服务端授权并读回绑定配置。

每次知识创作都要在会话中展示目标资产空间、taxonomy/domain/topic 和预计 Git path。默认路径为：

```text
knowledge/<domain>/<topic>/<knowledge-slug>/
├── KNOWLEDGE.md
├── metadata.yaml
├── sources.yaml
└── CHANGELOG.md
```

Agent 不能把知识候选随意堆在根目录。Workbench 要在提交前检查 taxonomy、slug、重复 canonical key、owner、敏感等级、CODEOWNERS 和 WeKnora mapping；WeKnora 的物理结构可以不同，但逻辑路径、知识 ID、版本、来源 commit 和 ACL 必须可双向追溯。

### 2.1 进入知识创作会话

用户在「提炼知识&经验」核对获准来源，明确选择正式创建或修订知识且服务端验证空间、来源/基线与动作权限后，平台才创建独立的 `Knowledge Creation Session` 和 `Knowledge Draft`，随后在同一会话内继续创作；只读核证不建会话。用户可以暂停、恢复或并行打开其他会话；材料、草稿、待确认项和异步操作不会串线。

用户可以上传会议纪要、粘贴文本、导入文件或提交已授权的资料链接。个人 Inbox 中保存链接只留有权定位，不抓取/解析；在「提炼知识&经验」中，成员明确选择链接用于梳理且服务端核当前主体、来源、用途、目标空间和该链接的受限获取范围后，才可对已验证支持的来源临时抓取固定版本并解析。为只读判断是否值得提炼而进行的获准解析可先于正式 Creation Session；抓取本身不代表团队候选受理、正式建稿或发布。未获准或获取/解析能力未通过目标验证时保留最小待核定位，不能生成已完整解析的候选；团队提交及正式创作另行授权。平台保存获准保留的原始材料引用、固定原件版本/hash、捕获人、形成/生效/截止和读取时间、workspace、来源类型和敏感等级；原件默认留原系统，创作时经授权的临时读取或获单独许可的处理副本只用于固定版本/覆盖核验，不构成 Workbench 持久原文阅读或默认归档。长篇原文仅在目标 WeKnora 确有有权的对应来源文档及准确深链时跳转阅读；否则提供有权原系统定位或人工核对路径，不伪造来源文档。文件可上传不意味着格式已通过解析验证。首期格式、大小、语言/版式与时效规则须由材料/知识 owner 先定，扫描件及复杂表格是否纳入由目标环境实测决定。逐区块记录已覆盖/部分解析/未取得/排除及原因，保存页/段/表格锚点和附件未读清单；关键段落无法回原件、漏页漏表、超出已验证范围或时效不明时，只保留有权的最小待人工核对线索，不把片段当完整事实，也不生成可送审的正式知识候选。补证后需对固定原件重新核对覆盖与时效，模型推断或高置信度不能补全缺失来源。

原始材料不是正式知识，只能作为候选生成的依据。业务原文按权限和保留策略存放，不写入模型长期 Memory 或公开日志。

#### 2.1.1 嵌在原任务里的轻量摄取与纠错

首期入口不要求用户每天另开“整理知识”任务：会议结束处理纪要、查规则答疑、执行流程发现例外或收到实际消费反馈时，贡献者在授权的 Workbench 中复用当下材料/来源引用，补一条“这条规则适用什么范围”“这里已经过期”等短说明；只有明确进入正式知识创作/修订，或反馈分流后确定正式修订并通过服务端空间、来源/基线和动作授权，才打开独立 Creation Session，保留原任务/来源引用、捕获时间、team/asset-space、敏感等级与责任人。没有授权的链接不抓取，聊天结论、下游完整 Prompt/业务原文和个人记忆不自动入库；不承诺自动接入会议、聊天或业务系统。

用户当天只需判断候选是否值得保留、能否定位来源，以及谁来确认；可先保存/暂停，待确认项进入工作台已有“待处理事项”，不要把未处理内容伪装成正式知识。发现已发布资产错误的消费者从结果/引用处提交最小 feedback reference（或由授权贡献者手工登记来源和问题），工作台核验资产空间、版本及权限后生成反馈候选；无法核验时标记待对账而非直接修改 WeKnora。见[工作台首页与待处理入口](09-工作台信息架构与核心对象.md#2-工作台首页与一级导航)与[第一用户/受益者的责任](04-角色、治理与运营机制.md#首期试点的三类核心角色)。

### 2.2 Agent 梳理

Agent 只对已获权且可按固定原件版本核对的范围做结构化梳理，至少区分事实、决策、规则/定义、行动项、争议、冲突和待确认事项。每一条候选都要带原文定位或来源引用；覆盖缺口和时间不明的内容仅列「待人工核对」线索，关键内容未补齐并重验前不可成为可送审的正式知识候选。解析覆盖核验不等于业务事实核证；模型推断必须标为推断，不能伪装成原文事实。

### 2.3 讨论与确认

用户可以逐条接受、修改、合并、拆分或拒绝候选。针对具体条目与草稿修订的有权评论先由 Workbench 独立持久保存；仅在目标 DSH 实测提供可核的评论/turn/持久回复关联及成功终态后，才能按当前草稿版本条件创建新的待核稿修订，迟到或重复的旧回复不得覆盖新稿。若宿主能力不可用，保留评论及人工改写待核稿，不将本地预置回复或 `accepted` 当成原生回复完成。Agent 可以解释抽取依据、提出更清楚的表达并提醒冲突，但不能替用户完成事实确认。

确认界面至少展示候选内容、原文证据、Agent 推断、用户差异、适用范围、例外、owner、steward 和复核日期。

日常小修订沿用同一确认路径：第一用户/贡献者对照原文接受、修改或拒绝，领域 steward 对事实、范围、例外、敏感等级及下次复核负责；过期、冲突、无证据或涉及权限变更的条目保留待确认/复核，不因输入短、重复出现或 Agent 高置信度而跳过人工审查。可聚合同一知识的重复提问与问题线索以减少搬运，但须保留各自来源和差异，遇到同资产并行草稿先核对 base revision 并人工合并。Skill 相关的步骤/契约/测试由 Skill owner 判断，不由知识 steward 代替；审核人仍对相应发布负责。

### 2.4 提交和索引

```text
Knowledge Draft
  → schema/source/ACL 校验
  → Git branch/commit/MR
  → CI + steward review
  → protected main merge
  → Git merge event（验签、去重、落库）
  → Workbench outbox operation
  → persistent worker 读取 merge commit
  → WeKnora ingest
  → index/Wiki document/version/source/ACL read-back
  → 检索冒烟验证
  → published knowledge
```

Webhook 或 CI 事件只说明 Git 中发生了合并，不代表索引成功。Worker 必须从 merge commit 读取 canonical 内容，不信任 webhook 直接携带的正文；重复事件、旧 SHA、乱序和 provider 超时必须由幂等与对账处理。只有 WeKnora 读回指定 `knowledge_id`、`version`、`source_commit`、`repo_path`、`asset_space_id` 和 ACL，并通过检索验证后，才能进入 `published`。

这条轻量路径只缩短**发现问题 → 留候选 → 找回待处理**的操作，不改 Git protected main、CI、steward/reviewer 批准或 index/read-back 门禁。已批准版本才可作为下游带来源、范围和版本的知识引用；原文、草稿、WeKnora Wiki 页面或分块的直接编辑不能作为本项目的 Git 双向同步与批准发布证据。新版待验证时保持旧版状态可见，对已知过期/错误引用按 steward 决策提示复核或停止使用并对账，不隐式切换到未经审核的内容。WeKnora 的更新接口与同步能力需按目标环境另行验证，不能推定已有集成；相关边界见[更新的 WeKnora 调研](../../../研究/产品/知识库/tencent-weknora.md#51-wiki索引与-git-原稿的一致性)。

## 3. 生产线二：工作流到 Skill

### 3.1 进入 Skill 创作会话

用户在「打磨可复用的技能」核证有权候选或旧版，明确决定正式创作/修订且服务端验证空间、来源/基线和动作权限后，平台才创建独立的 `Skill Creation Session` 和 `Workflow Draft`。创建后可描述工作流、提交获准 SOP/模板或历史产物；已分流的 Feedback Candidate 仅在正式修订决定和授权后关联新会话。沿用旧版或回宿主任务均不建会话。Agent 的追问、建模、Skill 生成和测试都必须绑定当前 `session_id` 和 `draft_revision_id`。

### 3.2 描述工作方式

用户在 Skill 创作会话中用自然语言描述触发时机、输入、步骤、判断、例外、工具需求、确需时的知识查询、查不到时向用户核实的路径、输出和成功标准。

### 3.3 Agent 追问和建模

Agent 主动发现输入校验、输出结构、步骤依赖、边界条件、建议与执行的区别、按需知识查询及零结果/无权/失效时用户核实、工具需求、人工确认点和测试构造缺口。工作台将结果保存为 Workflow Draft。Workflow 是业务过程模型，不等同于最终 Skill。

### 3.4 生成 Skill 包

Skill 包必须生成到当前 `asset_repository` repository root 下的 canonical path：

```text
skills/<domain>/<name>/
├── SKILL.md                 # 用途、边界、步骤、输入输出、依赖
├── skill.yaml               # id、版本、owner、风险、effects、权限需求
├── contract/                # input/output 和 effects 契约
│   ├── input.schema.json
│   ├── output.schema.json
│   └── effects.yaml
├── scripts/                 # 可选的确定性处理脚本
├── references/              # 可选模板、规则和示例
├── tests/
│   ├── golden/              # 代表性样例和期望结果
│   ├── boundary/            # 缺失、超范围和歧义输入
│   ├── regression/          # 历史失败和人工纠正
│   └── security/            # 越权、敏感数据和提示注入
├── dependencies.lock
└── CHANGELOG.md
```

`skills/<domain>/<name>/` 是 Git canonical source 路径；SkillHub 或 DSH 的外部 package layout 可以不同，但 package manifest 必须记录 `asset_repository_id`、source repository、source path 和 approved merge commit。实际 loader 字段以目标 SkillHub/DSH 能力验证结果为准，不能把尚未验证的约定当成集成事实。

### 3.5 样例试跑和评测

用户将真实但已脱敏的样例放入测试区，查看输入、输出、知识引用、工具需求声明、期望与实际差异、失败原因、脚本/契约/权限门禁和版本比较。试跑只产生评测结果，不自动发布，也不会把样例中的新事实直接写成正式知识。

### 3.6 提交和发布

```text
Skill Draft
  → input/output/schema 校验
  → permission/effects/security 校验
  → golden/boundary/regression/security 测试
  → 用户确认
  → Git branch/commit/MR
  → review + CI（合并前仍审核中）
  → canonical protected main 经审核合并（Skill 已发布）
  → 从 merge commit 打包
  → immutable package digest
  → SkillHub release/version/digest 真实读回（若选用）；否则记录受控管理员固定包 fallback 或经 ADR 批准的等价 Registry
  → 已批准的固定 package digest
  → TeamAI distribution/read-back（如启用）
  → DSH handoff/load 由下游验证
```

Skill 的 `已发布` 仅由 canonical Git 受保护 main 上经 MR/CI/指定审核人批准的 merge commit 确认；MR、CI 或审核批准但未合并时仍为 `审核中`。打包、管理员固定包 fallback 均不改变该状态。SkillHub 仅在选用且 release/version/digest 真实读回后，才提供该 Registry 自身的 release 证据；未选用时以已审 Git/CI 固定包和明确标记的管理员 fallback（或经 ADR 批准的等价 Registry）留证，不冒称 SkillHub `released`。Registry 失败/未知不抹除已核实的 Git 已发布事实，但不得展示 Registry 发布成功或放行要求该 release 的后续分发。TeamAI 只同步与已批准固定包对应的团队仓库版本，不将默认 `pull` 当作 digest pin，也不重新解析未经审核的 `latest` 或从另一份源码构建。TeamAI 安装成功不等于 DSH 已加载，必须分别保留目标、installed revision、文件 digest、profile 和 loaded read-back；任一环节不可用时保留可对账的 fallback/blocked 状态，不得发生版本漂移。

### 3.7 分发与同步线（Skill/Agent）

```text
已批准的固定 package digest（SkillHub 真实 release、受控管理员 fallback 或经 ADR 批准的等价 Registry）
  → 经审核映射的 TeamAI 团队仓库 commit（如启用）
  → 目标 workspace 的会话边界自动 pull 或有权成员主动 pull（均须先 init；能力待目标验证）
  → 目标文件清单/摘要与源包 digest 的映射读回
  → DSH handoff
  → DSH profile/loaded digest/session read-back
  → run may start
```

TeamAI 是可选的目标同步适配器，不是 Git 审批、Skill 质量门禁或 Registry release 的替代品；同步仓库 commit 不天然锁定源包 digest，需建立并读回映射。DSH handoff request 也不等于 loaded；在 loaded digest/profile 未读回前，工作台只能显示 `handoff_pending` 或 `unknown`，不能报告可运行。TeamAI 或 DSH 不可用时，管理员可按同一个固定 digest 进行受控目标安装，并保留目标、profile、文件摘要和加载读回证据，不冒称 TeamAI 分发完成。


本项目对下游只交接**已批准资产的引用和完整性信息**，不交接一个自建运行时。最小交接记录包括：

```yaml
source_commit: <approved-git-commit>
asset_type: knowledge | skill
asset_id: <asset-id>
asset_version: <semantic-or-domain-version>
package_digest: sha256:...
skillhub_release_id: <release-id>
distribution_target: <teamai-workspace-or-admin-target>
teamai_installed_revision: <target-revision>
knowledge_dependencies: []
required_capabilities: []
compatible_targets: []
distribution_status: published | fallback | unknown
handoff_target: <dsh-provider-or-admin-path>
dsh_handoff_id: <handoff-id>
dsh_profile_version: <profile-version>
dsh_loaded_digest: <loaded-digest>
```

交接状态只能说明固定版本是否已被目标适配器或管理员处理并读回，不能替代 Harness 的 `loaded`、`running` 或 `succeeded`。目标 Harness 环境应自行验证 discovery/load，并返回可关联的 feedback reference。

## 5. 反馈分流

发布后的实际消费由下游 Harness 或业务系统产生最小消费事件和结果引用：

```text
Skill 按 pinned digest 加载
  → 实际开始一次逻辑调用
  → 消费事件（invocation_id/attempt_no/version/digest）
  → 技术、契约或业务结果
  → 用户/业务 feedback reference
  → 工作台校验来源、team/asset-space、版本/digest 和幂等性
  → 调用、使用人数、成功和 Badcase 聚合
  → triage
  → 知识复核 / Skill 回归 / 分发故障 / 平台协作
  → 独立 Feedback Candidate（受理、去重、补证、分流或关闭）
  → 仅确需正式知识/Skill 创作或修订且经服务端授权时，关联新 Creation Session
```

调用次数按 `invocation_id` 去重，重试按 `attempt_no` 单独统计；使用人数只统计经过验证的人类主体，服务账号和自动任务单独统计。技术完成、契约成功和业务成功分开记录，unknown 和无业务结果不能推断为成功。Badcase 区分报告数、确认数和受影响调用数，旧版本指标不能被新版本或 `latest` 覆盖。工作台不接收完整 Prompt、输出、业务原文或 Tool Call trace，只保存可审计的最小引用和聚合指标。

```text
Harness/业务系统反馈
  ├─ 事实、范围、来源或引用错误 → 知识复核候选
  ├─ 步骤、契约、输出或质量错误 → Skill 回归/修订候选
  ├─ 工作流步骤、人工节点或完成条件错误 → Workflow 修订候选
  ├─ 发布、安装、版本漂移或读回错误 → 分发故障候选
  └─ Harness/provider/业务运行问题 → 下游平台协作任务
```

反馈只作为候选或任务，不直接覆盖正式资产。模型可以整理反馈，人和 CI 决定是否进入正式生产线。

### 5.1 日常反馈 → 周期复核 → 下次使用

轻量闭环不额外要求消费者维护知识库：一线人员在原任务中发现“找不到、引用不适用、结果不对”时，保留任务侧结果引用、所见资产 ID/版本、问题分类及必要的脱敏证据；能继续完成任务的先人工处理业务结果，不能让反馈入口代替 Harness 的运行时批准或业务系统记录。下游若尚无真实事件接口，可在授权范围内由人登记引用并注明来源/不可验证项，不能把手工记录报成真实 Harness 消费或业务成功。

| 阶段 | 在既有工作中的小动作 | 下一步与可见证据 |
|---|---|---|
| 当次任务（消费/发现） | 第一受益者查已发布知识的来源、适用范围和版本，或使用经下游验证的固定 Skill；发现差异即留下最小引用 | 工作台按实际 asset-space/版本关联反馈，业务结果仍由 Harness/业务系统或结果 Owner 确认；无结果记 `unknown` |
| 当天/下次进入工作台（收集/确认） | 第一用户从“待处理事项”打开候选，对照纪要、规则或脱敏样例确认来源、范围和冲突；不够确定就保留待确认 | Knowledge Draft/Workflow Draft 的差异、原文定位、确认人和待复核日期；重复反馈可合并但保留受影响调用引用 |
| 每周复核（分流/精炼） | steward/Skill owner 按[治理中的每周复核队列](04-角色、治理与运营机制.md#每周复核队列)处理过期、引用失效、契约或回归；平台/分发 owner 处理索引/版本故障 | 责任人、原因、复核结论；需要修订时从 Feedback Candidate fork 新 Creation Session，拒绝/延期也留原因与复审时间 |
| 审核发布与下次使用（验证） | 贡献者提交改动，审核人审查，CI/Provider 读回后再把已批准版本交还给同类任务；原消费者可对下一次真实任务报告是否仍需查找或返工 | Git MR/merge commit、WeKnora document/version/source/ACL + 检索验证或 Skill tests/release/digest/handoff；下游独立消费/结果引用与新 Badcase 关联版本 |

这是一条有条件的正反馈路径，而非自动自我训练：首先用户看到准确可引用的内容或可审查的候选，之后看到错误有人处理并有版本化证据，最后才能用同类任务与人工基线比较查找、首次成功、返工和处理时长。按[首期基线验证假设](01-问题、用户与产品范围.md#41-先记录再检验的假设)记录第一用户维护/审核负担与第一受益者收益；低覆盖率、小样本、未验证集成或 `unknown` 时只报告可观察到的阶段，不声称效益已经实现。每月由业务结果 Owner 与第一推动者结合[三层指标](01-问题、用户与产品范围.md#341-指标分层)决定继续、调整或停止，而不以发布数或加载数替代价值。

## 6. 责任与证据

| 步骤 | 责任人 | 用户可见产物 | 最低证据 |
|---|---|---|---|
| 接收材料 | 贡献者 | 原始材料卡片 | 来源、捕获人、时间 |
| Agent 梳理 | 模型/平台 | 候选卡片 | 原文引用、生成记录 |
| 知识确认 | 贡献者/steward | 已确认知识草稿 | 修改差异、确认人、待解决项 |
| Workflow 建模 | 贡献者/Skill owner | 工作流草稿 | 输入、步骤、判断、例外、成功标准 |
| Skill 生成 | 模型/平台 | Skill 文件包 | schema、依赖、生成记录 |
| 试跑评测 | 用户/CI | 测试结果 | 样例、版本、输出差异、门禁 |
| 提交审核 | owner/reviewer | MR/release | commit、approval、理由 |
| 索引/发布 | worker/provider | WeKnora/SkillHub 状态 | receipt、版本、digest、读回 |
| 下游交接 | 分发/运行 owner | handoff record | target、package digest、状态 |
| 反馈 | Harness 使用者/owner | 修订候选或协作任务 | 版本引用、问题分类和必要证据 |

## 7. 非程序员体验

业务人员只需要理解：

```text
放入材料 → 讨论确认 → 提交
描述工作 → 试跑修改 → 发布
发布交接 → 在 DeepSeek Harness 会话中消费 → 反馈
```

Git、commit、MR、pipeline、index job、package digest 和 handoff record 可以查看，但不要求业务人员手工操作。Workspace、Session、工具调用和运行时人工批准由 DeepSeek Harness 界面负责。
