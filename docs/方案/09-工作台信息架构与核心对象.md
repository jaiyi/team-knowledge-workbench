# 工作台信息架构与核心对象

> 本文是 Team Knowledge Workbench 信息架构的权威定义。它规定用户从哪里开始、一次创作如何推进，以及 Creation Session、草稿、正式资产、发布和下游 Harness 如何分层。

## 1. 产品形态

工作台不是 Git、WeKnora、SkillHub 和 DeepSeek Harness 的管理后台拼盘，也不是发布后的任务运行器。它以五个用户目标入口组织日常工作；**需要正式创作或修订时**，以创作会话（Creation Session）作为可恢复的协作工作单元，并作为可被多个团队安装的 `team-knowledge-workbench` DSH Desktop Workbench Plugin 交付：

正式创作或修订时的会话路径（查阅、反馈和核证不强制走这条路径）：

```text
用户从材料、Skill 候选或反馈中确认需要正式创作或修订
  → 创建一个独立的创作会话
  → Agent 梳理、追问、起草和试跑
  → 用户讨论、修改和确认
  → 平台提交、审核、发布并记录交接证据
```

每个团队的 Workbench 首次进入需要完成或读取服务端的资产空间绑定。拟通过经目标验证的 DSH Desktop 身份上下文进入；服务端交换机制必须先完成身份与撤权 Spike，映射到 `principal_id`、团队成员和角色后才决定可访问的 Git/WeKnora/候选 Skill Registry/分发资源；不以公司统一身份系统接入作为 P0 前提。普通创作者只看到当前授权的 `team_id`/`asset_space_id`、知识目录和可操作的会话；管理员才可配置 Git repository、WeKnora space、taxonomy、steward、review policy、distribution target 和服务连接。不同团队安装同一 Workbench 时，Creation Session、Draft、source ref、发布 job 和审计不得串线。

## 2. 工作台首页与一级导航

现行[产品设计](../产品/界面功能设计/README.md)以用户目标而非下游系统组织五个一级入口。默认首页「我的工作台」先提供个人 Inbox 主动暂存入口，再呈现本人有权的使用、待办和反馈，不强制启动创作；下面的 Creation Session、资产与发布等是入口内的**对象和子视图**，不是并列一级导航。旧版两个创建按钮和四项一级路由的线框示意仅作为创作能力的历史设计参考，现行导航与[工程映射](11-开发工程设计与集成基线.md#2-五入口到工程能力的映射)为准：

```text
Team Knowledge Workbench
├─ 我的工作台（默认；个人 Inbox、本人使用与反馈、待办和回访）
├─ 提炼知识&经验（导入来源 → 事实梳理 → 经验总结 → 加入知识库 → 可跳过的优化已有 Skill）
├─ 打磨可复用的技能（页内：引入 Skill → 自动校验 → 具体修改与复测 → 审核提交）
├─ 连接业务数据源（团队可发现 / 待申请；依真实授权和 Provider 契约开放）
└─ 团队业务资产大盘（最新进展 / 全局概览 / 智能诊断；详情内看正式版本及发布证据）
```

从材料、Skill 候选、现有正式版本或已分流反馈开始**需要提交的创作**，才进入相应独立的 Knowledge/Skill Creation Session；只查看、核证、报告疑点或继续 DSH 原生对话不必创建新资产；尚未建立会话的浏览/核证状态由入口页持有，后端按身份和资源重鉴权，不能假称已有正式草稿或可恢复会话。页面中必须标明来源/当前身份权限、真实可用与待验证能力的差别。

**个人暂存 Inbox（默认入口内，不是第六入口）**：`InboxItem` 是独立于 Creation Session、Draft、Source Material 与 Feedback Candidate 的个人私有保存对象。用户可将本人有权的来源链接/定位或少量笔记暂存以便稍后整理；保存、回访和导航都不触发对该链接的服务端抓取/解析。服务端在 PostgreSQL 保存私有条目、受控来源引用及状态/时间，只有必要且经来源/用途/敏感级别授权的内容才另放加密对象存储，PG 持有对象引用而非默认保存完整业务原文。保存条目只表示个人收件成功，不自动调用 Agent、建 Session/Draft、提交 Git、索引 WeKnora、创建反馈或触发 DSH。打开「提炼知识&经验」仅显示经当前身份/来源重鉴权的待核交接提示，不写团队对象；用户另行选择具体内容、来源、分享范围、目标空间和用途并获授权时，可提交最小团队待核候选并取得独立 `submission_id`/受理回执，**仍不创建 Session/Draft 或正式资产**。知识入口如需对链接内容做只读梳理，须成员在该入口明确选用并由服务端重新核来源/用途/空间及受限获取门；获准临时解析也不等于团队候选受理或建会话。只有随后明确决定正式知识新建/修订时，重新核来源 ACL、用途、目标资产空间、基线与动作权限，获准后按 2.1 创建会话；取消或失败仍留在个人 Inbox，个人条目删除不自动撤销另行获准的团队候选。未来 IM 来源仅在单独获批的身份/消息权限、同意与留存契约经验证后接入，首期不自动收群消息。详细权限、留存及接口见[11 第 4–5 节](11-开发工程设计与集成基线.md#4-身份权限与团队隔离)，待证实风险见[12](12-未决工程风险与决策记录.md#二个人-inbox-新增风险与决策门不冲销以上九项)。

**管理员子页（不改变五入口）**：当前空间有权管理员可从空间上下文进入「团队空间与连接」，查看/变更 Git 仓库绑定、WeKnora space、审批策略、可选 Skill 注册/分发目标及各项真实读回；无权成员只看到与自己任务有关的阻断原因和申请/联系路径。插件安装后的普通成员不填写每台机器各自的 Provider 地址或 Token，PostgreSQL/对象存储的部署配置由平台运维集中管理。具体初装、连接检查、密钥和配置变更门禁见[工程设计 3.1](11-开发工程设计与集成基线.md#31-多人安装后的配置与管理员入口拟议)；当前静态原型没有管理员子页，这是一项待开发设计而非已有交互。

### 2.1 创作会话的两类创建动作（不等于首页一级入口）

从材料提炼出有正式知识去向时创建 Knowledge Session；从现有或外部获准 Skill 候选进入深层修订、或从稳定工作方式进入 Skill 创作时创建 Skill Session。它们是会话类型而非要求首页只有两个按钮。知识会话需绑定当前团队资产空间和规范目录上下文；只读查阅或核证先在入口内完成，不提前创建会话：

1. 用户从现行材料、Skill、正式资产版本或反馈入口决定创建/修订；只读查阅不触发创建；
2. 工作台根据服务端授权创建或读取当前 `team_id`、`asset_space_id` 和 Git/WeKnora binding；
3. 知识会话选择 taxonomy/domain/topic，预览 `knowledge/<domain>/<topic>/<knowledge-slug>/` 目标路径；
4. 服务端核过空间、来源/基线和动作权限后，才创建对应类型的 Draft 和 Creation Session；
5. 用户立即进入该会话；
6. 会话内承载材料、Agent 对话、结构化草稿、确认、测试、提交和发布。

启动动作必须返回 `session_id`、`draft_id` 和当前阶段，避免用户创建后还要在多个系统页面中寻找上下文。

### 2.2 最近创作

显示用户最近参与的知识和 Skill Creation Session，包括标题、类型、当前阶段、会话状态、最近修改、待处理事项和失败/未知操作。点击后回到会话原位置，而不是跳到孤立的系统状态页。

### 2.3 待处理事项

按会话聚合待确认事实、待补充边界、待解决冲突、待审核、待重试、待人工对账和待处理反馈。每个事项都链接回产生它的会话和草稿版本。

### 2.4 资产与发布

用于查看已经脱离创作会话的正式资产、版本和发布记录：

- 已发布知识（WeKnora 授权读回）和已发布 Skill（经审合入 canonical Git protected main；下游步骤另列）；
- Git/MR/CI、WeKnora、SkillHub 和 handoff 的证据；
- 发布失败、未知、对账和回滚记录；
- 独立受理的 Feedback Candidate，以及仅在正式创作/修订决定并重新获授权后关联的新会话。

它是查阅和治理入口，不替代创作会话，也不展示或控制完整 Harness run。

## 3. Creation Session

### 3.1 定义和边界

Creation Session 是一次围绕特定目标的、可暂停和可审计的创作上下文。它不是正式 Knowledge 或 Skill asset，不是 Git branch 的同义词，也不是 DeepSeek Harness Session。

每个会话必须隔离：

- Agent 对话和上下文；
- source material 或 workflow input；
- draft、用户修改和待确认项；
- 测试 fixture 与 evaluation result；
- pending approval、发布操作和异步 job；
- 回调、错误、审计和外部引用。

多个会话可以只读引用同一来源材料或正式资产，但不能共享可变草稿和待处理操作。

### 3.2 会话类型与阶段

`phase` 是由会话类型定义的**底层处理阶段**，不是现行入口页的展示步骤；材料页的「导入来源／事实梳理／经验总结／加入知识库／优化已有 Skill（可跳过）」和 Skill 页的「引入 Skill／自动校验／具体修改与复测／审核提交」由第 2 节与产品设计定义。一个导航步骤可以只读核证、不创建会话；建会话后才将操作映射到下述 `phase`/资产状态。

知识创作会话：

```text
材料 → 梳理 → 确认 → 提交 → 发布
```

Skill 创作会话：

```text
描述 → 建模 → 生成 → 测试 → 发布
```

阶段是用户可见的协作进度，不等同于正式资产生命周期。会话进入“发布”阶段也不代表 WeKnora、SkillHub 或 Harness 已经成功。

### 3.3 会话生命周期

```text
active ──→ paused ──→ active
   │          │
   ├──────────┴──→ archived
   ├─────────────→ forked
   └─────────────→ read_only
```

- `active`：允许会话成员编辑和发起受授权动作；
- `paused`：保留上下文和草稿，不启动新的生成或发布动作；
- `archived`：不再编辑，但保留审计、版本和恢复依据；
- `forked`：从当前草稿或正式版本创建新的独立会话；
- `read_only`：可查看和导出证据，不可改变草稿或发起外部写入。

恢复、分叉和重试都必须使用新的操作幂等键，并先读取当前会话状态，不能重复创建 MR、release 或 index job。

### 3.4 会话最小字段

```yaml
session_id: cs_<id>
workspace_id: <workspace>
team_id: <server-resolved-team>
asset_space_id: <server-resolved-space>
session_type: knowledge | skill
owner_id: <user>
collaborator_ids: []
source_refs: []
base_asset_id: <optional>
base_revision: <optional>
draft_id: <id>
draft_revision_id: <id>
phase: material | organize | confirm | submit | publish # knowledge only
# skill phase: describe | model | generate | test | publish
status: active | paused | archived | read_only
state_version: 12
correlation_id: <id>
created_at: <timestamp>
updated_at: <timestamp>
archived_at: <optional>
```

此处的 `phase` 是会话类型对应的用户可见阶段示意，`team_id`/`asset_space_id` 必须由服务端鉴权绑定，不接受客户端自行指定为权限事实；具体数据字典及状态迁移以[控制面状态模型](06-数据、状态与可追溯性.md)为准。`forked` 表示产生新会话的动作/关系，不能作为旧会话脱离其当前生命周期的替代状态。

## 4. 会话内动作与责任链

每个会话动作都显示当前团队和资产空间，并在提交、确认、审核和发布时展示责任人及执行身份：`created_by`、`confirmed_by`、`approved_by`、`released_by` 是真实 DSH 用户或团队角色；`executed_by`、`service_identity_id` 是实际调用 Git、WeKnora、SkillHub 或 TeamLab 的受控服务身份。客户端提交的 owner、approver、publisher 或 `team_id` 只是意图，服务端必须从认证上下文和 PostgreSQL 的成员/角色绑定重新校验。

发布证据须区分 `approved`、`publishing`、知识 `published` 或 Skill `released`、`handoff_verified`；`loaded`、`running` 仅展示有下游独立读回/事件来源的状态，**不是工作台自身的发布状态**。Workbench 安装、市场启用或 DSH ownership metadata 不得被展示为正式资产发布；外部调用半成功、数据库不可用、Worker 重启或回调缺失时显示 `unknown`、`degraded` 或 `reconciling`，并提供人工对账入口。

## 5. 会话内界面

每个 Creation Session 使用同一套结构，减少用户在不同 view 之间跳转：

1. **对话区**：Agent 追问、解释、发现冲突和提出修改；
2. **工作区**：知识候选、Workflow Draft 或 Skill 文件树；
3. **证据区**：原文引用、测试结果、差异、版本和 provider 状态；
4. **动作区**：确认、试跑、保存、提交、发布、重试、对账、暂停和归档。

Agent 每次生成或修改都必须说明变更、依据、事实与推断的区别、待确认项和下一步。不得在聊天中静默覆盖整个草稿或正式资产。

## 6. 知识创作会话

“从获准材料正式创建/修订知识”经服务端核空间、来源/基线与动作授权后，才创建 `Knowledge Draft + Knowledge Creation Session`；只读核对不创建。随后用户在同一会话内完成：

```text
上传/引用材料
  → 梳理事实、决策、规则、行动项、争议和冲突
  → 逐条确认来源、范围、例外、owner 和 steward
  → 预览变更并提交 Git/MR/CI
  → 审核通过后同步 WeKnora 并读回索引
```

原始材料、模型推断、待确认内容和正式知识始终分开。用户可以从会话中创建多个知识候选，但每个候选都必须有来源和确认记录，并预览规范 Git path。默认知识目录为：

```text
knowledge/<domain>/<topic>/<knowledge-slug>/
├── KNOWLEDGE.md
├── metadata.yaml
├── sources.yaml
└── CHANGELOG.md
```

提交前必须展示 Git↔WeKnora mapping；WeKnora 物理索引可以不同，但其 document metadata 至少能回到 `knowledge_id`、`repo_path`、version、source commit、sensitivity 和 ACL。

## 7. Skill 创作会话

“从指定候选/版本创建或修订 Skill”只有在核证后明确决定正式创作，且服务端通过来源、基线和动作授权时才创建 `Workflow Draft + Skill Creation Session`，随后在同一会话内完成：

```text
描述任务
  → 追问输入、步骤、判断、例外、输出和成功标准
  → 生成 Skill 文件包、契约、脚本/资源和测试集
  → 用脱敏样例试跑、比较和修订
  → 提交 Git MR/CI、指定审核人批准及 protected merge
  → 从固定 commit 构建 package/digest；选用 Registry 则核 release，未选则标管理员固定包 fallback
  → 目标安装及 DSH 加载分别读回，再生成 handoff record
```

测试结果回到当前 Skill 会话；下游反馈先成为独立候选，只有正式修订决定并通过服务端授权后才关联新会话。它们不能直接改写已发布版本。

## 8. 并行会话与同资产冲突

一个用户可以同时打开多个知识会话和多个 Skill 会话，知识与 Skill 会话也可以并行。每个会话拥有独立上下文和异步操作；旧会话或旧回调不能覆盖新状态。

多个会话可以基于同一正式资产修订，但必须记录 `base_asset_id` 和 `base_revision`：

```text
Session A base_revision = 7
Session B base_revision = 7
Session A 发布 revision 8
Session B 提交时发现当前 revision = 8
  → 阻止静默覆盖
  → 标记 revision_conflict
  → 展示双方差异
  → 由 owner/steward 人工合并或重新 fork
```

冲突解决后要产生新的 draft revision 和审计记录；不能通过最后写入者获胜解决。

## 9. 核心对象层级

```text
Workspace
└─ Creation Session
   ├─ Source Material / Workflow Draft
   ├─ Knowledge Draft / Skill Draft
   ├─ Draft Revision
   ├─ Test Case / Evaluation Result
   ├─ Approval / Operation / Job
   └─ Release / Handoff Record

Formal Asset
└─ Asset Revision
   └─ Release
      └─ Downstream handoff reference

Feedback Candidate
└─ new Creation Session（仅明确正式修订并获授权时）

InboxItem（PG 个人私有；独立于上述对象；可选加密对象引用）
```

| 对象 | 说明 | 权威写入面 |
|---|---|---|
| Workspace | 用户、项目和资产的隔离边界 | 工作台治理配置 |
| Creation Session | 一次知识或 Skill 创作上下文 | PostgreSQL 工作台控制面 |
| Source Material | 会议纪要、文件、文本或授权链接 | 加密对象存储/来源系统，数据库保存引用 |
| Draft / Draft Revision | 会话内可编辑候选及其修订 | PostgreSQL 工作台控制面，正式提交后进入 Git |
| Asset Revision | 正式资产的不可变修订 | Git + MR/CI/人工审核 |
| Knowledge/Skill Release | 固定版本的资产类型专属发布证据：知识为受审 Git 版本及 WeKnora 授权检索读回，Skill 为经核验的受审 canonical Git merge；包 digest、选用时 Registry release 与目标交接另记 | 工作台正式发布记录引用 Git/WeKnora 权威证据；Registry/目标读回仅证明各自后续阶段 |
| Handoff Record | 批准版本交给下游适配器或管理员的引用 | 工作台与目标 provider 读回 |
| InboxItem | 个人私有暂存的来源定位/笔记，打开知识页不写团队对象；明确获准分享时形成独立 submission 候选，只有其后正式创作决定且重鉴权才可关联新会话；不等于团队来源、正式资产或反馈 | PostgreSQL 私有控制面，必要内容另存获准加密对象存储 |
| Inbox Submission | 本人按具体内容/范围/用途主动提交的团队待核最小候选，以独立 `submission_id` 和授权回执保存；不等于 Session/Draft、Feedback Candidate、Git 或 WeKnora 知识 | PostgreSQL 团队空间待核控制面，按来源和目标空间授权 |
| Feedback Candidate | 下游反馈形成的独立待核候选；可受理、分流、关闭和回访，只有确认需正式创作/修订时才关联新会话 | 工作台控制面 |
| Consumption Summary | 按 team/asset-space、Skill/version/digest 聚合的调用、活跃用户、成功、unknown 和 Badcase 指标 | 工作台分析层，来源是下游最小消费事件 |
| Consumption Event Reference | 单次逻辑调用、尝试、结果和反馈的最小可追溯引用 | Harness/业务系统产生，工作台校验后保存 |

## 10. 明确不属于本工作台

以下对象由 DeepSeek Harness 或业务系统拥有，工作台只保存必要的外部引用：

- Harness Workspace/Session；
- Task、Run、Step、Tool Call 和 runtime human gate；
- Artifact、Outcome、恢复、运行时重试和完整运行时间线；
- Secret 注入、工具授权和实际业务写入。

工作台可以展示按 Skill/version/digest 聚合的消费摘要、使用人数、技术/契约/业务成功和 Badcase，但不提供完整运行时下钻；原始运行事实和完整 trace 仍由 Harness 或业务系统拥有。

`approved`（审核批准）、Skill `已发布`（canonical Git protected main 经审 merge）、Knowledge `published`（WeKnora 授权读回/检索）、`registry_released`（选用时）、`handoff_verified`、`loaded`、`running` 和 `succeeded` 必须分开存储和展示。工作台的发布成功不能表示 Harness runtime 成功；管理员固定包回执不是 Skill 已发布。

## 11. 一致性原则

- 需要创建或深层修订正式知识/Skill 时，分别创建独立的 Creation Session；五个导航入口本身不自动创建会话；
- 会话、草稿、资产修订、发布、交接和 Harness Session 使用不同标识和生命周期；
- 同一正式资产的并行编辑必须做 base revision 检查；
- 所有提交、索引、发布、交接、恢复和重试都要幂等并读回实际结果；
- 反馈先生成独立候选与回访记录，可核验、去重、分流、补证或有理由关闭；只有确认需要正式知识/Skill 新建或修订且通过来源、基线与权限核验时，才关联新会话，不直接覆盖正式资产；
- 首页优先展示可行动的下一步，底层系统状态作为证据而非主导航；
- 消费摘要必须展示时间窗口、Skill/version/digest、数据覆盖率和 unknown，不把无反馈显示为无问题。

## 12. 屏幕规格与低保真线框（历史会话子视图示意）

以下线框中的「工作台/知识创作会话/Skill 创作会话/资产与发布」和两个创建按钮是**旧版路由与首页方案**，不再定义一级导航和现行默认首页。现行五入口与子视图以第 2 节、[产品逐页设计](../产品/界面功能设计/README.md)及[工程映射](11-开发工程设计与集成基线.md#2-五入口到工程能力的映射)为准。仍保留以下材料的会话隔离、页面信息层级、鉴权、状态、可行动下一步和真实读回规格；正式实现先把会话列表/审核证据/资产版本/反馈队列放进正确的现行入口，再据目标宿主做视觉设计。这些示意不是前端实现、像素级视觉稿或 API 契约，所有数量和状态均来自当前授权范围内的服务端事实；示例文字不代表真实数据。

### 12.3 创作工作区：知识与 Skill 共用骨架

```text
+--------------------------------------------------------------------------------+
| 知识/Skill 会话标题 | 当前团队/资产空间 | 会话 ID | 草稿修订 | 保存状态 |
| 阶段：材料 > 梳理 > 确认 > 提交 > 发布   (Skill：描述 > 建模 > 生成 > 测试 > 发布)|
| 状态摘要：草稿待确认 / 提交审核中 / 发布读回中 ...；下一步：谁、为何 |
+----------------------+--------------------------------+------------------------+
| 对话与追问           | 结构化工作区                   | 证据与待办             |
| Agent 问题及建议     | 当前候选 / Workflow / Skill 包  | 来源定位 / 事实或推断  |
| 用户回复与变更摘要   | 可编辑字段、差异、版本         | 冲突 / 测试 / 审核/读回|
|                     | 选中项与待确认数               | 操作绑定修订 / 当前修订 |
+----------------------+--------------------------------+------------------------+
| [保存草稿] [暂停/恢复] [试跑(仅 Skill)] [确认选中项] [预览提交]     |
| 后续动作在通过门禁时才出现；失败/未知提供查看原因或对账入口           |
+--------------------------------------------------------------------------------+
```

- **进入/保存**：入口确定当前团队和资产空间；知识入口先选 taxonomy/domain/topic 并预览 `knowledge/<domain>/<topic>/<knowledge-slug>/`，Skill 入口创建 Workflow Draft。成功创建后直接返回同一会话里的 `session_id`、`draft_id`、阶段和当前修订；创建结果无法确认时不盲点重复创建，先查原操作/会话。区分“本地有未保存更改”“保存中”“已保存（修订/时间）”“保存失败（更改尚未保存）”；失败允许保留本地编辑并在重新读取会话修订后安全重试。阶段前进不等于发布成功。
- **知识工作区**：材料卡标记来源、定位、捕获人、时间、敏感等级及权限；候选按事实、决策、规则、行动项、争议/冲突和推断分组。选中一条同时看到原文证据、Agent 推断、用户改动差异、适用范围、例外、owner、steward、复核日期和“接受/修改/拆分/拒绝/待确认”。有权 steward 可对指定候选与草稿修订明确[限定适用范围]、[拒绝并说明理由]、[暂缓至复核时间]或[要求补充证据]，记录判断、来源及下一责任人；贡献者可提出意见，但不能冒用专家确认。拒绝/补证/暂缓在未解决前阻断该候选的当前修订提交，暂缓到期也不自动变成通过；每个候选独立处理，其他合格候选可按范围推进。无来源、事实冲突或未经有权者确认的内容保持待确认，不进入正式提交；一会话多个候选须分别展示目标 Git path/去重检查、修订和确认人。提交预览展示 canonical path、Git↔WeKnora mapping、敏感等级/ACL、最终变更和未解决项。
- **Skill 工作区**：左侧追问目标、触发、输入、步骤/判断、例外、输出和成功标准；中间在 Workflow Draft 与 Skill Draft（文件树/差异/契约）之间切换；右侧按需显示固定知识查询对象/版本及查不到时的用户核实提示、能力请求（不是权限授予）、脱敏样例、测试结果及人审待办。试跑显示当前草稿修订、期望/实际差异、失败原因、人工纠正与下一步；失败只使测试待修，不自动改正式 Skill。Skill schema、目录、门禁和发布细节以[10-Workflow 到 Skill 的生成、测试与发布](10-Workflow到Skill的生成、测试与发布.md)为准，此处只规定入口和可见信息。
- **修改归因**：Agent 每轮建议旁列“改了什么、依据何处、何者是推断、哪些仍需确认”，用户可逐项采纳或拒绝；保存产生新草稿修订并保留差异，不静默覆盖。专家拒绝、暂缓或补证决定绑定候选 ID、当时草稿修订、身份、理由及时间；新修订须重新处理受影响的确认，不沿用旧修订的通过/拒绝结论作为当前事实。审核、测试和发布证据分别标明操作绑定的草稿修订、已批准 merge commit/正式资产版本及当前草稿修订；审核后再次编辑不得把旧修订的通过或读回归功于当前修订。并行会话提交前对照正式 `base_revision`；若已变化，禁止提交，展示双方差异和“联系 owner/steward 合并”或“以新会话分叉”，解决后形成新修订。
- **动作门禁**：仅贡献者/owner 可确认自身负责的候选或提出提交；审核与发布由有权角色按策略执行。提交/重试前显示目标资产、草稿修订、当前检查结果和责任人；进入审核后仍可返回查看草稿，但任何改动都必须产生新修订并重新过相应门禁。外部操作进行中保留返回会话入口，禁止并发重复提交。

### 12.4 审核、发布与证据视图

同一会话的“预览提交/查看审核”与资产与发布中的“发布记录”指向同一条经授权的证据链：前者保留草稿和讨论，后者围绕正式版本及操作读回。审核者看到明确的“为何需要我审批”，贡献者看到等待谁；无权限者只看到允许查阅的状态和可联系的责任角色。

```text
+--------------------------------------------------------------------------------+
| 会话 K-12 / 知识候选 #3 | 草稿 r4 → 目标资产 v3 | [回到会话]          |
| 当前：待 steward 审核（不是已发布） | 下一步：王某复核范围和例外      |
+-------------------------------+------------------------------------------------+
| 审核前对照                    | 责任与门禁                                     |
| 原文引用 + 确认人/时间        | 贡献者、steward、审核者；实际 Git 执行身份    |
| 事实 / 推断 / 未确认           | 目录、ACL、差异、CI、测试及阻断项             |
| 草稿差异 + base revision      | [批准] [驳回并写明原因] [要求修改]（按权限）   |
+-------------------------------+------------------------------------------------+
| 证据时间线：提交请求 → Git MR/CI → 人审 → merge commit → provider 操作 |
|   知识：WeKnora document/version/source/path/ACL 读回 → 检索验证       |
|   Skill：package/source/digest → SkillHub release/version/digest 读回   |
|   后续：distribution/handoff → 目标确认/加载读回（如有，另列状态）      |
| 每一步：状态、责任人或服务身份、时间、版本/目标、证据链接、失败/未知原因|
+--------------------------------------------------------------------------------+
| [查看 MR/审核意见] [查看读回] [请求对账]（仅在对应状态及权限下）       |
+--------------------------------------------------------------------------------+
```

- “批准”需展示适用范围、差异、来源和门禁结论，由指定审核者经 Git MR/CI 与受保护分支策略确认并记录身份、时间和理由；`approved` 只说明审核批准，`publishing` 只说明相应异步外部步骤进行中。知识须 WeKnora 对指定版本/source/path/ACL 的读回及授权检索验证才能显示“已发布可检索”；Skill 经 MR/CI/指定审核人批准并核实合入 canonical Git protected main 后显示该不可变版本“已发布”，合并前（含已批准未合并）保持“审核中”；漏 event 或审核/合并归属未核实则显示“待对账/无法确认”，不得凭 webhook/打包/fallback 晋级。Skill package/digest、所选 Registry release/version/digest 读回（才显示该 Registry“已发布”）或管理员固定包 `fallback_only` 单列；fallback 不使 Skill 已发布，Registry 失败/未知不抹去已核实的 Git 发布事实。目标安装、DSH loaded 和实际消费各有独立读回；MR 合并不能替代知识及 Skill 下游事实，provider 接收或请求返回成功不能替代任一步的所需证据。插件安装状态另属 Workbench，不混入资产发布。
- `rejected` 展示驳回人、原因和被驳回修订；给贡献者“回到草稿修订”并要求修改后重走提交/审核，不能在原批准上改内容后直接发布。CI 或 provider `failed` 显示失败步骤、证据与故障责任人；按角色选择修订、联系平台 owner 或在先读回后安全重试。
- 审核/操作 `waiting` 显示正在等谁、为什么、最近更新时间和下一次检查/超时升级；外部调用 `unknown`/`degraded`/`reconciling` 显示最后已证实的边界、无法确认的环节、对账负责人和记录入口，禁用“再发布一次”等可能重复写入的动作。人工对账先查询外部真实结果，再决定恢复/重试；不能把未知当失败或成功。
- 审核、发布、分发/交接、`loaded`、`running` 和业务结果分别列状态。Skill handoff 接受不等于 DSH profile 装载，目标版本/digest 不一致则阻断“可用”结论；Workbench 不提供 Harness run 控制按钮或完整执行时间线。证据链接按资产 ACL 展示，敏感原文和完整 trace 不复制到此页。

### 12.5 已发布资产详情与反馈候选队列

```text
+--------------------------------------------------------------------------------+
| 资产与发布 > 已发布知识 / 已发布 Skill / 发布记录 / 反馈候选         |
| [当前授权空间] [资产类型] [状态] [版本] [时间窗口] [含 unknown]       |
+--------------------------------------------------------------------------------+
| 资产：交接规则 | 类型：知识 | v3 | owner / steward | 复核日期         |
| 权威来源：Git path + merge commit | 索引：WeKnora 读回 + 检索验证      |
| Skill 则显示：经审 canonical main merge commit（已发布）+ v1.2；package digest、所选 Registry release 读回（若启用）或管理员固定包 fallback 及目标安装另列 |
| 交接：目标 + pinned digest + 接受/装载读回；与正式发布分开            |
| [查看版本差异] [查看发布证据] [查看关联反馈] [从该版本创建修订会话]  |
+--------------------------------------------------------------------------------+
| 实际采用/价值（仅有证据时）                                            |
| 窗口、来源、覆盖率、归因率、有效调用/尝试/人类用户、unknown            |
| 技术完成 / 契约成功 / 已确认业务成功 / Badcase（分别列分母和状态）     |
| 结果 Owner、业务完成标准/基线（若有）；无证据：业务价值未知           |
+--------------------------------------------------------------------------------+
| 反馈候选：[待分流] 版本/来源引用 | 类别 | 责任人 | 原因 | [查看并分流]|
+--------------------------------------------------------------------------------+
```

- 已发布列表以资产和**不可变版本**为主键语义：知识展示 `knowledge_id/version/source_commit`、canonical repo path、WeKnora document/version 与授权检索读回；Skill 展示 `skill_id/version`、经审 canonical protected main merge commit 的 Git `已发布` 证据，以及各自独立的 package digest、所选 Registry release（若启用）或有期限的管理员固定包 fallback、目标安装及 handoff/load 读回。Skill 合并前（含已批准未合并）只在“审核中”，不能凭管理员包进入已发布列表；合并已核实但 Registry/安装/加载失败或未知时，Git 已发布版本仍可列出并将下游步骤标明失败/待对账，不并入相应路径的成功计数。知识索引未读回仍不并入已发布知识；修订按钮从选定版本开新 Creation Session，并保留 `base_asset_id/base_revision`，不直接改现有资产。
- 反馈队列允许按 `created/triaged/assigned/in_progress/resolved/rejected/deferred/escalated` 和目标分类筛选；每条呈现来源系统与最小引用、实际资产版本/digest、问题摘要、必要证据、是否已验证归因、处理人、最近进展和下一步。未能归因/读回的条目标“待核验”，进入核验/平台协作，不自动算已确认 Badcase，也不填猜测版本。相同报告可标记重复并指向主候选，保留审计。
- 分流动作由有权 owner/reviewer 执行，记录理由并选知识复核、Skill 回归/Workflow 修订、分发故障或平台协作；有效修订从候选启动新的知识或 Skill 会话，保留原反馈、正式版本和新会话之间的链接。`rejected` 是反馈被驳回并记录原因，不是原资产撤销；分发故障交平台/分发 owner 处理，不绕过审核修改 Git 或已发布包。
- 资产详情中的“使用/价值”仅展示被验证来源的最小消费引用与聚合，不显示 Harness 完整 Run/Step/Tool Call、业务原文、个人排行榜。知识被索引说明可检索，不等于有人使用、引用正确或业务改善；Skill release、install、load 和试跑不计入真实调用。业务价值必须有业务结果 Owner/业务系统对成功标准的确认或有基线的改善证据，否则明确显示 `unknown`，不得展示“零问题/成功率 100%”。
- “我的贡献与学习”作为经授权的个人入口关联到现有会话/资产，不按使用频次打分：分别展示本人主动提交、整理来源、确认事实、纠正错误、审核范围或分享脱敏案例的可核查记录及其证据层级（候选保存、人类判断、正式版本读回、真实消费、业务结果）；记录不完整时标明未核验。本人可[申请更正贡献归因]，有权 owner/reviewer 查证并记录更正与原记录，不得静默重写发布审批身份；可以自愿领取核对来源、报告问题、边界测试等成长任务，不把是否参与转成绩效指标。不能从最小消费事件的 `actor_ref`、调用次数或速度生成个人贡献榜。
- 业务流程 Owner 的“团队决策卡”只在现有资产与发布的授权聚合范围内展示：场景/任务、人工基线与观察窗口、样本与覆盖率、真实消费/业务结果、`unknown` 及维护/审核负担，并允许记录[继续试点]、[补充维护资源]、[缩小范围]或[暂停]的理由、责任人与复核日期。低覆盖、小样本或未确认结果显示“证据不足”，不能推断减员、个人优劣或节省的人力；小组过小或筛选条件可反推个人时抑制或合并展示，且不提供按人钻取的消费轨迹。业务方确认资源承诺及人员成长机会，Workbench 只能呈现请求和决策，不自动决定工时、晋升或薪酬。

### 12.6 跨屏状态文案与下一步规则

各视图的状态描述必须含：**影响对象/版本 → 已证实事实 → 未完成原因 → 当前责任人/角色 → 可执行下一动作与入口**；有门禁或外部依赖时增加时间及证据。以下文案是布局验收的代表性状态，不要求照搬字符串。

| 状态 | 首页 / 会话 / 审核 / 资产与反馈应如何表达 | 下一动作与责任 |
|---|---|---|
| 空 `empty` | 当前授权空间下无会话/无待办/无发布资产/无反馈各自说明范围；权限或加载错误不得当作空。 | 首页提供五个按问题选择的入口及返回宿主路径；列表可重设筛选，资产页不生成虚构指标；无绑定找团队 asset owner。 |
| 已保存 `saved` | 显示“草稿 r4 已保存于…；仍未确认/发布”，返回首页显示上次位置；本地未保存、保存中与失败另标。 | 贡献者继续确认或暂停；不得把自动保存当人工确认。 |
| 等待 `waiting` | 明示“待指定审核人审核范围”“Skill 已批准待 canonical main 合并（审核中）”或“等待 WeKnora/所选 Registry 读回”，附当前已证实步骤、起始时间和回访点；未选用 Registry 不出现其状态。 | 审核者进入证据视图；贡献者查看/提醒；外部等待由平台 owner 监控，不重复发布。 |
| 驳回 `rejected` | 显示审核/反馈的驳回理由、对象修订/版本、提出人和时间；不抹掉原证据。 | 审核驳回由贡献者修改新草稿修订后重提；反馈驳回由反馈 owner 记录理由/按权限复核，不影响已发布版本。 |
| 失败 `failed/error` | 区分“草稿未保存”“CI 校验失败”“provider 明确失败”“列表读取失败”；仅在有证据时称确定失败。 | 可编辑失败由 owner 修订；明确外部失败由平台 owner 读回后决定重试或人工处理；列表错误保留原上下文并提供重试。 |
| 未知 `unknown/degraded/reconciling` | 显示最后可信步骤、缺少的读回/归因、对账记录和更新时间；Skill 合并事实不明不得标“已发布”，已核实 Git 合并但 Registry/安装未知则 Git“已发布”与下游“待对账”并列；未知不进入相应步骤成功计数。 | 平台/分发 owner 查原 Git commit/审核与外部结果并对账；限制重复提交、发布和错误归因；支持人工接管与升级。 |
| 成功 `succeeded` | 必须带**是哪一步**：保存成功、Skill 经审 canonical main merge（Git 已发布）、知识索引可检索（知识已发布）、所选 Registry 发布读回或管理员固定包 fallback 的操作回执、逐目标安装、DSH loaded、业务结果已确认分别表述；fallback 不使 Skill 已发布也不冒称 Registry `released`。 | 链接对应证据及正式版本；发布后由 owner 复核使用/反馈；未经业务结果确认仍写“价值未知”。 |

按钮是否可用以当前授权、最新修订和已读回状态为准；从首页/通知进入陈旧链接时重新读取，不以旧卡片状态发起写入。错误与未知信息不应在刷新后无声消失：保留最后可信步骤和对账历史，后台恢复后把最终结果回写到原会话/资产版本及对应待办。

### 12.7 消费归因与“价值”展示的判读约束

资产详情和反馈队列共用如下判读顺序，防止把平台进度误当真实效果：

```text
Git 审核 → Knowledge: protected merge → WeKnora 授权索引读回并检索验证（知识已发布）
         → Skill: 经审 canonical protected main merge（Skill 已发布）→ package/digest
                  → 所选 Registry release 读回或管理员 fallback（独立证据）
             → 分发/交接/加载（如适用，独立证据）
             → 下游有效逻辑调用与真实消费者（采用）
             → 可评估的技术、契约、业务结果及业务 Owner 确认（价值）
             → 可归因反馈/已确认 Badcase → 新候选/新会话
```

- 指标卡的标题和过滤条件固定显示 `team_id/asset_space_id` 对应的授权空间、环境、统计时间窗口、来源系统、最近更新/对账时间。Skill 必须固定到实际 `skill_id/version/package_digest`，不按 `latest` 回填历史；知识索引事件用 `knowledge_id/version/source_commit`，不伪装成 Skill 消费事件。归因失败、版本不符或尚未读回的数据进入“待核验”数量，不自动归入任一版本的成功。
- 采用区至少区分去重后的有效 `invocation_id` 调用数、含重试 `attempt_no` 的尝试数、去重人类消费者数（服务/批量单列）；发布、安装、加载、CI、工作区试跑和 health check 均不算调用。只有经校验的消费事件可以影响采用指标；无数据时写“暂无可验证消费数据”而非“0 次使用”，同时提示覆盖范围。
- 明示 `反馈覆盖率 = 有有效反馈或结果引用的调用数 / 有效调用数` 与“版本归因覆盖（可关联实际 version/digest 的已接收调用占比）”，给出各自分子、分母、未覆盖/unknown 数量；未接入或分母未知时显示“不可计算”，不能报 0% 或 100%。覆盖不足时 Badcase 率只解释为已观测比例，未收到反馈不等于没问题。
- 技术完成、契约成功、业务成功分别展示有证据的分子、可评估分母、`not_evaluable`/`unknown` 数量及来源。`business_success` 仅接受业务结果 Owner 或业务系统确认；若有基线，还需标注基线、样本量及窗口才能表达改善。发布、索引、handoff、loaded、runtime succeeded 与样例测试通过均不能替代业务成功。知识如暂无可靠真实引用/业务结果链路，价值区显式标注“不可归因/未知”，不硬凑 Skill 指标。
- 反馈核验只接收必要引用及问题分类，并展示与正式版本、commit/release/handoff 的反查链；对敏感资产按 ACL 控制访问并隐藏原始主体、业务原文及完整运行 trace。任何覆盖率、归因率或价值结论只代表该窗口和已验证来源，不能推广到全部团队或未接入下游。
