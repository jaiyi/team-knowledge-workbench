# 知识与 Skill 资产模型

> 知识和 Skill 是两类一等资产：知识描述 Agent 应该知道什么，Skill 描述 Agent 如何完成一类任务。两者共享治理底座，但不能混成一种资产。

## 1. 双资产关系

```text
Knowledge asset                    Skill asset
事实/规则/案例/流程/决策             可重复任务的执行契约和实现
        ↑ source/evidence                 ↓ depends_on
        └────────────── 下游 Harness consumption ──────────────┘
                         profile + tools + outcome
```

Skill 可以依赖一个或多个知识域/固定知识版本；它不能复制正式知识正文，也不能自行改变知识的权限和状态。

## 2. 资产分层

Creation Session 是创作控制对象，不是正式资产；正式资产从会话草稿经过审核后产生。

```text
Workspace
└─ Creation Session
   ├─ Source Material / Workflow Draft
   ├─ Knowledge Draft / Skill Draft
   ├─ Draft Revision
   ├─ Test Case / Evaluation Result
   └─ Approval / Operation / Job
       └─ Asset Revision
           └─ Release
               └─ Handoff Record

Feedback Candidate → 新的 Creation Session
```

| 对象 | 说明 | 首期 |
|---|---|---:|
| Workspace | 用户、项目和资产的隔离边界 | 必须 |
| Creation Session | 一次知识或 Skill 创作上下文；可暂停、恢复、归档、分叉或只读 | 必须 |
| 原始证据 | 说明发生了什么 | 必须 |
| 知识/Workflow/Skill Draft | 会话内可编辑的候选 | 必须 |
| Asset Revision | 经过 Git/MR/CI/人工审核的不可变正式修订 | 必须 |
| Knowledge/Skill Release | 带固定版本、digest 和目标的发布记录 | 必须 |
| Handoff Record | 批准版本交给下游适配器或管理员的引用 | 必须 |
| 运行记录 | 下游 Harness/业务系统对一次消费的引用或反馈 | 以引用接收，不复制完整运行面 |
| Feedback Candidate | 说明知识或 Skill 哪里需要改，并启动新会话 | 必须 |
| Plugin package / MCP | 受控工具和外部系统适配能力 | 后续（双资产稳定后） |
| Bot Memory | 运行时上下文和协作记忆 | 可选，不是正式资产 |

## 3. 知识资产

### 3.0 团队资产域与规范目录

`team-knowledge-asset` 是一个团队独立绑定的逻辑资产域，不是 `team-knowledge-workbench` 插件包本身，也不等同于某一个 Knowledge 或 Skill。默认情况下，它由一个 canonical Git repository、protected branch/CODEOWNERS、WeKnora space、ACL、taxonomy 和 steward/review policy 共同组成；`asset_space_id` 是该资产域的隔离键。多个团队可以安装同一个 Workbench，但每个团队分别拥有自己的 `asset_space_id` 和上述绑定。

P1 默认采用同仓模式：同一个 `asset_repository` 的 repository root 同时承载 `knowledge/` 和 `skills/` 两个正式资产根目录。下面的 `team-knowledge-asset/` 表示该 canonical repository 的逻辑根，不要求实际再嵌套一层同名目录；目录路径均相对于 repository root。一个团队资产域在 P1 只允许一个 active canonical repository，未来拆仓时必须通过工作台控制面的显式 repository binding 管理，不能靠目录名或客户端参数推断归属。

知识正文和 Skill 包必须落在稳定、可治理的逻辑目录中，不能由 Agent 平铺堆砌：

```text
team-knowledge-asset/
├── README.md
├── taxonomy/
│   └── v1.yaml
├── knowledge/
│   └── <domain>/<topic>/<knowledge-slug>/
│       ├── KNOWLEDGE.md
│       ├── metadata.yaml
│       ├── sources.yaml
│       └── CHANGELOG.md
├── skills/
│   └── <domain>/<name>/
│       ├── SKILL.md
│       ├── skill.yaml
│       ├── contract/
│       │   ├── input.schema.json
│       │   ├── output.schema.json
│       │   └── effects.yaml
│       ├── tests/
│       │   ├── golden/
│       │   └── regression/
│       ├── dependencies.lock
│       └── CHANGELOG.md
├── profiles/
└── CODEOWNERS
```

`knowledge/<domain>/<topic>/<knowledge-slug>/` 是 Knowledge 的 canonical path，`skills/<domain>/<name>/` 是 Skill package 的 canonical path。Knowledge 和 Skill 是同一团队资产域下的两类独立一等资产，不是父子对象关系；Skill 不嵌套在某一篇 Knowledge 下，也不复制 Knowledge 正文。Skill 通过 `skill.yaml` 的 `knowledge_dependencies` 使用固定的 Knowledge ID 和版本，例如：

```yaml
knowledge_dependencies:
  - id: knowledge.finance.invoice-policy
    version: 3.0.1
```

两类资产共享团队级 repository、ACL、CODEOWNERS、CI、安全扫描和审计边界，但分别拥有自己的 owner、版本、测试、审核、发布、回滚和生命周期。Knowledge 进入 WeKnora；Skill package 进入 SkillHub；TeamAI 和 DSH 只消费 SkillHub 已确认的 pinned digest，不改变 Knowledge 的 Git/WeKnora 权威。

`knowledge/<domain>/<topic>/<knowledge-slug>/` 是 canonical path 的一部分。Workbench 创建知识时要展示 domain/topic/path preview，校验 taxonomy、slug、重复 canonical key、owner、sensitivity 和 CODEOWNERS；新增分类需要 steward 批准。`metadata.yaml` 至少包含 `knowledge_id`、`version`、`status`、`team_id`、`asset_space_id`、`repo_path`、`taxonomy_version`、`source_commit`、`weknora_space_id` 和 ACL 引用。

WeKnora 的物理 collection/index 可以不同于 Git 目录，但必须按同一逻辑路径映射并保留 `knowledge_id`、`repo_path`、domain、topic、version、source commit、sensitivity、status 和 ACL。Git 是知识事实的 canonical source；WeKnora 是索引/检索层，不能在后台形成一套无法回溯的分类事实。移动、合并、重命名和退役必须由 Git MR 驱动，并完成 WeKnora 迁移、alias/redirect 或退役记录和读回对账。

```yaml
knowledge_id: knowledge.<domain>.<name>
version: 1.0.0
status: captured | candidate | reviewing | approved | publishing | published | stale | deprecated | rejected
team_id: <team-id>
asset_space_id: <asset-space-id>
asset_repository_id: <repository-id>
repo_path: knowledge/<domain>/<topic>/<knowledge-slug>/
taxonomy_version: v1
source_commit: <merge-commit>
weknora_space_id: <space-id>
owner: team-owner
steward: user-id
kind: fact | rule | case | procedure | decision
source_refs: []
applies_to: []
not_applies_to: []
last_reviewed_at: timestamp
next_review_at: timestamp
evidence_level: E0 | E1 | E2 | E3
sensitivity: public | internal | confidential | restricted
```

### 正文

1. 一句话结论；
2. 已确认事实；
3. 依据和来源；
4. 适用条件；
5. 不适用范围和例外；
6. 推断或建议（单独标记）；
7. 反例和未知项；
8. 下一次复核条件。

### 生命周期

```text
captured → candidate → reviewing → approved → publishing → published
```

`publishing` 表示 Git protected main 已产生 merge event，工作台已经创建 knowledge ingest operation，但 WeKnora 还没有完成读回。只有真实读回指定 `knowledge_id`、`version`、`source_commit`、`repo_path`、`asset_space_id` 和 ACL，并通过可检索性验证，才能进入 `published`。`index_failed`、`index_unknown` 和 `manual_required` 不得被自动修正为 published；索引失败时保留上一可用版本。

Creation Session 的状态与 Knowledge 生命周期分开：

```text
active → paused → active
   ├→ archived
   ├→ forked
   └→ read_only
```

会话结束不会自动改变正式资产状态；Feedback Candidate 必须创建新的修订会话。

## 4. Skill 资产

### 元数据

```yaml
id: skill.<domain>.<name>
version: 0.1.0
status: requested | scaffolded | authoring | validating | reviewing | approved | beta | stable | blocked | withdrawn | deprecated | retired
owner: team-owner
backup_owner: user-id
purpose: structured task description
knowledge_dependencies:
  - id: knowledge.<domain>.<name>
    version: 3.0.1
input_schema: contract/input.schema.json
output_schema: contract/output.schema.json
effects: contract/effects.yaml
risk_level: L0 | L1 | L2 | L3 | L4 | L5
compatible_profiles: []
package_digest: sha256:...
success_criteria:
  machine_checkable: true
  outcome_levels: [technical, contract, business]
  business_evidence_required: true
```

### 最小 Skill 包

```text
skills/<domain>/<name>/
├── SKILL.md
├── skill.yaml
├── contract/input.schema.json
├── contract/output.schema.json
├── contract/effects.yaml
├── tests/golden/
├── tests/regression/
├── dependencies.lock
└── CHANGELOG.md
```

### Skill 生命周期

Skill 的业务生命周期与外部分发状态分开记录：

```text
requested → scaffolded → authoring → validating → reviewing → approved → released
                                                   ↘ blocked/rejected
released → beta → stable
stable → withdrawn/deprecated → retired
```

其中：

- `approved`：Git 变更、质量门禁和人工审核通过；
- `released`：从固定 merge commit 构建的 package/digest 已由 SkillHub（或管理员 fallback）真实读回；
- `distributed/installed`：TeamAI 已按 pinned digest 到达目标并完成安装读回；
- `loaded`：DSH profile 实际装载并读回相同 digest；
- `beta/stable`：治理层允许哪些目标消费，不等于已经安装或运行。

建议将 `distributed`、`installed` 和 `loaded` 作为 `release`、`distribution_target`、`handoff_record` 的状态，不直接塞进 Skill 的业务生命周期。不能把 Git 合并、SkillHub 上传、TeamAI pull、Harness 加载或一次运行成功混为同一状态。

## 5. Plugin 资产（长期扩展）

Plugin 是平台或 Agent 可调用的受控外部能力，提供工具、服务适配器或运行时扩展；它不描述一类业务任务，也不替代 Skill。首期不建设独立业务 Plugin Marketplace，但应预留独立 manifest、权限和运行归因边界。

### 最小 metadata

```yaml
id: plugin.<domain>.<name>
version: 0.1.0
status: requested | authoring | validating | reviewing | approved | installed | enabled | disabled | withdrawn | retired
owner: team-owner
backup_owner: user-id
host_compatibility: ">= 2.0.0"
tools:
  - name: query_records
    input_schema: contract/query.schema.json
    output_schema: contract/result.schema.json
permissions:
  network: []
  data: []
  filesystem: []
required_secrets: []
dependencies: []
package_digest: sha256:...
health_check: configured
```

Plugin 必须声明工具、权限、网络/数据范围、凭据需求、宿主兼容性、依赖、digest、health 和 owner。实际权限仍由 profile、tool policy、workspace、环境和运行时授权共同决定。

### Plugin 生命周期

```text
requested → authoring → validating → reviewing → approved → installed → enabled
                                                        ├→ disabled
                                                        └→ rejected/blocked
enabled → withdrawn/deprecated → retired
```

`approved` 表示 package、manifest、安全和兼容性审核通过；`installed` 表示目标环境已安装；`enabled` 表示健康检查和权限授予均已确认。它们不能与 Skill 的 `stable` 或一次工具调用成功混为一谈。

Plugin package 可以捆绑一个或多个 Skill，但 Plugin 是安装/运行单位，Skill 是业务能力单位，必须分别版本、审核、测试和回滚。
## 6. Agent Manifest 与分发包

### Agent Manifest/分发包（后续复用）

Agent Manifest 是对可运行 Agent 的组合描述，可以引用固定的 Skill/version/digest、知识 profile/version、模型配置、工具需求、运行策略和人工确认点。它适合支持 TeamAI 的跨团队 Agent 分发，但不拥有被引用资产的 canonical source，也不能绕过各自的 owner、ACL、回归和审批。

建议结构：

```yaml
id: agent.<domain>.<name>
version: 0.1.0
skills:
  - id: skill.<domain>.<name>
    version: 1.2.0
    digest: sha256:...
knowledge_profiles: []
model_profile: default
plugin_tools: []
human_confirmation: required
compatible_targets: []
```

### 分发 metadata

TeamAI 或其他分发适配器可以记录 `distribution_target`、`workspace_id`、`source_revision`、`package_digest`、`skillhub_release_id`、`pinned_digest`、`installed_revision`、`profile_version`、`sync_status`、`dsh_handoff_id`、`dsh_loaded_digest` 和 `last_error_code`。这些字段只说明固定版本如何到达目标环境，不改变知识、Skill 或 Plugin 本身的生命周期状态。

## 7. Skill 必须声明和验证

- 输入和输出 schema；
- 依赖的知识 ID、版本策略和引用要求；
- 依赖锁定、许可证和 SBOM；
- 工具需求、读写 effects、网络和数据范围；
- 运行环境、资源限制和兼容 profile；
- 风险等级和人工确认点；
- golden cases、回归集和失败态；
- package digest 必须由固定 merge commit 的构建产物计算并在 SkillHub release 后保持不可变；
- TeamAI 和 DSH 必须校验 pinned digest，不能用 `latest`、名称或 semver 推断实际内容；
- `installed_revision` 表示目标文件/仓库修订，`package_digest` 表示包内容完整性，两者不能互相替代；
- owner、审核人、变更记录、回滚版本和退役条件。

自然语言说明不能替代机器可读契约；Skill 不能自行获得权限、直接写正式知识或依赖漂移的 `latest`。

## 8. 版本关系

| 标识 | 含义 |
|---|---|
| Git commit | 知识或 Skill 源码不可变变更 |
| knowledge version | 面向业务的知识修订号 |
| Skill semver | Skill 分发版本 |
| package digest | 从固定 Git merge commit 构建的 Skill 内容完整性标识 |
| SkillHub release | SkillHub 对 package/digest 的实际发布记录和读回证据 |
| pinned digest | TeamAI 和 DSH 必须消费的不可漂移 package digest |
| TeamAI installed revision | 目标 workspace/仓库实际安装的修订，不替代 digest |
| DSH loaded digest | 目标 profile 实际装载的内容完整性证据 |
| Plugin semver | Plugin package 分发版本 |
| Plugin digest | Plugin 内容完整性 |
| index version | WeKnora 索引版本 |
| handoff record | 已批准资产交给下游适配器/管理员的交接引用 |
| downstream profile/session | DeepSeek Harness 实际消费上下文，由下游维护 |
| feedback reference | 下游运行反馈或问题的可关联引用 |

必须能够追踪：

```text
Git merge commit
  → package digest
  → SkillHub release/read-back
  → pinned digest
  → TeamAI installed revision/digest read-back
  → DSH loaded digest/profile read-back
  → run

feedback reference → downstream skill/version/digest + knowledge/version
                  → handoff/release record → Git commit
```

本项目不要求复制完整的 DSH session、run、tool call 或业务 outcome 数据。

## 9. 资产边界

- WeKnora 不是 Skill Registry；
- SkillHub 不是知识审批系统；
- Plugin Registry/Runtime 不是 Skill 业务质量管理系统；
- DSH 不是正式源和发布审批系统；
- 运行记录同时关联 `knowledge/version`、`skill/version/digest`、`plugin/version/digest`、`profile` 和 `tool calls`；
- 反馈是候选/任务，不是正文、代码或 Plugin package；
- 一次运行成功不等于知识成立、Skill stable 或 Plugin enabled。
