# 数据、状态与可追溯性

## 1. 工作台会话与资产状态

### 1.1 外部 operation 状态

知识 ingest、选定 Registry 的 Skill release（如采用 SkillHub）、可选 TeamAI distribution 和 DSH handoff 统一使用独立的操作状态，不把它们直接塞进资产生命周期：

```text
queued → running → waiting_readback → succeeded
                         ├→ failed
                         ├→ unknown
                         └→ reconciling
```

因此：`knowledge.published` 表示 WeKnora 实际索引并可检索；`skill.released`（界面称「已发布」）仅表示该固定版本经批准合入团队 canonical Git 受保护主分支且 merge/CI/审核证据已核验，不依赖 Registry 是否选用或目标是否安装；选用 Registry 时，单独记录 `registry_released` 及 release/version/digest 的真实读回（若选 SkillHub 则为 SkillHub 事实）；管理员固定包 fallback 使用独立的 `release_mode=admin,fallback_only`，仅针对已发布、已构建的包，不写成 Registry released，也不能使未合并版本已发布；`distribution.succeeded` 只表示所选目标按 pinned digest 安装并读回（TeamAI 如启用）；`dsh.loaded` 表示目标 profile 实际装载。Git 合并事件、Provider 接受请求、HTTP 200 或 worker 调用完成都不能替代各自的权威核验。
### 1.2 Creation Session

```text
active → paused → active
   ├→ archived
   ├→ forked
   └→ read_only
```

`paused` 保留上下文但不启动新的生成或发布动作；`archived` 保留审计和恢复依据；`forked` 创建新的独立 `session_id` 和 draft revision；`read_only` 只允许查看证据。会话状态不代表正式资产状态。

### Draft 与并发

每个草稿修订至少关联 `session_id`、`draft_id`、`draft_revision_id`、`base_asset_id`、`base_revision` 和 `state_version`。提交、发布、恢复、重试和回调都必须校验 expected state/version；并行会话发现 base revision 已变化时进入 `revision_conflict`，由人工合并，禁止静默覆盖。

### 知识

```text
captured → candidate → reviewing → approved → publishing → published
```

异常/终态：`index_failed`、`index_unknown`、`stale`、`deprecated`、`rejected`、`manual_required`。`deprecated` 仅在已审退役 commit **以及声明范围内旧索引/入口不可再检索的读回**齐全时表示当前版本已退役，不表示历史 Git/PG 证据被物理删除；未证实的撤回使用 `retiring/withdrawal_unknown`，紧急撤权未证实使用 `revocation_unknown/manual_required`，迁移残留使用 `migration_unknown/manual_required`。这些是资产可用性/异常视图，不覆盖独立 operation 的 `unknown/reconciling`。同一资产的旧已验证版本只在仍获授权且内容有效时可继续提供；任何阻断 epoch 后的旧读回不能恢复公开状态。`published` 指一个固定版本在固定空间/目标的真实检索事实，不能只凭 PG 草稿、Git merge 或 WeKnora 请求成功推断。具体时序见[工程设计 5.2–5.3](11-开发工程设计与集成基线.md#52-knowledge-增改退役与权限变更契约拟议)。

### Skill

```text
requested → scaffolded → authoring → validating → reviewing → approved（待合并）
                                         ├→ blocked                 ↓ canonical protected Git merge 核验
                                         └→ rejected             released（已发布）→ beta → stable
stable → withdrawn/deprecated → retired
```

`approved` 只说明审核通过但尚未核实合入，仍显示审核中/待合并；合入团队 canonical 受保护 Git 主分支并核验仓库、ref、CI、审核及 merge commit 后，固定 Skill 版本才 `released`（正式已发布）。构建固定包、可选 Registry release/read-back、管理员 `fallback_only` 交接、逐目标 installed 和 DSH loaded 是已发布版本的独立后续事实；Registry 失败或未选不抹去 Git 已发布，fallback 不使未合并 Skill 已发布，也不自动晋级 `beta/stable`。成熟度仍以 08 中按声明资产类型、Provider、目标与证据范围的 Go/No-Go 为准，Git 已发布绝不等于目标可用或业务成功。

### Plugin

```text
requested → authoring → validating → reviewing → approved → installed → enabled
                                                     ├→ disabled
                                                     └→ blocked/withdrawn
```

Plugin `enabled` 必须同时有安装读回、权限授予、兼容性检查和健康证据；`installed`、`enabled`、`healthy` 和一次工具调用成功不能混为一谈。
### 发布/装载/启用不能混为一谈

### Workbench/资产/索引状态

- `workbench_installed`：DSH Desktop 已安装指定 Workbench package/version/digest；
- `asset_published`：固定资产版本已达其各自权威发布门：Skill 为已审 canonical Git protected merge；知识还须 WeKnora 指定版本/ACL 的授权检索读回；不表示目标安装、装载或运行；
- `weknora_indexed`：WeKnora 读回指定 knowledge/version/source/path/ACL；
- `loaded`：DSH profile 实际装载固定 Skill digest；
- `succeeded`：一次下游运行有真实结果或人工验证。

## 2. 下游运行和反馈引用

DeepSeek Harness 或业务系统拥有完整的 Session、Task、Run、Step、Tool Call、人工 gate、Artifact、Outcome、恢复和运行状态。本工作台不复制这些控制对象，只接收可关联的反馈引用：

```text
feedback_reference → asset/version/digest → handoff/release → Git commit
```

反馈复核状态仍由工作台管理：

```text
created → triaged → assigned → in_progress → resolved
                                  ├→ rejected
                                  ├→ deferred
                                  └→ escalated
```

反馈任务必须标明目标：`knowledge_review`、`skill_regression`、`distribution_incident` 或 `platform_collaboration`。

`principal`、`team_membership`、`role_binding` 和 `service_identity` 描述拟由已验证 DSH 身份交换映射出的人员、团队角色和外部执行身份；`connection_binding`/`connection_config_revision` 保存当前空间的受控目标引用、配置版本/激活状态、最后检查证据和审计，`credential_binding` 仅引用服务端密钥管理，不保存或回显 Secret。每个 operation 固定创建时的配置版本与原目标，变更/撤权后先读回旧目标再对账，不自动用新凭据重放。`team`、`asset_space` 和 `asset_repository` 描述每个团队独立的 `team-knowledge-asset` 绑定；`workbench_installation` 只描述 DSH Desktop 插件包在目标宿主的版本、digest、enabled/restart/read-back；`deployment_environment` 描述腾讯云非生产/生产验证环境；`weknora_mapping` 描述稳定资产 ID、Git canonical path 与 WeKnora document/collection/index 的逐版本映射、旧 document IDs、迁移/退役和对账状态，不能只存当前路径。`integration_event`/`merge_event` 保存 Git 事件验签、重放去重和 merge commit；`outbox_operation`、`worker_attempt`/`lease` 保存异步编排；`weknora_readback`、`release_readback` 和 `dsh_load_readback` 保存下游实际证据；`consumption_event_reference` 只保存经过校验的最小 Skill 消费、结果和反馈引用，`metric_aggregate` 保存按 team/asset-space/Skill/version/digest 聚合的调用、主体、结果和 badcase 指标，不复制 Harness 完整运行面。Workbench market 安装记录不能替代资产 release、WeKnora publish 或 Skill consumption 记录。

PostgreSQL 是 Team Knowledge Backend 的过程控制面，保存上述结构化对象、Creation Session、Draft、审批、外部操作、Job、幂等、outbox、reconciliation 和审计。小型结构化草稿可存 JSONB；原件默认留在有权来源系统，PG 保存最小来源定位/固定版本与核证锚点。仅经来源 owner 单独批准复制、用途、保留期和撤权清理时，必要的原始材料/附件副本才放入加密对象存储；大型获准测试 fixture 同样按用途和期限保存，数据库只留 URI、hash、大小、来源和敏感等级。Git、WeKnora、SkillHub 和 TeamLab 的专业数据仍由各自系统负责，Workbench 不直接写 WeKnora 内部数据库。

## 4. 身份责任与执行归因

Workbench 拟复用**经目标验证**的 DSH Desktop 身份上下文，不以公司统一身份系统接入作为 P0 前提；真实资产写入前必须验证后端能安全交换该身份、处理撤销并重新授权。后端从已验证的 DSH subject 映射 `principal_id`、团队成员和角色；客户端提交的 `team_id`、owner、approver 或 publisher 只能作为请求意图，不能作为授权事实。`desktopWorkbenchOwnership` 是只读宿主元数据，不是授权系统。

业务责任身份和技术执行身份分开记录：真实用户承担 `requested_by`、`created_by`、`confirmed_by`、`approved_by`、`released_by` 和 `owner_id`；Git bot、WeKnora adapter、SkillHub publisher、TeamLab adapter 和后台 Worker 承担 `executed_by`/`service_identity_id`。Git commit 可以由 Workbench service account 写入，但 MR、commit trailer、asset metadata 和审计必须关联真实责任人。DSH launch token、用户登录 token 和某个组件的服务凭据不能跨组件复用为通用 credential。

## 5. PostgreSQL 与外部存储边界

P0 在腾讯云为 Team Knowledge Backend 配置独立 PostgreSQL database/schema/user，使用私网/TLS、Secret Manager、连接池、迁移基线、备份、PITR/恢复演练和监控。所有团队资源、Job 和外部操作带 `team_id`/`asset_space_id`；同空间**当前有效**的 `canonical_key` 与 `repo_path` 唯一，历史 `asset_revision`/旧路径映射按 `(asset_space_id,asset_id,source_commit,repo_path)` 保留，旧路径复用前先验证无索引残留及身份冲突；`provider + repository_identity` 唯一；每个 `asset_space_id` 最多一个 active canonical `asset_repository`。Knowledge/Skill 的 repo path 必须位于已绑定 repository 的允许 root 下，拒绝绝对路径、`..`、符号链接逃逸和跨团队 repository identity。数据库不可用、Worker 重启或外部调用半成功时必须显示 `unknown`/`degraded`/`reconciling`，不能伪造成功。

PostgreSQL 保存过程状态和审计；加密对象存储仅在另获批准的用途、范围和期限内保存必要原件/附件副本与测试 fixture；Git 保存正式知识和 Skill；WeKnora 默认保存正式知识索引，若目标另有有权来源文档须独立核版本、ACL 与逐文档深链，不混用正式知识索引；SkillHub/TeamLab 保存各自分发状态。Workbench 通过 API/adapter 访问这些组件，不直接写 WeKnora 内部数据库。

## 6. 最小追踪链

正式知识与 Skill 共用经授权的创作/审核/异步操作骨架，但分别关联各自的发布与消费事实；只读浏览或独立反馈候选不必产生 creation session：

```text
actor → team/asset-space/repository binding
  →（明确新建/修订才创建）creation session → draft/draft revision
  → Git MR/CI/指定审核人批准（仍审核中）→ canonical protected merge commit
  → 验签/去重并读回核验 merge event、固定版本及仓库/ref/CI/审核（Skill 在此正式已发布）→ outbox operation → worker attempt/read-back
  ├─ Knowledge: WeKnora document/version/source/ACL + 授权检索/撤权读回（知识在此 published）
  └─ Skill: 已发布固定 commit → package digest + 测试/目标格式校验证据
       → 所选 Registry release/read-back 或已发布固定包的管理员 fallback（各自独立）
       → TeamAI 团队仓库 commit（启用时）或受控目标安装
       → 逐目标 installed file manifest/digest read-back
       → DSH 指定 profile loaded digest read-back
  → 有可信运行事件时关联实际消费与反馈；缺证保留 unknown
```

一次下游消费应能反查实际使用的 Knowledge ID/version/source/WeKnora document（若有知识引用）与 Skill ID/version/package digest（若有 Skill 执行）、Git commit、目标安装及 DSH profile/loaded digest；**仅选用** SkillHub/TeamAI 时才要求对应 release/installed revision 读回，不把未选的 Provider 写成必填或成功。没有已证实的调用/来源/业务结果时保持未知，不伪造完整链。

## 7. 幂等和恢复

- merge event 以 `event_id` 去重；
- 知识增改及撤回/迁移步骤以 `asset_space_id + repository_identity + merge_commit_sha + asset_id + change_kind + provider_target` 去重；`path` 仅作已验证的路径映射而非永久身份，同一个 commit 多资产必须逐资产展开；
- SkillHub release 以 `skill_id + package_digest` 去重；
- TeamAI distribution 以 `target + pinned_digest + profile` 去重；
- DSH handoff 以 `target + profile + pinned_digest` 去重；
- 消费事件以 `event_id`/`idempotency_key` 去重，`invocation_id` 区分逻辑调用，`attempt_no` 区分重试；
- 重试前先读回 Git/MR/index/package/release/installation/handoff 状态；
- worker 领取租约后崩溃，先 read-back 再重试；provider 已完成但本地状态未知时不得盲目重新创建；
- 所有创建、提交、发布、交接、消费和反馈写操作使用 idempotency key；
- 状态更新带 expected state/state version，旧回调不能覆盖新状态；
- 发布、交接、消费或反馈半成功、版本漂移、迟到事件和断网状态进入 `unknown`/`reconciling`，不能直接标成成功；
- 消费事件必须归因到实际 `skill_id/version/package_digest`，不能用 `latest` 覆盖历史聚合；
- 事件落库后再确认接收；
- 删除优先软退役，保留旧版本、digest、审计、历史聚合和回滚 pin；退役/迁移需逐个历史索引及入口核验不可见性，无法证明则留 `unknown/manual_required` 而非 `deprecated`；紧急撤权先阻断受控访问并核查外部直连，不等 Git 合并。
- 持久游标定期扫描受保护 Git commit、PG receipt/operation/资产指针与 WeKnora 实际文档、ACL、可检索性；漏事件只从经审查的 Git commit 补出站，索引孤儿先隔离，不从 WeKnora 反向创建正式资产；扫不全不得推进游标。

## 8. 状态证据

| 状态 | 必须证据 |
|---|---|
| knowledge ingest succeeded | provider operation、document/version/source/repo_path/ACL read-back |
| knowledge published（固定版本） | 经批准 Git merge commit + ingest 读回 document/version/source/repo_path/ACL，且实际授权检索命中；当前可用指针仍需查撤权/退役 epoch |
| knowledge deprecated（当前可用性） | 已审退役 commit + 所有声明范围旧索引/受控与直连入口不可再检索的负向读回；历史 Git/PG 不作物理删除声明 |
| knowledge revocation applied（指定主体/范围） | 服务端即时拒绝和缓存清理证据 + 外部 ACL、链接、直连入口的拒绝读回；缺任一范围保持 unknown 并升级 |
| skill approved（审核中/待合并） | 指定审核人批准、CI、contract/test 和待合并的 MR/revision；不能以批准回执替代 protected merge |
| skill released（正式已发布的固定版本） | canonical repository 稳定 ID、受保护主分支、该 Skill/version 的 merge commit、审核与 CI、经核验的 merge event/受保护 ref 读回；镜像仓合并、未验签事件或迟到事件不能替代 |
| skill packaged | 从已发布 merge commit 构建的 package manifest、package digest、source commit 与版本映射 |
| registry released（仅经选型真实 Registry） | 实际 release id、固定 version/digest、status read-back；若选 SkillHub，记录 SkillHub release id；失败或 unknown 不回退已证实的 Git 发布 |
| admin fallback_only（后续交接） | 已发布 canonical Git commit、固定 package/digest、操作者、目标、期限、回滚和对账记录；不得标记 Registry released，未合并时不可交接 |
| distribution installed | target、pinned digest、installed revision 和文件清单的目标读回；仅选用 TeamAI 时记录 TeamAI read-back |
| dsh handed off | handoff id、profile、target、accepted status |
| dsh loaded | loaded digest/profile/read-back |
