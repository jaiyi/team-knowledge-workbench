# 数据、状态与可追溯性

## 1. 工作台会话与资产状态

### 1.1 外部 operation 状态

知识 ingest、SkillHub release、TeamAI distribution 和 DSH handoff 统一使用独立的操作状态，不把它们直接塞进资产生命周期：

```text
queued → running → waiting_readback → succeeded
                         ├→ failed
                         ├→ unknown
                         └→ reconciling
```

因此：`knowledge.published` 表示 WeKnora 实际索引并可检索；`skill.released` 表示 SkillHub release/digest 已读回；`distribution.succeeded` 表示目标按 pinned digest 安装并读回；`dsh.loaded` 表示目标 profile 实际装载。provider 已接受请求、HTTP 200 或 worker 调用完成都不足以推进这些状态。
### 1.2 Creation Session

```text
active → paused → active
   ├→ archived
   ├→ forked
   └→ read_only
```

`paused` 保留上下文但不启动新的生成或发布动作；`archived` 保留审计和恢复依据；`forked` 创建新的独立 `session_id` 和 draft revision；`read_only` 只允许查看证据。会话状态不代表正式资产状态。

### Draft 与并发

每个草稿修订至少关联 `session_id`、`draft_id`、`draft_revision_id`、`base_asset_id`、`base_revision` 和 `state_version`。提交、发布、恢复、重试和回调都必须校验 expected state/version；并行会话发现 base revision 已变化时进入 `revision_conflict`，由人工合并，禁止静默覆盖。

### 知识

```text
captured → candidate → reviewing → approved → publishing → published
```

异常/终态：`index_failed`、`index_unknown`、`stale`、`deprecated`、`rejected`、`manual_required`。

### Skill

```text
requested → scaffolded → authoring → validating → reviewing → approved → released
                                                   ├→ blocked
                                                   └→ rejected
released → beta → stable
stable → withdrawn/deprecated → retired
```

### Plugin

```text
requested → authoring → validating → reviewing → approved → installed → enabled
                                                     ├→ disabled
                                                     └→ blocked/withdrawn
```

Plugin `enabled` 必须同时有安装读回、权限授予、兼容性检查和健康证据；`installed`、`enabled`、`healthy` 和一次工具调用成功不能混为一谈。
### 发布/装载/启用不能混为一谈

### Workbench/资产/索引状态

- `workbench_installed`：DSH Desktop 已安装指定 Workbench package/version/digest；
- `asset_published`：当前团队资产已有 Git/CI/审核和目标发布证据；
- `weknora_indexed`：WeKnora 读回指定 knowledge/version/source/path/ACL；
- `loaded`：DSH profile 实际装载固定 Skill digest；
- `succeeded`：一次下游运行有真实结果或人工验证。

## 2. 下游运行和反馈引用

DeepSeek Harness 或业务系统拥有完整的 Session、Task、Run、Step、Tool Call、人工 gate、Artifact、Outcome、恢复和运行状态。本工作台不复制这些控制对象，只接收可关联的反馈引用：

```text
feedback_reference → asset/version/digest → handoff/release → Git commit
```

反馈复核状态仍由工作台管理：

```text
created → triaged → assigned → in_progress → resolved
                                  ├→ rejected
                                  ├→ deferred
                                  └→ escalated
```

反馈任务必须标明目标：`knowledge_review`、`skill_regression`、`distribution_incident` 或 `platform_collaboration`。

`principal`、`team_membership`、`role_binding` 和 `service_identity` 描述当前 DSH 认证上下文映射出的人员、团队角色和外部执行身份；`team`、`asset_space` 和 `asset_repository` 描述每个团队独立的 `team-knowledge-asset` 绑定；`workbench_installation` 只描述 DSH Desktop 插件包在目标宿主的版本、digest、enabled/restart/read-back；`deployment_environment` 描述腾讯云非生产/生产验证环境；`weknora_mapping` 描述 Git canonical path 与 WeKnora document/collection/index 的映射和对账状态。`integration_event`/`merge_event` 保存 Git 事件验签、重放去重和 merge commit；`outbox_operation`、`worker_attempt`/`lease` 保存异步编排；`weknora_readback`、`release_readback` 和 `dsh_load_readback` 保存下游实际证据；`consumption_event_reference` 只保存经过校验的最小 Skill 消费、结果和反馈引用，`metric_aggregate` 保存按 team/asset-space/Skill/version/digest 聚合的调用、主体、结果和 badcase 指标，不复制 Harness 完整运行面。Workbench market 安装记录不能替代资产 release、WeKnora publish 或 Skill consumption 记录。

PostgreSQL 是 Team Knowledge Backend 的过程控制面，保存上述结构化对象、Creation Session、Draft、审批、外部操作、Job、幂等、outbox、reconciliation 和审计。小型结构化草稿可存 JSONB；原始会议材料、附件和大型测试 fixture 放在加密对象存储，数据库只保存 URI、hash、大小、来源和敏感等级。Git、WeKnora、SkillHub 和 TeamLab 的专业数据仍由各自系统负责，Workbench 不直接写 WeKnora 内部数据库。

关键字段：`event_id`、`merge_commit_sha`、`protected_ref`、`provider_operation_id`、`outbox_operation_id`、`job_attempt`、`lease_expires_at`、`readback_at`、`readback_status`、`dsh_subject`、`principal_id`、`service_identity_id`、`tenant_id`、`team_id`、`asset_space_id`、`asset_repository_id`、`repository_identity`、`repository_kind`、`canonical_path`、`asset_repo`、`repo_path`、`taxonomy_version`、`weknora_space_id`、`weknora_document_id`、`weknora_index_version`、`workbench_version`、`workbench_digest`、`deployment_environment`、`session_id`、`workspace_id`、`session_type`、`owner_id`、`collaborator_ids`、`requested_by`、`created_by`、`confirmed_by`、`approved_by`、`released_by`、`executed_by`、`source_refs`、`base_asset_id`、`base_revision`、`draft_id`、`draft_revision_id`、`phase`、`session_status`、`actor_id`、`asset_id`、`asset_type`、`source_commit`、`knowledge_version`、`skill_version`、`skillhub_release_id`、`package_digest`、`pinned_digest`、`distribution_target`、`teamai_installed_revision`、`dsh_handoff_id`、`dsh_loaded_digest`、`dsh_profile_version`、`handoff_status`、`invocation_id`、`attempt_no`、`actor_type`、`actor_ref`、`runtime_status`、`outcome_status`、`outcome_reference`、`feedback_reference`、`source_system`、`schema_version`、`execution_success_count`、`contract_success_count`、`business_success_count`、`badcase_report_count`、`confirmed_badcase_count`、`affected_invocation_count`、`feedback_coverage`、`idempotency_key`、`correlation_id`、`state_version`、`reconciliation_status`、`created_at`、`updated_at`、`archived_at`、`last_error_code`。

`asset_repository` 至少保存 `asset_repository_id`、`team_id`、`asset_space_id`、`repository_kind`、`repository_identity`、`repository_url`、`canonical_path`、`protected_ref`、`credential_binding_id`、`webhook_source_id`、`status` 和审计时间。`repository_identity` 使用 provider 的稳定仓库标识，不能只依赖可变 URL；`credential_binding_id` 和 webhook secret 只引用受控凭据，不在业务表中保存 Token。P1 每个 `asset_space_id` 最多一个 active canonical repository；拆仓时以 `repository_kind: knowledge | skill` 显式区分，并保留与同一 `team_id`/`asset_space_id` 的绑定。

## 4. 身份责任与执行归因

Workbench 当前复用 DSH Desktop 的认证上下文，不以公司统一身份系统接入作为 P0 前提。后端从已验证的 DSH subject 映射 `principal_id`、团队成员和角色；客户端提交的 `team_id`、owner、approver 或 publisher 只能作为请求意图，不能作为授权事实。`desktopWorkbenchOwnership` 是只读宿主元数据，不是授权系统。

业务责任身份和技术执行身份分开记录：真实用户承担 `requested_by`、`created_by`、`confirmed_by`、`approved_by`、`released_by` 和 `owner_id`；Git bot、WeKnora adapter、SkillHub publisher、TeamLab adapter 和后台 Worker 承担 `executed_by`/`service_identity_id`。Git commit 可以由 Workbench service account 写入，但 MR、commit trailer、asset metadata 和审计必须关联真实责任人。DSH launch token、用户登录 token 和某个组件的服务凭据不能跨组件复用为通用 credential。

## 5. PostgreSQL 与外部存储边界

P0 在腾讯云为 Team Knowledge Backend 配置独立 PostgreSQL database/schema/user，使用私网/TLS、Secret Manager、连接池、迁移基线、备份、PITR/恢复演练和监控。所有团队资源、Job 和外部操作带 `team_id`/`asset_space_id`；`asset_space_id + canonical_key`、`asset_space_id + repo_path` 和 `provider + repository_identity` 需要唯一约束；每个 `asset_space_id` 最多一个 active canonical `asset_repository`。Knowledge/Skill 的 repo path 必须位于已绑定 repository 的允许 root 下，拒绝绝对路径、`..`、符号链接逃逸和跨团队 repository identity。数据库不可用、Worker 重启或外部调用半成功时必须显示 `unknown`/`degraded`/`reconciling`，不能伪造成功。

PostgreSQL 保存过程状态和审计；加密对象存储保存原始材料、附件和大型 fixture；Git 保存正式知识和 Skill；WeKnora 保存知识索引；SkillHub/TeamLab 保存各自分发状态。Workbench 通过 API/adapter 访问这些组件，不直接写 WeKnora 内部数据库。

## 6. 最小追踪链

```text
actor
  → team/asset-space/repository binding
  → creation session
  → draft/draft revision
  → merge event
  → outbox operation
  → worker job/attempt/lease
  → repository identity/protected ref/repo path
  → merge commit
  → WeKnora ingest/readback
  → asset revision
  → package digest
  → SkillHub release/readback
  → pinned digest
  → TeamAI installation/readback
  → DSH handoff/load readback
  → feedback reference/review task
```

一次下游 run 至少能反查 knowledge version/source、merge commit、WeKnora document/version/ACL、Skill package digest、SkillHub release、TeamAI installed revision 和 DSH profile/loaded digest。

## 7. 幂等和恢复

- merge event 以 `event_id` 去重；
- 知识 ingest 以 `merge_commit_sha + knowledge_scope` 去重；
- SkillHub release 以 `skill_id + package_digest` 去重；
- TeamAI distribution 以 `target + pinned_digest + profile` 去重；
- DSH handoff 以 `target + profile + pinned_digest` 去重；
- 消费事件以 `event_id`/`idempotency_key` 去重，`invocation_id` 区分逻辑调用，`attempt_no` 区分重试；
- 重试前先读回 Git/MR/index/package/release/installation/handoff 状态；
- worker 领取租约后崩溃，先 read-back 再重试；provider 已完成但本地状态未知时不得盲目重新创建；
- 所有创建、提交、发布、交接、消费和反馈写操作使用 idempotency key；
- 状态更新带 expected state/state version，旧回调不能覆盖新状态；
- 发布、交接、消费或反馈半成功、版本漂移、迟到事件和断网状态进入 `unknown`/`reconciling`，不能直接标成成功；
- 消费事件必须归因到实际 `skill_id/version/package_digest`，不能用 `latest` 覆盖历史聚合；
- 事件落库后再确认接收；
- 删除优先软退役，保留旧版本、digest、审计、历史聚合和回滚 pin。

## 8. 状态证据

| 状态 | 必须证据 |
|---|---|
| knowledge ingest succeeded | provider operation、document/version/source/repo_path/ACL read-back |
| knowledge published | ingest read-back 且实际可检索 |
| skill packaged | package manifest、package digest、source commit |
| skill approved | Git commit、CI、contract/test、approval |
| skillhub released | SkillHub release id、实际 digest、release status read-back |
| distribution installed | target、pinned digest、installed revision、文件清单和 TeamAI read-back |
| dsh handed off | handoff id、profile、target、accepted status |
| dsh loaded | loaded digest/profile/read-back |
| handoff verified | target、source/package digest、handoff response 或管理员确认 |
| feedback accepted | 外部引用、版本、问题分类和处理人 |
| consumption accepted | invocation_id、实际 Skill version/digest、actor_type、runtime/outcome status 和来源系统 |
| metric aggregate | 时间窗口、team/asset-space、Skill/version/digest、调用/主体/结果/badcase 聚合、覆盖率和更新时间 |
| unknown | provider 查询证据、对账记录和人工处理状态 |

业务原文、密钥、Cookie、密码、个人敏感信息和工具敏感参数不能进入 Git、WeKnora 正文、长期 Memory 或 trace。
