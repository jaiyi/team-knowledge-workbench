# 发布、安全与故障处置

## 1. 知识发布链

当前用户通过 DSH Desktop 认证上下文进入 Workbench。后端将已验证的 DSH subject 映射为 `principal_id`、团队成员和 asset-space 角色；认证上下文只决定请求者身份，不能直接扩大 Git、WeKnora、SkillHub 或 TeamLab 权限。用户确认/审批与外部技术执行分开记录：`confirmed_by`/`approved_by`/`released_by` 是业务责任人，`executed_by`/`service_identity_id` 是实际调用 Git bot、WeKnora adapter、SkillHub publisher 或 TeamLab adapter 的服务身份。

只有 `Knowledge Creation Session` 中的 approved draft revision 才能启动发布。发布前必须同时锁定团队资产空间和规范 Git path：

```text
Knowledge Creation Session
  → approved draft revision
  → 服务端校验 principal、team/asset-space 权限、base revision、taxonomy、repo path、来源、敏感性和幂等键
  → Git branch/MR（受控 service identity 执行）
  → CI
  → steward/审核人批准
  → 合并受保护 main
  → Git merge event（验签、去重、落库）
  → Workbench outbox operation
  → persistent worker 从 merge commit 读取 canonical 内容
  → WeKnora ingest
  → 真实读回 document/version/source/repo_path/ACL
  → 检索冒烟验证
  → knowledge = published
```

Webhook 到达、任务入队、provider 接受请求或 HTTP 200 都不能直接推进 `published`。Worker 崩溃、索引超时或读回不一致时进入 `index_unknown`/`reconciling`；索引失败必须保留旧版本，不能先删除旧文档再等待新索引。

## 2. Skill 发布链

只有 `Skill Creation Session` 中完成测试并获批准的 draft revision 才能启动发布：

```text
Skill Creation Session
  → contract/golden/regression/security 证据
  → approved draft revision
  → 服务端校验 principal、team/asset-space 权限、base revision、metadata、schema、依赖、effects 和路径
  → Skill owner + 审核人批准
  → 合并受保护 main
  → 从 merge commit 构建 package
  → 生成 immutable package digest
  → SkillHub release
  → 真实 release/version/digest 读回
  → pinned digest
  → TeamAI distribution/read-back（如启用）
  → DSH handoff/load 由下游验证
```

`approved` 只说明 Git 治理门禁通过；SkillHub release read-back 才证明 `released`。TeamAI 只能消费已确认的 pinned digest，并必须读回 target、installed revision、文件清单和实际 digest；TeamAI 安装不等于 DSH loaded。

## 3. Workbench Plugin 市场安装链

`team-knowledge-workbench` 是可复用的 DSH Desktop Workbench Plugin，可以通过宿主支持的 market/catalog 或内部受控安装路径分发给多个团队：

```text
构建 server/client package
  → canonical repository identity、版本和 digest 校验
  → DSH Workbench market/catalog 安装
  → Desktop 重启
  → client/server 注册、enabled、Session ownership 和 UI read-back
  → 团队管理员完成 team/asset-space binding
  → Workbench 可用
```

这条链只证明 Workbench package 到达目标 Desktop。它不证明 `team-knowledge-asset` 已发布、Git/MR 已批准、WeKnora 已索引、SkillHub 已发布或 Harness 已加载。Workbench host 的本地 state、ownership metadata 和 market install record 不是团队授权或资产 canonical source。Workbench 后端使用独立身份和 worker credential；DSH launch token 不是可复用 API credential。

同一 Workbench 可以被多个团队安装，但每个安装必须绑定独立的 `team_id`、`asset_space_id`、Git repository、WeKnora space、ACL 和治理策略。安装、升级、禁用、卸载和配置变更都要有审计、回滚和读回；前台 mode switch 不会自动停止后台任务，长任务必须使用显式 owner、cancellation、幂等和 reconciliation。
## 4. 分发与交接链（验证后）

```text
SkillHub pinned digest
  → TeamAI distribution request
  → target workspace install/pull
  → TeamAI installed revision/file list/digest read-back
  → DSH handoff
  → DSH profile/loaded digest/read-back
  → beta/stable profile 可消费
```

TeamAI、SkillHub 和管理员不是并列的 Skill 发布权威：SkillHub 先确认 package/digest，TeamAI 再负责目标分发，DSH 最后确认 profile 实际装载。SkillHub 不可用时，管理员只能发布同一个固定 package/digest；TeamAI 不可用时，管理员只能按同一个 pinned digest 安装；DSH loaded 未读回时禁止报告 `loaded` 或开始运行。

### 分发门禁

目标仓库和分支保护、路径/删除安全、secret 和敏感信息扫描、依赖锁定、profile 兼容、版本 pin、Hook 权限限制、幂等、安装/删除清理、文件清单读回、回滚和审计。外网或跨安全域只允许脱敏/公开样本，不得同步正式敏感知识、生产凭据或高风险工具。

TeamAI 不可用或目标能力未验证时，使用 SkillHub 或管理员发布，保持 package、digest、profile、安装读回和回滚语义。

## 5. CI 门禁

### 共同门禁

格式、schema、ID、路径、owner、sensitivity、来源、secret、个人敏感信息、重复 canonical key、链接、CODEOWNERS、受保护分支和变更范围。

### Skill 门禁

input/output schema、知识依赖、effects 和 profile 权限兼容、依赖锁定、许可证/SBOM、golden/regression、digest 生成和危险权限变更。

### 发布链门禁

- merge commit 必须与批准的 head SHA 一致；
- merge event 必须验签、去重并在确认接收前落库；
- package digest 必须由固定 merge commit 的构建产物计算，不接受客户端传入；
- SkillHub read-back digest 必须与 package digest 一致；
- TeamAI request 必须引用 SkillHub 已确认的 pinned digest，不能引用 `latest`；
- TeamAI installed digest 必须与 pinned digest 一致；
- DSH profile 必须与目标 digest/profile 兼容并返回 loaded read-back。

### Plugin 门禁

manifest、tool input/output schema、最小权限、Secret Manager 引用、网络/数据范围、依赖锁定、许可证/SBOM、宿主兼容性、沙箱/进程隔离、超时/重试/幂等、health、digest、安装/卸载清理和危险权限变更。

CI 判断机器可验证事实，不能代替业务 steward、Skill owner 或 Plugin owner 判断事实、任务价值和外部系统责任。

## 6. 审核规则

- 知识结构/格式变更：至少 1 名 steward；
- 知识事实、范围、敏感等级变更：steward + 领域审核人；
- Plugin manifest、权限/凭据、宿主兼容性、health 或安装变更：Plugin owner + 平台/安全审核；
- 跨域、机密、权限和生产写入：双人审核或额外 owner 批准；
- beta/stable、撤回、退役和回滚：明确责任人和审计理由；
- 合并前重新检查 head SHA、CI 和 approval。

## 7. 权限和数据保护

Creation Session 使用 session-scoped authorization：用户只能读取当前会话授权的 source refs、drafts、测试 fixture 和外部操作；共享来源只能以只读引用访问。所有生成、提交、发布、handoff、恢复和重试都必须带 `session_id`、`idempotency_key`、`correlation_id` 和 expected `state_version`。旧会话、旧 draft revision 或旧 provider callback 不得覆盖当前状态。

Skill 只能声明能力需求，实际权限由用户、workspace、profile、tool policy、环境和运行时授权共同决定。普通 Agent 默认看不到高风险工具；工具调用必须重新校验 schema、ACL、risk 和 approval。

Git 只保存脱敏内容、Skill 源码、测试和引用；WeKnora 按文档、空间、用户和业务域过滤；Secret 通过受控 Secret Manager 提供，不进入 Prompt、Skill、Git、Memory 或 trace。

## 8. 审计

发布、交接、消费、反馈、权限变更、索引、审批、回滚和反馈至少记录：`event_id`、`merge_commit_sha`、`outbox_operation_id`、`job_attempt`、`provider_operation_id`、`invocation_id`、`attempt_no`、`requested_by`、`created_by`、`confirmed_by`、`approved_by`、`released_by`、`executed_by`、`actor_type`、`service_identity_id`、action、resource/type、version、source commit、package/pinned digest、target、TeamAI installed revision、DSH handoff/load id、runtime/outcome status、feedback reference、badcase category/status、request、reason、result、readback status、时间和 correlation。

消费事件接入必须校验来源身份、payload schema、team/asset-space、实际 Skill version/digest、幂等键和事件时间；未知 digest、跨团队引用、重复或迟到事件进入拒绝/隔离或对账流程。指标报表不得包含 Prompt、完整输出、业务原文、Token、Cookie、密码、个人敏感信息或完整 Tool Call trace。Harness 的 session/run/tool trace 由下游保管，本项目只保存必要的消费/结果/反馈引用和聚合指标。

审计必须能关联 Git MR/CI/merge event、WeKnora index job/read-back、SkillHub release/read-back、TeamAI distribution/install/read-back、DSH handoff/load、消费引用、反馈 triage、approval 和修复版本。Harness 的 session/run/tool trace 由下游保管，本项目只保存必要的外部引用。

## 9. 故障处置

- merge event 丢失：通过 Git merge commit 对账或轮询补发；
- merge event 重放/乱序：按 event id 去重并校验 head/state version；
- outbox backlog 或 worker 租约过期：不推进 published/released，恢复租约后先读回再重试；
- WeKnora ingest 已调用但 read-back unknown：保留旧索引，进入对账；
- SkillHub release unknown 或 digest 不一致：禁止进入 TeamAI；
- TeamAI installed revision/digest 与 pinned digest 不一致：阻断 DSH handoff；
- DSH loaded digest 与 pinned digest 不一致或状态未知：禁止运行；
- handoff 部分成功：进入 reconciling，不自动创建新版本；

## 10. 回滚

### 知识

定位错误版本 → 冻结/退役 → Git 回到上一有效版本 → 重新索引 → 读回检索结果 → 审计和复盘。

### Skill

停止新的 SkillHub release → 定位旧 package/digest → SkillHub 旧 release/read-back → 旧 pinned digest → TeamAI distribution/read-back → DSH handoff/load/read-back → smoke/regression → 审计和复盘。

### 交接

停止新的 TeamAI 同步/DSH handoff → 定位 target、pinned digest、installed revision 和 handoff status → 回到旧 SkillHub package/digest → 重新提交 TeamAI distribution → 读回安装和 DSH loaded 状态 → 清理残留文件 → 审计和复盘。

### Plugin

定位 Plugin/package/installation/profile 版本 → 停止新调用 → 禁用或撤回 → 回到旧 digest/profile pin → health/smoke/regression → 读回实际权限和工具注册 → 审计和复盘。

取消 HTTP 请求不代表外部动作已取消；所有取消和超时都必须补查真实状态。
