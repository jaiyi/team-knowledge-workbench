# 问题、用户与产品范围

## 1. 业务问题

团队不是单纯缺少一个知识库，而是缺少一个可复用、可被多个部门安装，同时又能让各团队独立沉淀资产的创作发布工作台：

- 会议、资料、复盘和规则散落在文档、聊天和个人记忆中；
- Agent 可以总结，却不能把事实、决策、规则和待确认事项清楚拆开；
- 知识未经确认就进入检索，会把推断传播成组织事实；
- 同一类任务反复依赖个人经验和临时 Prompt，无法稳定复用；
- 用户说“我平时这样做”，系统却不能把它追问成输入、步骤、判断、例外、脚本和测试；
- Skill 发布前缺少样例试跑和质量证据，发布后也无法固定版本并追溯；
- Git、WeKnora、SkillHub 和 DeepSeek Harness 各自有能力，但用户需要跨系统手工搬运；
- 下游 Harness 的反馈无法判断应该修知识、修 Skill、修权限还是修分发。

因此目标是：

> 让用户在一个工作台里完成“带材料来、一起梳理、确认提交、用样例测试、审核发布”，并把发布后的资产交给 DeepSeek Harness 会话消费。

## 2. 用户与责任

| 角色 | 在本工作台中的动作 | 负责什么 |
|---|---|---|
| 贡献者 | 上传资料、描述工作流、确认草稿、提交反馈 | 输入事实和业务需求 |
| 领域 steward | 审核知识事实、范围、例外和敏感等级 | 知识正确性 |
| Skill owner | 完善工作流、确认契约、维护脚本和测试 | Skill 行为和质量 |
| 审核人 | 审核跨域、敏感或高风险资产的提交/发布 | 发布责任 |
| 平台 owner | 维护模板、权限、Git/CI、WeKnora、SkillHub 适配 | 创作发布平台可靠性 |
| Workbench 平台 owner | 维护 `team-knowledge-workbench` 包、DSH Desktop 市场/内部安装契约和宿主兼容性 | 插件版本、构建、安装、升级、回滚和市场证据 |
| 团队 asset owner | 配置本团队 `team-knowledge-asset` 的 Git、WeKnora、taxonomy 和治理 | 资产空间边界、owner、ACL、steward 和发布策略 |
| WeKnora space admin | 管理团队索引空间和权限读回 | document/version/source/ACL 对账 |
| 分发/运行 owner | 验证 SkillHub、DSH Provider、profile 和交接链路 | 下游版本到达与能力验证 |
| Harness 使用者 | 在 DeepSeek Harness 会话中消费已发布资产并反馈 | 运行效果和问题上下文 |


早期一人可以兼任多个角色，但知识责任、Skill 责任、发布责任和下游运行责任必须分别明确。

### 2.1 首期用户分层：为什么会在原有工作中使用

以下是待试点验证的使用动机和价值假设，不是已完成的访谈或用户研究结论。首期先选一个低风险、高频、可回放流程，按[角色与治理中的三类核心角色](04-角色、治理与运营机制.md#首期试点的三类核心角色)分别招募，不把所有团队成员、平台管理员或资产作者统称为“用户”。一人兼任时，仍分别记录其创作、审核、消费和业务结果确认行为。

| 用户分层 | 原有工作触发点与可能的动机 | 第一个可信的小收益（待验证） | 不足以证明的事情 |
|---|---|---|---|
| 第一推动者：业务流程 Owner | 重复提问、交接不一致或返工占用流程资源；需要决定是否值得投入领域专家与审核时间 | 能选定一类任务，看到人工基线、维护成本、消费结果引用和继续/停止依据，而不是只看到资产数 | 安装、发布或演示成功不是业务改善 |
| 第一用户（Knowledge-first）：领域专家/知识 steward | 会议或规则更新后反复整理资料、回答同样的问题，还要防止过期/无来源说法流传 | 在已有纪要/答疑中顺手留下带原文定位的候选；一次确认后可提交审阅，少做重复搬运；检索读回后才可供消费 | Agent 摘要、候选确认或索引请求本身不是准确知识或节省时间的证明 |
| 第一用户（Skill-first）：Workflow/Skill owner | 反复口述同一流程、维护临时 Prompt 和修正不一致产物 | 从现有 SOP/脱敏样例起草契约和测试，能看出差异并固定可审核版本 | 样例通过、release 或 load 不等于实际任务成功 |
| 第一受益者：一线执行者/Harness 使用者 | 做任务时需查规则、询问专家、核对步骤或返工 | 在原任务位置拿到有范围、来源、版本的可用引用，或使用固定版本 Skill；发现错误时能就地留下最小反馈引用，免于重复解释问题 | 点击、引用展示、加载或“没有反馈”不等于任务更快更对 |

Knowledge-first 优先验证第一用户是否愿意持续维护正式知识，以及第一受益者是否真正减少查找/沟通/返工；Skill 同期进入 MVP，但真实 SkillHub/TeamAI/DSH 分发不作为首个 Knowledge 业务价值闭环的前提。具体试点人员、场景及承诺成本由业务侧确认，见[试点输入卡与实施路线](08-MVP实施、验证与验收.md#2-实施路线推荐)。

## 3. 工作台用户任务

### 3.1 资料变知识

用户在「提炼知识&经验」核对来源并明确选择正式创建或修订知识后，服务端先验证资产空间、来源/基线和动作权限，才创建独立的 Knowledge Creation Session 与 Knowledge Draft；只读核对不创建会话。后续创作在该会话内完成：

1. 把会议纪要或资料放入会话；
2. 看到结构化摘要和来源定位；
3. 逐条确认事实、决策、规则、行动项、争议和待确认项；
4. 选择哪些内容值得沉淀为团队知识；
5. 预览知识资产、适用范围和引用关系；
6. 暂停、恢复或与其他会话并行工作；
7. 点击提交，由平台完成 Git 变更、CI、审核流和 WeKnora 同步；
8. 在会话中看到成功、失败、未知或需要人工处理的证据。

### 3.2 工作流变 Skill

用户在「打磨可复用的技能」核对有权候选或旧版，确认存在稳定可测试的正式新建/修订需求，且服务端验证空间、来源/基线及动作权限后，才创建独立的 Skill Creation Session 和 Workflow Draft；沿用旧版、只读核证或回宿主任务不创建。后续创作在该会话内完成：

1. 描述一个反复发生的任务及其目标；
2. Agent 追问输入、步骤、判断、例外、工具、输出、边界和成功标准；
3. 用户确认工作流草稿；
4. Agent 生成 Skill 包的说明、资源、脚本、契约和测试例；
5. 用户用脱敏例子试跑并比较结果；
6. 修改后再次测试；
7. 点击确认并提交，经 Git MR/CI、指定审核人与 protected merge 固定批准版本及 package/digest；仅选用经验证 Registry 时记录其 release，未选则标有期限的管理员固定包 fallback；
8. 工作台生成交接 metadata，供 DeepSeek Harness Provider/discovery/load 消费。

知识和 Skill 会话可以并行，彼此隔离上下文、草稿、测试和异步操作。若多个会话基于同一正式资产修订，平台必须检查 base revision，发现变化时阻止静默覆盖并进入人工合并。

### 3.3 多团队安装与资产隔离

同一个 `team-knowledge-workbench` 可以被公司内多个部门安装。安装后每个团队分别绑定自己的 `team-knowledge-asset`、Git repository、WeKnora space、taxonomy、steward、ACL 和发布策略；Workbench package、DSH market install state 和团队资产 release 是不同对象。普通创作者只在当前授权的 asset space 中创作，不能通过客户端参数跨团队读取或提交。

首期不建设通用 SaaS 多租户控制面，但必须支持明确的团队 asset-space 隔离和至少两个团队的非生产安装验证。

### 3.4 发布后的消费与反馈

发布后的会话由 DeepSeek Harness 或业务系统负责：

1. Harness 发现已发布 Skill；
2. Harness 在自己的 workspace/session 中决定是否加载和使用；
3. Harness 依据自身 profile、工具策略、用户身份和人工批准执行；
4. 业务系统保存运行结果和业务事实；
5. 下游以最小消费事件、feedback reference、版本引用、问题分类和必要证据回传；
6. 工作台校验团队、资产空间、Skill 版本/digest、事件幂等性和来源身份；
7. 工作台将反馈分流为知识复核、Skill 回归、分发故障或平台协作任务。

本项目不提供上述会话执行、工具调用、运行时人工 gate 或业务任务状态机；工作台只接收最小消费/结果引用和聚合所需字段，不复制完整 Session、Run、Step、Tool Call 或业务原文。

#### 3.4.1 指标分层

发布后的消费指标分三层实现，分别回答不同问题，不能用平台运行状态替代业务价值：

```text
价值指标：知识或 Skill 是否改善了实际业务任务结果？
采用指标：用户和团队是否真正使用、复用和维护资产？
平台可靠性指标：发布、分发和消费基础设施是否稳定、可追踪、可恢复？
```

三层指标都必须按实际 `team_id`、`asset_space_id`、环境、统计窗口、数据来源和资产 ACL 归因。Skill 消费和构建指标增加 `skill_id`、`skill_version`、`package_digest`；Knowledge 索引指标增加 `knowledge_id`、`knowledge_version`、`source_commit`、`document_id` 或 `repo_path`；Provider/Worker 可靠性指标增加 `provider`、`operation_type` 和 `operation_id`。不能为了复用 Skill 消费事件而填充无意义的 Skill 标识。没有足够业务结果证据时，价值指标显示 `unknown`，不得用技术成功、没有反馈或没有 Badcase 推断业务成功。

##### 价值指标

| 指标 | 定义 | 统计规则 |
|---|---|---|
| 业务任务完成率 | 达到预先定义业务完成标准的任务比例 | 必须有业务系统或业务结果 Owner 的结果确认 |
| 首次成功率 | 第一次执行后无需返工即达到完成标准的调用比例 | 以逻辑 `invocation_id` 统计，不把重试当成首次执行 |
| 人工返工率 | 需要人工重做、补充或纠正的调用比例 | 关联人工介入或返工结果，不把普通反馈自动算作返工 |
| 平均处理时长 | 从任务开始到业务结果确认的时间 | 明确开始、结束和业务确认时间；无法确认时计入 unknown |
| 业务错误率 | 经业务结果 Owner 确认的错误调用比例 | 只使用已确认业务结果，不把运行失败直接当作业务错误 |
| 已确认 Badcase 率 | 已确认 Badcase 调用数 / 有效调用数 | 低反馈覆盖率时只表示已观测问题比例 |
| 目标业务指标改善 | 相对于人工基线的改善幅度 | 必须记录基线、目标、样本量、统计窗口和结果 Owner |

结果状态统一分为：

```text
technical_success
contract_success
business_success
failed
unknown
```

其中技术完成、契约成功和业务成功必须分别展示：

- `technical_success`：Harness 运行完成，且没有未处理运行时错误；
- `contract_success`：输入输出 schema、effects、权限和必要约束通过；
- `business_success`：业务系统或业务结果 Owner 确认达到 Skill 的业务成功标准。

##### 采用指标

| 指标 | 定义 | 统计规则 |
|---|---|---|
| 有效调用次数 | `invocation_count`，下游实际开始的不同逻辑 Skill 调用数 | 以 `invocation_id` 去重；release、install、handoff、discovery、load、health check、CI 回归和加载失败不计入 |
| 执行尝试次数 | `attempt_count`，包括同一逻辑调用的重试次数 | 同一 `invocation_id` 的不同 `attempt_no` 分开计数 |
| 活跃消费用户数 | `active_user_count`，窗口内至少有一次有效调用的不同人类主体数 | 同一人多次只计 1；服务账号、批处理和自动任务单独统计 |
| 发布版本消费率 | 已发布且在统计窗口内被实际消费的版本比例 | 只统计有有效消费事件的版本 |
| 版本复用率 | 同一发布版本被多个独立任务或用户实际复用的程度 | 按逻辑调用或去重用户计算，不把安装数当作复用数 |
| 周/月复用用户数 | 在不同时间窗口重复使用同一资产的用户数 | 明确时间窗口和资产版本归因 |
| 反馈覆盖率 | 有有效反馈或结果引用的有效调用比例 | 反馈缺失不能推断业务成功 |
| 资产维护及时率 | 需要复核或更新的资产在约定 SLA 内完成处理的比例 | 以复核任务创建和关闭时间计算 |

必须区分：

```text
invocation_count = 逻辑调用次数
attempt_count = 执行尝试次数，包含重试
active_user_count = 去重后的有效消费主体数量
```

重试不重复计算为新的业务调用，但必须保留为独立执行尝试，用于稳定性和成本分析。

##### 平台可靠性指标

| 指标 | 定义 | 统计规则 |
|---|---|---|
| merge-to-index 时延 | Git protected main merge 到 WeKnora 可验证检索的时间 | 必须记录 merge、ingest、read-back 和检索验证时间 |
| package build 成功率 | 合法 Skill 变更成功生成 immutable package 的比例 | 按合法构建请求统计，排除重复请求但保留失败原因 |
| Provider read-back 成功率 | Provider 操作后能读取并验证最终状态的比例 | 按操作类型、Provider、错误码和状态模式分组 |
| outbox backlog | 未完成或等待重试的异步操作数量 | 区分 pending、retrying、unknown 和 dead-letter |
| retry rate | 需要重试的 Provider 或 Worker 操作比例 | 记录首次失败原因和最终结果 |
| unknown 数量 | 当前无法确认最终状态的操作数量 | 不计为成功或失败，必须进入对账 |
| unknown 持续时间 | 从进入 unknown 到完成对账或人工接管的时间 | 超过阈值触发告警和升级 |
| digest mismatch 数量 | 源 commit、package、release、安装或加载摘要不一致的次数 | 任何 mismatch 均阻断后续消费并进入对账 |
| 回滚成功率 | 回滚完成并经过 read-back 验证的比例 | 只统计有明确回滚目标和最终状态的操作 |
| provider error rate | 按 Provider、操作类型和错误码统计的失败比例 | 与业务失败、契约失败分开统计 |

可靠性指标不能替代价值指标。即使 `read-back` 成功、outbox 没有积压或 `runtime_status = succeeded`，也不能直接得出 `business_success`。

不同成熟阶段使用的最小指标范围见[指标与成熟度定义](#346-指标与成熟度定义)。

#### 3.4.2 可以看到哪些消费指标

可以按团队、asset space、Skill、版本、`package_digest`、profile、环境和日/周/月时间窗口查看上述三层聚合指标，但不能把发布、安装或加载误报成使用。报表至少展示统计窗口、分母、unknown 数量、数据覆盖率、数据来源、更新时间和最后对账时间。

“成功次数”默认分开展示技术完成、契约成功和业务成功；如果界面只显示一个成功指标，名称必须是“已确认业务成功次数”，不得用“没有 badcase”推断成功。

#### 3.4.3 最小消费事件和版本归因

每条 Skill 消费事件至少包含：

```yaml
event_type: skill_consumption
event_id: <event-id>
idempotency_key: <key>
invocation_id: <logical-invocation-id>
attempt_no: 1
team_id: <team-id>
asset_space_id: <asset-space-id>
skill_id: skill.<domain>.<name>
skill_version: 1.2.0
package_digest: sha256:...
skillhub_release_id: <release-id-if-selected>
handoff_id: <handoff-id-if-available>
target: <target>
profile_version: <profile>
actor_type: human | service | batch | unknown
actor_ref: <scoped-or-redacted-reference>
started_at: timestamp
completed_at: timestamp
runtime_status: running | succeeded | failed | unknown
technical_status: passed | failed | not_evaluable | unknown
contract_status: passed | failed | not_evaluable | unknown
business_status: passed | failed | not_evaluable | unknown
outcome_reference: <business-result-reference>
feedback_reference: <feedback-reference>
source_system: harness | business_system
schema_version: 2
```

三个结果状态独立记录，不使用互斥的单一 `outcome_status`：

- `technical_status = passed` 才能计入技术完成；
- `contract_status = passed` 才能计入契约成功；
- `business_status = passed` 才能计入已确认业务成功；
- `not_evaluable` 表示当前没有足够证据，不计入对应成功率分母；
- `unknown` 表示应该有结果但暂时无法确认，不能直接算成功或失败。

`business_status = passed` 可以由业务系统或业务结果 Owner 确认，但不能反向覆盖技术或契约状态；工作台可以校验状态组合，禁止业务成功在技术状态明确失败时直接成立，除非业务系统提供经审计的人工例外依据。

消费必须归因到实际加载的 `skill_id/version/package_digest`，不能用 `latest` 覆盖历史版本。`invocation_id` 相同而 `attempt_no` 不同，调用次数计 1、尝试次数按实际增加；只有下游明确创建新的逻辑任务时才计为新的调用。

其他指标使用独立事件类型，不复用 Skill 消费事件：

```text
event_type: knowledge_index | package_build | provider_operation | skill_consumption
```

Knowledge 索引事件至少关联 `knowledge_id`、`knowledge_version`、`source_commit`、`document_id`/`repo_path`；package build 事件至少关联 `skill_id`、`source_commit` 和 `package_digest`；Provider/Worker 事件至少关联 `provider`、`operation_type`、`operation_id` 和目标资源。所有事件仍必须包含团队、asset space、幂等键、时间、来源身份和 schema version。索引读回只证明可检索，不证明被查询、引用或帮助任务。

知识消费另拟 `knowledge_query`（查询开始与结束、含零结果）、`knowledge_retrieval`（返回的具体有权版本）和 `knowledge_citation`（答案/任务实际引用的具体版本）三个相互关联但不互相替代的事件；它们是 **Workbench 内部候选契约，非已验证 DSH/WeKnora 原生事件**。共同最小字段为 `schema_version,event_id,idempotency_key,source_system,source_event_ref,team_id,asset_space_id,environment,query_id,task_id,actor_type,actor_ref,occurred_at,received_at`；检索与引用还需 `knowledge_id,knowledge_version,source_commit,document_id,document_version`（可读回时）及授权/适用时点校验引用；查询需 `query_status/result_count`，允许 `result_count=0` 并区分空结果、被拒绝和未回传。一个查询可返回多个文档、一个任务可发出多个查询，同一版本可被重复引用，分别按 `query_id`、`query_id+knowledge_id+version`、`task_id+knowledge_id+version` 去重，不能相加当任务成功。接收端用可信来源及空间 ACL 核实引用 ID 与当时真实可用版本；无法核对的引用标 `unknown`，无源事件不补造“未命中”。是否能从目标 DSH 原生回答可靠识别**实际引用**及准确版本须经宿主 Spike；仅看到 WeKnora 返回结果时只能报告检索，不得写成引用。业务系统/结果 Owner 的结果回执独立关联 `task_id` 和预设成功标准。

原始 Prompt、完整输出、业务文件、工具敏感参数、Token、Cookie、密码、个人敏感信息和完整 Tool Call trace 仍由 Harness/业务系统按各自授权和保留策略管理，不进入工作台指标表或长期审计记录；也不得假定宿主日志原本已脱敏。

#### 3.4.4 指标归因、去重与隐私边界

指标必须使用与事件类型匹配的实际资产标识：Skill 使用 `skill_id/version/package_digest`，Knowledge 使用 `knowledge_id/version/source_commit`，Provider/Worker 使用 `operation_id` 和目标资源。指标按 `team_id`、`asset_space_id` 和资产 ACL 隔离；普通用户不应看到个人排行或原始主体标识；restricted/confidential 资产使用受控角色访问、小样本抑制和访问审计。

资产贡献归因与消费归因分离：本人可在授权范围内查看自己提交、整理、确认、审核、纠错和分享的可核验证据，并请求有权 owner/reviewer 留痕更正；审核/批准身份不得通过更正记录改写。`actor_ref` 只用于最小消费去重、版本归因和必要的反馈核验，不能关联成经理可见的个人使用轨迹、效率/速度榜、Agent 采纳率或绩效评分。管理者只能查看授权团队/任务的汇总与维护负担；低人数、交叉筛选或稀疏事件可反推个人时必须抑制、合并或隐藏，并记录报表访问。员工个人贡献视图也不得打开他人的消费原始事件或跨团队资产。

#### 3.4.5 Badcase 反馈和分流

Badcase 先进入 `created → triaged → assigned → in_progress → resolved`，并支持 `duplicate`、`rejected`、`deferred`、`escalated`。只有能够关联有效消费、Skill 版本/digest、问题分类和必要证据，并经过确认的反馈，才能计入 `confirmed_badcase_count`。

建议分类：

| 分类 | 典型问题 | 分流目标 |
|---|---|---|
| `knowledge_factual` / `knowledge_missing` | 事实、引用、范围或知识缺失 | 知识复核/MR |
| `skill_contract` | 输入输出或 schema 不匹配 | Skill 契约修订 |
| `skill_logic` / `skill_quality` | 步骤、判断、例外或结果质量问题 | Skill 回归/MR |
| `workflow_definition` | 原工作流或成功标准定义不正确 | Workflow 修订 |
| `distribution_version` | 版本漂移、digest 不一致、加载错误 | 分发故障/回滚 |
| `runtime_platform` | Harness、模型、网络或基础设施故障 | 平台协作 |
| `business_outcome` | 技术完成但业务结果未达标 | 知识/Skill 联合复核 |

重复反馈可以合并为一个 badcase；一个 badcase 可以关联多个受影响调用。反馈先形成独立的 Feedback Candidate，可受理、核验、分流、补证、关闭及回访；只有确认需要正式知识/Skill 创作或修订，并通过服务端授权时才关联新 Creation Session，权限/平台/业务问题无需创建资产会话。

#### 3.4.6 指标与成熟度定义

指标按成熟阶段逐步启用，不要求 Contract Beta 一开始建设完整业务分析平台：

| 成熟阶段 | 必须可见的指标 | 不得作出的结论 |
|---|---|---|
| Contract Beta | 平台可靠性指标，以及 schema、权限、幂等、重试、read-back 和回滚证据 | 不得宣称业务价值、真实用户采用或真实 Provider 已接通 |
| Pilot Beta | 采用指标，以及至少一个真实低风险场景的价值指标；技术/契约/业务结果分层 | 不得把 fallback 结果标为真实 Provider 成功，不得把样例成功标为 stable |
| Stable | 三层指标均可统计并按版本/digest 追溯；价值 Owner 确认；可靠性、反馈和 Badcase 达到约定阈值 | 不得把某一资产、profile 或 provider 范围内的 stable 扩大解释为全局生产能力 |

#### 3.4.7 报表、覆盖率与权限边界

报表建议同时展示：

```text
execution_success_rate = technical_passed_count / technical_evaluable_invocation_count
contract_success_rate = contract_passed_count / contract_evaluable_invocation_count
business_success_rate = business_passed_count / business_evaluable_invocation_count
feedback_coverage = 有结果或反馈引用的调用数 / 有效调用数
```

上述三个 `*_evaluable_invocation_count` 是**预先定义为应评估该层的有效调用**（排除有明确理由的 `not_evaluable`，包含到结果截止时间仍待确认的 `unknown`），因此原公式中 `unknown` 不进通过分子时，该值只是包含未决样本的**保守下界**，不是已确认失败率的补数。还需并列 `已判定样本通过率 = passed / (passed + failed)`、`裁决覆盖率 = (passed + failed) / 应评估有效调用数`、每层 `not_evaluable` 与 `unknown` 数量；不具备预先定义的任务/契约适用范围时，不得事后挑选有结果的样本作为分母。`not_evaluable` 仅用于该层按预定规则确实不适用或有审计理由不可评估，**不能**用它吞掉应有却未回传的结果。运行中/仍在截止期限内与超期缺回传分列，`failed` 只来自明确的负向证据；到达截止时间仍无结果记 `unknown`，允许迟到结果经对账修正并留报表快照/版本。

报表先固定 `team_id × asset_space_id × environment × 资产准确版本（Skill 含 digest）× 观察窗口 × 事件来源`，规定按 `started_at`/查询发生时间入窗、结果截止时间、迟到修订和双时间戳；对 `event_id/idempotency_key` 去重后，Skill 以实际开始的 distinct `invocation_id` 计有效调用，distinct `(invocation_id,attempt_no)` 另计尝试。观测覆盖率须以独立可信开始/查询底账为分母：`收到且经验证可归因的逻辑调用或查询数 / 同范围独立底账实际开始数`；底账不可得时不得仅用收到的事件推断总体覆盖率、实际总量或总体成功率，展示“不可计算”和已观测样本计数。版本/digest 不可归因的事件进隔离/对账，不得悄悄从已声明的总体分母消失；并列归因率、丢失/拒收/撤权/迟到计数与最后对账时间。真人去重必须是有权且验证过的主体，batch/service/unknown 分开，不以事件条数估计人数。

知识不用统一的“执行成功率”：对**预先圈定任务/查询范围及其目标资产版本**、有权核验目标版本/时点的查询，`正确有权版命中率 = 返回经核验正确版本的 distinct query_id / 同范围可核验的 distinct query_id`（含零结果/错误命中）；如果没有预定目标资产版本，零结果查询只能先进入任务/查询范围的总体分母，不得事后强行归到某个已返回资产版本；按具体资产版本切片仅在目标版本由独立任务真值预先确定时报告。`经复核引用适用率 = 被有权复核为适用的 distinct task_id+knowledge_id+version / 已复核该引用适用性的同键数量`，同时展示检索→实际引用的转化数、未复核引用、抽样方式与知识查询/引用观测覆盖率。若没有独立查询底账、准确版真值或无法从回答核实引用，这些率均不可计算，不得以搜索命中数冒充。业务任务结果另按事先圈定的同类任务、预设标准、业务系统或结果 Owner 回执和人工基线统计，避免只纳入用了资产的成功任务而产生选择偏差；一次 Skill 或知识被使用不等于任务因其成功。

低反馈覆盖率时，badcase 率只能作为已观测问题的比例，按**受影响的去重调用**而非报告条数计算，不能解释为真实错误率；“没有反馈”不等于“没有 badcase”。原始最小引用短期保留，聚合指标可长期保留，具体期限按安全/合规策略确定。团队决策报表还要并列人工基线、观察窗口、样本/覆盖率、待办与维护耗时、资源承诺及未知项，才能讨论继续、补充资源、缩小或暂停；隐藏的小样本不能用其他筛选或差值还原。不得据此声称岗位可替代、个人能力优劣或人力节约已证实。

## 4. 首期场景与基线验证假设

选择一个低风险、频繁、可回放的场景，例如：

- 项目复盘整理：把复盘材料整理成知识候选和行动项；
- 研究资料初筛：基于已批准知识生成带来源的证据卡片；
- 流程规则检查：依据知识规则生成结构化检查结果。

场景必须明确输入、知识范围、Skill 产出、审核边界、成功标准、Git/WeKnora 与固定包/digest（如选用 SkillHub 则加 release 读回）的证据，以及 Harness 反馈如何回流。

### 4.1 先记录、再检验的假设

业务侧在试点输入卡中确认场景、第一推动者/用户/受益者、业务结果 Owner、人工基线、目标改善、样本量、统计窗口、允许的维护/审核成本和停止条件；没有这些输入只做契约或脱敏回放，不宣称真实用户采用。以下为待证伪的问题，不预设改善数值或任何真实 Provider 已接通：

| 假设与正向信号 | 如何建立同口径人工基线与试点对照 | 失败或暂停信号 |
|---|---|---|
| H1 第一用户愿意在原有纪要、答疑或规则变更时顺手提交候选，并持续纠错，而不靠一次性导入 | 同类材料按现有方式与工作台方式分别记录整理到确认/可检索的耗时、人工修订、审核返工和每周复核负担；看持续提交和复核按时率 | 需要额外搬运材料、候选无来源、确认负担超过可接受成本，或只有平台人员代录 |
| H2 第一受益者在实际任务中使用可核验的知识或固定版本 Skill，减少查找、重复提问或返工 | 先记原任务查找/沟通、首次完成、返工和耗时；再按同类任务、难度与时间窗口记录实际引用/消费版本、结果引用与业务结果 Owner 确认；区分 Knowledge 引用和 Skill 调用 | 只见发布/安装/展示无真实消费，引用过期/越权，或任务结果不可归因、无改善 |
| H3 反馈能在日常工作中被低成本提交、分流和修复，并使下次任务获益 | 记录原有纠错路径和耗时；试点记录反馈覆盖率、被确认问题、责任人、关闭时长、新版 Git/索引或 Skill 测试证据及修复后的同类任务结果 | 问题无人接、旧版仍被引用、回写绕过审核，或维护成本抵消收益 |

先让用户在单次任务里获得**可引用的正确范围/来源或可审查的候选**，再验证持续复用与反馈关闭，最后验证任务结果改善和维护成本可接受。这是递进的正反馈假设，不把草稿生成、WeKnora 检索命中、Skill 测试通过或平台 `read-back` 当作最终收益。采用、价值和平台可靠性仍按[3.4.1 指标分层](#341-指标分层)分别观察；小样本、未确认业务结果和低反馈覆盖率只报告观察及 `unknown`。按[治理中的试点角色和成熟度门禁](04-角色、治理与运营机制.md#首期试点分布与最小配置)及[阶段 9 试点决策](08-MVP实施、验证与验收.md#阶段-9非生产试点复盘与成熟度决策)决定继续、调整或停止。

## 5. MVP 必须有

### 工作台能力

- 五个按问题并列选择的 Workbench 入口，默认「我的工作台」先提供个人 Inbox 的主动暂存入口，并展示本人有权使用、反馈和回访；DSH 原生对话属于宿主；只读查阅、来源/旧版核证、沿用已有版和返回原任务不创建会话，明确进行正式知识/Skill 新建或修订且通过服务端空间、来源/基线与动作授权后才创建对应 Creation Session 和 Draft；
- 最近创作、待处理事项和会话内恢复；
- 原始材料、Agent 草稿和用户修订的对照；
- 待确认项、来源定位、引用和差异；
- 提交、审核、发布、失败和重试状态；
- Skill 样例试跑和评测结果；
- 发布版本、digest、交接 metadata 和反馈引用。

### 知识能力

- 知识候选卡片；
- 来源、证据、适用范围、owner 和复核日期；
- Git/CI 变更、审核、回滚；
- WeKnora Wiki/索引、ACL、来源和版本引用；
- 从会议材料到知识版本的追踪链。

### Skill 能力

- Workflow 草稿和 Skill 模板化创建；
- input/output schema；
- 确需时的固定知识引用与查不到时向用户核实、工具需求、effects 和风险等级；
- 说明、资源、脚本、golden cases 和回归测试；
- 样例运行、结果比较和失败诊断；
- Git/CI 版本、review、digest 和变更记录；
- 受审 Git MR/CI/指定审核人批准与受保护分支合并、从固定 commit 构建不可变 package/digest、发布/安装/加载各层证据与交接记录；TeamAI 优先作为多端分发候选验证、SkillHub 仅在独立 Registry 契约确有必要且目标验证通过时选用，否则使用有期限的管理员固定包 fallback；

## 6. 明确不做

- 不建设本项目自己的任务执行入口和通用 Agent Runtime；
- 不复制 DeepSeek Harness 的 Workspace、Session、Skill loader、Tool Call、运行时人工 gate、恢复和完整运行观测；
- 不把完整 `Task`、`Run`、`Artifact`、`Outcome` 作为本项目的一等运行控制面；
- 不让模型直接发布知识或 Skill；
- 不让用户必须手工操作 Git、CI、索引任务或发布命令；
- 不让 Skill 自行获得工具权限或扩大数据范围；
- 不把 WeKnora 当作 Skill Registry；
- 不把 Bot Memory、群聊结论或运行日志直接当正式资产；
- 不在首期建设通用 SaaS 多租户控制面、独立业务 Plugin Marketplace、复杂 Agent 联邦和高风险生产写入；但支持同一 Workbench 面向多个团队的独立 asset-space 安装验证；
- 不因为一次样例成功就自动晋升 stable；
- 不把 TeamAI、SkillHub 或 Harness 的自动化当成绕过审核的路径。

## 7. 价值与退出标准

观察：

- 有效引用率；
- 知识候选确认率和过期率；
- Skill 样例通过率、回归失败率和人工纠正率；
- 从材料到可用知识的耗时；
- 从工作流描述到可用 Skill 的耗时；
- 发布失败、版本漂移和回滚时间；
- 下游 Harness 发现/加载成功率及反馈可归因率；
- 按实际 `package_digest` 统计的 Skill 调用次数、活跃用户数、技术/契约/业务成功次数；
- Badcase 报告数、已确认 Badcase 数、受影响调用数和反馈覆盖率；
- 版本级消费数据能够回溯到已审 Git commit、固定 Skill 包/digest、实际目标安装与 DSH 加载/交接；选用 SkillHub 或 TeamAI 时再分别关联其真实 release 或逐目标安装读回；
- 未知状态、迟到事件和版本不一致可对账，不把无反馈误认为成功；
- 重复劳动和返工下降。

如果工作台只是增加一个聊天入口，却没有减少知识整理、Skill 编写、审核交接或返工成本，应停止扩展并重新评估场景。
