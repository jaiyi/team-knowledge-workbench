# 4. 没有真实访谈时，怎样做初版和迭代

当前无法获取业务的真实访谈，仍可以基于组织工作的一般规律设计初版。初版聚焦**一个团队自己的团队资产 Git 仓库与一类获授权任务**，以团队成员在任务中查找、在资产上补充和纠错为主线，而不是先按角色分工作台。前提是分清：**什么是我们选择遵守的产品原则，什么只是尚未证实的判断，什么将来需要真实使用才能知道。** 不等数据齐全才动手，也不把经验写成事实。

## 先把三类话分开

- **初版原则**：DSH 承接当前任务中获授权的知识检索和 Skill 推荐，推荐不等于安装、加载或执行；业务 Tool 的接口和授权由外部供给方、数据责任方及宿主运行策略控制，团队资产中的目录引用或依赖声明不授予调用权；团队成员只能在本团队获授权的资产范围内贡献选中文本评论、背景、来源证据或拟修订；未经授权不能看来源或泄露摘要；未经有权人针对特定修订及范围确认、审核和发布的说法不能冒充正式结论；Agent 不批准当前业务决定；有权人可限制范围、要求补证、拒绝或暂缓；反馈有去向、修订不静默覆盖。这些是要坚持的产品约束，不能因为调用量上升就取消。
- **设计假设**：成员愿意从任务中的检索结果回到本团队资产的具体文本，留下可处理的背景、证据和修订建议；带出处和适用条件的结果比单段答案更能帮助行动；低负担选区评论比填写知识表更可能发生；聚合同类冲突、保留版本上下文能减轻有权人的核查负担；按任务和关键判断点梳理候选能力地图，比统计知识条目更容易发现具体缺口；机制以后可能供其他团队分别复用，但这不是初版的跨团队使用场景。这些是做初版的依据，目前没有真实业务证据。
- **待观察的事实**：DSH 的检索和推荐是否真的帮助当前任务而不被误认为已加载能力；选区评论、背景、来源证据与拟修订是否被用到并得到回应；确认和维护到底增加还是减少工作量，哪些问题值得沉淀，成员是否正确识别了“不适用”，候选能力地图能否帮助本团队负责人作出补证、保留人工处理或安排维护资源的决定。这些需要上线后的真实任务、授权范围内的观察和责任方核实；没有测量就明确说不知道。

## 把假设写成能够被推翻的决定

| 初版选择背后的假设 | 先做的产品选择 | 看到什么说明可能错了 | 随后怎样调整 |
| --- | --- | --- | --- |
| 重复解释的判断值得保留 | 在本团队资产的具体版本/选区关联来源、评论和同类疑点，仅对值得复用的判断建立候选修订 | 几乎没有同类问题再出现；整理维护比直接咨询更费力 | 不资产化或缩小范围，给出一次性处理回执，改为联系人/模板即可 |
| 成员需要的不只是答案，还要知道能否沿用 | DSH 中在获授权范围内检索、推荐相关 Skill；结果区分已确认结论与待核对资料，显示出处、条件、例外和未知项；推荐只供核对 | 成员仍一律重复问有权人，把“可参考”当业务批准，或把推荐误认成已安装/加载 | 区分呈现、来源还是逐次审批问题；改推荐措辞和呈现，必要时退出场景 |
| 针对选中文本贡献背景、证据和建议比填知识表更易发生 | 从结果回到本团队资产的具体版本与选区留下评论、可访问的来源证据或拟修订；无选区时保留任务疑点，并分别回访受理和修复 | 几乎没人报、评论脱离旧版上下文，或意见长期无人处理 | 调整定位与回访，明确责任和容量；不能承接时缩小范围 |
| Agent 整理与成员建议能减少而非转嫁确认工作 | 在同一修订上列证据差异、旧版范围与待核实点，有权人可限界、拒绝或补证，确认绑定特定版本 | 核对 AI 错误或意见花更多时间、待办积压 | 减少自动草稿，只处理高价值冲突；安排维护容量，不降低审核门槛 |
| 业务 Tool 的独立入口能帮助成员发现能力、了解申请条件，而非制造“已有数据”的错觉 | Tool 独立展示组织已开通且团队可发现的列表与外部能力广场；显示提供方、数据范围、申请去向、接入/授权/未知状态和 Skill 依赖；仅在宿主运行时通过权限核验后查询 | 成员把“已开通”误读为本人有权调用，把广场可申请当已获批，或在无权限/故障时仍看到伪实时值 | 收紧两种状态的措辞与运行门禁；必要时只提供原系统入口，不展示 Tool 推荐或查询值 |
| 本团队一类任务中的共性机制有价值 | 以本团队 Git 仓库为唯一资产边界，统一来源、权限、边界、版本、反馈及确认门禁 | 连这一类任务都需要重造流程，或统一模板抹掉例外 | 重新划分共性与任务特例；不承诺跨团队使用场景或已验证平台性 |
| 候选能力地图有助于找到缺口，而非制造“资产数量”目标 | 先在本团队一类任务内人工列关键判断点，关联有权查看的来源、已确认知识、维护责任与待确认项 | 有资产覆盖但实际任务仍卡住；遗漏重要判断点；只有条目数却无法说明下一步做什么 | 与业务负责人核对任务拆分和缺口原因；保留未知状态，必要时撤回覆盖结论 |

表格里的“看到什么”都是**将来应检查的反例**，不是已经观察到的结果；调整动作也不是自动规则，需要负责人结合任务风险决定。

## 如何选初版范围，而不是虚构一个试点

先按几个条件筛选本团队的**候选**任务：问题会重复、已有可查的来源、有人能确认适用边界、误用风险可控、有机会观察前后两次同类工作。初版只绑定该团队自己的团队资产 Git 仓库，接入一类任务、限定成员与资产可见范围；将任务拆成关键判断点，先标出“有确认知识/只有资料/依赖人/外部 Tool 可查询但需权限/未知/明确不适合沉淀”，再看哪些缺口值得投入。Tool 先演示外部已定义的只读接口的使用关系，不承诺初版建设 Tool 目录、接口网关或审批后台，也不把后续 Plugin catalog/runtime 的方案阶段提前当成已上线能力。采购、设备、交接等例子仅用于检查判断方式是否说得通，不能写成已有业务承诺、跨团队产品场景或用户调研发现。

设计时即使没有真实用户，也可以用公开或脱敏的模拟材料走完整流程：成员从 DSH 当前任务检索知识、看到只供选择的 Skill 推荐，结果缺条件或遇到冲突；成员回到本团队资产的具体版本选中相关文本添加评论、背景、来源证据或拟修订，无可定位资产时提交任务疑点；有权人要求补证、拒绝或限定范围，对特定草稿修订确认；受理与实际审核、发布状态分开显示，旧版停用，下一次类似任务再查找；负责成员同时从候选能力地图进入对应判断点，核对未知项。这样的演练只能发现交互与边界问题，**不能证明真实用户会使用，也不能证明业务收益**。何时开放真实任务、谁审核和哪些权限可用，仍要按正式方案执行。

## 从第一天就分辨是哪类问题

同一句“这个回答没帮到我”，可能意味着完全不同的事。初版反馈至少要能追问：

1. **没找到**：资料根本没有、无权限可看，还是检索/入口没找到？
2. **找到了但不敢用**：缺出处、条件、确认信息，还是本来就必须逐次人工审批？
3. **用了却不适用**：条件标错了、使用者理解偏了，还是出现了新例外？
4. **过期或冲突**：本团队资产的来源变化、不同适用条件下说法不同，或旧版未及时停止引用？
5. **不值得沉淀**：偶发、变化太快，还是长期维护成本高于复用收益？

不是每个反馈都要生成知识。选中文本评论还须保留本团队资产 Git 版本及原位置，版本变动后不能静默把旧评论当成新版意见；背景、来源证据和建议只在获授权的范围内可见，不因成员能贡献就获得确认或发布权。反馈应让有责任的人能区分“改呈现、补依据、修订结论、按当前业务流程处理、停止资产化”；成员能看见受理与处理去向。获取信号要最小化，只收能完成授权处理所需的信息；不要保存敏感业务原文、凭证、完整 Prompt/Tool Call trace，也不能为了衡量效果重建个人使用画像。

## 用真实使用来决定下一步，而不是用发布量宣布成功

接入真实任务后，先留出观察窗口，记录没有产品时本团队怎么处理同类问题，才有可比较的起点。再分别看：成员拿到**可用且适用的判断**花了多久；背景、证据和建议是否被用来处理真实疑点；重复答疑减少了多少、确认审核维护新增多少；不确定和例外有没有正确交回人处理；误用和返工是否上升；同一团队第二类任务能否复用机制。其他团队日后能否分别复用产品包仍是更远的待验证问题，不做初版跨团队工作流。缺少业务结果或反馈覆盖时只能说“尚不知道”，不能用发布、推荐、安装、加载、Agent 调用数代替实际工作效果。

这不是要求第一版就给出精确的收益数字，而是要求产品**能被证伪**。若复用发生且质量没有下降、维护投入可承受，就继续；若入口错了就调整入口；若专家负担过重就缩小正式知识范围或增加维护资源；若错误增加或价值长期低于成本，就暂停该场景，考虑更简单的组织办法。业务结果需由有责任的人结合真实任务确认；产品团队不替他们宣布“已节省人力”。

## 真实试点前的原始素材、研究和独立复核协议

**以下是待执行协议，不是已取得的访谈、试点或收益报告。** 先由业务侧按[实施验收的阶段 0](../方案/08-MVP实施、验证与验收.md#阶段-0方案冻结与实施输入)确认一类低风险、可回放的任务、第一推动者/第一用户/受益者、业务结果 Owner、人工基线、目标改善和停止条件，并明确样本访问权、保存范围、观察窗口与有权复核者；未确认不能把静态原型演练当成 Pilot Beta。

- **从未经整理的一手样本开始**：在获准范围内查看一项真实任务最初怎样被提出、当时成员实际看得到的原件版本与生效日期、原业务系统的当时及最终回执、群聊/邮件中的反复求证和改口、现有模板或联系人怎样被使用、有权人现有纠错/过期审核流程。刻意纳入成功、失败、未找到、找到却没用、使用后发现不适用、主动放弃使用的例子；没有可回访结果的任务单独标未知。产品说明、模型总结、竞品、虚构周报及浏览器 fixture 仅用于提出问题，不能取代这些原始样本。禁止将受限报告/PPT 原文、客户信息、生产凭据或完整会话/Tool Call trace 粘入普通团队资产与研究交接。
- **用逐例方法检验而非问“想不想用 AI”**：现场观察受益者按旧流程完成同类任务，做关键事件访谈与任务时间线（发问→寻找→核条件→请人确认→办理→结果）；把每个关键判断写成“当时可见来源/版本/时点/授权→提出的说法→反例与未知→责任人的选择→业务回执”。对同类任务比较人工基线与受控试用，记录使用者找证、贡献者整理、专家核证/纠错及后续维护**总时间**，同时记录返工、误用、正确停下交人的次数。预设竞争性解释：也许是检索入口而非知识缺失、源文件本身过期、权限不给、规则必须逐次审批，或联系人/模板更省事；不能把所有改善都归功于 AI。
- **工具与可审计记录**：使用按任务编号脱敏的观察表、证据登记表（来源系统、版本、时点、访问资格、允许引用范围、未读部分、复核人）、判断点时间线、盲评用的脱敏同类题和人工基线/试用对照表；仓库的版本化方案文档及静态原型仅用于跟踪设计假设和交互回归。真正的业务状态、Git/CI、WeKnora、SkillHub、DSH 和 Tool 各自从其有权系统读回；`fake/admin` 契约测试不代替 `real` 提供方证据。
- **谁能证明什么**：来源责任方核原始记录、权限与生效期；业务结果 Owner 对照原任务及原业务系统结果确认正确性和负面影响；未参与设计的同领域复核者在条件允许时盲评边界/异常案例，有权维护人核实际确认和维护负担。技术团队只对版本、权限隔离、Provider 读回及回滚证据负责。三方意见冲突要保留异议并补证；结果未知不计成功、不计失败，无反馈也不等于无误用。小样本汇总不做个人画像或排名。

按业务侧预先确认的观察窗口、目标和停止条件作决定：若可比任务中的正确适用与正确停止改善、总投入可承受，才继续；若只是找不到已知内容，先改入口/模板；若专家核对过载，收窄正式知识和维护范围；若必须逐次审批或安全误用增加，回原系统/人工并暂停该场景。没有基线、授权、结果 Owner 或足够结果回执时不宣布收益，记录缺口和下一次复核责任。上述研究的执行和真实 Provider 验收仍以正式实施路线为准。

这一篇不是访谈计划，也不是已验证价值报告，而是初版的**假设与学习机制**：先让组织能够安全地试用一条完整闭环，然后让真实反馈决定下一步长成什么样。
