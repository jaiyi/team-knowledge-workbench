# 3. 产品蓝图：让工作中的判断可复用、可核对

[前一篇](02-知识工程难在哪里.md)指出了五处断点：选错要留下的内容、新任务里不知能否适用、确认与维护责任失衡、使用与纠错离工作太远、只统计活动却不知效果。本篇逐项回答：**同一团队的成员在 DSH 原生任务中怎样取得可核对依据、主动挑选值得留下的线索；Workbench 怎样把获准来源和任务线索变成可讨论、可修订的候选，以及哪些动作仍须有权者对特定版本负责。** 不按“员工页/专家页/管理页”拆分产品入口。这是拟设计的体验，不是已上线功能或已验证的用户需求。

初版只围绕**一个团队自己的团队资产 Git 仓库**：成员在 DSH Desktop 原生对话中完成业务任务；知识检索、Skill 匹配和外部 Tool 查询的具体呈现，均须以宿主实际能力、接入和授权核实为准，不由 Workbench 复制原生会话或预设已集成。Workbench 默认首页称「我的工作台」，在原有个人使用反馈与行动索引旁加入本人**手动保存、回访和删除**的个人 Inbox；[HTML 原型](可视化原型/index.html)以浏览器内存示意虚构 Inbox 线索暂存、查看、删除和到知识页的待核提示，同时保留固定虚构的个人使用情景、失败反馈和其它入口，**不代表真实保存或授权**，不以导入材料为进入工作台的前提。Inbox 不自动采集 Session、反馈、Git、WeKnora 或既有本地 `knowledge-inbox/deposits/`；拟议以 PG 存最小元数据、可有权回读时只存原系统引用，获准复制才存加密对象副本，均非已实现集成。成员从个人项转团队须就具体内容、来源及目标再次授权；反馈路径与团队审核门禁仍各自独立。进入材料梳理或已有资产处理路径后，获准文档或已有资产才是主要输入：先核具体任务场景下的来源、时间、权限及现有版本，再决定引用、补证/修订、新增候选或不沉淀。成员觉得原生任务中某次调整值得留下时，也可**选择**主动复盘，核对可见证据、复用边界与分享范围，再人工交接最小线索；任务不需要复盘才能完成。Workbench 在 DSH 中承载 LLM 辅助的知识提炼、Skill 草稿打磨与质量核对，并让成员从一个入口看审核进度；指定审核与正式版本仍由 Git 审核合并判定，不是模型或站内按钮批准。PostgreSQL 除链接/资产 ID 映射和团队连接配置，还保存个人 Inbox、待核候选、创作会话/草稿修订、评论、授权作用域、异步操作及读回对账等工作过程；正式知识与 Skill 源码/版本归 Git，获批知识的授权索引与检索归 WeKnora，原生任务和 Skill 实际装载/运行归 DSH。Workbench 在本团队权限范围内仍负责组织来源/线索受理、已有版对照、讨论、修订与回访；稳定、可测试的步骤才进入 Skill 创作。Tool 的供给和授权由接口提供方、数据责任方及宿主运行策略分别控制，团队仓库只记录允许公开的使用关系与 Skill 依赖，不储存实时数据或凭据。任务实时状态、当前业务审批与执行仍留在原业务系统。产品里至少要区分**来源资料与工作记录、有时效的当前事实、当前问题/反馈、待确认的候选判断、已确认的特定版本知识、Skill 的推荐与实际运行状态、获授权的实时查询结果、当前业务决定**。一次复盘、提问或评论不会自动生成正式知识，引用知识、推荐 Skill 或查到数据也不等于批准当前业务。

这条链不是“导入纪要 → 自动生成 Skill”：纪要、周报、交接、报告只是可能的来源，原件默认留有权原系统；Workbench 管最小定位/核证线索，不提供持久原文阅读或默认来源全文索引。确有 WeKnora 对应来源文档且权限/精确深链可核时才跳外部阅读，必要副本的保留另行授权；事实需核发生和生效时间，经验需核条件与反例，Skill 需核步骤、测试、权限及停止点。Workbench 可以协助主动识别来源中的**零到多个待核增量**，先比对有权查看的现有版本，重复、无增量、证据不足或不值得沉淀也要有去向；用户讨论过候选不等于事实已核准或正式资产已发布。私有部署的大模型和受控环境是处理获准资料的**设计前提**，不是此刻已接通 DSH、资料库或生产模型的证明，来源权限、复制、留存与目标页重新授权仍分别核验。

想直观看到其中的部分交互，可打开[Workbench 可视化产品概念稿](可视化原型/index.html)（[演示路线与边界](可视化原型/README.md)）。它以内置 **111 行完整虚构合成周报**和仅由指定本地文件字节指纹命中的人工线索，示意五步材料工作区、同 ID 事实／经验对照、第四步本地去向树及可跳过的第五步；文件选择器可在本机阅读全文读取小型 UTF-8 TXT／MD／CSV，但不会为任意文件自动抽取。也用虚构数据示意 DSH 任务、主动复盘与手工交接候选、工作记录及业务对象线索、知识创作/讨论与特定修订的确认发布、候选能力地图；这些均非真实 DSH、模型、授权检索、Tool 调用、Skill 测试、Git 写入或资料库集成。下文的问题聚合、回访及异常去向是拟设计的产品流程，不表示原型已逐一实现；原型也不是已安装的插件。

| 第二篇的断点 | 从成员目的出发的触点 | 失败时必须有的去向 |
| --- | --- | --- |
| 选不对要留下什么 | Workbench 对获准的完整材料先逐段核覆盖、来源资格、当前事实与旧版适用，再通过去向文件树决定引用、补证/修订、新建候选、回原系统或不沉淀；Skill 核对仅为可跳过的第五步 | 记录不等于当前事实；核不到版本、时间或权限就保留待核问题，不凭空新建 |
| 新任务不知能否适用 | DSH 原生任务中按接入能力核对来源、版本、边界及 Skill 状态 | 缺条件、冲突、过期或无权限时停下找人；推荐不自动加载 |
| 确认和维护负担失衡 | 同一资产修订上的证据、讨论与有权人版本确认/维护 | 补证、拒绝、暂缓或无人承接时不自动通过 |
| 工作中用不上、错了难反馈 | 自愿复盘交接或进入 Workbench 具体对象/版本评论，按实际宿主能力设计回访 | 受理不冒充修复；任务继续按原流程办理 |

## 1. 选什么留下：先核文档能否补足具体场景，再决定创作

Workbench 的输入有两类：一份获准使用的纪要、周报、交接材料、制度或报告走左侧「提炼知识&经验」，同一个材料工作区以「导入来源 → 事实梳理 → 经验总结 → 加入知识库」为共同四步；团队已有或外部形成的 Skill 则走独立「打磨可复用的技能」，从其有权来源定位、准确版本／digest、适用任务、步骤依赖和测试证据开始，不要求先处理一份周报。本团队已有资产的一句争议文本仍可从有权资产详情进入指定修订。正式产品拟在符合 Skill 缺口条件时才提出可跳过的第五步「Skill 核对」，当前静态 HTML 则始终显示可跳过的第五步导航，不核实缺口。导入获准分享、版本可定位的完整本地文件，或在知识入口明确选择经服务端授权且目标受限获取/解析能力已验证的来源链接，或在不宜展示真实材料时使用篇幅与章节覆盖足以演练全篇处理的完整合成材料；Inbox 仅留链接定位，不因保存而抓取。只读到部分、未取得附件或无权读取时显式标注覆盖缺口，不能把缩写当全文。事实梳理、经验总结各以当前选中项待核稿／评论（桌面约 2/3）为主，旁侧约 1/3 同步对照这一项可访问的已有事实记录或正式知识准确版本；右侧随选中项更新、随主内容滚动而不悬浮固定或停在前一项，移动端对照接在本项之后，各项逐条标证据状态。事实梳理中的数字先核指标口径与有权报表，仅在当前身份、用途、字段/对象、时间窗与只读通道获授权时就地核 Tool，不另起步骤。「加入知识库」以去向文件树预览来源留原系统／获准阅读、时点事实回权威系统、经验及有条件的正式知识候选、规则待核、报表与计划回原任务等独立路径；只有可核的知识候选才预览 `knowledge/<domain>/<topic>/<knowledge-slug>/`，不能为来源、事实、计划凭空建 Git 文件。若重复稳定可测且有既有 Skill 质量缺口或真正新增理由，才进入第五步比较合成 Skill／人工写法、预览门禁或选择跳过；这不是 Skill 试跑或受控创作。**不设独立能力体检页/按钮**；材料第五步只是到 Skill 质量核对的可选关联，并非独立「打磨可复用的技能」的替代入口。引入只表示先核候选，不等于已经接收 Skill 包、批准团队版本或完成目标安装；指定旧版的知识修订与 Skill 的受控创作仍按各自门禁进入深层工作区。成员选择“这份材料将帮助哪类任务、哪个项目或产品线、在哪段时间里作什么判断”，Workbench 才核来源权限、版本、时态、旧版适用及反例；固定 fixture、工具目录可见或周报自述都不是已核证据。须区分原话究竟是已发生事实/计划/建议/已批准规则，核对象、适用及失效时间、反例与停止条件；同时在成员获授权范围核现有知识的精确 ID/版本、可见权限、确认状态和适用范围，Skill 则另核发布与目标安装/实际运行状态。仅语义相似或材料提到某方法，不证明这一场景已有可靠能力；检索不全、版本不明、过期或无权读时明确“无法核对”，不能推断缺失或以受限摘要泄露内容。只有确认这份来源相对当前能力的增量及维护责任，才进入后续候选；原文可查、模型会归纳，都不等于已确认的知识或可执行 Skill。

DSH 原生任务中的主动复盘是**可选的另一入口，而非导入文档或创作知识的默认前置步骤**：成员觉得某次有可复用调整时，可调用复盘 Skill，回看可见的任务过程，分清知识只是被提及还是确有版本化引用，Skill 只是被推荐还是实际加载/执行，Tool 只是被提到还是有授权调用回执。成员讨论复用性与分享范围，再自行复制最小、脱敏的候选到有权创作会话；或者先手动存为仅本人可回访的[个人 Inbox 项](界面功能设计/02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)，以后选择具体内容/来源/团队目标再次授权后才提交团队；没有宿主记录便写“无法确认”，不能自动抓取完整对话、产物或运行轨迹。未提交则 Workbench 不显示“已收到”。报告、PPT 等需要留存时先核来源与分享授权，走实际可用的资料入口；资料入库与正式知识修订是两条路。复盘 Skill 本身只是拟议流程，不因存在本地实例就认定已安装成团队能力。

Workbench 对获准提交的纪要、周报、交接材料或复盘线索使用同一套**先核来源、再识别增量**的处理逻辑：先区分来源原话、计划/意见、当前业务对象事实、可复用判断与描述性方法；关联项目/产品线等本团队查找线索，但不把记录标题或时间线当权威事实。Agent 可提出零到多个待核议题，对照可见的既有知识版本，分别指向已有引用、补证、指定版本修订、待裁冲突、可核查重后的新增或不沉淀；检索不可用、来源无权、版本不明时明确“待核”，不宣称没有重复。核对结果按**四种去向**给成员和负责人看，而非让每份文档自动触发创作：**① 已覆盖，引用准确版本**——本次对象、时点、条件与权限均匹配时给出可查依据，必要时改善查找入口；**② 已有判断但证据或边界待补，补证/指定版本修订**——带新来源、反例或有效期变化回到原 ID/基线，不复制出一条相似知识；**③ 可核实尚未覆盖且值得维护，提出新增候选**——先请有权者核证条件、维护责任，稳定步骤才另评估 Skill；**④ 不宜创作或暂不可核，留来源/待核问题或回原任务**——一次性状态、计划、缺权限、缺版本、来源冲突或检索不可用不强行提炼。冲突在②或④中并列保留来源，待有权者裁定；这四种是处理建议，不是模型替人批准事实、发布版本或运行 Skill。

未来在授权和目标环境能力核实之后，可以让受控的**子 Agent 分别核文档来源、现有知识/Skill 的精确版本及场景条件**，汇总支持与反证供人比较；子 Agent 只能读取各自有权范围，结果注明不可见/未知，不因多路分析就当作独立权威。**当前可视化原型未进行真实的子 Agent 比对、目标环境检索或运行核验**，固定样本/预编排结果只用于演示交互，不能显示为真实能力核对已完成。只需描述**眼前卡在哪里**，或对已有回答选一个原因：没找到、两份说法冲突、这次不适用、疑似过期。找到本团队已有资产时，可以选中相关文本留下评论、补充理解所需的背景、贴上有权访问的来源位置或提出拟修订内容；没有资产时保留任务疑点，待人判断是否值得沉淀。不要求先选知识分类、编写条目。入口必须在当前团队获授权的工作范围内；敏感材料只记录完成处理所需的最小信息，不把原文搬进公开队列。

要处理这些贡献时，负责成员可以按问题聚合查看关联的团队资产路径与版本、选中文本位置、已有资料或结论、重复线索、尚缺证据与当前处理人，而不是先进入“资产负责人后台”；**原型中的内容讨论与修订提议仍是虚构示意，并未实现问题聚合或独立收件箱**。拟设计的处理动作是：**关联已有知识并改善呈现；合并同类反馈；请贡献者补背景或来源；建立待核实候选修订；转交当前业务负责人处理；说明该问题一次性或变化太快，不予沉淀。** Agent 可协助比较、去重和起草疑点，不能自行判断“这条值得正式发布”。一次性处理和不予沉淀都要给提问者可理解的回执。

只有当问题可能重复、复核成本值得投入、依据和适用条件能说清、维护责任能落实时，才进入候选判断。候选保留原问题、资产版本与选区定位、来源、尚缺证据、拟适用范围、负责人和下一步；**已保存评论、已分派、待确认、正式可引用**不能合成一个“完成”状态。源文件修改后需核对原选区是否仍对应，不能把旧评论默认为对新版的确认。若找不到有权确认的人，显示待决定并交业务负责人安排人手或缩小范围，不让积压被默认批准。

## 2. 成员在任务中怎样判断“这次能不能用”

团队成员在 DSH Desktop 的**原生对话**中询问具体问题并自愿补充必要条件，例如事项类型和适用时间；未知条件允许留空。若目标宿主的团队知识检索与 Skill 匹配能力经接入和授权验证，可展示该成员有权查看的结论及相关 Skill 线索，附推荐缘由、来源/版本、范围、所依赖的外部 Tool 与待核条件，不把推荐等同安装、加载、执行或授权；若尚不支持，先在原生任务中给出可核查的来源去向或由成员手动打开 Workbench，不假装插件已在聊天里显示结果卡。Agent 不得把看不到的来源改写成泄露内容的摘要。若业务系统尚未连接，产品**不能假装知道当前任务的实时状态**，必须让成员自行核对或回到原系统。

若宿主可验证地展示团队检索结果，目标是让人看见可核对的来源、版本与状态，而不是一段不分来源的“最终答案”；**结果卡只是待验证的呈现方式，不是初版必须嵌入 DSH 的控件**：

- **当前可参考什么**：本团队资产中已确认的结论、对应 Git 版本、来源和确认范围；若只有资料或 AI 整理，直接标为“供核对，尚未确认”。Skill 推荐单列为可选线索，不冒充已加载能力。
- **要满足什么条件**：适用条件、例外和需重新复核的时间或变化；明确哪些条件已由可靠来源核对、哪些仅由员工填写或尚未知晓。
- **下一步能做什么**：查看有权访问的依据、补充条件、请有权人确认；在已验证可用的跳转能力下从结果进入本团队资产具体版本和文本讨论，否则手动打开相应资产，报告“这次不适用”并补背景、证据或拟修订。即便全部条件看似满足，也只表示结论在已确认的范围内**可供参考**，不表示当前业务获批。

有相关资料但没有确认结论时，停在“资料可参考，不能据此宣称已确认”；条件缺失时提示补条件或找人；来源冲突、疑似过期或超出适用范围时并列呈现分歧，标明“暂不能据此判断”及负责的处理路径；成员无权看依据时不给泄露内容的答案或 Skill 推荐，提示申请授权或走既有人工渠道。没有有权接手者时，不能显示一个虚构的“已转交专家”，而要提示业务负责人待分派和当前任务仍需按原规则处理。

产品要观察的不是“回答或推荐了几次”，而是成员是否在同类任务中更快找到**能核对、适用或明确需要人确认**的结果；成员仍反复找有权人时，要区分是入口没找到、结果缺证据，还是该任务本来就必须逐次审批。

### 实时数据由外部 Tool 提供，不由团队创作或授权

知识解释判断依据，Tool 从业务系统获取当前事实，Skill 可以按稳定步骤组合二者。例如 `get_product_inventory(product_id)` 查询 ERP 库存，`get_part_price(part_id)` 查询采购数仓价格。两者都只是**外部供给的只读接口示例**，并非本团队已接入的能力；价格还可能有字段、用途与对象范围限制。查询结果需标明接口/数据来源、查询时间、适用字段与权限范围；查询失败、数据过期或状态不明时不能拿历史文档补成“当前值”。Agent 使用查询值给出建议，也不能替人下业务决定。

在 DSH 任务中，成员可看清“组织已开通的 Tool、须申请权限、未接入、不可用/状态未知”，只在宿主确认当前调用身份、环境、工具策略及数据授权后才能实际查询。Workbench 左侧设独立的**业务接口目录**，不把接口目录塞进资产发布页：**团队可发现**列出组织已开放且当前团队可发现的 Tool，点击看用途、提供方、数据责任方、输入输出、字段范围和依赖 Skill；**待申请**展示允许团队发现、但尚未对本团队开通的能力及申请去向。这里的“已开通”不是当前用户/服务身份已获调用权，广场中的“可申请”也不是已经获批；目录条目的可见性本身仍按接口提供方策略控制。Workbench 只展示获准公开的外部 Tool 目录引用与团队使用关系，不在此新建生产接口或批准数据访问。ERP 接口可能由 ERP 系统与库存责任方负责，采购价格可能由采购数据责任方与数仓平台共同负责，授权方不固定为数仓中台。团队仓库中的依赖声明不等于外部目录已注册、接口已部署、团队已获授权，更不等于此刻这名成员/服务身份允许调用；真实凭据、授权、调用和审计均留在外部平台及宿主运行时。写库存、下单等写操作不沿用查询门禁，需另行设计更严格的审批和执行约束。

目录预计包含大量接口，两类列表都应按数据中台/提供方接口返回的业务域、源系统和用途标签（如 ERP、MES）搜索、筛选并分页；Workbench 只消费有权发现的标签和详情，不创建另一套分类权威。详情展示参数结构和限制；只有经提供方允许的低风险只读 Tool 才可通过受控宿主/提供方测试通道试参，广场或无权者不可直接请求生产接口。Tool 目录以外部 API 为主；若团队需要实际调用次数，应另据获授权的宿主成功调用回执按团队、Tool 和时间窗做最小化 Postgres 聚合，试参、浏览和推荐不等于实际调用，数据缺失时标“暂无法统计”，不存参数、结果或个人使用画像。

## 3. 从成员建议到有权确认：让维护负担有去向

同一团队的成员可以因为发现疑点而提出评论、证据或修改建议，也可能依授权承担确认工作；这是**同一资产的不同动作**，不要求分别进入“贡献者页”和“专家页”。有权人处理待确认修订时，看见具体争议、指向本团队 Git 仓库中哪个资产版本和选中文本、可查来源、旧版结论与适用范围、缺失条件、相关反馈，以及确认将影响哪些获授权的使用者。原资料的说法、成员提供的背景与证据、Agent 的推断、此前的人类确认要分层展示；不能让有权人替未经核实的摘要承担责任。

有权人可以**确认特定草稿修订和适用范围、缩小范围、要求补证、暂缓、拒绝或指出该事项必须回到业务会议/审批**；每个决定有真实责任人、理由和回执。评论和拟修订不是批准；草稿改动后原确认不沿用，旧版错误需提示停止引用并关联修订，不能直接覆盖历史。必要的会议仍由人召开，Workbench 负责把待决定点和证据准备好、会后记录有权人确认的结论，不替会议作取舍。通过确认仍不等于发布：正式审核、Git/CI、人类批准、Provider 读回和权限门禁按现行方案执行。

评论/待补证与待确认、待维护分开呈现为资产上的状态与处理视角，而不是强制的角色化导航：获授权的负责成员查看即将复核、冲突、无 owner、延期与积压，并可请求转交或升级；无人实际接收时责任不自动转移，版本也不自动发布。业务负责人据此决定投入时间、调整优先级、限制知识适用范围或继续人工处理。贡献者能看到自己的意见去向并申请更正归因，原确认、审核身份仍留痕；不以答题速度、反馈数量或 Agent 使用量评价个人。

要验证这一设计，需同时看重复解释是否减少、核对 Agent 草稿与成员建议及维护占用了多少时间、拒绝和补证是否能真实生效。若确认者更忙或待办积压，就缩小需正式确认的内容或补维护资源，而不是把“待办清零”当成成功。

## 4. 使用和纠错怎样嵌进日常工作

优先让成员在 DSH **原生任务**里完成工作，不由 Workbench 再造聊天或要求每次提问都写反馈。初版可让成员按需主动复盘，核对最小线索后手工交到 Workbench，或直接从团队有权查看的对象、来源和资产版本进入内容讨论；来源和权限经核实后才关联选中文本。宿主若以后验证支持轻提示、来源结果卡和最小上下文深链，再改进从结果进入评论及返回任务的路径，不把任务结束事件、自动总结卡、插件嵌入会话或完整 trace 读取作为初版依赖。业务系统暂时无法集成时，保留任务旁链接或责任人登记，明确说明仍需离开原任务。问题可按“没找到、看不懂/不敢用、条件不符、资料冲突、疑似过期”选原因；若没有对应资产选区，保留最小化任务疑点。关联**成员有权引用的**版本和来源，不强制提交完整聊天、完整 Prompt、Tool Call trace 或敏感业务原文。DSH 的 Skill 推荐不因反馈或评论自动安装、加载或运行。

成员在 Workbench 提交后可凭真实受理回执，在相应资产讨论位置或后续回访入口区分“已收到 → 已分派/待补充 → 人正在判断 → 已有处理结论/不予沉淀”。初版返回 DSH 原任务可由成员手动完成，精准跳转及原任务中的回访提示须等宿主导航能力验证；**仅复制线索、未提交时不显示已受理**。还要分清**问题有了去向、知识版本已更新、当前业务问题已解决**，后两者不是前者的自然结果。评论锚点随 Git 资产版本保存，换版后要提示是否需重新定位或复核，不将旧评论静默当新版的同意。若反馈触及当前任务的审批或安全风险，成员仍按原业务流程立即处理，不能等待知识修订代替业务处置。负责成员回应“只是展示不清”“需要补依据”“需要重新确认”“这次是例外”“不适合沉淀”时，应说明下一步由谁负责；已修订的结论也要在下一次类似使用中才能检验是否更好。

反馈、选区评论、背景、证据与建议修订的访问和分派都沿用**本团队资产与原来源权限**：本团队成员也只有在获授权时才能查看，不能把敏感来源或他人的工作轨迹转给无权者；初版不提供跨团队报告或跨团队资产贡献。只有在获授权、最小化且有小样本保护的条件下，才汇总问题类型和后续结果；没有反馈不代表没有错误。

## 5. 团队怎样看见能力与缺口，而不是看个人排名

这里的**团队能力**是本团队在明确情境下完成一类任务的本领，由人的经验、依据、流程、工具和责任共同支撑；**沉淀程度**是其中哪些关键判断能被本团队其他获授权成员可靠复用；**维护容量**才是有无人手和时间持续修订已有内容。十篇文档或三个 Skill 推荐不能直接等于十项或三项能力。

第一版先由本团队获授权的负责成员在**一类限定任务场景**中人工梳理候选能力地图：列任务、典型情境、关键判断点与停止点、责任人，关联本团队已有资料、已确认知识、稳定步骤及 Skill 是否真有目标安装/运行证据、外部业务 Tool 的接入与授权前提，以及仍需逐次人工决定的部分。一个示意任务“设备异常处置”可拆成识别异常、判断影响、选择处置、升级审批和复盘；这是用于设计的拆法，不代表已盘点任何真实团队。地图按任务浏览，点击关键判断点进入有权查看的知识或 Tool 使用关系，看“依据在哪、数据从何而来、谁能用、确认到哪版、哪些条件不清、谁负责处理”，再选择**补证、请人确认、申请 Tool 接入/使用资格、改入口、安排复核或明确保留人工路径**；能贡献的成员可在具体资产选区留下意见，无权者不能据此确认、发布或调用数据接口。检查的是**此场景能否在已知条件下可靠完成关键判断、遇到例外能否停下并交给人**，不是“几份资产覆盖几步”的自动能力评分；无真实任务证据只能称为“候选地图”。

每个判断点分别显示：完成任务是否有真实结果证据、依据和边界是否可靠、本团队其他获授权成员能否复用、变化后能否更新、投入是否值得；**不合成一个能力分**。缺口状态要能分开：有人会但没留下依据；只有资料没有确认判断；结论缺边界或过期；有内容但找不到或无权使用；可用但缺维护人；已有使用却缺结果证据；以及“这里本就需要逐次人工决定”。获授权的负责成员看到本团队范围内各状态与未知项，分母必须是**本次已梳理的任务和关键判断点**，不能推成全组织的能力覆盖率。

授权范围内的任务观察要分成两组可解释的信号：**效率**看同类任务中找到适用依据、完成必要确认所花的时间，重复答疑、返工和核证维护投入是否净减少；**管理**看本次梳理的关键判断点里哪些证据/权限/责任缺失、例外是否被正确升级、待核与维护积压有没有真实去向，以及负责人是否据此安排补证、维护资源或保留人工路径。业务结果须由责任方核实，设定同类任务的前后对照，缺基线或反馈覆盖不足便写“不知道”，不把资产数、Skill 推荐、安装、Agent 调用量当成收益或能力覆盖。业务负责人不能查看个人消费轨迹，不能以 `actor_ref`、提问量、贡献量、处理速度做画像或排名。小样本和筛选组合可能反推个人时应抑制展示。候选地图的价值也待检验：如果内容“覆盖”但真实任务仍卡住，说明判断点拆错、入口不对或所谓覆盖根本没有得到验证。

主动性也分阶段：先由成员在任务后自愿复盘、在 Workbench 留下可查的线索；待版本、来源时效、权限和责任链可核验，才尝试对限定场景主动提示冲突、复核超期或 Skill/Tool/人工衔接缺证的**待核候选**，请有权者判断，失败或证据不足时不制造待办或“已诊断”的错觉。未来所谓“数字员工”只能作为单独待验证的方向：先在明确任务、输入权限、知识适用边界、Skill 测试、Tool 授权与停止/人工交接都核实后再讨论可委托范围；不因候选地图或主动提示就获得自动执行业务和审批的权限。

## 一次贯穿演练：从无法判断到下一次可参考

以下是**虚构的产品演练**，不代表已有真实业务规则或试点：同一团队的成员在 DSH 原生任务中问“该用哪版清单”。若已核验团队检索接入与授权，宿主可提供旧纪要 A 和新模板 B 的来源及可见版本；否则成员从可用来源入口手动核对，不能假装已自动检索或显示结果卡。两份来源缺少任务类型与生效时间，不能确认；若有相关 Skill，只将推荐当待核线索，不安装或加载。成员补充可共享条件后仍发现冲突，在原任务主动复盘、核对可见证据与复用性，检查最小线索并手工交到 Workbench；也可直接到有权访问的团队资产版本，在引发分歧的文本旁评论、附可查来源与背景并提出拟修订。原任务继续按既有审批路径进行；纪要 A 中的说法不自动成为当前有效规则。

负责处理的成员把同类反馈关联为一个候选修订；有权确认的人在该资产的证据与讨论旁看到两份来源与冲突，可以要求补证、拒绝泛化，或仅确认“A 适用于某类任务、B 自某时起适用于另一类任务”的**特定草稿修订及范围**。只有经正式审核、Git/CI、人类批准、发布读回并核实可供使用的特定版本，才在后续本团队有权限的成员结果中作为已确认结论出现；先前评论者可看到受理、确认与实际更新各自的回执。下一次任务的条件若仍未知，产品依旧停在“请核对/请人确认”，而不是因为已有知识就自动批准。候选能力地图只在对应判断点关联这一版本，不据此宣称整类任务已具备成熟能力。

这个演练用来检查触点和例外路径是否闭合，不能证明使用者会采用、专家会省力或业务结果改善。

### 评审整个工作台时，反过来追问原任务

仍以“该用哪版清单”这一**虚构问题**为线索，但不要让用户为了展示产品而走完每页。首先在 DSH 的任务及原业务系统核本次任务类型、生效时点、可访问来源和当前业务审批责任；如果一通电话或原系统中的准确链接就能解决，Workbench 不应先要求导入材料。找不到依据与找到了但不适用也不是同一类问题：前者应检查入口、权限和来源版本，后者应核适用范围、冲突及反例。材料页提供的是来源原话和待核增量，讨论与修订只围绕指定版本及证据，有权确认、正式发布、下次使用和业务处理仍是互不替代的回执。

Skill 引入只在**确有稳定步骤的候选**值得核时发生，推荐不等于安装或执行；Tool 目录只帮人找外部数据责任方与申请去向，不能从“看见接口”推断已查到当前值。资产进展与智能诊断只显示各自依据与待核缺口，候选地图仅在这类任务的具体判断点上辅助选择“补证、改入口、留给人、申请权限或暂停资产化”。如果来源受限、确属逐次审批、复核成本高于重复问询，就停在最短的人工/原系统路径，并记录为何不沉淀。**下一次同类任务**还须由业务结果 Owner 核结果、误用、总耗时和维护成本；只有出版/发布/浏览证据时结论是“业务效果未知”。各页详细核对项见[同一任务跨页评审矩阵](界面功能设计/README.md#同一任务跨页评审矩阵拟议检查非业务发现)，后续研究协议见[初版假设与迭代](04-初版假设与迭代.md#真实试点前的原始素材研究和独立复核协议)。

## 初版先做什么、暂不做什么

初版只围绕**一个团队自己的团队资产 Git 仓库**及一类低风险、有可查依据的任务：Workbench 先对获准的完整材料或既有资产逐段核覆盖、场景、时间、权限、版本，经事实和经验核对后预览各项独立去向的文件树；Skill 的第五步核对仅在稳定可测且有具体缺口时可选，不是正式创作或试跑；DSH 原生任务中的主动复盘与人工最小线索交接是可选入口。Workbench 承接来源/记录的版本与业务对象线索、事实和经验的待核区分、已有资产核对、具体文本的评论/背景/来源证据/拟修订、受理回访、有权人的特定版本确认与审核，以及场景限定的候选能力地图。宿主的知识检索、Skill 匹配与结果呈现须实际验证；能展示时区分资料和已确认知识，不能展示时手动核对来源，不以结果卡或自动反馈控件作为初版前提。没有现成资产时保留任务疑点；不能集成业务系统时允许任务旁链接或手工接入，但必须如实显示入口和实时信息的局限。页面可以合并呈现，以上描述的是必要的动作和状态差别，不要求按岗位搭建多个后台，更不需要初版建设大而全的控制台。

不自动把资料、评论或拟修订升级成知识，不把一句 Prompt 当 Skill，不把 Skill 推荐当安装/加载，不在 Workbench 重建业务执行器，也不把单次回答、推荐、发布、安装或加载计成业务收益。只有步骤稳定、可测试、权限和异常处理清楚时才考虑 Skill。正式资产要有来源、范围、责任、人工审核与可追踪版本；Git 审核、CI、人类批准、Provider 读回及下游权限门禁不能因产品交互而省掉。生产 Token、Cookie、密码、敏感业务原文、完整 Prompt/Tool Call trace 不应进入产品记录；资料、答案、选区评论、证据、反馈、地图与报表按本团队资产和来源权限隔离，不设计跨团队贡献或查阅路径。

交互能否让员工少重复确认、让专家不过载，以及能力地图能否指导投入，都是**待真实使用检验的假设**，不是此刻已实现的效果。具体观察和调整办法见[下一篇](04-初版假设与迭代.md)。
