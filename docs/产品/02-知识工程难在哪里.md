# 2. 把判断变成组织能力，难在哪里

[前一篇](01-什么是组织知识工程为什么要做.md)提出：组织反复为已处理过的问题查找资料、解释背景和确认适用性；知识工程要让上一轮判断成为下一轮工作的可靠起点。平台要解决的不是“怎么存更多文件”，而是让判断在不同的人和任务之间流转时，不丢掉依据、边界和责任。

## 先看判断如何在组织中流动

一条判断通常不是从“写知识”开始的，而是有人在工作中碰到问题：查资料、和同事对齐，请专家处理例外，最后在某个范围内作出决定。后来的人还要能发现它、判断能否沿用、在使用中指出不合适之处，再由有责任的人修订。

可以把循环简化为：**遇到问题 → 形成判断 → 保留依据和边界 → 在新任务中找到并核对 → 使用或请人处理 → 针对具体内容反馈变化 → 再确认。** 初版只在一个团队自己的团队资产 Git 仓库及其授权范围内打通这个循环：DSH 承接任务里的检索与 Skill 推荐，Workbench 让成员对具体资产贡献意见；推荐不等于加载。任何一段断掉，都不会有稳定的复用：存了却找不到、找到了不敢用、用了不知已过期，都只会把成本移到别处。

## 第一处断点：选什么留下、留下到什么程度

组织每天产生的信息远多于可长期维护的判断。临时联系人、当前工单状态、闲聊中的建议和经确认的处理原则，不能进入同一种“权威知识”池。决定是否投入，应先看重复频率、重新确认的代价、误用风险，以及能否说清适用范围；一次性问题可能只需及时解决，不必做成资产。

这里需要区分**资料、待确认说法、经确认的知识、可重复执行的步骤，以及取得实时业务数据的外部 Tool**。Tool 的接口和数据不因为团队用得上就变成团队知识资产；成员可围绕本团队资产的选中文本留下评论、背景和来源证据，提出拟修订内容；这些贡献与 Agent 从纪要提取出的结论一样，先是待核实的建议，不因表达通顺就成为正式知识。只有步骤稳定、边界与失败处理清楚、可测试，才值得进一步考虑受控的 Skill；“常被问到”或“被推荐”不等于“允许自动安装、加载或执行”。

## 第二处断点：新任务里如何判断“这次适用吗”

假设旧纪要说某类项目按 A 清单办理，现有模板却是 B 版。这不是一个搜索排序问题：两份材料可能针对不同情境，也可能已有一份失效。只展示一个答案，会掩盖使用者真正需要知道的东西——来源、确认者、适用条件、例外与当前版本。

平台应能把“有资料可参考”“AI 整理了可能的说法”“某人确认了某版本结论”清楚地区分；员工看不清证据或没有查看权限时，不能用看似完整的摘要绕开访问控制。遇到缺条件、冲突或过期迹象，可信的结果可以是“目前无法确认，下一步找谁”，而不是编一个统一口径。

## 第三处断点：谁有权判断，谁有能力维护

团队成员想快点拿到答案，也可能是最早发现旧结论不适用的人；有权确认的人则要核对材料、处理例外、确认修订，还要完成本职工作。贡献入口可以对本团队获授权的成员开放，确认与发布权限不能跟着开放。若每条评论都形成审核任务，团队效率可能只是向有权人转嫁了负担；他们也会担心过去的判断被系统无限泛化，出了问题仍由自己负责。

必须让判断权与责任一致：有权确认的人能限定范围、要求补证、暂缓、拒绝或撤回结论；确认须绑定具体草稿修订及适用范围，草稿变化后不能继续沿用旧确认。审核、发布与 Git 版本留痕不能因多人可评论而省略。维护压力、无人接手或长期积压由业务负责人决定投入、缩小范围或保留人工咨询。产品可以让负担可见、把重复解释变成一次可复用的工作，不能凭空创造人手，也不能拿个人提问与处理速度做绩效排名。

## 第四处断点：使用与纠错有没有发生在工作里

团队成员遇到问题时是在完成任务，不是在参加“知识建设活动”。如果必须另开角色后台、先选分类再写一篇文档，他们大概率继续发消息问熟人。DSH 的任务入口应能在权限范围内找到可核对的知识并推荐相关 Skill；推荐只供选择，不自动加载。发现疑点时，Workbench 应让成员回到本团队资产的具体版本和选中文本，附评论、必要背景、可访问的来源证据或拟修订内容，而不是要求写完整知识；没有现成资产的疑点也要有回报去向。

反馈之后还要能回访：有人受理了吗？是改善展示、修改结论，还是新问题需要当前业务决策？选中文本评论需保留所指资产版本与定位；版本变化后要可追踪或标出定位已失效，不能静默附到新版。“已收到”不等于“已解决”。培训与分享有助于形成共同语言，但替代不了低负担的入口、明确的责任人与可见的处理结果。

## 第五处断点：有没有学到什么，而不只是数了多少

发布数、问答次数和培训人数只能证明发生过活动，不能证明工作变好。初版要能区分：找不到已有内容；找到但看不懂或不敢用；使用后发现不适用或过期；错误根本来自选错了要沉淀的问题。不同症状对应不同的修改，不能都归为“知识不够多”。

将来有真实使用时，才有条件在**同一团队获授权的一类任务**中对照：成员从提问到可用判断的耗时、必要人工确认是否正确发生、确认和维护新增时间、误用和返工；还要看评论、证据与修订是否真正帮助下一次任务，而不只数贡献量。没有反馈不等于没有错误；样本不足或无法观察业务结果就说“还不知道”。目前这些是**准备观察的信号，不是已经测得的效果**。

## 平台该统一什么，领域又必须自己决定什么

上面的断点可能出现在不同领域，但初版的**产品工作空间只对应一个团队自己的团队资产 Git 仓库**。其他团队日后如使用同一产品，也应另行绑定资产、权限和责任，不形成跨团队浏览或贡献的产品流程。初版可先把分工划清：

| 边界 | 应承担的事 | 不应替别人做的事 |
| --- | --- | --- |
| DSH 任务入口 | 在当前成员获授权的范围内提供知识检索、来源线索、相关 Skill 推荐及已接入的业务 Tool 调用入口 | 以推荐代替 Skill 安装、加载、执行或业务批准；以团队资产绑定代替数据授权 |
| Workbench 与团队资产 | 让本团队成员围绕可访问资产的具体文本、版本补背景、附证据和提出修订；让来源、权限、适用范围、确认状态、维护责任和反馈去向可追踪，并展示外部 Tool 的使用关系与依赖 | 因可贡献就放开确认/发布、跨团队访问或自动认定草稿成立；创建业务接口或授予数据权限 |
| 团队内有权确认、审核和发布的人 | 按真实授权确认具体修订与范围，经正式审核和 Git/CI 等门禁发布并维护版本 | 把未经确认的材料当作自动可用的正式答案，或把服务身份算作责任人 |
| Agent | 在授权范围内查找、比较、整理、指出缺口并帮助呈现 | 自行确认结论、越权查阅或扩大执行权限 |
| 原业务系统及接口/数据责任方 | 保留实时状态、任务办理、业务审批与执行记录；提供 Tool 接口，确定数据可见范围与授权 | 依靠知识条目替代当前状态与责任链；因团队申请就默认允许生产查询 |

Workbench 是团队成员处理这些贡献、判断与反馈的界面，不是知识工程的全部，也不要求按角色拆成互不相通的后台。先在一个团队的一类任务内检验闭环；未来若复用产品包，各团队仍须隔离资产授权和责任。若统一过度，抹掉任务例外，则平台可能更危险。产品蓝图见[下一篇](03-Workbench如何解决.md)。
