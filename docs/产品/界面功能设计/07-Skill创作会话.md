# 07 · Skill 创作会话（拟议页面规格）

> 供 PM 与团队评审的设计提议，不代表已实现、已验证宿主能力或已上线的业务流程。页面按“创作一条可复用工作方式”的任务组织，不按创作者、审核人另拆页面。返回[页面索引](README.md)。依据：[产品蓝图](../03-Workbench如何解决.md)、[初版假设](../04-初版假设与迭代.md)、[交互原型](../可视化原型/index.html)及[Workflow 到 Skill 的边界](../../方案/10-Workflow到Skill的生成、测试与发布.md)。

## 场景与目的

本团队成员有两种按输入类型区分的路径：从左侧 **「打磨可复用的技能」** 直接核对团队已有或外部形成的 Skill（有权来源、准确版本／digest、适用任务、步骤依赖和真实测试证据），不要求先走材料流程；或从[工作台](02-Workbench工作台.md)「提炼知识&经验」的可跳过第五步，由一份材料的具体线索关联到 Skill 核对。材料路径仍为导入获准的完整本地文件／长篇完整脱敏合成 fixture → 事实梳理 → 经验总结 → 加入知识库的去向文件树 → **可跳过的第五步 Skill 核对**。事实和经验两步各以桌面约 2/3 当前选中项待核稿／评论、1/3 该项对应的有权时点事实记录／正式知识准确版本对照呈现，切换选中项时右栏同步更新、随内容滚动不悬浮固定，移动端对照接在本项之后；数字的报表口径与 Tool 授权条件在事实梳理中就地核，不另设一步。第四步按独立门禁给来源、事实、经验、规则、报表、计划、Tool 等分配去向，仅可核正式知识候选预览 Git 文件，不伪造来源、事实、计划的 Git 文件。确有已有 Skill 的具体质量缺口，或经核实无适用旧版且流程重复稳定可复测时，才在第五步条件性比较合成 Skill／人工写法及正常／边界／异常示例；不做 Skill 时可直接跳过，不影响第四步的去向。只有有权且有进一步核证／真实脱敏测试条件时才进入本 Skill 深层工作区；成员也可从[团队资产](10-资产与发布.md)的已有版只读详情有权精准进入。没有独立「能力体检」页/按钮；独立「打磨可复用的技能」入口先在阶段①引入 Skill 候选，而不是把材料步骤再复制一遍。当前静态示例已有长篇完整虚构周报、第四步去向树和第五步合成比较／跳过入口；仅匹配样例按人工 fixture 整理，SK-01 v1 周报整理 Skill 及“实际／预计”问题均为虚构。成员也可在 DSH 主动运行[任务复盘 Skill](12-任务复盘Skill.md)，先核对任务过程与实际使用证据，再讨论复用/特例，并手动复制用户确认、脱敏的**候选结论**；这不证明既有 Skill 曾加载、执行或失败。仅当没有适用的已有版本，且从[团队知识骨架](13-团队知识骨架与工作记录.md)的描述性方法或真实工作流找到稳定、合法、可复测步骤时，才考虑新建。描述性经验可以独立存在，不为凑 Skill 而封装。正式产品要将已有版的改进或真正新增绑定可核来源、版本/基线及样例，形成 Workflow Draft、Skill Draft 和真实脱敏测试证据后才受控提交；这不是从[DSH 对话与任务](01-DSH对话与任务.md)的一次推荐直接生成、安装、加载或运行 Skill。流程不稳定、依赖当前逐次审批时停在人工路径；静态原型只演示质量核对，不提供上述真实执行或发布。

## 从 Skill 引入或材料第五步到版本质量核对（拟设计）

「打磨可复用的技能」入口在阶段①「引入 Skill」按输入形态分流，带来一份已形成的候选能力包或待核定位线索，不是强制材料先入库，也不是仅凭描述自动创建 Skill。阶段①同一输入区选择：团队资产指定版、页面预置虚构样包、获准本地目录，或来源定位（例如固定 Git revision／压缩包位置／最小描述，暂不读取）；选择并不会自动取得文件内容。团队已有正式版从有权资产搜索/详情**选择**指定资产与基线版本／digest，由系统带入 `base_asset_id/base_revision`，用户不手填 ID；草稿仍是草稿，不能在正式版选项中伪造 ID。外部形成版先核合法分享与纳入范围、原始来源版本／digest（不可得标未知），**没有本团队资产 ID**。只有 SOP/Prompt/零散步骤时，应作为“从工作流创建 Skill”的候选先核是否稳定可封装，不能假装收到现成 Skill 包。材料第五步只携带已有版的具体问题，复盘只携带用户确认且获准分享的最小线索；这些也不凭空生成文件包。

**目标交互**仍为同一候选的四阶段：①用上述单一入口选输入形态，并可在这里带回用户确认、获准的修订包；②按**当前实际可读取输入**重新诊断来源、基线、声明与案例，只有确实取得上一版/原候选内容且身份、版本可核对时才展示有依据的前后差异，否则写“无法比较／原候选关联待确认”，不虚构 diff；③在单组业务信息和停止动作中审稿、复测；④五项提交前质量门只凭有权回执。修订包不是另一份自动新增的 Skill，也不需要额外「引入新 Skill」或「带回 DSH 版」按钮；从 DSH 讨论后由用户回到**同一阶段①、同一输入区**重新选择形态带入，经确认的关联可沿用当前会话，未确认关联不覆盖原候选。每次实际输入/包修订改变，旧测试均失效，新版本须重测；无法读取的外部来源、只看文件名的本地目录不能借用采购案例。**当前 HTML 的已验证范围**：同一阶段①输入区可选择预置虚构采购原版 v0.1／固定改版 v0.2，并在②重诊断、有限比较预置停止片段与文件名、使旧演练失效；其他来源线索和目录只可确认替换输入，不核身份或真实内容，也没有读入 DSH 改后包、自动解析任意包或真实前后包比较。③的 DSH 手动交接提示默认可见，只有文字建议时可在当前待核草稿继续编辑。现有本地规则只针对固定虚构样例，不是 Skill、模型、Tool 或 Runner 真实执行；另用完全隔离的虚构齐门样例演示请求、未知对账、受理、指定审核、Git 受保护主干合并后的正式发布、可选 Registry 读回及目标安装，不产生真实权威回执。材料路径独立保留可跳过的第五步。

真实产品应在获权后对**当前输入**读取固定包版本，核合法分享和准确已有版，再按限定任务的输入/输出与停止条件给出可解释的适用去向；阶段①收到修订包后自动针对**该输入**重诊断，而不是沿用旧结论。若确实取得并核准上一包内容与版本，逐文件展示原件不变的前后内容与诊断差异；若只提供外部文件名、来源定位或无法确认其对应原候选，关联只能标“待确认”，不自动声称原版、覆盖现有草稿或展示真实 diff。系统逐文件定位有证据的缺口，无法自动决定业务边界时请求补充。来源原件保持不可变，待核草稿有独立 revision 与回退；每次包、输入或草稿变化立即使旧修订测试/送审资格失效，真实测试须用获准脱敏输入、依赖版本、实际输出与禁止行为断言绑定新的当前修订，重测后才能过门。LLM 可在受控环境运行，但不能只用命中率或让同一模型自行出题、自行裁定。只有第④阶段确认提交前所需证据，才开放提交审核，而非自动批准或发布。Git/CI/指定人审与受保护主干合并、可选 SkillHub/Registry release/version/digest 读回、分发安装、加载、真实执行与业务价值属于提交之后的不同权威阶段，不要求提交前已有这些回执，也不能由前一阶段推定下一阶段。

团队已有正式版从有权资产选择指定 ID 和准确基线，外部形成版不要求团队 ID；只有 SOP/Prompt 时先作为工作流候选，不能伪装收到 Skill 包。目标阶段①在同一个输入区按形态处理资产版、预置样例、获准本地目录和来源定位；收到用户从 DSH 带回的修订时也回此处，不另设带回按钮。本地目录仅取前 80 个文件名，不读内容、不运行脚本；Git 不拉取，ZIP 不解压。当前 HTML 已用同一①输入区演示两份固定虚构采购样包 v0.1/v0.2 的重新诊断和有限对照；对其他输入仅显示关联未核并要求显式确认替换，不读取 DSH 带回的任意修订包，也不能作真实文件比较。名称命中不等于原候选关联、合法性、安全、契约或通过测试。

从材料进入时，工作台的「提炼知识&经验」不另设体检流程：「导入完整来源 → 事实梳理 → 经验总结 → 加入知识库去向文件树 → 可选 Skill 核对」中，事实和经验两步各以当前选中项的待核稿与评论为主，右栏对照**同一项**的有权时点事实记录或已有正式知识准确版本；换项立即更新、不粘住旧项也不悬浮固定，并标清已核／来源自述待核／冲突／未取得／不适用及出处。数字只在事实梳理中核指标口径，且仅在用途、身份、对象/字段、时间窗和只读通道获授权时就地用 Tool 核证，否则回有权报表与人工。第四步**在同一工作区**用去向文件树分别预览来源留存／阅读、事实回权威系统、经验知识候选、规则、KPI／计划和 Tool 申请及独立门禁；仅可核的正式知识候选显示 `knowledge/<domain>/<topic>/<knowledge-slug>/` 文件预览，原件、时点事实、计划或 Skill 不作为该目录的文件。第五步仅在有稳定可测的具体 Skill 缺口时并列比较合成 Skill 写法与合成人工写法；正常/边界/异常 fixture 展示误用风险、人工停止点及版本依赖，不宣称已试跑或证明某一方优胜。用户可跳过，第四步去向不变；示例先给「引用既有版／补证或修订指定版／维持人工／建议评估新增」的条件性去向，只有成员有权且确有缺口才跳本深层会话，不通过看过对比自动建 Skill。进入本会话时显示限定任务、判断点、期望输出、合法输入/材料格式及实际可读范围；无法确认文件授权、解析能力或页段锚点时保留最小线索，不拿模拟文件做真实测试。逐个核对可访问的**已有 Skill 的准确版本/digest**、确需查询时的知识版本与有效起止、触发/输入/停止条件、正常/边界/异常样例质量、维护 owner、反馈与失效信号；把“已有但条件不适用/依赖断开/未安装”与“真正缺 Skill”分开。优先修订指定版本、补测试/安装验证或保持人工路径，仅当稳定步骤确有空缺且有 owner 与脱敏样例时提出新 Skill Draft；需要实时数据的 Tool 依赖仅为需求声明，不等于可调用或应封装审批。

与[场景评估卡](11-候选能力地图.md)关联时，卡片明示场景 owner、Skill 维护 owner、核证/审核责任人与待指派、适用范围及生效/复核/到期依据；材料描述、Agent 建议与本地设计清单只能是「暂定／待补证」。草稿质量合格须有绑定修订、输入及依赖版本的真实脱敏试跑、期望与实际断言、失败和停止条件；Skill 的 `skill.released`／「已发布」仅在指定修订通过 Git/CI 与有权审核，且合入 canonical 受保护 Git main 的 merge commit 经核实后成立。包 digest 是固定构建身份，不是发布证据；可选 SkillHub/Registry 的 release/version/digest 读回另记 `registry_released`，其未知或失败不抹掉已核 Git 发布；管理员固定包 fallback 仅能在 Git 已发布后供下游取用，自身不是发布。发布、Registry 状态、逐目标安装、DSH profile 加载、真实任务执行及业务结果分别展示证据和发生时间，缺一项不得推定下一项。未来数字员工运行也须单独核身份、安装/加载、版本与执行回执；当前静态原型没有模型、子 Agent、Skill 试跑、Tool 调用或这些宿主接入。

### 一条 Skill 的分层质量判断（拟设计，不是单项评分）

方案中的 Skill 是可复用、可测试、可版本化和可发布的**任务能力包，不是一段 Prompt**。以下是把[资产与生命周期](../../方案/03-知识资产与生命周期.md#7-skill-必须声明和验证)和[Workflow 到 Skill 的生成、测试与发布](../../方案/10-Workflow到Skill的生成、测试与发布.md)转成用户能作决定的核对顺序；每层只对**当前限定任务、指定修订/版本和目标环境**成立，不显示笼统的“标准 Skill 分数”。每项同时展示证据定位、已核／待补／冲突／未知／不适用、所能支持的结论、下一责任人和动作。字段填满、Agent 建议或查看合成示例都不能使一项自动变成“已核”。

| 判断层 | 用户要回答的问题与所需证据 | 缺证、失败或不适用时的去向 |
| --- | --- | --- |
| 1 · 值得封装 | 这是一类边界明确、重复稳定、可检验的任务吗？是否先查有权的适用旧版、有维护人及可承受的复核成本？场景 owner 核任务范围、反例与人工基线。 | 已有适用版先引用；旧版有问题则补证／修订指定基线；流程易变、依赖逐次业务审批或不值得维护时保留描述性知识／人工，不强行新建。查不到有权版本写“未知”，不写“没有旧版”。 |
| 2 · 候选可进入创作 | 团队已有正式版从有权资产选 ID、基线 revision/version、package digest、owner 与当前权限；外部形成版**不要求团队 ID**，先核分享资格、原始版本/digest、最小来源定位与内容清单。`SKILL.md` 是现成包的主说明；外部缺 `skill.yaml`、contract 或 tests 可先作为待补候选，非通过送审。两类再核触发、合法输入/输出、稳定步骤与判断、例外/停止/人工节点、确需时的知识查询与时效、Tool/effects/数据范围及维护责任。 | 来源无权、格式不可读、基线不明或已有版适用性未知先补证/申请授权；知识查询无权或查不到，向用户说明并请求核实，不据此判断知识不存在或绕权检索，也不自动创作。只有 SOP/Prompt 走工作流候选，材料第五步仅带具体缺口，资产详情仅带指定版待核定位，复盘仅带获准的最小线索；目的页重新核权和基线。 |
| 3 · 草稿可送审核 | 在团队受控源码 `skills/<domain>/<name>/` 下审说明、机器可读 input/output/effects 契约、确需时的固定知识引用及查不到/无权/过期的用户核实路径、依赖锁定/许可证与 SBOM、安全/网络/资源/profile 声明、风险和人工门禁、维护与回滚策略。脱敏 fixture 涵盖 golden、boundary、exception、regression、security；记录当前 `session_id/draft_revision_id`、输入与依赖版本、期望/实际、断言、失败/人工纠正及复测。Skill owner 核任务质量，CI 核机器可验内容。 | 一次合成比较、仅有期望结果或单例通过都不算已测试；测试失败修订并绑定新修订重测，实际查询失权/不可用时停止依赖该知识的判断并请用户核实，不把 Skill 的 Git 发布或安装状态自动改写成知识状态。正式宿主的 schema/loader 以目标 SkillHub/DSH 验证为准，不能仅凭项目内包目录推定兼容。 |
| 4 · 受控发布 | 有权 owner/reviewer 针对指定草稿及最新基线确认，Git MR/CI 审核通过；批准但未合并保持「审核中」。只有指定版本合入 canonical 受保护 Git main 且 merge commit 经核验，才记 `skill.released`／「已发布」。包 digest 绑定不可变构建；若启用 SkillHub/Registry，release/version/digest 的真实读回另记 `registry_released`，不成为 Git 发布前置条件。 | 拒绝/CI 失败退回当前修订；仅提交、批准或未合并不能称已发布；Git 合并状态未知先对账。Registry 失败/未知不遮蔽已核 Git 发布，也不能冒称 Registry 已发布。管理员固定包 fallback 仅在 Git 已发布后用于下游取包，不构成另一种发布；旧可用版本不因新草稿消失。 |
| 5 · 目标可用与实际价值 | 针对目标环境分别核 pinned digest 分发与安装读回、DSH profile/tool policy 的 load/read-back、真实任务的技术完成/契约成功与有权业务结果确认；各项附版本/digest、时间、环境、责任方和反馈范围。beta/stable 还需真实场景、失败纠正、回归、回滚 pin、复核安排及维护容量。 | released 不等于 installed、loaded、executed、business_success；无宿主证据保持 unknown，失败按版本归因与回归，一次执行成功不能宣称 stable 或普遍有效。运行权限仍由下游决定。 |

本项目建议的**源码包**最低包含 `SKILL.md`、`skill.yaml`、`contract/input.schema.json`、`contract/output.schema.json`、`contract/effects.yaml`、`tests/golden/`、`tests/regression/`、`dependencies.lock`、`CHANGELOG.md`；boundary/exception/security 等测试同样是送审评测门槛，脚本与参考资源按需包含。`SKILL.md` 说明使用边界、步骤、确需时的知识查询对象/用途、查不到或无权时向用户核实及停止相应结论；`skill.yaml` 固定 ID、版本、owner、风险、schema、可选知识引用、effects、兼容目标和测试/发布策略。Git 源码目录与 SkillHub/DSH 外部包装不必相同，具体 loader 字段须目标环境验证；自然语言说明不能替代机器可读契约，也不能赋予 Tool 调用权限。详见[方案中的包内容与映射](../../方案/10-Workflow到Skill的生成、测试与发布.md#skill-包内容)。

### 按缺口决定去向，而不是默认生成 Skill

入口先比较**本次任务条件**与有权可见的准确已有版本：条件吻合且质量与目标证据足够才建议引用该版；步骤、例外或测试不足则锁定 `base_asset_id/base_revision` 进入补证或修订；仅缺安装/加载回执则交下游对账，不要以未安装冒充没有 Skill。经核无适用旧版、重复稳定且可脱敏测试、有人维护时才提出新的 Workflow/Skill Draft。证据冲突、无分享权或尚需逐次业务决定时可缩小范围、暂缓或保留人工；每个结论注明核证者、版本、适用时间和下一动作，不能因本地待核提案或浏览器演练产生真实受理事项。只有被真正受理/指派的补证或审核，才进入工作台的个人事项。

## 页面内容

### 采购周报整理 Skill：把抽取、修改、案例与缺口串起来

原型预置**两份固定虚构样包** `采购周报整理 Skill · v0.1/v0.2`：用现有完整虚构周报说明业务背景，但不复制或扫描受限真实周报。页面用于说明前后审阅的是**固定虚构采购原始声明与修订情景 fixture**，修订侧仅按本地字段和规则拟议预览，绝非读取真实原包与实际返还文件后的 diff。原版预置 `SKILL.md` 的用途/输入/输出/触发/停止/依赖片段和 `references/summary-template.md` 的“已发生／预计／待核”格式；改版预置更明确的停止片段和 input/output schema **文件名**，并未读取或验证 schema 内容。两版均没有团队正式 ID 或发布状态。它是演示对象，不是一次真实“把 SOP 自动生成完整 Skill 包”。从第一步选中该包后，后三个阶段始终针对同一候选；用户也可以从虚构的有权资产列表按名称/ID 选 SK-02 v1.1，带入 `base_asset_id/base_revision`（真实 digest 未读回），但不能把 SK-02 当作采购周报能力。正式产品应搜索有权资产、先展示可选准确版本和适用范围，用户点选而非手写 ID；从资产详情深链进来也须重验权限与基线。

**系统能抽取什么，谁补什么**：正式产品获权读取固定包后，解析带文件锚点的任务、输入输出、停止条件、依赖和环境，并与本次条件、适用旧版对照；未读的保持未知。静态第①阶段只确认候选身份及文件名；第②阶段集中只读展示预置采购样包的声明、未取得的内容、五类案例计数与可展开逐例对照。只有第③阶段的一组业务字段允许编辑，避免左右两份任务范围及分散输入。用户核准本次业务边界、人工停止点和责任线索；来源合法性、准确基线、既有版、真实 Tool 权限与宿主目标兼容由有权服务读回，不能手填为“已核”。创作阶段定义适用范围，不等于 Agent 已在宿主判断调用。

**修改发生在哪里**：在 Workbench 的这条 Skill 创作会话内，以来源固定版 fork `draft_revision`；用户核任务范围、允许输入、禁用结论及无权停止动作，系统据此拟出 `SKILL.md` 停止段、输入/输出契约、effects 能力需求声明与五类测试的逐文件变更。用户按“原件不变 → 拟修改/拟新增”逐项审阅依据、待确认事实和责任，**不要求手工创建 JSON/YAML/测试文件**；只有真正可读取、可关联的上一版才可称为前后文件比较；`skill.yaml`、依赖锁、变更记录及真实授权也需补齐。正式产品由有权服务保存独立草稿、生成/检查文件，冲突时核新基线，不覆盖正式来源。第③阶段也可按当前候选的自动诊断、包结构待核项、责任人、五类案例计数及不一致断言生成**针对性、最小化、可人工审阅**的 DSH 讨论提示词；未读候选不能套采购样包的失败案例，交接默认不带用户填入的链接、路径或原文。用户主动带到 DSH 原生对话讨论后，回同一条 Workbench 会话的**阶段①输入区**带入获准、确认可分享的修订包（按实际形态选择入口），随后重诊断、可证比较、形成新修订并重测；回复本身不能证明包已保存、Runner 已测试或 owner 已确认。HTML 仅在浏览器内存记示意文件预览和修订号，刷新丢失；预览不是写出的可用 JSON/YAML、测试文件或可提交的受控包，尚未实现上述带回和真实比较。

**验证与过筛**：第②阶段针对本次输入重新列 testcase 数，未运行必须显示未运行而非默认全过，并可按需展开逐例输入、预期/禁止、示意实际与断言；第③阶段只提供当前草稿的浏览器规则重演操作，完成后回②看逐例诊断。更换输入或修订变化须使旧演练失效并重跑，不能把原候选的结果当成修订包结果；仅目录名或来源线索无测试案例时不显示借来的通过数。正式受控 Runner 须将包 digest、修订、依赖、获准脱敏 fixture、真实输出、断言与业务人工核证绑定；**未经批准 Draft 的静态校验与可执行试跑分开**：隔离 Runner 未经安全/平台负向验证前，只能做不执行候选代码、不调用真实 Tool 的静态检查，页面固定虚构规则重演也不能充作真实测试。仅在隔离非生产 Runner 已验证最小权限、无生产凭据、网络/文件/进程及跨空间边界、资源/成本额度和超时终止，且当前修订、fixture、主体权限重新核实后开放受控试跑；未就绪、撤权或超限时明确阻断，不允许用 DSH、CI 或通用 Tool 绕过或把静态通过标为 `tested`。第④阶段五项提交前质量门：来源 ACL/固定基线/旧版检索；场景责任人确认范围与人工停止；规范受控包、依赖锁和维护 owner；安全/Tool/effects/许可证及目标兼容；当前修订五类真实测试与人工复核。每门列缺项、责任和有权回执来源，不能手勾。五门齐全才允许正式产品请求送审，提交请求仍须经历受理、Git/CI/有权人审核、canonical 受保护 main 合并核验（至此 `skill.released`）；若启用 SkillHub/Registry，release/version/digest 读回另记 `registry_released`，未知时对账，不撤销已核 Git 发布。TeamAI 上游流程编排能力须按实际接口验证，如启用则在 Git 发布且取得可用的 pinned digest（可选 Registry 读回或管理员在 Git 发布后的固定包 fallback）后分发/逐目标安装并读回，DSH 加载另核。静态原型中的虚构齐门示例与真实候选隔离。

### 同一候选的四阶段（材料第五步不是入口第一步）

| 阶段 | 用户操作及系统处理 | 静态原型边界 |
| --- | --- | --- |
| 1 · 引入 Skill | 同一输入区按形态选择团队资产指定版、虚构样包、获准本地目录或外部来源定位；从 DSH 带回修订也回阶段①按实际形态输入，先确认原候选关联，不另设“新 Skill”或“带回版”动作。 | 当前可选固定虚构采购原版/预置改版、SK-02、目录文件名及定位线索；链接不拉取、ZIP 不解压、本地目录不读内容；任意 DSH 带回包的读取未实现。 |
| 2 · 自动校验 | 每次输入变化重诊断当前可得内容/未知与责任、testcase 计数；上一版内容确实可得且关联明确时才比较，否则说明关联或对照不可判定。 | 只有采购两个固定样包可比较预置停止片段与文件名；目录只比较文件名，身份/内容未知；其他输入没有真实包 diff。 |
| 3 · 具体修改与复测 | DSH 交接默认可见；只有文字建议则留在本地草稿继续编辑，取得获准改后包则回①按形态提供；输入或修订改变即废止旧测试，针对当前修订重测。 | ②集中展示逐例结果，③仅有内存提案和固定虚构规则演练操作；提示词不包含用户填写的链接、路径和自由文本，不自动发送或导入 DSH 包。 |
| 4 · 审核提交 | 五门有权回执绑定固定包与修订才允许请求送审；指定审核与 canonical 受保护 Git main 合并核验后才记已发布，Registry 可选读回、安装与加载分别核。 | 当前候选提交始终阻断；隔离虚构齐门样例只演示状态顺序。 |

原型不会自动保存 Skill 包、调用模型/子 Agent/Tool 或产生正式测试证据；固定虚构包的文本规则演练不改变这条边界。新建 Skill 是**没有适用旧版且重复稳定、可复测**时的后续拟议分支；材料第五步的合成比较也不创建任何文件。正式 Skill 包使用 `skills/<domain>/<name>/`，与 `knowledge/<domain>/<topic>/<knowledge-slug>/` 为仓库根下的平级目录。

- 页面上方：当前输入、版本、本地待核提案及演练状态同屏展示；回阶段①不清空当前候选，同一输入区接收初次选择和改后输入，不以额外「引入新 Skill」或「带回 DSH 版」按钮另起流程。原版/预置改版依固定虚构身份比较；从资产详情指向其他 ID/基线、选择其他样包、来源线索或目录时，先在①提示关联未核，确认仅替换本页输入并重新诊断，**不证明同一候选**。确认前保留当前输入和演练；切换后旧演练仅保留历史对照，不成为新输入测试。撤权清除内存，刷新后不能恢复，也不以浏览器存储保存来源线索或交接文本。
- 差异区：当前 HTML 的采购样包 rN 仅能按文件切换**固定虚构来源片段与拟议内容**，展示本次字段、虚构案例依据及下一位核证人，非真实原件到 DSH 修订包的 diff。目标有实际可读且经核关联的原包与修订包才对照；外部文件名或单一来源定位不证明关联，也不得推断文件内容。来源文件不被覆盖，输入/修订变化后旧测试失效。
- 门禁区：系统按候选与修订定位提交前缺项，Git/CI/人审及发布、安装/加载/执行的证据仅作提交后的时序说明，不把它们要求为提交前的回执。

DSH Runtime Session 与 Skill Creation Session 分离。已安装 DSH Desktop `0.2.0-rc.2` 的 Session Controller 文档和代码显示原生 Session 可按 ID 创建、恢复并 retain，但尚未验明把完整原生会话嵌入第三方 Workbench 面板、精确切换到关联 Session 的插件导航及目标 Profile 权限；`selectPanel(null)` 仅切回对话面板，不选中指定 Session。因此本轮只演示按**当前诊断**生成可审阅、用户主动交接的最小提示词，不画伪原生聊天、不自动发消息，不把 DSH 回复作包/权限/测试回执。后续若做关联，须验证目标版本 create 返回结构、Session ID 与创作会话关系、准确导航/重连/历史、完成 turn 的唯一对账、授权与撤权释放、模型数据留存，再另行实施。已发布 Skill 的修改也在本创作会话基于固定资产版本发起独立修订，而不是在[团队资产](10-资产与发布.md)直接覆盖正式版本；工作台仅在成员对这份修订有明确当前动作时显示待办，创建者在别人审核期间只关注进展，详见[工作台事项规则](02-Workbench工作台.md)。每次保存、提交与异步回调重新校验会话、草稿修订、权限和幂等状态。发布后的分发/安装、DSH profile 加载、真实任务运行与业务成效是**独立状态和权威**；Workbench 不提供宿主运行按钮。失败的业务任务只形成可追溯的反馈候选，不直接改写现有 Skill。本地 `knowledge-compounding` 是用户工作区实例；它的收件箱 `accepted/merged` 回执不代表本页已有团队版、安装或运行。

## 跨页路径

[工作台](02-Workbench工作台.md)有「提炼知识&经验」和「打磨可复用的技能」两条独立输入路径：前者第四步以去向文件树分别预览知识及非知识门禁，若有具体稳定可测 Skill 缺口才在可跳过的第五步比较合成写法，再关联本页；后者从团队已有或外部形成的 Skill 的最小定位直接开始，先核来源、准确版本与适用，不经过周报四步。跳过第五步既不阻断第四步，也不生成 Skill。当前 HTML 用长篇虚构周报、去向文件树和第五步合成比较／跳过入口演示该顺序，未经真实版本、缺口或流程稳定性核证。也可从[团队资产](10-资产与发布.md)的已发布版本只读详情明确选择继续处理。这些入口都不是「默认从工作流新建 Skill」；只有核实无适用既有版、重复稳定且可复测时才走新建分支。[DSH 对话与任务](01-DSH对话与任务.md)的 Skill 推荐只提示范围与依赖，不能一键视为已有创作会话或已安装。知识引用到[知识创作会话](03-知识创作会话.md)核对来源；需外部只读能力时查看[已开通 Tool](08-已开通Tool.md)或[Tool 广场](09-Tool广场.md)，但目录可见与能力需求均不授予运行时权限；[候选能力地图](11-候选能力地图.md)仅将稳定步骤作为判断点证据。发布/反馈处理仍在本会话的特定修订中进行，而非在团队资产页操作或在宿主运行会话中编辑正式资产。

## 访问与数据边界

每团队独立 Git 仓库、草稿、测试、job 和审核；服务端基于 DSH 身份映射校验 `team_id/asset_space_id/session_id` 与来源 ACL，不能用客户端路径或宿主 ownership 当授权。真实确认、审核、发布责任人和执行服务身份分列。Skill 的 Tool 依赖不等于 Tool 注册、接入、数据授权；提供方/数据责任方与 DSH 运行策略决定可否调用。Git 仅纳入受控脱敏文件与引用，不保存 Token、生产输入、敏感原文或完整 Prompt/Tool Call trace。

## 与当前原型的差距及待确认

现有静态原型的左侧独立入口为「打磨可复用的技能」，页内以「引入 Skill」为第一阶段，共四阶段：同一阶段①选择虚构 SK-02、**固定虚构采购原版 v0.1 与预置改版 v0.2**、其他固定虚构目录、本地目录前 80 个文件名或来源定位；不拉 Git、不解 ZIP、不读本地目录内容。返回①不清空当前输入；预置采购两版按固定虚构片段和文件名对照并重新诊断，其他输入须确认替换，目录仅比较文件名且身份/内容未知，旧演练不会作为新输入测试。第②阶段显示当前输入已得/未知信息、有限对照、案例计数与按需逐例结果；第③阶段把针对当前诊断的 DSH 手动交接提示默认展开，文字建议可继续修改本地待核草稿，获准改后包则回①按形态提供；采购样包可按需审阅九项**固定来源片段与内存拟议修订**，五例浏览器规则重演并非真实测试。第④阶段当前候选五门无真实回执始终阻断；隔离虚构齐门链只示意指定审核→canonical 受保护 Git main 合并核验后 `skill.released`→可选 Registry 读回/未知对账或 Git 发布后的固定包 fallback→逐目标安装，不是审核事实。没有上传/解析任意包、读取 DSH 带回包、真实 diff、可校验受控文件、Runner、真实身份、ACL、旧版检索、持久 Skill 草稿、Git/CI/人审、Git main 合并核验、SkillHub/TeamAI 读回或 DSH 加载；“提交触发 TeamAI 流程”的接口契约尚待验证。材料路径仍有可跳过的第五步，互不混用。
