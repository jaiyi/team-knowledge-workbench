# 01｜DSH 对话与任务：任务为主，复盘是可选支线

> 这是 DSH Desktop **原生对话与任务**的产品衔接设计，不是在 Workbench 内再造对话。知识检索、Skill 匹配、业务 Tool 调用和它们的展示均须以目标 DSH 实际能力/外部集成为准；本稿不宣称这些已内置或已验证。初版不依赖插件嵌入原生会话、任务完成事件、自动回顾卡或读取完整运行轨迹。

## 何时进入，要完成什么

成员打开 DSH 是为了处理眼前的问题，例如核对清单或查询获授权的业务数据。**任务的提问、追问、执行和业务判断是主线**；如宿主实际支持且已获授权，团队知识为判断提供依据，Skill 辅助稳定步骤，Tool 获取当前事实。Workbench 只在成员发现值得改进的地方时介入，不要求预先切换“知识工程模式”，不以完成复盘作为任务成功的前提。

当成员觉得“刚才反复纠正了某条知识”“某个步骤值得改进”“缺一个可用的查询接口”时，**主动调用[任务复盘 Skill](12-任务复盘Skill.md)**。先在原生对话回看任务过程、已有资产的实际使用证据和成员的额外调整；与成员逐项讨论哪些可复用、哪些是一次性特殊处理，再确认是否更新/新增知识或 Skill、处理外部 Tool 前提或不沉淀。若有报告、PPT 等产物，还应讨论其来源和分享权限、是否适合走已验证的团队资料库入口；产物入库不等于正式知识发布。最终由成员检查、删减敏感内容并选择是否手动保存最小线索到[我的工作台个人 Inbox](02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)，或按现有路径复制交接结论到有权的知识/Skill 会话。保存仅供本人回访，**不是**团队接收；如要从个人项转交团队，须对内容、来源、团队目标再次明确授权并在目的页重验。无论哪条路径，复盘不复审当次业务批准，也不自动上传产物、自动抓取 Session。

## 从当前任务到团队知识：上游只提供原材料

[团队知识骨架与工作记录](13-团队知识骨架与工作记录.md)把**获准分享的纪要/周报/交接/报告**作为可追溯的来源记录，把**项目、产品线或业务专题**作为团队自定的查找轴；从记录核对出来的当前分工等对象事实、提炼出的规则/判断/描述性方法，再到可测试的 Skill，分别是不同的内容。DSH 的一次对话可能产生线索，却不是一份自动归档的工作记录，也不是项目的最新事实。宿主仍专注完成眼前任务；成员在确有沉淀意愿时才主动复盘。

复盘可先提出少量**原子线索**，请成员逐条决定：关联/纠正哪份有权分享的工作记录；需核对哪项项目/产品线事实及其有效时间；是否值得形成带边界的团队经验；是否已有稳定步骤足以进入 Skill 创作；或仅在原任务处理。一个记录能引出多条事实/经验，也可以什么都不引出。成员选中、核对复用性和分享范围之后，才人工复制**最小化的候选**到 Workbench；未明确提交就不显示“团队已收到”。需要留整份报告/PPT 时走原系统或实际验证过的资料库入口，受限记录不应被复制为团队知识。

**本地 Skill 与产品集成分开看。** 当前 DSH 工作区里已有用户创作的 `knowledge-compounding` Skill，可把逐条确认的候选写到当前工作目录的 `knowledge-inbox/deposits/`；它是一个本地交接实例，不证明 Workbench 已接入该文件收件箱、[拟议个人 Inbox](02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)或团队已正式发布该 Skill。本稿的初版路径仍是人工选择、检查并复制候选；个人 Inbox 是**另行拟议的手动保存功能**，不会自动读取 `knowledge-inbox/deposits/`。若以后验证文件交接，需明确谁授权 Workbench 读取哪一份收件箱、同一收件箱路径、只受理允许转交的条目，并返回确切条目 ID；工作台写回的 `status/<id>.json` 由成员在对应收件箱运行 `inbox.py sync` 才会更新本地状态。`accepted` 仅是原材料处理回执，不能写成事实已核准、知识已发布或 Skill 已安装；这不是已实现的自动同步。**系统也不应因脚本存在便自行运行 sync 或读取全部用户工作区。**

## 原生任务界面与 Workbench 分工

| 当前环节 | 留在 DSH 原生会话 | Workbench 承接什么 | 尚须验证的技术前提 |
| --- | --- | --- | --- |
| 找依据、核适用性 | 成员继续原生对话；可用时展示带来源、版本、范围的团队知识；资料/Agent 整理和正式知识分开 | 需要修订的依据进入[知识创作](03-知识创作会话.md)或[内容讨论](04-内容讨论.md) | DSH 中获授权团队检索及结果呈现如何接入；不能先画成插件必有结果卡 |
| 用 Skill 或查实时事实 | 真实推荐、安装/加载/执行状态与 Tool 调用由宿主和外部平台负责，缺失/失败/未知不能被“说起来做了”代替 | 稳定步骤的候选改进进入[Skill 创作](07-Skill创作会话.md)；目录与申请到[Tool](08-已开通Tool.md) | 当前环境的 Skill/Tool 状态与使用证据是否可由宿主核对；团队仓库不授数据权限 |
| 业务处理之后选择复盘 | 用户主动在原生对话调用[任务复盘 Skill](12-任务复盘Skill.md)：回看过程与资产证据、核对额外调整，讨论复用性/特殊性和产物去向；不要求结束事件 | 用户确认结论后**手动复制**最小化候选文本到相应会话；未粘贴/提交则 Workbench 不产生事项；报告/PPT 的资料提交另循有权且经验证的入口 | Skill 的上下文可见范围和安装/触发方式；完整 Session trace、用户所有文件变更、自动结束提醒及资料库上传入口均不能假定 |
| 返回原任务 | 原生会话仍是当前任务来源，成员继续处理、复核时效与业务状态 | 只提示如何回原任务；未来有可靠导航接口再做精准返回 | 从支线回到同一个宿主 Session、跨页自动带参/回访定位未做目标版本验证 |

**界面原则**：不以我们的插件重画 DSH 原生聊天；不强制在每条回答旁添反馈控件或在任务结束弹总结卡。只有在运行时验证真实支持后，才考虑宿主轻提示、可核查结果卡或更顺畅的跳转。在此之前，“调用复盘 Skill → 人工复制 → 打开对应 Workbench 创作会话”本身就是完整的可试用假设。

## 主动复盘与复制的具体流转

| 触发与操作 | 产生的状态/结果 | 失败、未知和下一步 |
| --- | --- | --- |
| 成员认为某次任务有改进线索，主动运行复盘 Skill，并限定要复盘的可见内容 | Skill 先按任务目标、依据、关键步骤、用户调整及业务结果回看过程，再把知识“提及/核验引用”、Skill“推荐/加载/执行”、Tool“提及/核验调用”按证据分列；未知明确标出 | 若仅能看到当前对话，只能称“对话中出现/用户陈述”；无调用证据写“无法确认”，不捏造额外调整或业务成效 |
| 成员与 Skill 逐条讨论调整是同类任务可复用、有条件复用、当次特殊处理还是证据不足，并商量线索去向 | 可提出获准分享的来源定位、待核项目/产品事实、描述性经验、具体既有知识/Skill 版本待核或稳定流程的 Skill 候选；Tool 去外部目录与授权流程，一次性处理/证据不足可不沉淀 | 未经用户回答不能写“已确认可复用”；讨论结论不核准当前事实，也不是正式草稿确认或发布批准；产物是否存在及能否分享须另问 |
| 如有报告/PPT，成员核对来源、版本、敏感内容和分享授权；再检查交接文本 | 获准分享时引导使用**经核实且有权限**的团队资料库入口保存来源资料；拟提炼的知识仍要另走创作/发布门禁。候选摘要只带非敏感任务类型、证据、边界、用户讨论结论、未知和下一步 | 无入口/无授权则暂不上传；生产标识、库存价格、客户信息、完整对话/Prompt/Tool trace 不进入摘要；产物提交不等于正式知识或对团队公开 |
| 成员打开合适的创作会话、粘贴经讨论确认的交接结论并明确提交 | Workbench 把它标为“用户提供的复盘候选，待核实”，给受理 ID 与回访去向；先关联可访问的[工作记录/业务对象](13-团队知识骨架与工作记录.md)或指出来源待核，再选事实/经验/Skill 候选、既有资产/基线和下一动作 | 粘贴不证实实际调用或正式来源；工作记录/纪要中的说法不自动成为当前事实；无资产可以登记疑点，不伪造选区。未提交则不说“已收到”；复用性讨论、草稿核对、发布分开处理 |
| 成员继续原生任务或返回业务系统 | 当前业务继续由宿主及原业务系统按现有权限与审批处理；新知识正式生效后也需在后续任务重新核适用性 | 不能靠复盘或知识更新倒推出当前任务已解决；精确返回同一 Session 若未验证，保留原生会话中手动返回的路径 |

### 看得见的例子，不伪造运行事实

在虚构的“A 清单／B 模板”任务中，用户在对话里补充“旧规则时期的常规任务仍参考 A”。复盘可以说“本段对话出现 A、B 两份资料，用户补充适用条件”，随后问“同类任务都适用吗，还是此次特殊处理？报告/PPT 如有最终版本，是否有权作为来源资料分享？”**没有授权检索记录时，不能写‘本次确实引用 K-01 v1’**；没有 Skill/Tool 运行记录时，也不能写它们执行或调用成功。只有用户讨论确认后，才将有条件复用的候选复制到[内容讨论](04-内容讨论.md)核源；若产物含客户信息，先不上传、不粘贴原文，等待授权与脱敏，再决定资料去向。

另一任务如果在对话中出现“已查库存”字样，但没有可见的 ERP 调用事件，复盘应写“对话声称查询，实际调用与结果无法确认”；实时库存仍只能来自已授权的业务系统，不能从历史知识推断。完整格式和去向见[任务复盘 Skill](12-任务复盘Skill.md)。

## 任务中的统一意图与可追溯使用（拟设计）

成员在原生任务里可以说「这份获准材料能否用」或「这类任务缺什么能力」，**同一材料／能力意图**不要求先决定是知识、Skill、Tool 还是来源归档。当前可行的交接仍是主动复盘、逐项核对分享范围并人工复制最小线索；未来才可能由宿主提供获授权的最小上下文与精确返回定位。复盘应把任务情境、判断点、对象/有效时点和来源资格带给[场景评估卡](11-候选能力地图.md)，但未接入的 DSH 对话不会自动生成卡或持久化任务资料。材料能否被处理要在本场景单独核来源授权、文件格式的实际解析能力、页段锚点及覆盖/未读范围；不能用 TXT 演示推断 PDF/PPT/附件也可读。

面向当前回答并列说明证据归因：**知识**标可核 ID／版本、适用与生效/失效区间及真实检索引用回执；**Skill**区分推荐、已发布、安装、加载和真实执行及版本；**Tool**区分目录提及、接入/授权与有权运行调用的接口、时间和结果状态。仅由用户叙述或复盘推断的使用写「提及／待核」，无事件回执写「无法确认」，不得写为实际引用/运行。已有知识或 Skill 在该判断点足以支持时优先校适用条件与质量/缺陷，再考虑修订或新建；实时事实和逐次批准依然走业务系统。场景 owner、核证责任人和资产 owner 分列，生效依据和下次复核日期不明时写待核。当前原型不连接 DSH、模型、子 Agent 或业务 Tool；未来数字员工沿用同样的版本、授权、使用和结果证据门槛，但其接入、身份及回执尚未验证。

## 权限、原型差距与待验证问题

知识来源权限、Skill 安装/加载、Tool 数据授权、业务审批属于不同门禁。复盘材料只能来自用户当前可访问的内容或实际经授权提供的运行证据；转到 Workbench 之前由用户审查复制内容，目标页仍要重新鉴权。不能复制敏感原文或完整 Prompt/Tool Call trace；也不能把用户口述升级成系统审计记录。

**原型已示意**：静态原生对话的位置、次级虚构知识/Skill/Tool 示例、按需触发的三段模拟复盘、产物去向讨论与人工复制候选；Workbench 内还有固定虚构的项目/产品线视图和工作记录详情，不代表已从真实来源读回。**原型未做到**：DSH 宿主中的真实项目/产品线视图与实际任务、真实知识/Skill/Tool 运行证据、工作记录的真实来源接入和权限核验、文件式收件箱回流；原型不连接 DSH，也没有真实 Skill 执行记录。**待验证**：目标 DSH 是否支持 Skill 安装触发及当前会话上下文读取；是否向 Skill 提供经授权的知识引用、Skill 加载/执行和 Tool 调用记录；团队资料库的真实上传入口与分享/索引权限；用户从创作会话回原生 Session 的可靠方式。插件同屏嵌入原生会话、自动任务结束卡只是将来的独立实验，**不是本流程的依赖**。

## 优先讨论

1. 用户会在什么真实工作节点想复盘？主动调用是否比持续弹出提示更符合“任务优先”？
2. 限定哪些可观察信号，才足以建议改知识、改 Skill 或去 Tool 申请，而不是让用户花时间纠错？
3. 哪些任务场景含有不宜复制的内容，需要把“只在当前对话中查看”设为默认建议？
