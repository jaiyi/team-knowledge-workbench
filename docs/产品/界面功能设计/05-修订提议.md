# 05｜修订提议：说清要改哪一版、为什么改

> 页面位置：知识内容讨论之后的内页，也可以由有权访问的已有资产进入。“提议”是候选草稿，不直接改正式 Git 版本；提出建议和正式确认是两种动作。

## 何时进入，要完成什么

讨论指出旧知识漏写某个条件，成员已经有可核查的建议，需要把“可能哪里不对”转成**供有权人判断的具体差异、来源和适用范围**。若仍缺关键证据，可以先保留草稿和补证项，不因急着消灭待办而发布。

## 页面必须有的信息

- 所属团队及资产 ID、**精确基线 Git 版本**、段落/文字快照，当前正式版本和基线是否仍可用于提议；关联评论、原问题及可失效的 DSH 任务返回定位。
- 修改前后差异、明确的判断陈述、依据链接及可见性、拟适用/排除范围、生效/复核条件、待核对事实、可能受影响的已授权使用场景。
- 提议人、草稿修订版本或不可变标识、当前接手/确认去向与审核状态；“草稿被修改后以前确认不再有效”要贴在具体状态旁。

## 功能流转

| 功能 / 触发 | 前提与动作 | 状态 / 下一步 | 异常与处理 |
| --- | --- | --- | --- |
| 从讨论建立修订 | 对有关资产有读取及提议权限；选明确基线和争议位置，引用有权分享的来源，填建议文本/理由/范围 | 保存为“候选草稿，待补证或待核对”，回链原讨论；进入[修订核对](06-修订核对.md)前可邀请继续补证 | 无资产时先到[知识创作会话](03-知识创作会话.md)建立新候选，不伪造对不存在正文的 patch；来源无权限时不复制其原文 |
| 比较旧版与草稿 | 按基线和新内容展示差异，分开原资料事实、成员推断、Agent 建议与此前有权确认 | 使核对者知道确认的到底是哪一句、哪些范围，不能只看 AI 摘要 | 基线已变更/已停用时暂停进入确认，人工比较新旧语义后重定基线或撤销提议；并行提议不得盲目覆盖 |
| 修改提议：改文字、范围或依据 | 产生新的草稿修订标识，记录编辑原因和被替代草稿；向曾核对者显示哪些部分被更改 | 所有绑定旧草稿的正式确认失效，状态回到待核对；保留历史决定而不伪造持续批准 | 只有格式差别是否需重确认也须定义规则；默认从严，无法证明同一内容则重核 |
| 撤回、暂缓、合并 | 提议人或有权处理者记录理由与所依据的其他提议；处理回执同步给相关问题 | “已撤回/暂缓/关联另一修订”保留审计与继续路径 | 不能删除已被引用的历史；合并后得到新草稿，旧确认不继承；无人承接继续标待安排 |
| 送核对 | 验证基线仍有效、主要来源可见、责任范围有人承担；明确确认需要按资产策略授权 | [修订核对](06-修订核对.md)只收到这一草稿修订及拟适用范围 | 来源仍冲突、无法确定范围时允许退回补证，而不是替确认者默认选择 |

### 一个具体差异（虚构）

旧版：“旧规则时期，常规任务可参考清单 A。”新提议不是“B 比 A 新，所以改用 B”，而是“在已核实的旧规则时期常规任务继续参考 A；B 的生效时间和任务范围待确认，暂不用于当前判断”。这份草稿可以明确保留未知；确认者也可进一步缩小范围。未核实 B 的生效条件之前，不得将“最新模板”推成普遍适用的正式判断。

## 跨页与状态

讨论中的问题可能以“已形成提议”得到阶段性回应，但离“已确认”与发布后的只读[团队资产](10-资产与发布.md)中“可引用”还有距离；原 DSH 任务照旧走当前业务流程。草稿只由获授权的人看，来源权限不能因引用到提议而扩大。正式审核的 Git diff 与本页面草稿须对应同一不可变修订标识；不一致必须回核对。

**原型已示意**：以 K-01 v1 和旧版评论建立演示提议、编辑后失去确认。**原型未做到**：真实基线并发冲突、多个提议合并、来源鉴权、可追溯的草稿 revision 以及真正的审核绑定。**待验证**：团队修订更接近段落建议、结构化判断补全还是完整 Git patch。

## 优先讨论

1. 草稿最小必填的是哪几项，如何避免把核证负担全推给提出问题的人？
2. 当范围缩小或来源更新时，如何精确判定以前确认需全部作废还是局部重核？初版可默认重核。
3. 基线和正式版并发更新时，是引导人工重定基线还是保留两条独立候选？
