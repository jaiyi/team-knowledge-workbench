# 04｜内容讨论：留下能核查的问题，不让反馈掉进黑洞

> 页面位置：知识创作会话中的内页，也可由 DSH 结果/问题卡直接进入。评论、补背景、来源证据和任务疑点是**贡献**，不是已确认知识。以下的分派、合并、回访是拟设计流程，原型目前只演示单条资产上的评论。

## 何时进入，要完成什么

成员发现“B 模板是否真的替代 A 清单”无法由现有答案判断；可以在有权访问的资产旧版上选中相关段落说明差异，也可以因检索不到资产而只登记任务疑点。目标是保留**为什么不敢沿用、可查依据在哪里、谁应继续做什么**，而不是强迫成员先写一篇修订文档。按当前业务流程需要即刻处理的审批和安全风险，不等待评论回复。

## 页面信息与两种入口

- **有资产**：展示精确资产 ID、Git 版本、段落稳定标识/选中文字快照、来源与权限、相关问题；评论区区分原文、成员看法、可查来源、Agent 整理和有权确认。选区评论为待验证低负担假设，段落级添加问题作为无选区替代。
- **无资产**：展示任务问题的最小摘要、反馈原因、可失效任务返回定位（如宿主确有可验证定位）和“没有资产可锚定”标记；不强制关联一条无关知识。成员也可从[任务复盘 Skill](12-任务复盘Skill.md)讨论复用性后手动粘贴脱敏线索：标明用户确认的是**值得核查的候选**，不是已经确认的正式知识、宿主调用日志或已受理工单；只有明确提交后才回执“已收到”。报告/PPT 的受限原文不粘进讨论，获准分享的来源须另走核实后的资料入口；本页只存必要的授权引用和待核问题。
- 同时可见谁实际接手（若有）、缺什么证据、下一动作和更新时间；“已收到”“已分派”“待补充”“正在判断”“有处理结论/不沉淀”“相关新版本可引用”分开显示。

## 功能流转

| 功能 / 触发 | 人与系统怎样操作 | 状态 / 下一步 | 失败、异常与限制 |
| --- | --- | --- | --- |
| 留下评论或无资产疑点 | 从 DSH 带最小化问题类型/返回定位；有资产时核对权限和基线锚点，再提交具体疑问、可共享背景和可查来源位置 | 返回“已收到 + 问题 ID + 何处看进展”，原任务继续；不生成正式知识 | 无授权不能保存或展示受限原文；锚点失效时保留旧版定位并请求人工定位，不能自动贴新版；无资产保留疑点而不是评论假锚点 |
| 附来源与补背景 | 有权访问的人提供资料链接/引用位置、适用时间和差异；标明待核对，不把资料摘要当确认事实 | 问题可由“待补充”回到“待判断”，保留原贡献与新增证据的来源 | 来源不可访问/失效时提示缩小引用或走原权限流程，禁止复制秘密原文进公开讨论；Agent 汇总须注明未核实 |
| 按问题处理与合并 | 有权限的负责成员先核实是否同一判断点，查看重复线索并记录处理原因；可分派、请求补充、关联既有资产或合并重复项 | 记录实际接手人和处理进展；并入主问题后保留原问题回访定位 | 分派请求不等于对方已接收；合并不扩大权限/适用范围；无人承接显示待分派并交业务负责人安排，而不是“已转专家” |
| 决定去向 | 对可能复用的判断建立[修订提议](05-修订提议.md)或新候选；仅展示不清可改入口；当次业务判断转原系统；不值得沉淀需说明原因 | 给贡献者可理解的处理结论、负责人和回访链接；问题处理结论与发布版本是两条状态 | 不能仅以评论数多就自动发布，也不能把“已受理”写成“已解决”；若有紧急风险按业务应急渠道先处理 |
| 跟踪和回访 | 贡献者从 DSH 原结果位置/工作台/直达链接查看授权进度；相关版本真正发布且可读回时再显示其版本 | 可回原任务重新核条件，或继续对具体旧版/新版提出问题 | 已撤权时只显示授权允许的元信息；任务失效不重放受限历史，说明安全返回路径 |

## 版本与责任

评论至少绑定资产 ID、Git 基线版本、稳定段落定位及选中文字快照；修订提议另持独立基线。新版出现不代表旧评论迁移、更不代表针对旧版的同意延续。对指定修订的正式确认在[修订核对](06-修订核对.md)，审核/发布在对应的[知识创作会话](03-知识创作会话.md)内按修订受控执行，[团队资产](10-资产与发布.md)只读展示结果。评论贡献可归因、可纠错，但不以提交数量评价个人。

**原型已示意**：在宿主答案或旧版知识中选中文字（或选预设句）、写评论/来源、看到评论绑定旧版；「我的工作台」（原「我的使用与改进」）首页还允许就固定虚构的无事件引用、版本不明情景提交本地问题报告；顶部个人 Inbox 的虚构暂存是另一个仅本人内存对象，主动跳知识页也不会自动生成本页问题或正式受理。**原型未做到**：内容讨论内对无资产疑点的正式受理与问题 ID、真实分派/合并、任务回访、权限收敛和版本重定位；首页本地报告也不等于已受理工单。**待验证**：选区评论是否低负担，尤其对移动端、长文档及引用来源复杂的材料。

## 优先讨论

1. “无资产疑点”是否先存在 DSH 任务旁，再按具体内容与来源获准提交 Workbench 的团队问题，而不是误把个人 Inbox 收藏当正式问题收件箱？
2. 什么时候合并重复反馈会掩盖不同适用情境，应明确保留两条？
3. 回访的最小有效信息是什么，怎样避免把敏感问题暴露给无关团队成员？
