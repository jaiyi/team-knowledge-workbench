# 13｜团队知识骨架：从工作记录到当前认知，再到 Skill

> 这是跨入口的**产品功能规格**，不是新增的左侧一级页面，也不是已实现的资料库、自动抽取或 PG 表结构。它回答“团队的内容按什么对象组织，成员从哪里看、怎么更新”，与[DSH 原生任务](01-DSH对话与任务.md)、[知识创作](03-知识创作会话.md)和[Skill 创作](07-Skill创作会话.md)一起评审。初版仍限定一个团队自己的资产空间；项目/产品线是该团队内部的工作线索，不是跨团队资产流通。

## 首先分清：提炼链与查找轴

成员在 DSH 中首先要完成业务任务；并非每段对话或每份文件都应入库。**获准分享的工作记录是来源；围绕业务对象维护的是有时间边界的事实；跨任务仍适用的约定、判断、经验和方法论是描述性知识；稳定且可测试的工作流才可能封装为 Skill。** 这些是可以关联的对象，而非必须逐级“升级”的四个文件夹。

| 对象 | 成员怎样理解 | 典型条目 | 成立的边界 |
| --- | --- | --- | --- |
| 工作记录／来源 | “当时留下了什么？” | 会议纪要、项目周报、交接材料、报告/PPT、授权可引用的原始资料 | 记录可能混有事实、建议、计划和争议；可查到原件不代表其中每句话是当前事实。默认原件留有权系统，Workbench 先登记安全定位与版本；只在 WeKnora 确有对应有权来源文档及精确深链时跳转阅读，不默认归档或建来源全文索引 |
| 复盘原材料／待核线索 | “本次任务有什么值得带去看看？” | DSH 主动复盘后的某条判断、纠偏、依据、边界、方法或疑问 | 用户认为值得复用只表示值得核查；未提交给 Workbench 时它还是本地/原任务线索，不等同会议纪要全文或团队正式资产 |
| 业务对象及其事实 | “我们现在围绕什么工作，当前是什么情况？” | 项目/产品线/专题及其范围、里程碑、当前协作分工、生效时点 | 项目是稳定的关联锚点，事实则有来源和有效期。旧纪要所说的分工不自动成为现在的人员安排；分工也不授予系统确认/发布权限 |
| 团队经验 | “在什么条件下我们怎样理解和处理？” | 协作约定、规则、判断、决策先例、踩坑经验、描述性方法论 | 要说清依据、适用范围、反例和何时复核；一次项目特例不能被包装成普遍规则 |
| Skill | “哪段工作流可以在限定条件下辅助执行？” | 有输入、步骤、判断点、人类节点、异常/停止条件和脱敏测试的流程封装 | 描述方法不等于可执行 Skill；发布版与目标安装、加载及某次任务实际执行另行核实 |

**另有一条正交的“业务对象轴”**：每个团队沿用自己的项目、产品线、业务专题，也可逐步增加合适的工作对象。记录、事实、经验及 Skill 可以关联一个或多个业务对象；同一条经验在两个项目页出现时仍是同一对象/版本，不复制正文。会议纪要、周报是来源的记录形式，“判断/方法”是提炼内容的表达方式；时间线是视图，不是另设的知识可信等级。WeKnora Wiki 可派生有来源的主题页，其页面关系图只是页面导航/引用；项目/产品线等**实体关系图谱**需逐边核来源、有效时间与 ACL，未经确认的候选边不代替业务对象页的当前事实；Wiki 或分块编辑也不回写 Git 正式版。

### 尊重团队查找习惯，而不是让业务自己从空白造体系

第一次进入时，可选择常用查找线索（项目、产品线、专题或先搜索）并建立一两个当前对象；产品预置可更名、可排序、可隐藏的“工作记录／当前事实／经验与方法／Skill”**视图模板**，以及会议纪要、周报、职责安排、判断/方法的最少字段提示。团队可不用周报，也可先按项目和时间找记录；不预填组织架构和不存在的业务事实。成员可以从 DSH 候选、已有记录、搜索结果或具体项目进入同一条内容。导航位置、名称和分组可调整，但稳定对象 ID、来源、版本和引用关系不因改目录而变化；跨项目关联不是复制。

产品不按“谁问得多、谁写得多”自动建栏目，也不擅自把旧条目重新分类。建议新增/合并栏目时先展示会影响的入口和现有关系，由团队选择；没有频繁使用的栏目可隐藏而不删除对象或历史。初版若无法可靠维护对象关系，宁可提供来源列表、关键词搜索和人工关联，也不假装有实时更新的“项目当前状态”。

### 创建、纠错与提炼：以问题为入口，不要求先选分类

1. **留记录或引用来源。** 核原系统、准确版本、当前阅读权限与最小定位；Workbench 仅统筹来源引用、证据锚点和处理状态，原件默认留有权原系统。不建设持久原文阅读或来源全文索引；WeKnora 已独立托管该来源文档且目标 ID/版本、ACL、精确深链均可核时才提供外部阅读，缺映射改为有权原系统定位或人工核对。另行批准的必要副本须单独定用途/期限/清理，非默认路径；Git 不存原件。WeKnora 来源文档可读不代表已核实其说法或已发布正式知识。具体门禁与失败对账见[知识创作的两条去向](03-知识创作会话.md#两条独立去向原件外部定位阅读与正式知识)。
2. **整理对象事实。** 从有权访问的纪要/周报或业务系统线索中，先按项目／产品线连续列脱敏事实点，标出来源时点、已发生的来源说法／预测／计划与当前性待核；用户在具体事实点评论后由模型生成下一版当前待核梳理稿，保留旧稿与评论以便比较／回退；无异议无需逐条点确认。来源说法独立且不可变，草稿改版不等于当前事实核证；核对发生与生效时间、反证、可见范围和权威系统后，才可能形成当前事实。产生新版时保留旧有效区间、变更理由及来源；如果权威事实在外部系统且暂不能读回，只给引用与核查去向，不自称同步了最新分工。
3. **从事实出发总结方法经验，而不是改写来源。** 事实梳理之后，产品提出**下次会问什么、能作什么有条件判断、凭什么、何时不可照用**，将整份来源综合为 0..N 段可读的完整待核经验稿；用户在段落上评论即可生成该议题完整的下一版待核稿、替换当前讨论稿并保留旧稿／评论，也可人工自然语言改写、标继续待核／不沉淀，不需要填一排知识字段。生成失败或回复无法与本次评论唯一关联时保留旧稿，来源和正式知识从不因此被覆盖。末尾一起看来源、事实和经验的分层去向，但整体核对不意味着一个动作就完成来源定位、事实确认和正式发布。来源仅在有权外部系统或已核 WeKnora 指定来源文档阅读；可读取不意味着其中事实或判断已核证。为检查覆盖，内部仍按**项目／产品线／跨项目专题／待关联 × 事实／经验／规则**逐段审计：事实带时点回原业务对象核，经验带条件与反例才可能成为描述性知识，规则须批准和正式适用边界；无可核规则时留空。矩阵单元与 22 条原子处理线索只是证据和去向视图，不是一篇正式知识，也不决定 taxonomy。经验可以跨多个对象和来源段，保持唯一 ID，汇总支持、局限与反证；KPI、计划、一次性处置可仅留来源或回业务系统，不为完成提取硬凑知识。先按团队、成员权限及版本核已有正式知识，再区分准确版本的已有覆盖（引用）、新证据（补证）、边界变化（指定版本修订）、冲突（待裁定）、可核查重后的新增及索引/权限不可核（待核而非认定不存在）。只追问已有知识和有权来源均不能提供、且影响结论的缺口；来源原话与 Agent 推断分开，一段经验可引用多份来源并允许零条正式知识增量。
4. **有必要才封装 Skill。** 经验中的稳定步骤可以进入 Skill 创作；复核触发、输入、步骤、人类节点、异常/停止、脱敏样例与依赖版本。仍需逐次业务审批或无法脱敏测试时保持描述性方法／人工路径；不能把原纪要直接转成可执行 Skill。
5. **在原位置纠错。** 记录事实错误优先到原系统更正并在本页标替代/争议；“记录真实写过某句话”与“现在认为那句话正确”分别保存。当前事实或经验有误，回到对应知识的来源、基线和修订会话；Skill 步骤/依赖问题到 Skill 创作；当前业务审批或实时数据回原系统/获授权 Tool。撤权时收敛全部关联视图，不借时间线或关联标题泄露原文。

### 用户看到的状态，系统留下的证据

对**知识和 Skill 的正式内容**，使用同一套易懂的主状态：“整理中 → 待核对 → 团队可用 → 已停用”。它描述**具体版本／修订**，不是整项资产的单值状态：v1 可以团队可用，同时 v2 整理中。整理不足退回补充；核对时具体确认、Git/CI、人审和目标版本读回由系统按类型核验，不要求成员背多段技术阶段；失败/状态未知在该状态旁说明“缺什么、谁可处理”，不能伪装为团队可用。被拒绝/撤回的候选只是结束该次尝试，不是“已停用”正式版本。Skill 的发布状态与特定用户工作区安装、宿主加载/真实执行并列呈现，不混作主状态。

工作记录仅展示**原件可否访问/定位及来源版本**，不得套“团队可用”；复盘原材料/问题仅展示**本地草稿、已收到、有处理结论/未采纳/合并等回访**，不得套正式资产状态。资料入库、原材料受理、事实核证、正式发布、Skill 安装是不同事件。系统保存详细事件给审计，前台在列表用一句“当前是什么＋哪里不足”，在详情按需展开版本和证据。

| 何时采集 | 最少需要的信息 | 在哪展示／谁来维护 |
| --- | --- | --- |
| 记录/线索进入时 | 来源 ID 或有权访问的安全定位、源版本/形成时间、来源权限/敏感度、非敏感摘要（可缺）、关联对象（可待定）与待核问题 | 来源卡显示「原系统可定位／WeKnora 指定来源文档已核可跳／原文未接入或待人工核对」及核验时间；只有实际深链和有权读回时才给 WeKnora 阅读入口。无权时不显示标题和摘要，本地文件不冒充已入库 |
| 事实/经验开始整理时 | 候选陈述、来源原话与定位、推断标记、已知知识 ID/版本及适用边界、真正影响结论的待核时间/范围/反例；来源与既有知识中确实都不可得的信息才标缺口。正式证据等级映射未定义，不由 Agent 自行定级 | 项目页“待核”与知识创作详情；初存只需安全最小线索，送核前才补指定草稿、依据与维护责任，不要求提交来源时填齐发布字段，也不填造未确认的时间和负责人 |
| 送核对时 | 固定草稿修订与基线、前后差异、来源权限和冲突、谁明确承接下一步/谁可执行受控动作；Skill 再补测试、依赖、异常/停止条件 | 知识或 Skill 的核对区；无预设岗位页面，具体操作时重新核实身份、资产策略和来源访问 |
| 正式版本及后续维护时 | Git 内容版本/提交、核对与审核范围、发布/目标读回和授权范围、替代/停用关系与原因、关联来源和业务对象、最近复核时间 | 团队资产只读显示权威证据；正式审核、发布与读回动作在对应知识/Skill 创作会话；业务对象页只摘录有权引用的当前版本并标明“截至何时”；PG 可承接工作对象/关系/状态事件的**后续工程方案假设**，Git 保留受控内容版本与审核痕迹，两者须按版本对账，不在此承诺已有实现 |

### 一个虚构的跨页演练

成员在 DSH 核对项目 A 的交接材料，主动复盘时发现一处值得核查的模板边界；Skill 只形成**待核候选**，成员检查可分享内容后决定交给 Workbench。另一份有权分享的周会纪要说“成员 B 接手资料索引，模板 C 先试用”，登记为项目 A 和产品线 P 的**来源记录**，带会议时间、版本和权限。项目页先显示来源时间线及“分工/模板待核”，**不会**马上把 B 写成当前责任人，更不会直接认定模板 C 普遍适用。

经确认协作安排的生效时间和证据后，新建项目 A 的**当前分工事实**，保留上阶段分工的截止时点。模板 C 的试用范围尚不清楚，先作为待核判断；后续核实反例，才形成“在条件 X 下参考 C”的**团队经验**，项目 A 和产品线 P 关联的是同一条知识。若“比较旧清单和新模板”形成稳定、可用脱敏样例测试的步骤，再创建引用该知识版本的 Skill；未形成时保留描述性方法即可。发布后后续 DSH 任务仍按具体条件核对；项目页面的当前分工与系统发布权限无关。

## 边界、原型差距与评审点

- 权限贯穿来源、候选、关联视图与目标系统；撤权后不展示受限标题、摘要或由多个关系推断出的事实。未连接/无法读回时写“无法核实”，不能把空列表当成没有记录。外部 Tool 当前库存/价格和业务审批不进入项目“长期事实”。
- [当前原型](../可视化原型/index.html)仅演示 DSH 的虚构任务、主动复盘与手工候选交接，以及 **111 行完整虚构合成周报**的五步静态材料导航「导入来源 → 事实梳理 → 经验总结 → 加入知识库 → 可跳过的 Skill 核对」：文件选择器可在本机阅读全文读取 UTF-8 TXT／MD／CSV（≤200 KB），但只有内置合成周报或固定字节指纹匹配的本地参考文件提供人工编排议题；事实与经验均有随当前选中项 ID 更新的待核稿／评论和同项合成对照（桌面约 2/3 + 1/3，窄屏对照接在本项之后），不能声称已核权威事实或正式知识准确版本。数字的口径及 Tool 授权须在事实梳理就地核，不独立成步；第四步本地去向树分别预览来源、事实、经验、规则、当期 KPI、计划、一次性处置、附件／非正文与外部 Tool，以及条件性 `knowledge/…` 文字提示，**未预览 Git 规范文件，Tool 节点不申请权限或调用接口**；第五步仅比较合成 Skill 与人工写法、允许跳过，不另设体检页。111 行／22 条线索的参考索引逐段范围清单只是**参考文件**的折叠证据下钻，不证明虚构全文逐句真实解析；来源阅读／Wiki、当前事实核证与 Git 正式知识均未执行，树节点不提供提交回执；另有 K-01 的独立修订与发布模拟，以及工作记录、业务对象和事实时间线的静态示意；**没有**真实资料上传/复杂格式解析、模型知识提取、知识检索/查重、可配置导航、PG 存储、资料库导入、团队仓库写入或 Skill 安装状态。要先验证目标团队怎么找东西和现有资料入口，不能把本规格当上线能力。
- 优先拿一份可脱敏纪要、一次周报、一个项目的分工变化和一条描述性方法演练：团队是否能说出“记录写过什么”与“当前事实是什么”的差别？先按项目、产品线、时间还是搜索找？维护当前事实的成本是否值得？若几乎无人维护，缩小结构化事实范围，不增加强制字段或目录。
