# 12｜任务复盘 Skill：和用户一起判断什么值得留下

> 这是**拟设计的 Skill 产品规格**，不是已安装、已加载或已执行的 Skill，也不是 DSH 已支持读取完整 Session/Tool trace 的证据。它在 DSH 原生对话中由用户主动触发；当前任务仍以完成业务工作为主，知识复利是可选的支线。返回[界面索引](README.md)。

## 为什么做，何时不做

成员在处理完一段任务后，可能曾纠正一条知识的适用范围、手工改了报告，或发现本该查询实时数据却只能去业务系统查。此时可以主动说“帮我复盘这次任务”。Skill 的目标不是马上列一张资产清单并给建议，而是**先回看任务怎么完成，再和成员确认哪些调整可复用，最后形成交给创作会话的结论**。复盘不能代替当次业务复核或审批，也不强迫每个任务都留下知识。

若任务仍在处置、证据不足或用户认为全部是一次性处理，合理结论可以是“暂不沉淀”。初版不自动识别任务结束，不在用户未要求时读取或保存完整会话。

## 工作方式：先复盘、再讨论、最后交接

1. **圈定任务并回看过程。** 用户在原生对话主动指定任务或可见轮次；Skill 按“任务目标 → 查找依据/使用资产 → 关键判断和执行 → 用户后续调整 → 当次结果”重建简短过程。区分看得见的步骤、用户补充的步骤和看不见的部分，不把一轮交互结束视作任务完成，也不假设能读取已关闭 Session、用户本地文件差异或完整 trace。
2. **核对既有资产怎样参与。** 对知识列出提及、检索、带版本引用等不同证据；对 Skill 列出推荐、安装/加载、执行；对 Tool 列出目录可见、授权调用和调用结果。逐项说清来源、版本或时点以及“无法确认”，把资料、正式知识、运行记录、外部实时事实和当前业务结论分开；先问用户是否漏掉了实际使用的资产，再考虑改什么。
3. **找出额外调整，请用户纠正。** 将 Agent 原建议或初稿与可见后续版本、用户自述的改动并排，指出调整了哪里、当前可核实程度与可能原因。若只能看到用户口述，写“用户称”；若两版不可得，直接问“是否另改过，方便描述变化和原因吗？”，不凭空推断修改或功劳。
4. **逐条讨论复用性。** 针对每处调整问：“换一个同类任务还会这样做吗？什么条件下适用？是修正现有资产，还是这个项目/审批的一次性特例？有无反例？”由用户校正事实并确认是“可复用／有条件可复用／特殊处理／证据不足”。Skill 可建议分类但不能代替用户定性；条件和反例不清时先保留疑问，不写成通用规则。
5. **商量线索去向。** 对确认值得留下的部分，问是补有权分享的来源记录/定位、核查某业务对象的事实与有效时间、提炼描述性团队经验、修订具体知识/Skill（ID、版本待核），还是稳定流程值得另建 Skill；一次性处理仍留原任务/原业务系统。Tool 缺口转外部提供方的目录、接入或权限流程，不在 Workbench 创作生产 Tool。依据不足可暂不沉淀；讨论结论并不授予任何人事实确认或资产发布权。
6. **问产物去向，再输出结论。** 如有报告、PPT 等实际产物，先讨论是否适合作为资料提交、谁有权分享、哪些内容受限，按下文的资料与知识双路径引导；用户核对结论、确认交接文本已去除敏感内容后，才输出按去向分开的短文本。用户尚未确认复用性时只输出“待讨论问题”；产物分享权限不明时只写“待授权/不转交”，不能称为已获准入库。复制与提交由成员自主完成；若另行选择手动保存到[我的工作台个人 Inbox](02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)，也只供本人回访，不能把个人保存当作团队交接，转团队须针对内容、来源和目标再次授权。Skill 不能自行向 Inbox 写入，未来 IM 内容仍须另获同意。

### 原子线索先分流，不要求每条都做成资产

复盘是[DSH 当前任务](01-DSH对话与任务.md)通往[团队知识骨架](13-团队知识骨架与工作记录.md)的**可选上游**。对每处值得留下的调整，先问它是“需要补一条获准分享的工作记录或来源定位”“某项目/产品线的分工、范围等当前事实需要核查”“跨任务成立的约定/判断/描述性方法值得提炼”“流程已稳定且可测试、值得做成 Skill”，还是“一次性处理/不沉淀”。一个任务可给多条相互独立的候选；用户回答的是**值得核查的去向**，不是为整份纪要、项目事实、知识修订或 Skill 发布作批准。工作记录可能混有计划、意见和争议，不能从一次用户复盘直接生成当前项目分工或团队通用规则；方法可以长期保持描述性，不强制升级为 Skill。

现有本地 `knowledge-compounding` Skill 是 DSH 工作区里用户创作的**实例**，可将候选写入当前工作目录的 `knowledge-inbox/deposits/`，而非已接入 Workbench 的通用产品服务或[拟议个人 Inbox](02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)。这个本地 deposits 目录不会自动同步到个人 Inbox，工作台也不会因本地 Skill 存在就读取工作区。它的 `draft → received → accepted/rejected/merged/superseded` 是**原材料回访**，不能和正式知识/Skill 的“整理中／待核对／团队可用／已停用”混用。若后续验证由工作台写回 `knowledge-inbox/status/<id>.json`，必须先核实目标收件箱位置、提交者授权、条目可分享性、身份映射、受理 ID 与状态含义；用户在**同一收件箱目录**运行 `inbox.py sync` 才会更新本地状态，不能因存在状态文件就称自动同步成功。初版仍以本页的人工检查、复制和明确提交为准，不运行任何本地同步脚本、不默认读取整个会话或全部收件箱。Skill 若要作为团队能力供其他成员使用，仍须在[Skill 创作](07-Skill创作会话.md)修订、测试、审核并受控分发。

## 可见性和证据等级

| 复盘可读到什么 | 可以怎样表述 | 不能推断什么 |
| --- | --- | --- |
| 当前上下文中的话语/可见回答 | “本段对话提到了知识 K-01／建议试用 Skill S” | 不能据此称其实际被检索、加载、执行或为本次结论提供了依据 |
| 用户的口述、手工补充或粘贴的修改 | “用户称随后改为人工核对”“用户提供了修改前后文本” | 未核验的叙述不能升级为系统操作记录或业务成功证据 |
| 宿主在授权范围内显式提供的版本化知识引用或 Skill/Tool 运行记录（**待能力验证**） | 带记录来源、对象 ID/版本、事件类型、可见时点；引用/加载/调用成功/调用失败逐项区分 | 记录也不能证明当前业务问题解决或调用结果永远新鲜；不在复制文本中暴露敏感参数和完整 trace |
| 来源不可见、权限不足、运行事件缺失 | “无法确认是否实际使用或调用成功”，建议用户核对来源/宿主记录 | 不填补缺失，不借受限来源的摘要泄露内容；会话转场后不假装掌握历史 |

若目标环境只给 Skill 当前对话文本，就采用**对话可见版**；即使 Skill 通过 Prompt 声称能看到“全部调用记录”，在没有真实事件与来源时仍只能写“对话中出现”。知识引用的 Git 版本和确认范围、Tool 的来源/查询时间、Skill 的真实版本/加载状态只能在可授权核实时列出。

## 报告、PPT 等任务产物：资料归档和知识修订分两条路

任务的实际产物可能有价值，但**产物不等于经过确认的团队知识**。复盘应先问“这次有报告、PPT、图表或其他最终版本吗？它们能否供本团队后续检索？”再核对产物版本、原始来源、制作/分享权限、客户或第三方内容、密级、可见范围、时效，以及其中是否含实时库存价格、个人信息或其他敏感内容。用户未确认权限和目标范围时，不预览受限内容，也不主动转存。

- **作为资料/来源**：对获准分享的版本，建议成员在已验证且有权使用的团队资料库上传/索引入口提交，保留来源、版本、访问范围和必要的脱敏处理。若实际入口、支持的文件类型、索引权限或审批要求尚未核实，只提醒“先确认平台入口和授权”，不能说已入库、已公开或已被 Agent 检索。未获分享许可的产物仍留在原业务系统；必要时只转交一个不泄露内容的待授权问题。
- **提炼可复用知识**：产物中某个判断依据、步骤或适用边界值得复用时，另发起[知识创作/讨论](03-知识创作会话.md)，引用有权访问的来源并核对资产基线；还要经过讨论、修订、确认、审核、正式发布和读回。原件上传不触发这条链，也不自动证明其中观点正确。Skill 流程类改进则交给[Skill 创作](07-Skill创作会话.md)。
- **仅当次处理/尚不能分享**：不上传、不复制原文到团队仓库；说明需先完成脱敏、授权或业务侧归档。即使资料已获准入库，也不把业务审批、实时数据或外部 Tool 权限一起带进去。

## 先对话确认，再给创作会话交接

复盘不能以第一轮回答里的推测代替成员判断。先展示简短过程和证据，再问影响结论的少量问题；用户可以逐项修正、补充反例或直接说不值得维护。示例为**虚构对话**，不表示真实调用已发生：

> Skill：这段“核对 A 清单与 B 模板”的对话提到了 A、B，未见正式知识检索记录或 Skill/Tool 运行记录。你后来补充“旧规则时期的常规任务仍参考 A”。这是原建议遗漏适用条件，还是这次项目的特殊审批？是否另改过最终报告？
>
> 用户：常规的旧规则任务都适用，不是这次特例。我在 PPT 里补了适用范围；PPT 有客户信息，不能直接分享。
>
> Skill：收到。先将“常规旧规则任务的范围”作为**用户确认的有条件复用候选**，请在创作会话查证 A/B 的版本与原始规则，不能直接宣布 A 已更新。PPT 暂不上传或粘贴内容；若以后获得授权并完成脱敏，可再核实团队资料库入口。还有其他调整或反例吗？
>
> 用户：没有；先讨论知识，不处理 PPT。

此时可以输出以下**供成员再次检查后复制**的最小文本。若用户没有回答复用性或资料授权问题，改成列出待确认问题，不填“用户确认”；若有多种去向，分段复制，避免把受限产物信息带到不具权限的目标页。

```text
【任务复盘交接｜用户核对的候选，不是正式知识/运行审计】
任务范围：<非敏感任务描述；业务结果为用户确认/未知>
过程与资产证据：<关键步骤；知识提及/核验引用，Skill 推荐/核验执行，Tool 提及/核验调用；各自版本、来源、时点或未知>
用户额外调整：<可见前后差异/用户自述/无法判断；不推断动机>
讨论结论与去向：<逐项写用户确认的可复用/有条件复用及边界、特殊处理、证据不足；对应来源定位/待核业务对象事实/团队经验/Skill 或不沉淀；未回答写待确认>
候选动作：<具体既有对象或资产 ID/版本待核与可能修订点，或新增候选；Tool 外部接入/权限事项；尚未核准当前事实、未正式发布>
任务产物：<有/无/未知；允许分享的资料版本与范围、需核实的入库入口；受限则仅写不上传/待授权，不附内容>
可转交引用与下一步：<仅有权分享的来源定位；在目标会话重新核来源/权限/资产基线，待谁进一步核对；不得含凭据、敏感值或完整 trace>
```

**虚构降级示例**：Agent 曾回答“已查库存”，但 Skill 看不到宿主运行事件和 ERP 回执。复盘只能写“对话声称查过库存，实际 Tool 调用及结果无法确认；请在有权的业务系统/宿主记录中核对”，不能显示库存数值，更不能凭历史资料推造实时值。

## 讨论结论分别去哪，什么时候停下

| 经用户讨论后的分类 | 推荐支线（成员选择） | 到达后首先核对 |
| --- | --- | --- |
| 获准分享的工作记录或原件定位 | [团队知识骨架与工作记录](13-团队知识骨架与工作记录.md)中的来源记录路径；实际资料提交前先核入口 | 核原件版本、发生时间、权限与记录中的事实/计划/意见；复盘条目不冒充完整纪要，来源入库不等于知识发布 |
| 项目/产品线的分工、范围或现状待核 | [业务对象与事实](13-团队知识骨架与工作记录.md)的原位置；必要时继续[知识创作](03-知识创作会话.md) | 按来源、生效区间、反证与原业务系统权威逐条核，用户口述不等于已确认当前事实 |
| 同类任务可复用的判断依据，或明确条件下才适用的描述性经验 | [内容讨论](04-内容讨论.md)或[知识创作会话](03-知识创作会话.md) | 是否已有资产、具体版本与有权引用的来源；不强迫经验封装成 Skill，也不把口述直接写成正式规则 |
| 稳定、可测试的步骤及输入、异常或停止条件 | [Skill 创作会话](07-Skill创作会话.md) | 具体 Skill 版本与脱敏样例；只有用户口述不能宣称 Skill 实际失败 |
| Tool 未开通、缺权限或宿主未接入 | [已开通 Tool](08-已开通Tool.md)或[Tool 广场](09-Tool广场.md)及外部提供方 | 目录可见、团队开通、数据批准和运行授权分别核对；申请不等于调用权 |
| 有权分享的报告/PPT 等产物 | 先核实团队资料库的实际上传/索引入口；其中需复用的判断另去知识创作 | 版本、来源、敏感内容、可见范围和授权；资料入库与正式知识发布分开 |
| 当次特殊处理，或证据不足 | DSH 原任务/原业务系统；必要时留待核实的问题 | 不创建通用资产，不自动生成团队待办或外泄原业务内容 |

## 对创作会话的交接：先复制，再核查

初版只提供**用户讨论确认后，人审核、复制与粘贴**。用户对复用性作出的确认只表明“这条候选值得核查”，不是对某一修订草稿的正式内容确认。复制前提醒检查生产标识、价格/库存、客户信息、凭据、敏感规则、不可公开来源以及完整 Prompt/Tool Call trace；受限产物只留下“不转交/待授权”状态，不附标题或能反推出内容的摘要。目标会话不解析文本自动执行变更，先标“用户粘贴的复盘候选（未核实）”，让成员选目标资产/基线版本并补可访问来源；未经授权的目标会话不得显示受限资料。用户仅查看结论时不在团队仓库留下反馈。未来若证实 DSH 授权事件和跨页传参可用，再考虑一键传递最小化结构化引用。这里的复制路径即便无需插件桥接，也仍取决于目标 DSH 对可安装 Skill 及上下文可见性的实际支持。

## 预期效果如何验证，而不是数输出数量

在同一团队一类任务的小范围试用中，观察成员是否愿意在需要时调用、**过程回看和额外调整是否准确、讨论能否识别可复用与特殊处理**、交接是否省下重新说明问题的时间，以及有权分享的产物能否找到正确资料去向。还要看粘贴后有多少被判“无须沉淀”、进入讨论/修订的线索能否找到来源与适用边界、核证者的新增负担和误报。只看调用量、建议数、输出长度、复制次数或产物上传数，都不能证明知识复利。若成员常为纠正虚构调用、捏造调整或错误归档建议而花时间，应缩窄可观察范围，甚至暂停试点。

**原型现状**：当前单文件原型已用虚构内存交互示意主动复盘的“回看过程 → 讨论复用性与产物去向 → 人工复制交接”，知识/Skill 页也示意粘贴候选和浏览器内“已收到”；它不是已安装或已运行的复盘 Skill，不证明真实 DSH 事件可见、Workbench 已受理、本地收件箱已接入或任何资产已发布。**待验证**：目标 DSH 能否安装/触发此类 Skill、Skill 实际能看见的上下文范围、能否提供脱敏且授权的事件证据、Workbench 是否适合接收粘贴线索；团队资料库的实际上传/索引入口、文件类型、分享审批、访问控制及受限产物处理能力。先用只读、虚构或获准脱敏的案例测试，不对真实生产任务自动留存、上传或公开。

## 评审问题

1. 回看过程时，哪些关键节点和证据足以让成员快速纠正遗漏，而不是重读一份长报告？
2. 与成员讨论复用性时，每次优先处理哪 1–3 条调整？遇到边界/反例不明确，如何坦诚保留疑问？
3. 哪类任务产物适合进入团队资料库、哪些必须留原系统？上传入口和审批要求应先通过实际平台验证，而不是在此猜测。
