# 06｜修订核对：一起查证，只有有权者确认特定草稿

> 页面位置：修订提议的核对内页。**任何获准访问材料的成员都可以补证/指出遗漏；正式确认、审核和发布分别受控**，不能用组织职级页替代资产策略。

## 何时进入，要完成什么

出现一份可审的修订草稿，需要有人判断“这些来源支持这句话吗、范围说清了吗、变化后谁维护”；可能由讨论者进来补背景，也可能由具备该判断权限的人进来作正式确认。目标是让责任人只对**看过的具体草稿修订与适用范围**负责，不对 Agent 未核实的摘要或无限未来的任务背书。

## 核对界面应呈现

- 原资产/基线 Git 版本、段落、旧结论及正式状态，提议的不可变草稿修订标识、修改前后差异、适用/例外范围、待决项。
- 原来源、成员背景与证据、Agent 比较、此前正式确认分层并列，注明每份材料的权限和可靠性；关联[内容讨论](04-内容讨论.md)与 DSH 问题回访定位。
- 当前谁实际接手、确认资格由哪条资产策略判定、草稿是否发生变化、确认后仍需经过哪些后续在[知识创作会话](03-知识创作会话.md)中进行的正式审核与读回。无权成员可评论，但无确认控件。

## 功能流转

| 功能 / 触发 | 前提与动作 | 状态 / 去向 | 异常与处理 |
| --- | --- | --- | --- |
| 补背景或指出问题 | 有权访问提议及相关来源的人在具体争议处提供引用/说明 | 追加待核查线索，可回[内容讨论](04-内容讨论.md)；并不自动改草稿 | 无权看来源不能靠核对页取得摘要；指出安全/当次审批风险时走原业务渠道 |
| 要求补证 | 实际接手者指出缺的来源、条件或适用范围，并明确下一步由谁处理 | 修订进入“待补证”，提议人获回执；补完后产生可核查的新草稿修订并重新进入核对 | 不能把“待补证”当作通过；长期无人处理需明确分派或缩小范围 |
| 缩小范围/调整草稿 | 有权参与的人建议排除未经证实的情境并更新文字；系统保留旧草稿和理由 | 新草稿标识出现，原草稿上的确认失效，待新版本核对 | 不可静默继承旧确认，即使改动看似很小；基线失效须先对账 |
| 确认特定修订 | 服务端在提交当刻重验人类确认身份、资产与来源权限、草稿不可变标识/基线、确认范围和利益/责任策略，要求明确“确认什么、不能确认什么” | 记录确认人的真实身份、时间、证据、范围、草稿标识及理由；标“已确认，待正式审核”，进入[知识创作会话的受控审核/发布流程](03-知识创作会话.md)；发布结果只读呈现在[团队资产](10-资产与发布.md) | 服务身份/Agent 不作责任人；资料冲突未解或权限不可核时不可提交；草稿一变即撤销适用的确认，不能按“已确认”继续发布 |
| 拒绝、暂缓、转原业务判断 | 有权人说明来源不可靠、当前情境不可泛化、必须开会或按单审批等理由，并指定回访 | “已拒绝/暂缓/由原业务处理”，关联问题收到可理解回执；旧正式版是否继续引用另行判断 | 旧版如有明显风险须标记停止引用/触发维护，不因拒绝新草稿就维持无条件可用 |
| 无人可确认 | 显示真正的待指派状态；业务负责人决定安排人、缩范围或维持逐次人工路径 | 修订保持未确认，原任务按业务规则继续 | 不生成虚构“专家已处理”，不按逾期自动通过，也不以评论投票取代判断责任 |

### “确认”不是“发布”，更不是“本次业务获批”

确认修订说的是“在列出的条件下，这一具体知识判断有依据”。正式版本还要对应 Git diff、CI、独立人审、Provider 发布读回与授权范围；源任务的审批由当次业务有权人办理。Agent 可比较两份清单，不能为 B 模板的生效时间补写事实。若会议确实必要，本页只准备待决点、会后留痕，不代替会议。

**原型已示意**：演示补证、拒绝、模拟权限确认，之后模拟正式审核。**原型未做到**：真实权限校验、确认范围细化、暂缓/缩范围/待指派、真实责任签署及外部对账。**待验证**：不同知识类别谁有资格确认，是否需多方核对；不能预设一律由“专家”或任意团队成员完成。

## 优先讨论

1. 先选低风险知识：哪类确认可由一名有权人负责，哪类必须另行人审或业务会议？
2. “拒绝新修订但旧版可能有风险”在界面上如何醒目且不自动撤回正式版本？
3. 待指派与积压由谁实际接收，怎样避免把所有评论都变成昂贵的确认待办？
