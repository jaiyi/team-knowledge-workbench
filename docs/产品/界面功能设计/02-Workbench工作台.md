# 02｜我的工作台：个人 Inbox、使用反馈与后续行动

> 页面位置：Workbench 五个并列入口之一「我的工作台」（原「我的使用与改进」）；其它四项仍为「提炼知识&经验／打磨可复用的技能／连接业务数据源／团队业务资产大盘」。DSH 原生对话属于宿主，不算 Workbench 入口。首页新增**本人主动保存、仅本人可见的 Inbox**，并保留原有本人使用反馈和具体行动索引；当前业务问题仍在 [DSH 对话与任务](01-DSH对话与任务.md) 和原业务系统解决。以下是拟设计；[现有 HTML 原型](../可视化原型/index.html)已将入口标成「我的工作台」，并以**浏览器内存**演示 Inbox 的手动暂存、查看、删除及到知识页的待核交接提示，旁边仍保留固定虚构使用情景和本地反馈；没有真实持久化、源任务深链、团队再次授权/受理，也不是真实个人历史、运行 trace、召回率或个人绩效统计。

## 何时进入，要完成什么

成员想保留一份**自己有权保存**、以后再看的最小工作线索时，主动选择内容、检查分享和留存资格后手动保存到**个人 Inbox**；不愿保存就直接回 DSH 或原系统。Inbox 不表示提交给团队。成员在宿主任务中发现知识没找到、版本可能不对、Skill 执行异常或结果没有帮助时，仍可从**本人的一次有权使用**进入原有反馈路径；没有消费事件也可以按最小线索报问题，不强制上传 trace。从左侧直接进入时可查看自己的 Inbox、最近使用与自己报告的问题，再看明确交给自己的处理动作和团队资产／创作入口；个人保存项、反馈和团队待办必须分开，不因保存或失败就默认新增知识或 Skill。团队存量与发布进展仍在[团队资产](10-资产与发布.md)；宿主任务有权版本说明或有权联系人已足够时，回原系统处理并停止资产化。

## 个人 Inbox：手动保存、回访、删除，不自动转团队

- **存什么、何时存**：成员在有权的原任务中手动挑选并核对最小摘要/片段或来源定位，主动点击「保存到我的 Inbox」，确认当前用途、来源授权、可留存范围和敏感内容处理；链接只作有权定位，保存、回访或到知识页导航都不自动抓取/解析链接内容。若成员在知识入口另行明确选用该来源，须重新核权并通过目标链接获取/解析门禁，不能沿用个人暂存许可。不得以“任务结束”“使用失败”自动创建个人收件项。不要默认复制完整 Session、Prompt、输出、Tool trace、业务产物、受限材料或凭据。来源本来不允许复制/留存或授权无法核实时，只提供原系统内受控定位/待授权提示，不能以“个人”之名绕过源权限。保存成功须有真实持久化回执；草稿、复制、按钮点击或失败/未知不能显示为已保存。
- **回来看、回去处理**：个人 Inbox 按当前身份、来源 ACL 和保存目的重验，显示获准的条目、来源/版本或时点、保存时间、可见性及留存状态；从条目返回原 DSH 任务或原系统时用不含会话原文的可失效定位，重验目标权限。链接过期、来源撤权或内容已删除时不展示缓存标题/片段，给出可用的原系统/人工渠道；不把不可访问写成空 Inbox。个人条目可留作阅读或主动删除，不因回访生成团队行动。
- **删什么、如何删**：由本人主动删除 Inbox 条目，撤回个人保存副本/定位在本产品的可见性；服务端删除相关个人元数据和经批准保存的对象副本，按实际保留/审计与备份规则说明删除进度和例外、失败重试及回执，不承诺可删除原系统原件、法定审计记录或已**另行授权**进入团队流程的独立对象。源撤权时立即停止展示，按权限及保留策略清理不可留存副本；删除不等于业务事实撤销、已发布知识回滚或源系统删除。
- **个人转团队分三步、逐步授权**：①成员从某条 Inbox 项**主动导航**到「提炼知识&经验」、讨论或 Skill 候选页，最多携带不泄露正文的待核定位，目的页重新核身份和来源 ACL；仅打开页面、预览或返回不提交、不共享、不创建团队候选或 Creation Session/Draft。②成员若确想将内容交团队，须另选具体**最小内容、来源、可分享范围、目标团队空间及接收目的**，明确再次授权并提交；目的页核准后才可产生独立 `submission_id`/受理回执。此回执只表示候选已收到，**不创建 Session/Draft**，也不等于核证、确认、Git 发布或 WeKnora 索引。③只有成员/有权处理者后来**明确选择正式知识或 Skill 创作/指定版修订**，服务端重新核目标空间、来源/基线、动作权限和分享范围后，才另建 Creation Session/Draft；受理 ID 与会话 ID 分列，未满足条件可停在待核候选或不沉淀。无权分享、撤权、拒绝、取消或网络未知时停在个人层或仅回原系统；不沿用保存时的个人同意作团队授权。即使团队候选经独立授权受理，删除 Inbox 也不自动销毁它；前后应让成员看清个人项、候选与会话的不同 ID、范围和删除边界。

**拟议存储与权限边界（不是现有系统已接通）**：仅用 PostgreSQL（PG）保存 Inbox 条目 ID、所有者/团队作用域、来源系统与有权引用、最小标题或脱敏摘要、目的/授权和留存状态、创建/失效时间、目标定位与操作回执等**最小元数据**；不将完整正文、Session 或附件放入 PG。若原系统支持按当前身份有权回读且禁止/无需复制，**只存原系统引用**，不保留原文副本；原系统撤权、删除或链接过期时引用即失效。仅当源许可复制、用户对特定内容与用途明确授权且保留期限可控时，才可把必要内容放入**获授权、加密、隔离且有删除/过期机制的对象存储**，PG 只记受控对象引用；打开时再核身份、来源 ACL、用途和过期状态，不由链接持有者直接公开读取。源系统不能提供安全回读、也不许复制时不保存正文；撤权及个人删除均应对 PG 与对象副本做状态/清理对账，审计仅留允许保留的最小回执。跨设备同步、加密密钥管理、备份清理和留存期限需在正式实现前由安全/来源责任方确认，**本轮只有产品目标，没有实际 PG 或对象存储集成**。

**明确不自动摄取**：Inbox 不是 DSH Session、个人使用反馈、团队 Git 仓库或 WeKnora 的自动采集器；本人反馈报告与最小消费事件仅用于原反馈/回访，不能暗中抄入 Inbox，Git 提交和 WeKnora 新文档也不会自动变为个人收藏。[现有本地 `knowledge-compounding` Skill](01-DSH对话与任务.md#从当前任务到团队知识上游只提供原材料)可写入工作目录的 `knowledge-inbox/deposits/`，它是用户工作区里的**另一套本地文件交接实例**，**没有连接到这个产品 Inbox**，不会因文件出现而在工作台入箱、受理或发布；本地 `accepted` 也不是团队知识批准。未来 IM/群聊消息若考虑接入，须单独取得用户及消息来源/相关方在该用途和范围的明确同意，设计独立的权限、最小化和撤回机制；本次不读取 IM、不默认继承 Inbox 保存或团队分享授权。

## 页面应该有的信息

目标首屏以**个人 Inbox 的主动保存/回访入口 + 原有本人最近使用 → 需确认的结果 → 我的反馈进展 → 后续资产行动**组织，旁边保留回宿主任务的短路径；Inbox 条目与原使用事件、反馈、团队待办分区呈现，不把个人留存计入资产或使用指标。只有能被当前身份和来源 ACL 查看、且可确定为本人消费的最小事件，才显示原有使用区域的资产标题、准确版本及可见状态；未取得、不可核、已失权和真正没有使用分别表示，不通过缓存标题、数量或小样本汇总泄漏受限对象。个人视图用于回访与发现问题，不统计个人产出或做绩效排行。

- 一条知识记录分别显示检索返回、命中的资产与准确版本／digest、是否引用、是否适用于限定任务和业务结果；一条 Skill 记录分别显示推荐、安装／加载、实际执行、技术结果、契约结果和业务结果。每层给出事件时间窗、最小引用与 `unknown`，不把推荐、浏览、目录可见或未反馈当真实使用或成功。无稳定资产版本时允许报问题，但不能猜版本或自动改旧版。
- 如展示任何「率」，须为同一层、同一窗口定义**分子／可评估分母**、覆盖范围、未知／不可评估数及小样本阈值：知识的正确有权版命中率、引用后适用比例，Skill 的实际执行技术完成率和契约成功率各自独立，业务结果由业务 Owner 另核。去重按 `invocation_id`，重试以 `attempt_no` 区分。无真实事件或分母时显示「不可计算」，不显示 `0%`；小样本优先写计数。成功与失败均须可核，不因无人反馈推断成功。
- 反馈可以选择「没找到／找错版或条件／Skill 执行异常／权限或分发／有结果却没帮助／无法归因」，指向本次使用引用和实际资产版本；脱敏说明可选，没有 trace 也能提交。提交只构成**用户报告**。受理和归因需明确谁核、依据何种回执与反证；候选分流到检索入口、知识来源与修订、Skill 脱敏回归、Provider/权限或原业务流程，不把相关性直接认定为根因。真实系统优先经授权关联 `event_id`／`invocation_id` 的最小引用；确需深入排障才在宿主按权限看脱敏诊断摘要，完整 Prompt、输出、凭据、业务文件和 Tool Call trace 不进入普通工作台。
- 回访按四条独立进度显示：报告提交及受理、原因核实与分流、特定资产版本的修订／发布／目标读回、**下一次相似任务**的实际使用与业务结果。反馈关闭不等于修订发布，发布不等于 Skill 安装／执行，也不等于业务问题解决；误报或无需资产化时可保留有理由的结论。正式改动另进创作会话与审核发布门禁，不在首页一键自动修复。

工作台仍承接[团队知识骨架](13-团队知识骨架与工作记录.md)的**具体行动与进展索引**，不是项目目录、工作记录全集或运行时间线。成员可按习惯找项目、产品线、来源、事实或经验，但只有被明确请求补证、受理问题等**具体工作项**才进入下述个人进行中；原件登记和一次消费不自动生成全团队待办。

- 当前团队资产空间绑定、消费事件可见范围与反馈状态；只展示当前身份和来源 ACL 允许的记录，不展示受限标题/摘要。未绑定、不可达、权限失效、无真实消费事件和确无记录不能混为一谈。左侧「提炼知识&经验」与「打磨可复用的技能」等按根因选择，是反馈核实后的可选去向；「连接业务数据源」先看目录和权限，「团队业务资产大盘」先查准确版。这些入口并列而非必须逐关完成。
- 按行动分类的入口：回 [DSH 任务](01-DSH对话与任务.md) 解决眼前问题；继续本人有权参与的内容讨论/补证；核对某份修订；看正式版本和异常；了解外部 Tool。进行中的事项分为“需要我处理”和“我关注的进展”；每张卡写明出现原因、具体对象与版本、下一步动作以及实际责任人/期限（若可见）。已结束的贡献保留可查，但不常驻进行中。
- 自己发起的问题的回访：已收到、待补充/已分派、人正在判断、有处理结论/不予沉淀、关联新版本可引用；**当前业务问题是否解决**作为另一条线，不由 Workbench 自动填写。
- 入口说明：左侧「提炼知识&经验」（旧称「导入材料」）与「打磨可复用的技能」（旧称「引入 Skill」）是**两类输入**，不是让外部 Skill 先走材料流程。前者按导入来源 → 事实梳理 → 经验总结 → 加入知识库 → 可选 Skill 核对（可跳过）梳理周报等来源；后者直接核团队已有版或外部形成的 Skill 的来源、准确版本／digest、适用任务、步骤依赖及真实脱敏测试证据，再判断引用、补证、修订或确有空缺时新增。材料第五步只提供两条路径之间的可选关联。不保留独立「能力体检」页或按钮；Skill 引入不等于导入包、发布、安装或运行，指定版本修订与审核另按门禁进入深层工作区。来源导入面向有权使用的完整文件、知识入口明确选择且受限获取能力已验证的来源链接或完整合成演示材料；第四步是独立去向的文件树预览，非知识内容不假装写入 Git。知识核对用于有依据/边界的判断，Skill 核对仅按条件预览合成比较；Tool 目录用于外部能力与申请去向，实时查询结果不记成团队知识。

## 提炼知识&经验与打磨可复用的技能：两类行动入口（拟设计）

从「提炼知识&经验」进入时，页面内先「提供获准材料」，核限定任务场景、期望判断及可分享的来源；**独立「打磨可复用的技能」不是材料第五步，也不是旧版五步流程**，当前产品与静态原型按[四阶段 Skill 会话](07-Skill创作会话.md#同一候选的四阶段材料第五步不是入口第一步)处理：①同一输入区选择团队指定版或外部／本地候选，带回获准改后包也回此处换输入；②按实际取得的包、文件名或定位线索诊断来源/版本、适用条件、依赖与缺口，案例数量和逐例结果集中在此阶段，不能核的旧版不冒称不存在；③在本 Workbench 的本地待核草稿中做具体修改和复测，上方默认给出可**手动**回 DSH 讨论的安全交接建议，文字回复不直接改包，改后包重新由①输入并在②重诊断；④按当前候选/修订核提交前五项质量门，缺权威证据就阻断并标补证责任与返回阶段。通过门槛也只允许申请审核，不等于 Git/CI/人审、SkillHub 版本/digest 读回、目标安装/加载/执行或业务结果。材料可跳过的第五步只是 Skill 优化线索的合成比较，不是 Skill 引入的第一步。当前原型的采购样包、预置改版、目录文件名及案例都是固定虚构演练，不是读取真实周报或 DSH 改后包、受控 Runner 试跑或正式提交资格；SK-02 是另一条示例资产，不借用采购样包的测试。外部 Tool 目录及依赖也不授予调用权。

如果成员的真实问题只需核适用时间或找原系统联系人，工作台应给出回宿主/人工渠道的最短路径，不引导其为了完成流程而先上传材料或引入 Skill。只有成员明确承接、有权访问的来源/基线和下一动作存在时，才将具体问题列入「需要我处理」；没有业务结果回执时不得把事项关闭误写成当次任务已解决。

材料主路仍是「导入来源 → 事实梳理 → 经验总结 → 加入知识库 → 可跳过的第五步 Skill 核对」：完整获准文件或完整合成材料按章节阅读，事实梳理复用章节与来源锚点，一章可关联零到多条事实；进展与计划可指向同一 ID，但不把计划当完成。事实/经验两步都以当前项待核稿、评论及同 ID 的有权事实记录/准确知识版本对照为主（桌面约 2/3 与 1/3，同步滚动不悬浮，移动端接在本项之后），显示来源自述、已核、未知或冲突依据；数字需核报表口径及 Tool 的身份、用途、字段、时间窗与只读权限，无权时回权威系统和人工。第四步的去向树把来源、事实、经验、规则、KPI/计划、一次性任务、Tool 等分别分流，非知识内容不伪造 Git 文件；第五步仅合成比较正常/边界/异常的 Skill／人工写法，可直接跳过而不改变第四步结果，既不试跑也不替代独立「引入 Skill」。未受理粘贴只是本地输入，不产生待办或自动抽取。找到适用旧版先引用或补证/修订指定版；确无适用旧版且稳定可测才评估新增，`skills/…` 与 `knowledge/…` 平级。



进入个人事项的应是**具体场景评估卡或其证据缺口的明确指派**，不是一张自动生成的“全员待评能力”卡。卡上显示限定任务/判断点、场景 owner 与核证承接人（无人则待指派）、生效起止或待核、证据来源/最后核实和下次复核、当前「暂定／待补证」与可引用正式资产版本的区别，以及各去向独立下一动作。只有真实受理/指派回执才能进入“需要我处理”；创建者可在“我关注的进展”看同一事项，不重复计数。知识引用、Skill 安装/加载/执行、Tool 目录/试参/真实调用各记独立证据和状态；无宿主事件时均显示未知，不用推荐或浏览推算次数。静态原型未提供该真实入口、场景归因或原生 DSH/未来数字员工使用回执；这里仅定义目标界面，不要求其运行模型、子 Agent 或工具。

## 主要功能怎样流转

个人 Inbox 的手动保存/回访和原有个人使用记录与反馈是**首页并列的个人路径**；个人收藏、一次消费或提交反馈均不自动算「需要我处理」。下表中的团队工作项仍按真实身份/回执索引；当前原型仅支持个人 Inbox 的内存暂存、查看、删除与到知识页的**待核交接提示**，及原反馈的本地提交与候选分流演练；并无持久化 Inbox 或服务端受理。

| 功能 / 触发 | 动作与状态 | 成功下一步 | 异常或不应发生的事 |
| --- | --- | --- | --- |
| 本人手动保存/回访/删除 Inbox 项 | 单独核来源可留存资格、本人同意、PG 元数据回执和（仅获准复制时）加密对象存储回执；回访/删除按当前权限和实际清理结果显示 | 本人回原任务或原系统；另经明确授权才提交最小候选给团队 | 不从 Session、反馈、Git、WeKnora、本地 `knowledge-inbox/deposits/` 自动入箱；未获许可不保存正文，个人项不生成团队待办或正式资产 |
| 个人项导航、候选受理、正式创作 | 主动导航只带待核定位供只读核对；另经具体内容/来源/团队目标的再次授权且服务端核准，才可独立提交候选并取得受理回执；仅后来明确决定正式创作/指定版修订且重核空间、来源/基线和动作权限，才另建 Session/Draft | 先只读核源，可停止或不沉淀；获准受理后到对应知识/Skill 创作或讨论继续判断是否要正式创建 | 保存同意不等于团队同意，导航不等于提交；`submission_id` 不等于 `session_id`，受理不直接建会话、不等于批准、Git 提交或 WeKnora 索引 |
| 进入团队空间 | 服务端确认团队绑定、当前身份和空间范围；只读汇总授权对象与可执行动作 | 从具体对象继续[知识创作](03-知识创作会话.md)、[Skill 创作](07-Skill创作会话.md)、[Tool](08-已开通Tool.md)或[团队资产](10-资产与发布.md) | 未绑定提示谁/什么流程处理绑定；失联显示“无法核实”，不清空待办、不伪称空团队；撤权后不展示缓存内容 |
| “继续我参与的问题” | 根据问题 ID、当前关系和权限读取受理/补证/处理记录，注明最近更新时间；有明确交给我的补证动作才算我的待办，否则是进展回访 | 进[内容讨论](04-内容讨论.md)补证或读回执；若源任务仍有效，返回 DSH | 处理人未接单时显示待指派而非“已转交”；无法看源内容时仅显示允许公开的状态/联系渠道 |
| “待核对的具体修订” | 仅对当前草稿有**明确指派/已承接的核对动作**且提交时满足确认资格者呈现确认待办；其他获授权成员可从对象页补证 | 有权确认者进[修订核对](06-修订核对.md)；其他有权成员仍可补证 | 没有确认者时提示分派/缩小范围/回人工业务路径；仅有资格、未获指派者不能被批量列为待办 |
| “找资产/看版本” | 搜索本团队可访问的知识、Skill、草稿与正式版本，清晰区分对象类型及状态 | 跳到指定知识/Skill 会话或[团队资产](10-资产与发布.md) | 仅搜到草稿不冒充正式可引用；无结果不冒充没有内容，说明检索范围/连接状态 |
| “现在去处理任务” | 以宿主安全链接打开新任务或返回原任务定位，并重验授权 | 到 [DSH 对话与任务](01-DSH对话与任务.md) | 不复制聊天内容，不在 Workbench 增加一个平行问答器 |

## 生命周期如何变成“我的事项”（拟议规则）

**不要用一条资产的状态直接生成个人待办。** 同一知识 K-01 可以有正式可引用的 v1、仍在核对的 R-02 和关于 v1 的另一条问题；一项 Skill 可以已发布，却还未在目标环境安装。正式版本的真实状态在[团队资产](10-资产与发布.md)，编辑和测试在相应创作会话。工作台只索引与**当前身份有关的具体工作项**，不改写它们的权威状态。

| 跟踪对象 | 状态从哪里核实 | 不能混成什么 |
| --- | --- | --- |
| 来源记录引出的待核事实／经验问题（`source_ref + issue_id`，可关联业务对象及版本） | 来源可见性以原系统/获准引用范围为准，问题受理与补证由[内容讨论](04-内容讨论.md)和[团队知识骨架](13-团队知识骨架与工作记录.md)的对象详情承接 | 记录本身不套知识发布状态；项目分工的历史记录不等于当前事实，也不给记录中提到的人自动分派待办或审核权 |
| 问题／评论 `issue_id`（可关联资产 ID、基线版本及来源锚点；也可没有资产） | [内容讨论](04-内容讨论.md)的受理、补证、实际承接、处理结论和回访 | “有人评论”不等于“该成员负责修订”；问题有结论不等于版本已发布或原业务已解决 |
| 知识候选／修订 `session_id + proposal_id + draft_revision_id` | [知识创作](03-知识创作会话.md)、[修订提议](05-修订提议.md)与[修订核对](06-修订核对.md)的保存、基线、确认记录 | 已发布 v1 与待核对 v2 不是同一个状态；旧草稿确认不能延续到新修订 |
| Skill 候选／修订 `session_id + draft_revision_id`，含固定基线与测试证据 | [Skill 创作](07-Skill创作会话.md)的会话、草稿、测试和受控提交记录 | `tested` 不等于批准；发布不等于安装、加载或运行 |
| 审核／发布／停用或对账 `release_job_id + 目标版本/digest` | 知识按 Git/CI、指定人审与 WeKnora 逐文档读回；Skill 按指定审核与 canonical 受保护 Git main 合并核验标 `skill.released`，可选 Registry 读回另记 `registry_released`；目标分发系统的逐目标安装另核，均标来源和时间 | Skill 已批准但未合并仍审核中；包 digest 不等于发布；请求或可选 Registry 的 `unknown` 不得掩盖已核 Git 发布，也不能冒称安装/加载成功 |

### 参与、当前责任与展示位置

“我参与过”只是**进入回访的线索**，不赋予查看受限内容、确认或发布的权力。服务端按团队、对象、来源权限与当前身份重新计算关系和可执行动作；没有可核验的身份映射时不生成个人列表。

| 我与工作项的关系 | 进行中显示位置 | 何时需要我行动 |
| --- | --- | --- |
| 我发起问题、留评论、补过来源，或明确订阅有权看的进展 | **我关注的进展**：受理、待分派、别人处理中、等待发布；只显示获准看的必要状态 | 只有处理者明确向我请求补证/澄清，且我仍有访问权，才生成“需要我处理”的补证动作；未回复的普通评论不产生确认义务 |
| 我创建知识／Skill 草稿或提议 | **我关注的进展**：别人核对、审核、发布时；自己已暂停且无下一动作时可从进行中收起 | 草稿未保存、我明确承接完善或被退回补证时，显示指向该会话/草稿的待办；“创建者”不等于永久维护人 |
| 我明确承接处理、维护、补证、定向核对、审核、发布或对账中的一项 | **需要我处理**，条件是动作仍有效、权限仍有效且绑定具体问题/修订/目标版本；待接收的分派邀请标“请决定是否承接”，不标“正在处理” | 具体操作须再次重验资格、来源、草稿修订、基线与责任策略；仅“有资格确认”不向所有人群发核对待办 |
| 我只看过资产、被 Agent 推荐过资产，或已完成历史贡献且无后续动作／关注 | 不进入进行中；需要时去资产页搜索版本或看有权查看的历史回执 | 后来出现新问题、收到明确请求或主动关注，才关联**新的**事项；不会复活旧待办 |

“需要我处理”与“我关注的进展”可以是同一工作项的两个视角，但**同一身份只显示一张主卡**：有真实待办时放前者，卡内保留进展和关注关系；动作结束后若仍有后续进展则移到后者。分派未被接收时，发起者看到“待承接”，受邀者（若被允许）看到“待决定是否承接”，团队有权调配者看到无人接手的安排动作；不得写成已有人负责。责任人的变更、拒绝承接和关注取消均需有回执和时间，不依赖对话推测。

### 状态变化与退出条件

下表的“工作台变化”针对**有权且关联的成员**，不是向全团队广播待办；不同阶段的权威记录可能并存，不用单个 `asset.status` 覆盖全部。

| 对象阶段／事件 | 工作台变化与负责动作 | 退出或接续 |
| --- | --- | --- |
| 发现问题、手工提交候选；已收到但尚未承接 | 发起者可关注受理回执；能调配的人若获明确责任，看到安排处理。仅手工粘贴、未提交时不产生团队事项 | 合并时原问题保留回访定位并指向主问题；关闭/判定不沉淀需说明原因，结束本项，不自动结束业务任务 |
| 待补背景、待完善草稿或 Skill 待建模／待测试 | 被明确请求补证者、已承接的创作者/维护者按具体缺口行动；其他参与者仅看进展。Skill 测试失败指向修订和重测，不暗示已发布 | 补证后形成新草稿修订、更新被指派动作；决定不做资产、撤回或转逐次人工处理时，记录结论，退出活动待办 |
| 某份知识草稿待确认；Skill 草稿测试通过、待审核 | **被定向指派且当前具备确认/审核资格**的人看到具体草稿与范围；提议者关注进展，普通评论者不进入确认队列 | 确认只是进入审核；驳回/退回补证由相应实际承接者处理，旧确认不自动继承。无人可确认时保留“待安排”，不按时间自动通过 |
| Git/CI/人审、Provider 目标版本读回；Skill 发布后目标安装／加载核验 | 有明确发布、对账或目标分发责任且具备相应权限的人处理对应异常；其他关联者看发布进展。Skill 发布后安装/加载可有**单独**事项，不能当作作者的默认待办 | 目标版本及授权读回一致后，发布事项结束；安装/加载状态单独确认，执行/业务效果没有证据则写未知 |
| 正式版可引用／Skill 目标状态验证完成 | 已完成且无后续动作的个人进行中卡退出；有权成员仍能在团队资产查看正式版，在已结束记录查原回执 | 新反馈、过期复核、停止引用或失效的证据建立**新问题/维护事项**并链接正式版本；不把已发布的 v1 改成“待完善” |
| 基线漂移、草稿变化、并行修订或停用旧版 | 指定修订的旧确认失效；有权且实际承接者看到重定基线、对比/合并或停用核验动作；关注者看到不再可按原范围引用的提示 | 不将旧评论或旧确认自动迁至新版；冲突、被拒绝的新草稿与旧版继续可用是三个独立判断 |
| 发布/安装返回 `unknown`、服务不可达、责任无人接手 | 按资产和阶段展示：Skill 的 Git 合并核验未知时不显示「已发布」，但已核实指定审核与 canonical 受保护 Git main 合并的 `skill.released` 不因可选 Registry release/readback 返回 `unknown` 而消失；Registry、逐目标安装与 DSH 加载的未知分别显示，不冒称已安装或有人处理中。有授权的对账/调配者看到对应动作，关联者看到允许公开的最后核实时间 | 对账后只更新相应权威状态；禁止未知时盲目重复写入或把断联解释为“暂无事项”。管理员固定包 fallback 仅在 Git 已发布后可供下游取包，不是发布 |

### 卡片、聚合与安全跳转

一张卡至少说明：**为何出现在这里**（我发起/关注/收到具体请求/已承接），**指向什么**（问题 ID 或会话及草稿修订 ID；关联资产 ID、基线 Git 版本、目标发布版本/digest，若适用）、当前阶段和权威来源/最近核实时间、我的下一动作或谁在等谁、目标页面及可用的 DSH 返回定位。一个问题链接多份修订时保留问题回访主卡并标关联数；同一修订的多条评论可合并为摘要，**不同草稿修订、不同目标版本或独立确认请求不得合并成一条可执行动作**。排序优先我能行动的明确请求与阻断，其后是有时间要求的回访和普通关注；期限只有真实设定才展示，不以逾期自动确认。

点击卡片时重验身份、团队、对象与来源 ACL，按动作到[讨论](04-内容讨论.md)、[知识创作](03-知识创作会话.md)/[Skill 创作](07-Skill创作会话.md)、[特定修订核对](06-修订核对.md)或[团队资产](10-资产与发布.md)，不以默认最新版本替换原锚点。撤权后即从个人聚合移除受限标题、摘要和缓存深链，只给获准的联系/申诉去向；请求转给其他有权人，原贡献留在审计而非继续显示为我能处理。同步中断或来源冲突时保留安全的“无法核实、上次核实于何时”占位，不把旧缓存当实时待办、也不显示“全部完成”；恢复后重新核验。来源无可信更新时间、身份或权限核验失败时不展示数量/名称以免侧漏。

### 两个典型例子

- 我评论 K-01 v1 的适用范围：评论受理后在**我关注的进展**；负责成员向我明确请求补充来源时移入**需要我处理**。其后对方提出 R-02，只有对 R-02 获指派且有资格者看到确认待办。我仅凭评论身份不会被要求确认。
- K-01 v1 已可引用，而 R-02 尚在核对：资产页仍展示 v1 正式状态；创作者在负责完善时看到 R-02 待办，已交核对后转关注。R-02 经正式审核和目标读回后这些进行中项结束。日后 v2 有新疑点时创建新的问题/修订事项，不篡改 v1/R-02 历史。Skill 同理，但 `released` 后目标安装及运行另行核证。

### 不应做成 KPI 看板

能汇总“本团队可见的无人承接修订、过期风险、发布状态未知”，但汇总必须带时间范围与授权分母；不允许按人员问答量、处理速度或贡献次数排行。地图只对限定任务的具体判断点作候选盘点，见[候选能力地图](11-候选能力地图.md)。小样本/组合筛选可能反推个人时不展示。

## 跨页与设计取舍

工作台是**个人 Inbox、使用反馈和具体动作的索引**，三者的授权及状态独立；不承担宿主运行时间线、内容讨论或审核发布本身；反馈详情指向一次最小事件引用，Inbox 指向成员主动保存的可回访个人项，待办卡指向特定问题/资产/版本，而非“去专家后台”。从 DSH 进来应优先保留原问题和可失效的返回定位，不能被通用首页吞掉。如果个人使用事件尚不可得，退回本人主动报问题和受理回执，不靠推荐或模拟按钮伪造真实记录；没有个人 Inbox 持久化回执则不声称收藏已保存。

**当前 HTML 实际演示（「我的工作台」）：**默认进入工作台，个人 Inbox 可手动填虚构最小线索标题、来源定位与备注，最多暂存十条；可查看、删除内存项，或主动从所选项跳至「提炼知识&经验」显示待核定位。跳页没有上传正文、自动受理/提取或团队分享，成员仍需在目标页核源与授权；刷新或模拟撤权清空本页状态。首屏另把固定虚构的知识／Skill 使用情景、两者各自「暂无可计算数据」、本人本地反馈进度放在创作入口之前。点情景可看最小虚构事件 ID、准确示意版或未知、未证实的结果；按类别提交可选的本地说明、查看候选诊断与四段进度，还可模拟标注候选去向，但不派单、不核根因、不发布或验证下一次结果。没有真实登录身份、PG/对象存储或原系统引用、真实源任务返回、服务端删除、团队再次授权/受理、消费事件、trace 上传、自动诊断、召回率或任务结果。首页不再重复摆放左侧四个入口的选择卡，也不另放讨论/修订/资产的导航卡；返回宿主从左侧进入，具体反馈详情仍按版本给出相应下一步。解决原任务后可以停止，不要求顺序完成或新建资产。讨论与修订仍是按指定版本进入的次级动作；原来的两张固定「需要我处理／我关注的进展」情景卡不再是首页首屏或可交互待办。

**其它入口的目标与原型边界不变：**左侧「提炼知识&经验」沿用页面内「导入来源 → 事实梳理 → 经验总结 → 加入知识库 → 可选 Skill 核对（可跳过）」演练；「打磨可复用的技能」并列接收已有／外部 Skill 的最小线索，不要求先读周报。连接业务数据源仍仅为外部目录及接入条件示意，未建立真实连接。材料只对合成样本和指定本地文件指纹使用人工预置议题，对照不是权威检索，第四步不是规范 Git 文件预览，第五步不是试跑。Skill 页面只有四阶段虚构演练，缺真实 Runner、正式提交或安装执行回执；Tool 目录没有授权调用。工作台反馈不能绕过各入口的测试、审核、发布和目标读回门禁。

**真实能力仍待验证：**个人 Inbox 的来源复制许可、主动保存/回访/删除与团队再次授权回执、PG 最小元数据和获准加密对象存储、原系统安全引用及撤权/清理对账；DSH/业务系统的最小消费事件、版本/digest 归因、重复调用与重试去重、权限撤销及 trace 受控引用；反馈受理和责任分流、准确版本修订、下一次业务结果均需各自权威回执。在此之前首页不得用固定情景计算率值，也不得把本地候选去向宣传为自动修复。

## 优先讨论

1. 成员是否愿意主动把哪类最小线索保存到个人 Inbox 并回来继续处理？原系统引用与获准加密副本各自何时必要，删除/撤权能否按真实保留规则给回执？
2. 在真实任务后是否会主动回看“哪一次使用没帮到我”，还是已有结果卡的精准深链和一句话反馈就足够？需要拿真实任务和未使用样本观察，不能凭原型决定。
3. 目标 DSH 能否在不复制完整 trace 的条件下提供最小且有权的消费事件、知识准确版引用和 Skill 执行回执？何时分母足以支持每一层可评估指标？
4. 谁确认失败归因和业务结果，哪些问题只需调检索入口、找来源责任人或回原流程，而非修订资产？受理、正式发布与下一次解决如何分别回访？
