# 1. 为什么组织需要知识工程

## 项目背景与前提假设

本产品以组织具备**私有部署的大模型及相应的受控运行环境**为前提：获授权的内部资料可以在符合组织要求的环境中供模型处理，保密能力由部署与治理机制保障。因此，这里不把“材料因保密而一概不能交给模型”设为产品要解决的主要矛盾；真正要解决的是如何把获准来源整理成可核对、可维护、可复用的团队知识，并让模型在具体任务中正确使用。

这是一项**设计前提，不是对当前环境已完成部署或材料已获授权的事实确认**。私有部署不等于所有资料都可访问、传输、持久化或发布；来源授权、成员权限和留存边界仍按各自规则执行。具体模型环境是否适合处理某类材料，由使用方自行评估并遵守其所属组织的要求；Workbench 首期不提供模型数据域审批、质量/成本配额或安全认证。后文讨论的 Agent 能力与产品流程均建立在实际使用已获相应授权的前提下，原型和本地验证不因此获得连接真实模型或传送生产材料的授权。

## 组织每天都在付出“弄清楚”的成本

员工遇到问题，会查文件、翻群聊、问熟人；说法不一，就请专家核实、开会讨论。这些做法有其必要性：遇到新情况、利益冲突或需要承担责任的决定，本来就该由人讨论。

但其中有一部分工作在反复发生：上次已经找过依据、对过口径、作过取舍；同一团队换一位成员、换一个类似任务，又得重找材料、重讲背景、重问一遍。即使找到了旧结论，也不一定知道当时针对什么条件、今天还算不算数。团队不仅重复付出了**找到信息**的成本，还重复付出了**判断是否适用**的成本。

客户答疑、设备故障、采购规则、设计选择、新人接手工作，都可能发生这种重复。这里不是说每个问题都有现成答案，而是说：**已经付出过的调查、判断和协作劳动，为什么没能成为下一次工作的起点？**

## 从工作记录走向可用的团队认知

组织知识工程的对象不止会议纪要或一份文件，也不等于把所有经验做成 Skill。会议纪要、周报、交接材料、报告等首先是**来源记录**，其中可能并存已发生的事实、尚未兑现的计划和不同人的意见。团队还需要按项目、产品线或具体任务找到这些记录，核对有时效的业务对象事实，从中提炼有适用条件的判断与描述性方法；只有步骤稳定、能测试且说清权限和停止条件的部分，才考虑封装为 Skill。这些对象可以关联，不必沿一条“文件 → 知识 → Skill”的流水线逐级升级；原件留在有权系统或经单独核准的阅读层，正式知识仍需受控版本与审核。

## 基本单元不是文件，而是可以重新检验的判断

> **知识工程服务于组织高效、可靠地做判断和协作。它把已经确认过的信息、判断依据和适用边界留下来，让人和 Agent 在下一次工作中用得上、用得对。**

要做到这一点，先在**同一团队自己的团队资产 Git 仓库**中明确可维护的资产边界，再分清四种东西。团队成员按当前任务目的找资料、补背景、给选中文本附来源证据或提出修订；能贡献，不等于能把建议直接确认为正式知识：

- **资料与工作记录**：制度、纪要、周报、案例、聊天等，说明“当时有什么信息、谁说过什么”；有来源不等于当下适用，记录中的计划也不等于已经发生。项目分工等当前事实还要核对来源权威、生效时间和变化。
- **可复用的判断**：说明“在什么条件下，依据什么，可以怎样理解或处理；例外是什么；由谁确认、谁负责更新”。这是知识工程优先让人和 Agent 找到的内容。
- **当前业务决定**：面对这一次的具体条件，由有责任的人作出判断、批准或承担后果。已有知识可以提供起点，不自动替他们决定。
- **执行动作**：在获得必要授权后做某件事。它的权限、失败处理和结果记录不能仅凭一条知识自动推导出来。

并非所有有用经验都值得变成正式知识。一次性事项和实时业务状态，应留在原工作流程或业务系统里；来源不清的经验可以提供线索，但不能冒充已确认的结论。团队还需要受控查询实时事实的 **Tool**，例如查询 ERP 库存或采购价格：知识说明如何判断，Tool 取得当下数据，Skill 可以按稳定步骤组合二者，但调用权不能靠写入团队仓库获得。知识工程做的是**有选择地保留、供人辨认和不断修正**，不是把所有信息搬进一个库。

## 为什么叫“复利”

如果一个判断经过一次查证和确认，之后被多次正确使用，后面的人就不必每次从零开始。下一次使用又可能带回新的例外、冲突和改进，使它在新的条件下更清楚。这样的积累，才有可能成为组织能力，而不只是某个人记得多。

复利不是条目越来越多，而是要看两边：后续工作少花的查找、解释、等待和返工成本，是否覆盖最初整理、审核和持续维护的成本；同时错误使用有没有增加。问题不重复、边界说不清或维护负担太高时，明确联系人、改一份模板，可能比建正式知识更好。

## 大模型有能力，但不天然懂这家企业

顶级大模型有很强的理解、归纳和推理能力。可以把它类比为一位能力出色、刚到岗的博士：面对陌生问题，它能很快分析材料、提出可能的解法；但它并不知道这家企业当前采用哪版规则、以前为什么作过某个取舍、谁有权批准，以及眼前任务进行到了哪一步。**会推理，不等于掌握这家企业做这件事所需的上下文。**

这里的上下文也不只是把更多文件塞进一次对话。它至少包括：当前任务要解决什么、可访问的事实和实时状态、已确认的结论及其依据、适用条件与例外、谁负责判断和批准。通用模型本身不能保证这些信息是最新的、彼此一致，也不能凭推理补出企业未提供的规则。缺少上下文，回答可能很聪明，却不能可靠地转化为员工下一步可用的工作成果。

## 知识工程怎样让能力进入工作

过去即使留下了可靠记录，下次使用的人仍要知道它在哪、猜对关键词、自己读懂上下文。团队知识工程把值得复用的判断连同来源、边界和责任保存在本团队资产中；成员仍在 DeepSeek Harness Desktop（DSH）的**原生对话与任务**里工作，获授权的知识检索、Skill 匹配及外部 Tool 查询能否呈现，均取决于目标宿主能力、实际接入和授权，不能先假定已内置。任务后如有值得留下的调整，成员可主动复盘、与 Agent 核对复用性及分享范围，自行挑选最小线索手动保存到拟议的[个人 Inbox](界面功能设计/02-Workbench工作台.md#个人-inbox手动保存回访删除不自动转团队)供本人回访，或明确复制给有权的创作会话；**个人保存不等于团队贡献**，从 Inbox 提交团队仍须核具体内容/来源并再次授权。Workbench 再协助对照已有资产、讨论、补证、修订，并由有权者对具体版本确认、审核和发布。**被提及、被推荐与实际引用、加载或执行分别核实**，推荐 Skill 不等于安装、加载或执行；实时状态仍从原业务系统取得，当前业务决定仍交给有责任的人。知识工程提供可用的团队上下文，模型提供处理上下文的能力；两者结合，才有机会减少重复查找、解释和确认，而非要求每次任务都产出知识。

这也带来风险：如果给 Agent 的是过期依据、相互冲突的材料，或超出原结论范围的新情况，它可能把错误说得十分流畅。更强的推理能力不能替代来源核实、适用性判断和授权。因此产品需要同时支持“该用的时候用得上”和“不能用的时候看得出来、停得下来”；Agent 改变查找、整理和复用的成本，不改变业务判断的责任归属。产品可以**逐步变得主动**：先由成员在原任务中主动复盘、提交线索；待来源、版本、权限和责任可核验后，再由 Workbench 在本团队限定范围提示可能冲突、过期或缺少衔接的候选，请人复核。主动发现不是自动采信、发布或替人审批。

如果未来要讨论“数字员工”，它应是更远的**待验证方向**，而不是当前产品已有的身份或执行权：必须先在特定场景证明知识有边界、Skill 可测试、外部 Tool 获授权、异常能停下且人工责任明确，才可能讨论扩大可委托的任务范围。不能因为模型会回答或资产增多，就宣称组织已经具备自主执行能力。

## 为什么它可能成为可复用的平台能力

采购规则、设备处置与设计决策不能套同一份答案；初版也不设计一个团队去查看、贡献或发布另一团队资产的产品场景。先在**一个团队自己的 Git 仓库和获授权的资产范围**中检验：结论从何而来，针对哪种情况，由谁确认，谁能看，发现变化找谁，旧说法何时停用。平台将来可以复用这些机制，但不同团队须各自绑定资产、权限与责任，不能因为插件相同就共享内容或确认权。

是否真的具备平台性，要待本团队的任务闭环经验证后，再看其他独立团队是否能分别复用机制；这不是初版的跨团队用户流程或既定成效。检验价值也要分开看：**效率**上，完成同类任务拿到适用依据的时间、重复解释和返工是否下降，扣除核证维护投入后还值不值得；**管理**上，负责人能否在明确场景的关键判断点看到已核依据、未知与例外、维护责任和待办，从而决定补证、投入资源或保留人工路径。两类都须用获授权的真实任务及可核证业务结果观察，不能以文档、Skill、推荐或 Agent 调用数代替，也不做个人画像。具体怎样划分平台与领域的责任、哪里最容易断，见[下一篇](02-知识工程难在哪里.md)。

以上是从组织工作方式出发提出的**产品判断**，不是基于本团队真实访谈得出的结论，更不是已证实的收益。现阶段先以它设计初版，随后用真实使用检验、修正甚至推翻它。采购、设备等仅是解释问题的示意场景，不代表已确定的试点。
