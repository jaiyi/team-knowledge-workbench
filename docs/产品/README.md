# 知识工程：一份可迭代的平台产品蓝图

**我们要解决的不是“文件不够多”，而是团队上一次付出过的调查、判断和协作劳动，下一次相似工作仍要从头再来。** 知识工程让经过确认的依据、结论和适用边界能被找到、正确使用、发现问题后及时更新。初版围绕**一个团队自己的团队资产 Git 仓库**展开：团队成员按眼前目的查找、补背景、指出疑点或提出修订，不必先进入某个角色专属后台。DeepSeek Harness Desktop（DSH）承接任务中的知识检索与 Skill 推荐（只推荐，不自动安装或加载），并在实际接入与授权后通过外部 Tool 查询业务系统当前数据；Agent 降低查找和整理成本；Workbench 承接团队成员围绕资产的贡献与有权人对特定版本的确认、审核、发布；左侧的「连接业务数据源」入口以「团队可发现」与「待申请」两个目录 tab 帮团队看清外部能力、Skill 依赖和申请去向；当前原型仅作虚构目录示意，没有真实连接。Tool 的接口、数据授权与实际调用不由团队资产仓库决定；原业务系统继续承担实时数据、任务与审批。

现阶段没有真实业务访谈、试点输入卡、原任务与结果回执。这是一份**基于经验和第一性原理的初版产品假设**：先设计一套可用、可信、可维护、可观察的闭环，之后用真实使用反馈改进或推翻假设。**我的工作台（原「我的使用与改进」）的下一轮假设**是让本人自愿手动保存最小、有权留存的线索到个人 Inbox，之后自行回访、返回原任务或删除；与原有本人知识／Skill 使用线索及失败反馈并列，不能把个人保存自动当团队贡献。转给团队知识或 Skill 流程须就具体内容、来源和团队目标再次授权：仅导航去核来源不提交，明确提交后至多得到独立候选受理回执、**不建 Creation Session/Draft**；只有随后明确选择正式创作/指定版修订并重验权限才新建会话。团队受理仍不等于核准、Git 发布或 WeKnora 索引；不自动采集 Session、使用反馈、Git、WeKnora 或本地 `knowledge-inbox/deposits/`。拟议只把最小元数据放 PG：有权安全回读时保存原系统引用，获准复制才把必要正文放加密对象存储；两者都未接入。真实召回／执行结果必须有分层回执和可评估分母；当前静态原型显示「我的工作台」，只有浏览器内存中虚构的 Inbox 暂存、查看、删除与到知识页的待核提示，以及原有虚构使用案例和反馈；没有服务端保存、授权/受理，真实指标显示不可计算，不接受完整 trace。**本轮整体评审**不把增加资产或页面当成更深入：从一类任务原来如何完成、哪里真正反复付出成本开始，分别检验来源是否可用、这次判断是否适用、有权者是否承担得起核对，以及下一次同类任务是否更好。联系人、模板、原业务系统链接或保留逐次人工判断都可能比新建知识／Skill 更合适；没有结果回执时只写“未知”。静态原型中的清单 A/B、周报、发布与指标都是虚构演练，不能作为上述结论的证据。请按顺序读：

1. [为什么组织需要知识工程](01-什么是组织知识工程为什么要做.md)：反复付出的成本是什么，什么才算知识复利，为什么 Agent 改变了这件事。
2. [难在哪里](02-知识工程难在哪里.md)：从形成判断到下一次正确使用，哪些环节可能断开，平台与领域各负责什么。
3. [Workbench 怎样承载这项能力](03-Workbench如何解决.md)：逐项对应前篇的五处断点，以同一团队成员的任务目的与资产贡献为主线，说明 DSH 任务入口、Workbench 中的选中文本评论与修订、有权人的版本确认及失败去向；Agent/Workbench/原业务系统各守什么边界。
4. [初版假设与迭代](04-初版假设与迭代.md)：暂时无法访谈时的设计依据、可被反驳的假设、反馈分类与后续取舍。

要逐页推敲入口、功能、异常和跳转，先看[界面功能设计索引](界面功能设计/README.md)中的**同一任务跨页评审矩阵**；要设计真实验证，见[初版假设与迭代](04-初版假设与迭代.md#真实试点前的原始素材研究和独立复核协议)。这两处分别是设计检查与待执行业务研究，不是已经完成的访谈或试点。Workbench 左侧拟定的五个并列入口现为「我的工作台／提炼知识&经验／打磨可复用的技能／连接业务数据源／团队业务资产大盘」，按具体缺口选择，不是必须完成的五步；DSH 原生对话是宿主，不计入五个入口。现有 HTML 已显示「我的工作台」和个人 Inbox 的内存演示；旧名「我的使用与改进」只是既有反馈区的历史称呼，并非另一个入口，HTML 中的暂存也不是真实持久化。原「导入材料」与「引入 Skill」对应两种不同输入：前者处理完整文本来源与知识去向，后者直接核团队已有或外部形成的 Skill 的有权来源、准确版本／digest、适用任务及测试条件，**无需独立「能力体检」页/按钮**，也不要求 Skill 先走材料工作区。材料主路是「导入来源 → 事实梳理 → 经验总结 → 加入知识库」，满足条件时可进入第五步「Skill 核对」，也可跳过。导入面向获准分享、版本可定位的完整本地文件；无真实原件时用篇幅与章节覆盖足以检验全篇处理的**完整合成材料**，不以几行结构缩写冒充整篇。事实与经验分别处理当前选中项待核稿和评论：桌面约 2/3 当前项、1/3 同一选中项的已有内容准确版本对照，右栏不悬浮固定或停在上一个条目，移动端对照跟在本项之后；逐项标证据状态。数字的报表口径及当前身份、用途、字段/对象、时间窗和只读通道授权在事实梳理中就地核对，不单设 Tool 步骤。「加入知识库」展示按来源／事实／经验／规则／计划等去向分流的文件树预览与独立门禁：只有经核条件的正式知识候选才预览规范 Git 知识路径，不给原件、事实快照或计划编造 Git 文件。第五步仅在稳定可测且确有 Skill 缺口时模拟对照与去向，可直接跳过；它是从材料到 Skill 的关联路径，并非外部 Skill 引入的必经步骤。合成 Skill／人工写法不是真实测试，也不另开体检页。Skill 入团队资产应走独立的受控版本、真实测试与指定审核；合入 canonical 受保护 Git 主分支并核验后才算 Skill 已发布，从固定 commit 构建的包、选用时 SkillHub Registry 读回及后续安装/加载则另列证据，不能写进知识目录或视作已安装。指定正式版受控修订或 Skill 深层创作仍按条件进入各自工作区。另有 DSH 宿主、Tool 双 tab、讨论、修订、核对、能力地图等视图；[团队知识骨架与工作记录](界面功能设计/13-团队知识骨架与工作记录.md)区分来源、待核线索、有时效的事实、描述性经验与可测试 Skill，**不是额外的一级导航**。这仍是供逐页 review 的拟设计；[可视化产品概念稿](可视化原型/index.html)与[原型导览](可视化原型/README.md)已以 **111 行完整虚构合成周报**、五步导航、同 ID 预编排对照、第四步本地去向树和可跳过的第五步作浏览器内人工 fixture 示意；文件选择器可阅读全文读取本地 UTF-8 TXT／MD／CSV（≤200 KB），但非匹配样本不会触发通用事实／经验抽取，匹配指纹也不证明授权或实时解析。第四步没有规范 Git 文件预览或独立 Tool 请求节点；这些属于拟议门禁与后续能力，浏览器内状态不能真实核来源/指标、调用 Tool、试跑 Skill、批准业务事实或写入／发布资产。现有原型用虚构数据和浏览器内状态示意复盘、手工交接、业务对象与工作记录内页、团队资产三 tab 与资产内只读详情，以及修订方向；资产数字和资产进展固定预置，发布操作仅在知识创作会话模拟。资产数字只在「最新进展」示意，全局概览默认同时展示项目 A/B/C 与产品线 P/Q/R 的业务关系和按版本去重的经验 / Skill 落点，选中对象后仍保留全队上下文；B/C、Q/R 和多数关系只是待核占位，不是业务事实或能力覆盖率；「智能诊断」以三条固定虚构巡检候选示意主动发现冲突、进展复核及限定业务流衔接问题，尚未接入真实自动扫描或授权数据。历史文档只有在核实逐文档映射及访问资格后才应跳转 WeKnora 对应文档；原型没有真实深链，不展示 Wiki 虚构正文或可点击的知识库首页入口。它不是真实 DSH/资料库/PG 集成；正文与逐页设计以团队成员的实际任务、贡献目的和本团队资产边界为准，原型不替换正式权限与发布门禁。

文中组织工作方式的分析是**设计推断**，采购、交接等情境是**示意案例**，不是选定的试点；未来的使用效果和跨领域复用能力都**待验证**。这四篇说明产品意图，不代表功能已上线，也不修改正式审核、发布、权限和验收规则。工程责任与门禁仍看[方案总览](../方案/00-方案总览与关键决策.md)、[治理](../方案/04-角色、治理与运营机制.md)、[工作台规格](../方案/09-工作台信息架构与核心对象.md)、[实施验收](../方案/08-MVP实施、验证与验收.md)和[验证材料](../验证/README.md)；发现产品意图与现行方案冲突时，明确提出决策，不以本目录暗改规则。
