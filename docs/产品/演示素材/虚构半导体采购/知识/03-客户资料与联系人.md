## 数据使用与更新规则（供验收设计）

只按业务必需开放字段：需求协调核对日期时无需看到邮箱；客户协调草拟 [K08](./08-客户回信草稿.md)时仍需后端核验发件身份、收件对象与所属项目。联系人变化由有权角色取得可回溯来源后更新版本，不允许从新闻网页抓取“联系人”直接覆盖。导出或批量查询必须有单独授权与最小化日志；发信工具即使技术可用也必须有二次确认与发送回执。本演示目录没有真实技术限制，需在测试部署检验。

**验收反例**：以模拟非 PX-A 项目成员读取 K03 应在资源侧被拒，随后不应通过 K14 周报、Skill 输出或 trace 找回邮箱；同一用户获授权只看项目摘要也不得导出通讯录。该结果需要实际权限测试，不是本文件的运行结果。

### 资料边界：一行代表什么

- 澄星终端、瀚岳设备和岚桥科技是三个互不合并的虚构客户，不是可推断的真实企业别名。
- PX-A、PX-B、PX-C 是演练项目键，不能当客户主数据 ID 或真实系统授权凭证。
- 每一行只记录“虚构项目—虚构联系人—演练角色—示例邮箱—沟通范围”的模拟对应关系。
- “需求接口”说明在演练中谁可以提出需求，不能推出许遥有签约、变更订单或同意交期的权限。
- “项目联络”不能推出陈禾能确认 PX-B 订单、付款或发运地址。
- “技术联络”不能推出贺鸣能把 PX-C 预测量变成采购订单。
- 表内没有电话、住址、真实公司编号、客户账户、抄送名单或签章，不得推断补齐。
- 客户名称和姓名虽属合成值，在演练中仍按受限字段处理，避免测试流程养成全员暴露习惯。
- `.example` 地址仅供识别样本关系，不得作为实际发送目标或“已验证邮箱”。
- 空缺的授权证据不是否定某人现实权限的证据；它只意味着本演练不能据此做该动作。
- 项目归属不能从姓名、邮箱域或新闻标题反向猜测；以受控台账的项目键为准。
- 不跨项目复用联系人映射，即使未来两条模拟记录同名也必须分别核对来源。

### 字段级证据账：客户与项目

- `客户名称` 的来源为本表合成演练行；它只标识假设业务对象，不证明工商身份。
- `项目键` 的来源为本表和 [K02 项目清单](./02-客户项目清单.md) 的模拟对应；不把一个键扩展成组织范围权限。
- `客户—项目关联` 允许回答“这条演练记录属于哪个项目”，不允许回答“谁可查全部客户”。
- 表头“虚构客户/项目”是两个不同概念拼列，未来结构化存储时应拆成字段。
- 项目键与客户名同时存在时，以相同记录版本中的映射校验；冲突时停止对外动作并待人工核对。
- [K09 新闻线索](./09-行业新闻链接线索.md)即使出现相似名称，也不是客户台账更新来源。
- [K14 周报](./14-采购周报与升级清单.md)的项目提及不能增补联系人字段。
- K02 可供项目概况核对，但“知道项目存在”不等于获得这张受限联系人表的读权。
- 面向需求角色的结果可以保留授权范围内的项目键，不必暴露客户名称和联系人映射。
- 跨项目汇总只有在聚合授权明确时才可能出现；项目级读取不可自然升级为全量台账导出。

### 字段级证据账：人、角色与渠道

- `联系人姓名` 只来自本表合成行；不作真实人身份断言。
- `演练角色` 是沟通定位描述，不是法律授权、采购签署权或发送授权。
- `示例邮箱` 为受限通信标识符；其语法看似邮箱，仍不得连接实际发信服务。
- `沟通范围` 限制如何解释该行，不授予内部人员查看或导出能力。
- PX-A 的许遥出现在 [K07 原文](./07-客户需求变更邮件.md) 的 From 行，交叉一致仅帮助追踪样本，不鉴别发件人身份。
- PX-A 的许遥出现在 [K08 草稿](./08-客户回信草稿.md) 的拟收件人行，不证明收件地址已经核验。
- PX-B 和 PX-C 在本包未提供对应客户来信；不能为陈禾或贺鸣生成对话记录。
- 内部吴衡为 K07 的合成收件角色及 K08 的拟发件角色，不能追加为第四条客户联系人。
- 未来真有联系人调整时，应由有权主体提交有来源的变更版本；本文件不记录该事件。
- “找到了邮箱”与“允许向该对象发送该内容”是两个独立判定，后一项还需要发信审批和渠道控制。
- 邮箱不能从域名反推组织真实性，也不能因域相同而扩展到其他人。
- 联系人姓名不能作为唯一键；版本、项目与来源上下文均须保留。

### 来源、状态与派生关系

- K03 是演示台账的合成源，不是 CRM 导出或真实客户提供的通讯录。
- K07 是客户请求样本，其发件字段可用于样本对照，不是修改 K03 的自动指令。
- K08 是内部未发草稿，拟收件字段只表现编写意图，不是通信发生证据。
- K10 是需求与订单版本的安全核对入口；它不能反向赋予 K03 或 K07 原文的访问权。
- 由 K03 派生的任何视图应带来源 ID、源版本及视图版本，以免脱离上下文被再利用。
- 来源版本与视图版本不同：前者定位原记录，后者定位一次特定字段过滤及授权规则。
- “去标识”不等于数据可公开；项目、日期和精确数量组合仍可能需要项目范围限制。
- 假设视图引用 K03，也不应把受限邮件正文一并嵌入视图。
- 只看到 K10 的变更摘要，不能倒推出存在一个可直接打开的 K07 附件链接。
- 将视图缓存给某个主体后，主体角色或项目范围撤销必须使缓存失效，不能继续离线分发。
- 来源撤回或被判有误时，依赖它的联系人视图需要标为待核并停止新用。
- 原件保留依照未来测试空间的规则；本文不设定已实施的留存期限。

### 拟议的资源侧授权顺序（尚不存在）

- 先确认请求主体的模拟身份，再核对其客户协调或负责人角色，避免匿名请求直接触及受限索引。
- 接着核对主体获准的项目集合，不能仅凭用户在问题中写“PX-A”推断项目权限。
- 再核对读取目的：核对联系人、拟写回复或追溯变更，不以泛泛“搜索相关内容”替代目的。
- 再核对动作：单条查阅、字段视图、批量查询、导出和发信是不同动作。
- 资源端应在检索前缩小可查文档和字段，不把 K03 全文传给无权模型再要求模型拒答。
- 对于按权访问全文的模拟客户协调/负责人，仍需项目匹配；角色名称不代表无限项目范围。
- 无权请求应在索引查询、向量召回和工具返回之前被拒，避免片段或相似度泄漏。
- 拒绝响应应不泄露“某姓名是否存在”或邮箱前缀，且保留最少量审计信息。
- 安全视图是资源端从已授权字段生成的另一个对象；不能让模型靠提示词删除原件字段充当视图。
- 本目录只有静态 Markdown，没有上述索引分区、身份服务、授权器或已发布的安全视图。
- 假设隔离测试空间准备就绪，才可用不同模拟主体测这些预期，不得把文档措辞当通过回执。
- 任何 Tool、Skill 或 trace 输出应沿用源限制，不能用换一条调用路径绕开资源端。

### 需求角色可见的字段最小化提案

- 假设为 PX-A 需求核对生成视图，字段可含 `project=PX-A`，不含姓名、邮箱及原文正文。
- 假设视图任务为核对请求窗口，可包含 `requested_quantity=800`，不可标成已确认供货量。
- 假设视图记录 `previous_window=2026-11-20` 和 `requested_window=2026-11-13`，日期来自获准请求摘要。
- 假设视图标记 `status=客户请求/待双方确认`，不写“订单生效”。
- 假设视图附来源视图 ID 和生成时间，不能附可直达 K07 的未授权全文链接。
- 假设只核对 PX-B 项目概况，不需要陈禾姓名或邮箱；本表不能擅自添加 PX-B 沟通事实。
- 假设只核对 PX-C 预测 200 件，完全不需要贺鸣的联系地址。
- 对外呼叫或发信所需收件信息不能走需求角色的视图补取，应回到授权客户协调流程。
- 安全视图如果包含姓名首字或邮箱脱敏前缀，仍可能构成不必要识别；优先完全省略。
- 视图字段的缺省应显式表达“按权未提供”，不要让使用者误判为客户没有联系人。
- 再加工摘要继承视图使用范围，不因文字短就自动放宽共享。
- 以上仅为字段规格提案，本包没有物化文件、API 返回或获准主体的执行记录。

### 反向推断与拼接边界

- 用项目键在 K02 找到客户，不代表可以拼出 K03 联系人；K02 与 K03 的限制分别判定。
- 用 K07 的署名与本表匹配可用于有权人的证据追踪，不能据此对需求角色披露署名。
- 用 K08 拟收件人推断客户“已收到确认邮件”属于从草稿制造通信事实。
- 用 `.example` 域名构造另一条邮箱属于无来源新增联系人资料。
- 用新闻页面类似姓名猜测哪一行过期，不能覆盖这三条原始合成行。
- 以“我已经知道姓名”为由索要邮箱，仍应独立判定字段读取权。
- 以“只要数量不要姓名”为由先召回原文再截取数字，仍属于不合格的全文先检索路径。
- 把被拒邮箱藏进引用标题、trace、日志、错误文本或导出列，仍是披露。
- 对一个项目有权不意味着可做三项目横向联系人搜索。
- 以客服身份模拟问答也不产生资源授权；提示词自报角色不可代替认证。

### 修改与更正时的版本纪律

- 编辑本表不能暗中修改 K07 原文的 From 行；来源不一致须保持两种证据并待核。
- 更正项目关联须记录更正依据、影响范围和版本；旧引用不能悄然指向新行。
- 更正邮箱须重新核验候选沟通渠道，即使示例域也不能作为可投递地址尝试。
- 删除某字段后的安全视图应重建或作废，不能让旧缓存继续携带该字段。
- 撤销查阅授权不等于删除审计记录；审计信息应最小化而非复制完整邮箱或邮件正文。
- 导出文件若曾获得模拟批准，审批也应绑定精确字段、项目和有效期；更改其一须重审。
- 对下游 K08 的拟收件人变更应触发草稿收件人核对，不能将旧批准直接沿用。
- 若 K07 被标为来源存疑，台账行仍只是演练联系方式，不能把 800 件请求当确认订单。
- 更新者的权限和更新内容应分别核验；能提出更正不等于能批准新联系方式。
- 当前三个联系人行保持原样；此节不宣布发生任何新增、更正或删除。

### 读取结果应如何作答

- 有权客户协调被问“PX-A 谁提出请求”时，可分别引用 K03 演练接口和 K07 的合成署名，标明来源与限制。
- 仅有项目摘要权的需求协调被问同题，应答自己只能依据按权视图核对数量、日期与状态，不能读取姓名。
- 被问“许遥是否签了合同”时，正确界限是本表不提供签署授权或合同证据。
- 被问“陈禾的最新邮箱”时，表内只有合成示例地址，不能承诺其真实或最新。
- 被问“贺鸣是否下了 200 件订单”时，PX-C 仍为预测；联系角色不能补足订单证据。
- 被问“谁可以给客户发 K08”时，应转向草稿审批和发信身份核验，不从联系人表推断内部授权。
- 被问“能否先把全部原件塞进模型再过滤”时，应明确否定，资源侧必须先限制检索与返回。
- 被问“脱敏摘要在哪下载”时，应说明本包尚未提供摘要资产或服务，不能给出虚构链接。
- 被问“测试是否已通过”时，应说明本节仅设计验收，不存在执行证据。

- PX-A 行的客户键是澄星终端；若输出把许遥归给瀚岳设备，即为跨行混淆。
- PX-A 行的演练角色是需求接口；输出“合同签署人”即为越过来源含义。
- PX-A 行邮箱后缀为 `.example`；页面不可呈现“点击即可投递”的操作暗示。
- PX-B 行仅表示项目联络；不能用 300 件项目申请反推陈禾已提出变更邮件。
- PX-B 行的邮箱也只在授权的联系人核对动作中可能显示，不能进入需求汇总。
- PX-C 行与概念验证相关；贺鸣的技术角色不能为预测 200 件背书为订单。
- PX-C 行不能从 K09 外部线索推断新增地址、手机号或其他联系渠道。
- 三行都没有真实客户唯一身份代码，因此不支持跨真实 CRM 的自动关联。
- 三行都没有有效签章证明，因此不能导出合同权限结论。
- 三行都没有实际沟通历史，因此不能回答“上次谈话说了什么”。

- K08 只标一个未发送的拟收件对象；不能当作联系人活跃度或送达率证据。

### 数据流中的撤销点（未来设计，未部署）

- 查询授权撤销后，新搜索应立即拒绝 K03 全文，不能等模型生成答案时再判断。
- 项目授权撤销后，旧项目视图 ID 应失效，不能因链接已知而继续打开。

- 来源字段被更正后，旧版本仍可受控追溯，公开视图则应按变更策略更新或下线。

- 已离线导出的文件无法用一次模型拒答收回，审批和副本管理必须前置。
