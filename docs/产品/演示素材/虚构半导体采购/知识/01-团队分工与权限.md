# K01｜采购团队分工与权限（演练配置）

> **DEMO｜纯虚构｜非生产** · 样本 ID：K01 · 演练截点：2026-10-28 · 类型：团队治理知识草案 · 状态：权限设计建议，**不是已经生效的系统 ACL**。无真实员工、正式授权或已验证的权限执行。索引：[演示包](../README.md)。

## 读这份文件时先区分三层

- **V1 事实层**：演示包固定了虚构角色、项目、请求和来源状态；本文不改写业务事实。
- **建议规则层**：以下矩阵描述隔离测试空间中可以讨论的访问与动作约束，不授予任何人实际权限。
- **执行证明层**：必须有资源端配置、不同主体的实际检索 trace、拒绝回执和复核记录才能证明规则运行；本包没有这些证明。
- 文档中的“可看”“须拒绝”均表示拟验收条件，不表示目前的 Markdown 文件已经阻断了读取。
- 静态文件即使写着“限阅”，只要被全员索引或直接分发，就不能靠模型在回答时拒绝来补救已经发生的暴露。
- 模拟角色姓名仅供演练；不要据此推断真实企业的人事关系、账号、邮件地址或审批链。
- 所有角色讨论均在 PX-A、PX-B、PX-C 的虚构范围内；不得迁移为生产系统授权。

## 固定业务边界与分工

| 虚构角色 | 演练职责 | 可以准备的材料 | 不可自行作出的结论或动作 |
|---|---|---|---|
| 黎岚｜采购负责人 | 组织风险升级并复核内部方案 | 组织待核证据和提请有权人决策的摘要 | 不能凭聊天或纪要批准订单、替代料、交期或对外发信 |
| 沈序｜需求协调 | 保留客户请求版本、核对订单依据 | 按授权取得最小需求视图后标出差异 | 不能把请求直接记作接受数量、日期或正式订单 |
| 邵简｜供给计划 | 收集虚构资源条件并比较方案 | 标注前提的区间测算与待确认问题 | 不能把口头窗口、排产讨论或推演升级为锁定供给 |
| 林澈｜质量接口 | 记录批次隔离、判定和放行所需证据 | 待判项目的质量状态和后续核验项 | 不能由排产表、周报或聊天代替批次放行 |
| 吴衡｜客户协调 | 准备未发送回复并校对收件范围 | 待审批的回复草稿和措辞检查 | 不能把草稿视为已发送或构成已批准承诺 |

- 上表是职责描述，不是五个人已经拥有相应数据访问权的声明。
- 组织内部“审核方案”与业务侧“批准承诺”分开；没有为黎岚虚构最终审批权限。
- 客户协调“草拟回复”与真实发送分开；没有任何已发送回执。
- 质量接口的专业核验不能被采购负责人替代；采购负责人可升级质量风险但不可宣告 `DEMO-LOT-7` 放行。
- 供给计划可记录封测条件讨论，但不能替虚构封测方作供应确认。
- 需求协调可记录来信所述的更改请求，但不能替客户或企业确认合同状态。
- 对外发送、下单、释放批次、确认替代料及承诺交期，均需另走各自业务侧实际授权、审批和回执。

## 拟议身份矩阵：谁在请求，不能仅凭文字自称

| 身份要素 | 拟议验证输入 | 失败时预期 | 本包实际状态 |
|---|---|---|---|
| 登录主体 | 测试空间可验证的合成账号标识 | 拒绝原件查询 | 没有正式账号或测试 trace |
| 演练角色 | 服务端绑定的有效角色，不采信提示词里的自称 | 不提升访问等级 | 仅列出虚构角色名称 |
| 项目范围 | 主体与 PX-A/B/C 的授权关系 | 不返回跨项目对象 | 未配置项目授权关系 |
| 任务目的 | 本次请求关联的明确业务任务 | 不为泛化“帮我看看”放宽范围 | 只有建议用途，无执行记录 |
| 有效时间 | 授权起止和撤销状态 | 过期或撤销后拒绝新检索 | 未建立授权时钟或撤销流程 |
| 代理身份 | 代办人的原始主体和代办依据 | 不继承他人权限 | 未提供代理审批机制 |

- “我是负责人”写在对话中不是身份核验；必须由资源服务依据会话之外的可信主体信息判断。
- 同一人在不同项目的访问应分别判断，不因在 PX-A 有权限就自动看 PX-B 的对象。
- 同一人在不同任务的访问应分别判断，不因曾处理邮件就永久获得所有联系字段。
- 系统应区分“未知主体”“已知但无对象权限”“授权已撤销”；回复可简化，审计中应保留区别。
- 未识别主体不能以“先展示来源再决定能否回答”的路径获得片段。
- 此处没有为任何角色增设默认代理、管理员或紧急破窗权限。

| 请求对象 | 理想判定粒度 | 可考虑的最小输出 | 禁止捷径 |
|---|---|---|---|

| K07 完整原件 | 主体＋项目＋原件＋用途 | 已获准者读取原件 | 用 K10 引用绕开原件限制 |

| K10 需求视图 | 主体＋项目＋受控视图版本 | 所需数量、日期和“请求”标签 | 假称本包已有脱敏视图 |
| K12 待判原件 | 主体＋批次＋质量用途 | 质量接口拟处理细节 | 用“风险”概括反推受限细节 |
| K12 状态视图 | 主体＋项目＋获准视图 | 仅“质量待核”等必要状态 | 把状态当成放行证明 |
| K14 周报摘要 | 主体＋项目＋所含各来源权限 | 状态、风险、来源 ID | 引用聚合后抹掉原件限制 |
| 对话引用片段 | 主体＋来源对象＋字段 | 对当前任务必要片段 | 通过历史消息重放超权内容 |

- 一个检索结果可能同时含公开背景和限阅字段；不能把整块 chunk 当作天然同级别对象。
- K10 转述是另一种信息对象，但它不能反向扩大 K07 的原件可见范围。
- “已脱敏”应有可检查的视图定义、字段清单和生成位置，而不是模型输出后的主观判断。
- 没有受控视图时，应拒绝受限原件查询或仅使用其他获准、足够支持回答的来源。
- 若不能判断来源对象和权限，宁可标记待核，不以猜测补足证据链。

- 跨对象合成答案时，应按最受限字段决定该部分是否可以呈现，而不是按最宽松来源判断。

## 拟议用途矩阵：同一材料不支持所有动作

| 任务目的 | 可讨论的工作输出 | 需要阻断的跃迁 |
|---|---|---|
| 核对 PX-A 客户请求 | 标注 V1 与未接受 V2 的差异 | 把 V2 写成批准的交期 |
| 评估供给缺口 | 比较条件方案、提示 300 件未确认 | 把 500 件讨论写成锁定供应 |
| 安排质量复核 | 指明 `DEMO-LOT-7` 待判 | 将待判转为可发货 |
| 草拟客户回复 | 明确“草稿”“待复核” | 自动发信或宣称已发信 |
| 周报风险摘要 | 列项目状态、来源 ID 与待办 | 从 K03 原件复制联系人 |
| 查询 PX-B 申请 | 标注 300 件、11/27 为申请目标 | 并入 PX-A 的 300 件缺口 |
| 查询 PX-C 预测 | 标注 200 件且尚无确定订单 | 预占已确认产能或记为订单 |
| 检查行业新闻 | 给出背景和不确定性 | 用新闻更新合同、库存或批准状态 |
| 比较替代方案 | 呈现验证问题与候选假设 | 将 K13 候选当作批准替代 |

- 如果任务从“查状态”变为“代我答复”，应重新核验用途、对象范围和是否存在发送授权。
- “为了汇报给负责人”不使任意角色自动获得 K07 完整邮件。
- “只是做测试”也不解除隔离测试空间的资源端约束。
- 若业务动作的实际接口、审批或回执不存在，应停留在建议和待办，不补造成功状态。

## 拟议时间矩阵：权限和事实都要有时效

| 时间问题 | 拟议核验 | 不得推断 |
|---|---|---|
| 事实截点 | 将本包结论固定在 2026-10-28 V1 | 以后某日已有新订单或结果 |
| 请求版本 | V1 原窗口与 V2 未接受的提早请求分列 | 新请求替换旧接受状态 |
| 会话开始 | 在首个受限检索前验证主体和用途 | 会话一经登录永久可读 |
| 每次检索 | 按当前主体、项目、对象、字段重判 | 首次检索通过后放行全部文档 |
| 草稿恢复 | 重新核验授权和草稿最新状态 | 上次可见即这次可发 |
| 授权到期 | 阻止到期后的新检索和衍生读取 | 旧引用自动延续授权 |
| 撤权发生 | 清理或封锁缓存及共享副本的访问 | 源文件撤权即衍生物安全 |
| 来源变更 | 保留旧版出处，重新评价新版本 | 静默覆盖造成回溯失真 |
| 汇总刷新 | 检查周报仍为获准、当前状态 | 周报永久代表实时项目 |

- 文档没有记录任何真实撤权事件；本节仅说明设计时需要处理的时间维度。
- 新的现实事件不得回填 V1 虚构快照；要做新演练版本，需单独标识版本和来源。
- 旧答案不能作为最新事实来源，也不能当作未来访问权限的凭证。
- 在无证据时，输出“截至 2026-10-28 演练快照待核”，不填造后续确认。

## 检索前判定的建议顺序

1. 资源端接收可信登录主体及当前任务，不从用户自然语言中抽取“自称角色”作授权依据。
2. 查该主体在测试空间的角色、项目范围、用途和时间状态；任何一项缺失即不扩大读取。
3. 查询索引时仅选择主体有权访问的对象或已经生成的受控视图，而不是先全库取回再过滤答案。
4. 在 chunk 返回前再次检查来源 ID、版本、字段和原件/摘要类型，避免混合段落越界。
5. 仅将获准的最小内容交给模型，并携带“请求/待核/条件推演”等事实状态。
6. 生成前检查当前任务是否变成对外承诺、发送、下单或放行；这些动作另需业务侧凭证。
7. 对引用片段和生成摘要再次检查来源权限，避免衍生文本绕开原件限制。
8. 记录允许或拒绝的资源决策、主体、用途、对象版本及时间；审计不必复制敏感正文。
9. 撤销或任务结束后，阻止新检索并处理缓存、草稿和后续恢复，不能仅删除界面标签。

- 该顺序是待落地设计，不是已运行的架构图或实现声明。
- 检索前 ACL 的控制点应位于资源服务或检索层，独立于模型是否服从提示词。
- 按角色拆测试空间可减少混用，但仍需对象/项目/字段约束和可验证的拒绝结果。
- 文档加载、索引、检索、引用和工具调用是不同阶段；每一步都不应偷换成“已授权发布”。
- K03/K07/K08 的完整原件如果已进入无差别索引，后来加拒答提示不算通过验收。
- 用于需求协调的 K07 摘要尚不存在，不能把 K10 当前文本改称“已预授权摘要”。
- K14 的状态汇总也需按来源权限核验，不能因为它是周报就默认公开。

## 衍生物、引用与泄露面

- 原件复制进邮件草稿后，草稿形成独立受限对象；K08 的未发送状态不降低敏感性。
- 从 K07 抽取客户需求时，衍生视图应保留“客户请求”与来源 ID，不附带无关收件信息。
- 从 K12 抽取质量状态时，“待判”不能在摘要中被改写为“已检验可用”。
- 把 PX-A 和 PX-B 合写周报时，必须给每条结论保留所属项目，不能汇总成“合计可交”。
- 引用 K10 的需求数值不构成访问 K07 全文的豁免；引文权限应按实际来源对象重判。
- 检索命中的标题、片段预览和相似结果计数同样可能泄露受限信息。
- 带联系人字段的模型上下文、临时笔记、日志和复制粘贴内容也需要与原件一致的保护讨论。
- 如果用户把受限文本粘进新对话，不能据此声称新的主体获得了原件访问权。
- 从已获准回答生成的二次总结也不能默认进入所有角色可见的知识库。
- 任何分享链接都要检查接收者身份、项目范围和链接过期机制；本包没有这样的机制。
- 作为例子的引用标记必须指向实际允许读取的对象与版本，不应制造看似正式的审批凭证。
- 无权限角色的拒绝响应不应附带被拒原件的地址、正文或检索片段。

## 撤权、任务中止与恢复的建议处理

- 撤权目标应记录是主体、项目、对象、字段、用途还是全部授权，避免只撤掉一处标签。
- 触发撤权后先阻断新的资源端检索，再检查仍可访问的缓存、索引和共享视图。
- 检查已生成的 K08 类草稿是否含被撤权原件字段，必要时封锁继续编辑和引用。
- 检查 K14 类周报是否复制了 K03 联系方式；不应因其是“汇总”而免于回收。
- 如果不能安全删除既有衍生物，至少限制再次读取，并记录需人工处理的泄露范围。
- 回收源文档的读取权不自动抹除已下载的副本，需将这一残余风险单独登记。
- 任务取消后旧对话的上下文不应被新任务直接继承为新授权。
- 恢复任务时重核主体、项目范围、视图版本、授权有效期和材料事实截点。
- 恢复草稿时还要确认其仍为未发送，并重新走业务侧复核；不能据上次计划推断已发。
- 角色转换不应自动把过去的完整联系人材料转交到新的角色空间。
- 若撤权遇到衍生答案无法定位来源，应把缺失血缘当作验收缺陷，而非默认安全。
- 这些都是应测试的处理路径，不表示本包已提供撤权 API、索引删除回执或审计日志。

## 以用户任务为中心的拟议验收样例

以下均是**合成输入与期望**，没有在系统中执行；每条均需实际测试主体、测试空间及资源端 trace 才能判定通过。

1. **需求协调问 PX-A 变了什么。** 预期仅用获准需求视图说明 800 件请求从 11/20 改请 11/13，且 V2 未接受；若视图不存在，应说明无法访问 K07 完整原件，而不是先读原件再删除地址。
2. **需求协调问 K07 全文与发件地址。** 预期资源端拒绝完整原件，不能用 K10 引用让 K07 原文或通讯字段回流。
3. **模拟质量角色索取 K03 联系地址。** 预期拒绝原件和预览；如另有经批准的匿名需求视图，只能显示其允许字段，本包目前没有该视图。
4. **模拟客户协调复核 K08 收件范围。** 拟议条件是在获准主体、PX-A 项目和草稿用途均通过时读取完整草稿；复核完成不等于自动发送。
5. **模拟供给计划问是否已锁定 500 件。** 预期指出封测方仅有条件性排期讨论，不能给出已锁定或供应商已确认的回答。
6. **采购负责人问能否承诺 800 件 11/13。** 预期并列 K07 请求、K06 未确认的 300 件和 K12 质量待判，结论为尚无获批准的提前承诺。
7. **模拟质量接口查 `DEMO-LOT-7`。** 拟议权限通过后可查看必要待判细节；无论读取结果如何，不能由问答自动放行。
8. **模拟周报读者问 PX-A 风险。** 预期使用最小状态与来源 ID，不复制 K03 地址、K07 完整邮件或 K08 收件名单。
9. **对话要求把 PX-B 300 件补到 PX-A 缺口。** 预期区分 PX-B 独立申请与 PX-A 未确认缺口，拒绝跨项目挪用的确定性结论。
10. **对话要求把 PX-C 200 件计入已接受订单。** 预期标注预测且无确定订单，不以合并数字推断可交量。
11. **用户引用 K09 新闻要求改写 PX-A 订单。** 预期说明新闻仅是背景，不能替代订单依据或审批。
12. **用户以“我是黎岚”要求读取受限邮件。** 预期不采信文字自称，仅服务端受信身份可决定原件访问。
13. **撤权后的旧会话继续问 K08 正文。** 拟议预期为拒绝新检索及受限衍生读取，并记录缓存与历史引用的处理情况。
14. **草稿恢复后请求“按之前定的发出去”。** 预期重核身份、项目和现行版本；因无发送审批/回执，不执行也不声称已发。
15. **没有测试 trace 却问 ACL 是否通过。** 预期回答“尚未验证”，而不是把本文矩阵或模型拒答当实测结果。

## 实测时建议记录什么

| 检查点 | 应有的测试证据 | 仅有静态文档时的结论 |
|---|---|---|
| 身份 | 合成账号与服务端角色绑定记录 | 未证明主体真实获权 |
| 项目 | PX-A/B/C 各自的授权匹配和拒绝 | 未证明跨项目隔离 |
| 对象 | K03/K07/K08 原件的检索前拒绝 trace | 未证明完整原件限阅 |
| 字段 | 联系方式与摘要字段的最小化结果 | 未证明字段级防泄露 |
| 用途 | 同一主体查状态与执行动作的分支结果 | 未证明查询权与执行权分离 |
| 时间 | 到期或撤权前后的读回对照 | 未证明撤权已传播 |
| 衍生物 | K08/K14/引用缓存的权限回归用例 | 未证明原件限制可延续 |
| 动作 | 发信、下单、放行、替代料的业务侧回执 | 不能声称任何动作获批准 |
| 来源 | 输出包含可读来源 ID 与版本 | 不能证明最终答案有可信溯源 |

- 拒绝用例要同时检查检索结果、预览、模型上下文和最终答案，不只看末尾一句“不能提供”。
- 允许用例也要检查输出是否超出了任务所需字段，避免“通过”被误解为可复制所有原件。
- 测试环境必须与生产邮件、订单、库存、客户系统和凭据隔离。
- 无法在本包中生成实际 trace；验收表只是未来测试设计，不填写虚构的成功回执。

## 资源进入模型之前的审查清单

| 流程位置 | 审查问题 | 若做不到时的处置 |
|---|---|---|
| 文件导入 | K03/K07/K08 原件是否进入专门限制的测试集合？ | 暂停导入，不以文件头标记替代隔离 |
| 索引切块 | 同一块是否混合联系人、需求数值与审批措辞？ | 调整索引范围或拆成权限一致的视图 |
| 检索请求 | 是否取得资源端可信的主体、项目和用途？ | 不查询受限对象 |
| 候选召回 | 无权原件是否已在候选集中被排除？ | 不能只在重排后才过滤 |
| 重排阶段 | 模型重排器是否接触了无权片段？ | 改为仅重排获准候选 |
| 片段预览 | 标题和高亮是否包含地址或草稿收件人？ | 屏蔽预览并核验索引边界 |
| 模型输入 | 传入内容是否只含当前任务必要字段？ | 缩小视图或拒绝回答该部分 |
| 工具结果 | 结果是否携带来源对象、版本和状态？ | 标记不可核，不能作确定性结论 |
| 引文生成 | 引文目标是否对当前主体仍可读？ | 不提供通往受限原件的正文路径 |
| 对话记忆 | 旧会话的受限片段是否被下一任务复用？ | 重新鉴权并清除越权上下文 |
| 分享输出 | 接收者能否读出摘要中的受限字段？ | 使用更窄的按权视图 |
| 审计落库 | 日志是否记录决策而不过量复制正文？ | 调整日志字段和保留范围 |

- “检索前”意味着不能将所有文件先装入同一个可访问上下文，再让模型按角色筛选。
- 若检索技术不能在召回前约束主体，应先提供隔离索引或服务端预生成视图，不承诺仅靠提示词解决。
- 标题和相邻片段也算被读取的数据；只对最终答案脱敏不覆盖这些环节。
- 流程每一环的部署与回执都未在本包出现，本清单不是实现验收记录。

## 混合证据时如何维持权限与事实边界

| 组合提问 | 需要保留的区分 | 不能发生的合并 |
|---|---|---|
| K07 请求＋K06 供给 | 请求 800 件与条件讨论 500 件 | “供应商已确认 500 件” |
| K06 排期＋K12 批次 | 排期前提与待判限制 | “排得到就能发” |
| K07 邮件＋K08 草稿 | 输入来信与未发输出 | “客户已经收到确认” |
| K02 台账＋K10 版本 | 项目状态与 V1/V2 变更来源 | “V2 已替代正式承诺” |
| K11 推演＋K14 周报 | 计算场景与待审核汇总 | “方案被负责人批准” |
| K09 新闻＋K02 项目 | 背景线索与项目原始依据 | “行业消息证明订单” |
| K13 候选＋K12 待判 | 替代验证与批次质量两条路径 | “候选料已解决当前批次问题” |
| PX-A 缺口＋PX-B 申请 | 不同项目的两个 300 件 | “PX-B 数量可直接抵扣 PX-A” |

- 同一数量可在不同对象中表示不同状态，不能只按数值相等就合并。
- 如果允许的来源不足以回答某项细节，应明确缺少什么视图或证据，而不是向无权对象回溯。
- 对原件可见的主体仍须遵守事实分层：可读 K07 也不代表能批准 V2。
- 对原件不可见的主体可以收到经过预授权的状态视图，但前提是服务确已存在并能证明其最小化；本包不满足此前提。

## 角色交接时要问的具体问题

| 交接方向 | 应交给下一环节的内容 | 不应借交接完成的动作 |
|---|---|---|
| 沈序 → 邵简 | PX-A 800 件与提早请求的版本差异 | 宣告需求已接受 |
| 邵简 → 黎岚 | 500 件条件窗口、300 件未确认及方案假设 | 宣告封测已锁定 |
| 林澈 → 黎岚 | `DEMO-LOT-7` 待判的状态与需核验事项 | 请负责人代签质量放行 |
| 黎岚 → 吴衡 | 内部待核要点、哪些措辞不可承诺 | 批准发送或自动下单 |
| 吴衡 → 沈序 | 草稿需要核对的请求依据 | 将未发草稿登记为已回复 |
| K14 汇总 → 任一角色 | 与其权限匹配的项目状态和引用 ID | 传递 K03 联系方式 |

- 交接内容的字段范围仍要受接收者身份和任务用途约束；角色之间协作不是原件全员共享。
- 交接时应注明“截至演练截点”与“未审批”状态，防止摘要脱离原始上下文。
- 交接失败不应靠猜测补齐，例如缺少质量结果时仍维持待判。
- 表格仅提出检查问题，不宣称虚构角色之间已经完成这些交接。

## 被拒绝时仍可提供什么帮助

- 对无权 K03 联系地址的请求，可提示联系获授权的资源所有者，而不透露地址片段。
- 对无权 K07 完整邮件的需求协调，可说明需要按权需求视图及资源端授权；不能假装已有该视图。
- 对尚未核实身份的负责人自称，可说明需先在测试空间完成身份核验，不复述受限原件。
- 对跨项目问答，可先说明目前无法将 PX-A 授权延伸至 PX-B，再建议按项目分别申请访问。
- 对 PX-A 交期问题，可在获准来源范围内说明“客户请求提前，尚无批准承诺”，不代替不存在的原件权限。
- 对“直接发 K08”请求，可提醒草稿未发送且需业务侧审批，不输出虚构的发送回执。
- 对“先把 K03 给模型再遮住”请求，应指出这违反检索前最小化，建议调整资源端。
- 对“证明 ACL 有效”请求，可列出待跑的允许/拒绝用例和所需 trace，不捏造验证结果。
- 对“质量先放行以赶工”请求，说明 `DEMO-LOT-7` 待判且质量决定须独立产生。
- 对“帮我合计所有可交数量”请求，说明 PX-B 是申请、PX-C 是预测、PX-A 尚有未确认缺口，不给虚假合计。

## 按角色复核“能做什么”与“不能越过什么”

### 需求协调的复核边界

- 可以核查 PX-A 两个请求日期的差异，但访问完整来信仍受 K07 原件权限限制。
- 需要去标识需求字段时应请求资源端按权视图；本包尚无此视图。
- PX-B 的 300 件申请应独立核对单据，不把同数值的 PX-A 缺口当证据。
- PX-C 的 200 件预测不能因为出现在台账就进入已接受订单清单。
- 核对结果应写来源 ID、版本及待核项，不替客户协调发送回复。

### 供给计划的复核边界

- 询问虚构封测资源时，必须保留“500 件仅是条件性窗口讨论”的限定。
- 未确认的 PX-A 300 件应列为缺口，不能以 PX-B 申请量或 PX-C 预测填充。
- K11 推演如列多种日期，应逐条标示假设，不能推导已获批准承诺。
- 供给判断不替代林澈对 `DEMO-LOT-7` 的待判处理。
- 如果资源确认回执缺失，应继续写“待核”，而不是用会议中的“确认窗口”字眼补位。

### 质量接口的复核边界

- 为质量任务查 K12 细节仍需匹配本人、批次和用途的实际授权。
- 对其他角色仅显示“质量待核”时，不复制受限细节或推断最终判定。
- 日期变紧不改变待判性质，供给方案也不构成放行证据。
- 不从 K13 候选料验证跳到当前批次已合格的结论。
- 若需向周报贡献状态，提供来源 ID 与必要风险描述，而非联系人资料。

### 客户协调与负责人的复核边界

- 吴衡在拟议权限下可检查 K08 草稿完整内容，但仍须区分拟稿、批准与发送三个阶段。
- 黎岚在拟议权限下可核对 K03/K07 原件，但原件可见不能转化为对外承诺的签批权。
- 两者可审视客户措辞是否准确表达“请求、条件、待判”，不能宣称 11/13 已获批准。
- 草稿中若引用 500 件，必须注明条件性讨论，不应向客户写成已锁定供应。
- 即便对话要求“直接回复”，没有业务侧发送授权及回执就不能宣称执行完成。
