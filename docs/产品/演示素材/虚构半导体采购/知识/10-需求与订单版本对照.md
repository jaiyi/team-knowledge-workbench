## 使用范围和事实层级

本表在同一视图对照请求、条件性供给讨论与缺失的订单生效依据，不是订单系统的镜像。
“V1”“V2”是演练中为便于比较而给客户请求线索加的标识，不是合法订单号或已生效的合同版本。
演练基准日 2026-10-28 以前，PX-A 原目标为 800 件、2026-11-20；新邮件仍为 800 件，请求改至 2026-11-13。
新日期属于客户请求字段，不能覆盖原目标的历史记录，也不能填入已接受交期字段。
[K06 专题会](./06-交期异常专题会纪要.md)只讨论附条件的 500 件封测模拟排程，余 300 件未确认。
[K12 质量记录](./12-质量异常与批次隔离.md)中的 `DEMO-LOT-7` 待判，条件性 500 件是否包含该批次未知。
本包没有 PX-A 新窗口获批、正式订单已修改、替代料获批或对外承诺已发送的证据。
PX-B 的 300 件是另一项目的申请；PX-C 的 200 件仍是预测，不能用于修补 PX-A 缺口。
数量单位“件”、项目代号和人物均为合成演练数据，不对应任何真实采购业务。

## 原件权限与摘要来源

[K01 权限演练](./01-团队分工与权限.md)规定，K07 完整客户邮件仅面向模拟客户协调与采购负责人。

K10 引述的 K07 时间、数量与请求窗口是演练包已经允许在对照中呈现的元数据/摘要，不是原件全文。
即使 K10 包含可见字段，也不能根据其链接、文件名或摘要，反向取得 K07 的完整正文、收件人和未授权细节。
未来若要从 K07 生成新的需求视图，资源端须在检索和传给模型**之前**验证用户、角色、项目、对象及目的。
视图应仅交付该角色所需字段，记录所用原件版本与授权决策；不能先全量检索再靠模型删掉敏感字段。
这些是拟议控制要求，不表示仓库 Markdown 已实现 ACL、去标识服务或资源端审计。
若当前使用者无权获取原件，应拒绝原件读取，仅使用真实系统允许的视图；不存在视图时明确“无法核验原文”。
摘要与原件如果以后出现差异，应由有权角色核实并记录更正来源，不让无权角色通过全文比对绕开权限。

## PX-A V1 → V2：逐字段保留差异

“变了什么”与“什么生效”是两组字段，不能由同一个版本号自动回答。
V1 是 10/26 会议引用的原计划；K05 当时只提醒可能有提前请求，尚未收到新请求。
V2 是 K07 在 10/27 16:20 的来信所表达的客户请求；此处仅使用获准对照字段，不复制完整邮件。

| 对照字段 | V1：10/26 原计划 | V2：10/27 请求 | 截点处置 |
|---|---|---|---|
| 项目代号 | PX-A | PX-A | 相同项目；不与 PX-B 混用 |
| 虚构客户 | 澄星终端 | 澄星终端 | 仅演练身份，不映射真实客户 |
| 演练料号 | `DEMO-PART-A`（见 [K02](./02-客户项目清单.md)） | 同一项目语境；不据此新增料号 | 仅是虚构标识 |
| 数量口径 | 原计划 800 件 | 请求数量 800 件 | 数量不变；可交数量未知 |
| 窗口字段 | 2026-11-20 原目标 | 请求改至 2026-11-13 | 变化只在请求窗口，不写已批准窗口 |
| 提出时间 | 10/26 会议引用旧目标 | K07 10/27 16:20 来信 | 不能将来信日期填入旧来源 |
| 信息性质 | 周会记录的计划线索 | 客户新请求 | 二者均非订单系统确认回执 |
| 原件范围 | K05 可按其权限查会议记录 | K07 完整原件受限 | 本表不扩大 K07 权限 |
| 内部接受/拒绝 | K05 没有展示正式承接 | K07 后也未见接受或拒绝回执 | 保持未核，不猜测已拒绝 |
| 正式订单版本 | 没有合法订单号证据 | 没有修改回执 | V1/V2 均非订单版本号 |
| 封测资源 | K05 安排核对 | 后续 K06 仅条件性讨论 | 无“800 已锁”证明 |
| 质量可放行量 | 10/26 判定未出 | K12 10/27 建档待判 | 不能填 500 或 800 |
| 对外回复 | K05 中性回复框架 | K08 后续仍为未发送草稿 | 无已发送承诺 |

在数量相同的情况下，窗口变化仍值得列为请求版本差异；但相同数量不能证明供给连续有效。
在窗口较早的情况下，“客户希望”应继续带着请求状态，而不是写成内部交期更新。
“未见接受证据”不等于“已明确拒绝客户”；拒绝同样需要可归属记录。
若未来获准证据显示旧窗口或新窗口已承接，另立证据项和生效时点，不倒改原邮件所说的话。

## 请求、评估、承接、对外沟通：分开的状态轴

一个客户请求可以被记录和评估，仍未形成可兑现交付义务。
内部讨论资源与质量，也不能替客户接受新窗口或替订单系统修改有效记录。
状态轴应分别存储，不以一个总的“已更新”覆盖其余状态。

| 状态轴 | 当前可支持的值 | 所需下一类证据 | 不应出现的跃迁 |
|---|---|---|---|
| 客户请求 | V2 提出 800 件、11/13 | 原文与适用范围由有权者核对 | 请求 → 已批准 |
| 内部需求核对 | 本表做有限对照 | 有效需求及订单凭证 | 表格存在 → 订单已修改 |
| 封测排程 | 条件性讨论 500 件 | 条件、组成、资源锁定回执 | 讨论 → 已锁资源 |
| 缺口 | PX-A 其余 300 件未确认 | 对应项目的新增供给依据 | 缺口 → PX-B 申请量 |
| 质量 | `DEMO-LOT-7` 隔离待判 | 独立判断和放行回执 | 讨论 → 全量可交 |
| 备选料 | 未获批准 | [K13](./13-备选料验证记录.md)所需验证与认可 | 候选 → 可替代 |
| 内部批准 | 未见获批准的提前交期 | 授权决策及适用范围 | 负责人参加会议 → 已批准 |
| 对客回复 | K08 未发草稿 | 审核与实际发送回执 | 草稿 → 已送达 |
| 订单修改 | 未见修改回执 | 授权业务系统的有效版本与回执 | V2 标签 → 生效订单 |

某一轴将来改变时，只更新有证据的字段和时点；其他轴保留旧状态或未知。
“未见回执”是本包证据范围内的结论，不是对所有现实系统作不存在断言。
有效订单的版本号和业务回执如果未来出现，应通过获准系统核验，不从文件名猜出。

### 升级所需的证据顺序（拟议，未执行）

1. 记录原始请求与时间：有权主体在可见范围内核对 K07，保留 V1 原目标和 V2 新请求。
2. 对照项目、数量、窗口与其他字段：任何含糊或冲突先列待核，不猜测客户授权范围。
3. 取得内部供给条件和质量可用性：分别核对 K06、K12 及必要的有效业务回执。
4. 向相应有权人提交可选择的方案：不以“拟议方案”冒充“审批完成”。
5. 如确实获批准，单独记录批准对象、适用数量/窗口、版本、生效时间和实际系统回执。
6. 对外沟通按相应授权及审核发送；分别保存草稿、审批、发送与客户回应状态。
7. 订单系统若完成修改，再保留旧版、新版、变更依据及系统确认；不能用邮件或本表代替。

以上是演练判断门槛，并非已经执行的审批链；本包没有补造步骤 5–7 的结果。
即便第 3 步只证明部分资源可排，也不能跳到第 5 步批准全部 800 件。

## 数量的四种角色，避免“300”串线

PX-A 的 800 是请求总量，不是可交量。
500 是 K06 在特定前提下可讨论的封测排程量，不是已锁、已放行或已承诺的数量。
PX-A 的另 300 是相对于请求总量的未确认缺口，不是额外新增需求。
PX-B 的 300 是不同客户、不同项目的独立申请，目标为 2026-11-27。
PX-C 的 200 是预测量，不是确定订单，也不是可转配库存。
“800 − 500 = 300”在这里仅说明 K06 如何描述剩余未确认范围，不是供给已确证的算式。
若质量判定影响条件性的 500，实际可放行量可能更低；本包不给出可计算值。

| 数量项 | 所属项目 | 业务语义 | 来源 | 禁止的复用 |
|---|---|---|---|---|
| 800 件 | PX-A | V1 原计划量、V2 请求量 | K05 / K07 可见摘要 | 写作已批准可交量 |
| 500 件 | PX-A | 附条件封测排程讨论 | K06 | 写作锁定量或发运量 |
| 300 件（差额） | PX-A | 剩余未确认范围 | K06 | 写作另一订单或确定库存 |
| 300 件（申请） | PX-B | 独立客户申请 | K05 | 抵消 PX-A 缺口 |
| 200 件 | PX-C | 预测 | K05 / K02 | 写作已承诺订单 |

项目身份、料号、时间与状态都应参与关联；只按数值做连接会得到错误结果。
这张表没有表达三项目间可互换物料，也没有提供调拨批准。

## PX-B、PX-C 独立对照

PX-B 的申请窗口为 2026-11-27，与 PX-A 的 11/13 请求不是同一交易的延期或替代版本。
[K05](./05-采购周例会纪要.md)要求复核 PX-B 的单据和供给，不能将“申请”改成“订单已接受”。
若后续出现 PX-B 的新请求，应在 PX-B 自己的版本链上记录，不能标成 PX-A V3。
PX-B 的 300 与 PX-A 缺口数字相等，只是相等；不存在可转用的原始证明。
PX-C 的 200 件没有确定窗口，项目跟踪和概念验证并不创建生效订单。
若后续客户真的提交 PX-C 正式需求，应另记提出时间、数量、窗口、接受状态及来源。
本包没有该后续事件，也没有可供 PX-A 使用的 PX-C 库存。

| 项目 | 本件能回答 | 待查事项 | 不应归入的状态 |
|---|---|---|---|
| PX-B | 申请 300 件，目标 11/27 | 单据、接受、供给证据 | PX-A 的未确认 300 件 |
| PX-C | 预测 200 件，未有确定窗口 | 是否出现正式请求及承接 | PX-A/PX-B 的有效订单 |

## 版本冲突与负例（均为假设，不是新增业务事实）

下表仅用来测试规则；引号中的错句均不是本包已核实的客户、内部或外部表态。
发现矛盾时，应并列给出来源、时点、字段和性质，而不是按最新文本一键覆盖。

| 假设输入 | 应追问的证据 | 预期处理 |
|---|---|---|
| “V2 比 V1 新，交期自动改为 11/13” | 谁接受、何时生效、有无订单回执 | V2 留在请求轴，原目标保留 |
| “客户发了邮件，所以 800 件都能提前” | 供给 500 的前提、300 的状态、质量判断 | 不能确认可交量 |

## 跨来源冲突的处理卡

时间冲突：先问各文档在陈述发生时点还是整理时点，再判断新信息是否改变同一字段。
[K05 的回顾节](./05-采购周例会纪要.md)是后来的编辑注，不是 10/26 同期确认 11/13。
如果搜索把 K05 回顾节排在 K07 之前，不可按检索排序判断事件先后。
数字冲突：先检查项目、业务角色和数量性质，再判断是否真的互相矛盾。
PX-A 缺口 300 与 PX-B 申请 300 不是两份对 PX-A 资源的冲突证词。
状态冲突：客户希望、内部可讨论、质量待判、批准交付彼此不是同义字段。
后续若出现相反的正式回执，记录其生效范围和时点，不删原请求的历史真实性。
权限冲突：受限原件与可读摘要并存时，采用合法可见范围；不要让可读记录升级成原件权限。

| 看似冲突的两句话 | 是否真冲突 | 处理方式 |
|---|---|---|
| K05：11/20 原目标；K07：11/13 新请求 | 不是，时点及状态不同 | 两栏并列，标记未获接受 |
| K07：请求 800；K06：讨论 500 | 不是，需求量与供给条件不同 | 保留余 300 未确认 |
| K06：可讨论 500；K12：批次待判 | 需核批次组成，不可算可用量 | 状态分开并提示风险 |
| K05：PX-B 申请 300；K06：PX-A 缺口 300 | 不是，不同项目与语义 | 保持项目隔离 |
| K05：PX-C 预测 200；K02：无确定订单 | 一致 | 两者都不升级为订单 |
| K08：准备回复；没有发送回执 | 不冲突 | 未发草稿不证明收悉 |

只有同一项目、同一字段、同一适用期间的来源说法不同，才进入真正冲突核查。
真正冲突时也先保留两条来源及其权限范围，让有权人裁定，不能凭更晚时间或更高文本语气选胜者。

## 假设发生新事件时怎样迁移状态

以下是规则测试中的“若……则……”示例，不陈述本包已发生新事件。
必须先取得独立凭证，然后只改变凭证覆盖的状态轴；旧来源仍按其原始时间保存。

| 假设后来取得 | 可更新的字段 | 仍不能自动更新 |
|---|---|---|
| 有权客户重发清楚的数量与窗口请求 | 客户请求版本及提出时间 | 内部接受、质量放行 |
| 内部书面确认可讨论 500 件的前提 | 排程条件与责任来源 | 已锁资源及全部 800 件 |
| 资源端确认锁定某一具体范围 | 被回执覆盖的资源字段 | 未涵盖的 PX-A 缺口 |
| 质量判定并对指定批次放行 | 判定范围内的质量状态 | 客户订单与对外承诺 |
| 授权人批准某一具体交付方案 | 所批准对象与条件 | 未获批准的其余数量 |
| 订单系统产生有效修改回执 | 回执覆盖的订单版本字段 | 所有旧请求文本的历史时点 |
| 有权人审核 K08 草稿 | 草稿审核状态 | 已发送、对方接受 |
| 邮件系统产生发送回执 | 实际发送状态与收件范围 | 客户签收、订单自动生效 |
| 客户答复接受某条件 | 对应沟通及同意范围 | 缺失的供给、质量批准 |

| PX-C 提出正式请求 | PX-C 请求状态 | 自动接受和锁量 |

这些迁移是设计示例，不能凭本表推算其发生概率、执行者或业务系统编号。
若新的凭证仅覆盖 500 件，不能据此更新另 300 件的状态；若只覆盖窗口，不能推断数量获准。
拒绝一个提前请求也不自动证明原目标已获正式承接；各版本的接受字段仍要逐项核对。

## 交接给复核者的最小摘要

复核者先说明自己可以看到哪些来源及视图，避免带入越权 K07 全文。
交接项一是 PX-A 请求侧：原目标 11/20、客户后提 11/13、数量仍为 800 件。
交接项二是供给侧：仅有附条件讨论 500 件，余 300 件无确认资源记录。
交接项三是质量侧：`DEMO-LOT-7` 隔离待判，且与 500 件的批次对应未知。
交接项四是决策侧：无新交期获批、订单变更、对外发送的回执。
交接项五是项目隔离：PX-B 的 300 件申请、PX-C 的 200 件预测不进入 PX-A 可交量。
交接时对每项附对应来源 ID 与“请求/讨论/待判/未证”的语义，不能只传一个总数。
对尚无授权或无可用视图的字段，交接“需要有权者核验”而不是复制完整原件。
只有在隔离测试空间配置检索前权限并保留 trace 后，才能检验这段交接口径是否真的按角色成立。
目前本件只是静态演练候选，不构成已经验证的权限或工作流结果。

## 按角色验收时的可观察边界（拟议测试）

下列行为须在真正配置权限的隔离测试空间检验，静态文件无法证明拒绝或脱敏已生效。
每次测试记录模拟身份、项目、请求的资源对象、授权决策、实际返回范围及是否出现受限内容。
不以模型最终答对作为唯一通过条件；若在检索阶段已经泄露 K07 全文，答案随后删去也不合格。

| 模拟提问者及任务 | 应获内容范围 | 需观察的阻断点 |
|---|---|---|
| 需求协调核对 PX-A 请求变化 | K10 可见的数量、时间、窗口和请求状态 | 未获准访问 K07 完整邮件 |
| 客户协调复核原邮件 | 按真实资源端授权取得 K07 对应原件 | 不因角色名写在文档中免去权限判断 |
| 采购负责人检查升级依据 | 授权范围内的请求与风险材料 | 不把审阅能力误当成交期审批结果 |

### 对摘要最小化的具体要求

授权摘要仅需说明谁的项目、请求的数量与窗口、提出时点，以及“尚非接受结果”。
若摘要含联系人地址、邮件完整正文或不相关项目文本，应在生成源头缩减，而非在答案后处理。
同一角色也须检查项目范围：获准 PX-A 的任务不自动获准其他客户原件。
不同任务目的可能要求不同最小字段；不能把一次可见性保存成永久通行令牌。
引用摘要时标注其基于 K07 的授权视图，不能伪称亲自阅读了原件全文。
若摘要服务尚不存在，本包只能展示这里已给出的按权元数据，不能临时让检索器全文抽取 K07 来代替。

## 核对清单与后续记录（未执行）

核对每个请求时，保存来源 ID、形成时间、项目、数量、窗口、性质与可见权限。
原目标和新请求分列；不要覆盖旧值而丢失变化前上下文。
