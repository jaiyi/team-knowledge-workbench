# 整体工程开发阶段划分

> 本文是工程实施路线的总览入口。它把 `docs/方案` 中的产品与架构决策转换为可开发、可测试、可部署、可回滚的工程阶段。每个阶段必须以证据和 Go/No-Go 决策推进，不以日历或代码量自动升级。

## 1. 文档目标与基本原则

本项目的工程目标是交付一个面向团队的 Knowledge + Skill 创作发布工作台，而不是重新实现 DeepSeek Harness Runtime。

工程实现遵循以下原则：

1. **先设计、后编码**：状态、边界、数据模型、Provider contract 和验收标准先形成文档，再实现代码。
2. **Knowledge-first、Skill 同期完成 MVP**：Knowledge 是首条发布纵向切片；Skill 只在确需查询时声明获授权的固定 Knowledge ID/version 及零结果、无权、失效的用户核实路径，不强制依赖知识。
3. **先 fake contract、后真实 Provider**：先用脱敏 fixture 和 fake provider 证明业务语义、幂等、失败和安全边界，再接入非生产真实服务；合成输入经真实非生产链读回与静态 fixture 是两种证据。
4. **模块化单体优先**：初期采用 API + Worker + PostgreSQL 控制面的模块化单体，不先拆微服务、Gateway 或 Plugin Runtime。
5. **权威边界不可混淆**：Git protected merge 是 Skill 指定版本正式发布的依据；Knowledge 还需 WeKnora 授权索引和检索读回；Workbench、可选 Registry/分发和 DSH/Harness 各自有独立状态。请求成功、安装成功或 HTTP 200 不等于最终业务成功。
6. **自动化不替代责任**：模型负责梳理和起草，脚本负责确定性门禁，人负责事实、范围、风险、审核和发布。
7. **所有外部结果必须读回**：没有最终 read-back 的索引、注册、安装、装载或交接只能是 pending、unknown、reconciling 或 fallback；Skill 已核验的 canonical Git 发布事实不因后续可选环节失败被改写。

## 2. 原始工程基线（历史快照）

本节记录最初设计时的 Knowledge contract foundation，不是当前仓库能力盘点；P0 子项、安装读回、持久化基础及 Go/No-Go 的最新结论见 [`03-P0当前状态描述.md`](./03-P0当前状态描述.md)，不要据此覆盖或推断状态。原始仓库按现状重建，不自动恢复此前被删除的旧脚手架；当时形成的最小工程基线与 readiness-only 切片包括：

- TypeScript ESM 工程配置；
- `apps/api` 最小 API 入口；
- `/healthz` 健康检查；
- Knowledge contract、状态迁移和结构化 evidence 边界；
- Zod application parsing、strict SemVer、深层 clone/freeze；
- application 层 principal/authorization/verifier 接口骨架；
- contract、unit、integration 测试；
- `npm install`、`npm run typecheck`、`npm run build`、`npm test` 可执行。

该基础切片在当时的结论为 `readiness_only`：只证明本地 contract、schema、状态机和测试行为，不证明真实认证、团队 ACL、Git/WeKnora 外部事实验证、生产发布或 `real_verified`。在真实 principal/provider adapter 完成前，只允许使用脱敏 fixture、fake provider 和隔离的 admin fallback。详见 [`02-Knowledge契约基础切片状态.md`](./02-Knowledge契约基础切片状态.md)。

该历史切片尚未实现数据库、Worker、Console、真实 principal/session authentication、真实 Provider、Workbench product package 的完整产品闭环、User-authored Plugin 和 Knowledge/Skill 业务流程；后续进展只看 03。因此“工程基线可构建”或“contract foundation 测试通过”不等于“产品闭环已完成”。

## 3. 阶段总览

### 阶段 P0：工程边界、能力侦察与最小 Workbench product package 骨架

**目标**：将方案冻结为工程基线，确认外部能力和身份/部署边界，并尽早验证 `team-knowledge-workbench` 是否可以作为 DSH Desktop Workbench product package 安装、启动和卸载。

**主要工作**：

- 试点输入、范围、责任人、风险和 Provider readiness matrix；
- 领域模型、状态机、错误码、事件、权限矩阵和 API/Provider contract 设计；
- API/Worker/adapter/package 的模块化单体目录和 fake provider 契约；
- `team-knowledge-workbench` 最小 package manifest、server/client entry、health endpoint；
- DSH Desktop fresh profile 的 build → package → digest → install → restart → load report → smoke → disable/uninstall/rollback Spike；
- 腾讯云非生产环境的部署可行性确认：Backend、Worker、PostgreSQL、对象存储、WeKnora 测试空间，以及具备制品时的 DSH/Harness 服务端；
- 脱敏 fixture、证据 manifest 和故障注入约定。

**明确不做**：完整 Knowledge/Skill 业务闭环、生产环境、高风险工具、完整 Harness Runtime、TeamAI 自动分发、User-authored Plugin Runtime/Marketplace。

**退出证据**：工程结构可运行；关键 schema/状态/错误有设计和测试；`P0-Workbench-Product-Package-Spike` 安装契约实际通过后，P0 才能形成 `P0 overall_go`；若为 `blocked/fallback_only`，只能按下述 `P0 transition_allowed_with_no_go` 继续隔离开发，不能视为 P0 通过；腾讯云环境和每个 Provider 都有 owner、目标版本、状态、阻塞原因和下一步。

### 阶段 P0-Workbench-Product-Package-Spike：Workbench product package 最小安装验证

这是 P0 内的第一个可视化工程交付，不复用方案文档的 `N0` 编号，专门回答：

> 最小 Workbench package 能不能在固定版本的 DSH Desktop fresh profile 中安装、启动、显示、健康检查、禁用、卸载和回滚？

**链路**：

```text
build → package → digest → fresh profile install
→ Desktop restart → server/client load report
→ UI/health smoke → disable → uninstall → rollback
```

`P0-Workbench-Product-Package-Spike` 的安装对象是用户电脑上的 DSH Desktop Workbench product package，不是腾讯云上的 DSH/Harness 服务端。它只证明 Workbench product package 的宿主安装和启动，不证明 Knowledge 已发布、WeKnora 已索引、SkillHub 已发布或 Harness 已加载 Skill。该 Spike 可以与 P0 的 Provider 侦察和 P1 的 fake contract 开发并行。

### 阶段 P1：控制面与 Knowledge-first 本地纵向切片

**目标**：用脱敏材料演示只读核证、明确获授权的正式创作、Knowledge candidate/确认/fake Git merge/fake WeKnora read-back 与检索；个人 Inbox、独立反馈和 Tool 契约可以并行开发，不由打开入口自动创建 Creation Session。

**真实资产写入前硬门禁**：P1 的 fake 链路可以先行，但在任何真实团队资产、真实 Git 或真实 WeKnora 写入前，必须先通过服务端身份映射与 ACL、两个 asset-space 隔离、路径/secret 负向测试、权限撤销、Worker 重启恢复和 unknown/reconciliation 演练。未通过时只能使用脱敏 fixture 和 fake/admin fallback。`blocked` 或 `fallback_only` 只允许继续隔离的 fake/admin 开发，不能解除真实资产写入、真实发布或 Pilot 的硬阻塞。

**主要工作**：

- 五入口的最小状态与导航契约：「我的工作台」「提炼知识&经验」「打磨可复用的技能」「连接业务数据源」「团队业务资产大盘」；DSH 原生对话不算第六入口；
- 私有 `InboxItem` 保存/回访/导航零抓取、零团队副作用；明确获准提交另产生 `submission_id`，正式创作再按当前来源/空间/动作重鉴权；
- 获准材料的格式/覆盖/锚点/时效及链接受限获取门设计；未经目标验证只留待核定位，不生成可送审正式候选；
- Creation Session、Draft、Draft Revision、Approval、Asset Revision，仅在明确正式创作并重新授权后创建；
- Knowledge path、metadata、sources、CHANGELOG；
- fake Git、fake WeKnora、fake object storage；
- source/version/ACL/read-back；
- 会话生命周期、并发 `base_revision` 冲突和审计；Workbench 评论独立持久化契约，不依赖未经验证的 DSH 回合回复；
- 版本化 Tool/MCP 只读 Demo 契约及大盘合成真实链验收卡；契约或静态 fixture 不冒充非生产真实调用；
- unit、contract、integration、E2E 测试。

**退出证据**：未确认内容不能进入 `published`；没有 read-back 和检索验证不能标记成功；重复事件不产生重复外部副作用；失败会进入 `unknown/reconciling`；证据可反查 actor、session、revision、commit、operation、source 和 ACL。

### 阶段 P2：持久化控制面、异步恢复与双资产隔离

**目标**：把本地纵向切片变成可重启、可恢复、可对账的模块化单体。

**主要工作**：

- PostgreSQL migration/repository/unique constraint/optimistic locking；
- outbox、worker lease、attempt、retry budget、dead-letter、manual retry；
- Provider operation、read-back、unknown/reconciling 和迟到 callback 拒绝；
- principal、team membership、role、asset-space ACL、service identity；
- 两个 asset-space 的数据、任务、发布状态和审计隔离；
- 备份、恢复、日志脱敏和安全回归。

**退出证据**：Worker 重启不丢任务、不重复副作用；跨团队资源访问被拒绝；权限撤销可生效；数据库恢复后可 reconciliation；任意半成功不被伪装成成功。

### 阶段 P3：真实非生产 Knowledge 发布链与最小 Console

**目标**：在不改变领域/application contract 的前提下接入真实非生产 Git 和 WeKnora，并提供最小业务工作台。

**Knowledge 链路**：

```text
用户确认 → Git branch/MR → CI/审核 → protected main merge
→ 验签 merge event → outbox/worker
→ WeKnora ingest → document/version/source/path/ACL read-back
→ retrieval smoke → published
```

**Console 范围**：五入口最小有权导航；个人 Inbox 和独立反馈可在 P1/P2 先行，正式创作才建立 Creation Session。知识入口提供材料覆盖/时效、候选确认、来源定位、评论、提交与失败/unknown/人工对账；资产大盘按资产 ID/版本去重、项目×产品线展示，只有合成材料从入口②经真实非生产审核/Git/Worker/WeKnora/ACL 检索进入入口⑤并读回，才称真实非生产集成。具体文档深链须重鉴权；原件优先跳经验证的 WeKnora 指定来源文档或有权原系统，不能伪造全文阅读。暂不做完整运行后台。

**并行 Tool Demo**：标准目录/详情/schema 与主体/字段/环境授权契约可用 fake 开发；实际验收须隔离非生产获准的只读合成 Tool 被真实调用，结果、来源、失败和审计可读回，不能用静态卡片、申请意向或浏览次数代替。

**退出证据**：真实非生产新增与修订链可重复，合成知识通过入口②的实际审核/Git/Worker/WeKnora 到入口⑤且有负向读回；失败保留获授权且有效的旧版本，失效/撤权旧版先阻断；逐文档 read-back 与检索通过后才标记 `published`，退役/旧索引/外部直连无法负向证明时保持 unknown/安全升级。用户不需要直接操作 Git。

### 阶段 P4：Skill MVP（与 Knowledge-first 汇合）

**目标**：在同一 MVP 周期完成 Workflow → Skill → 静态校验/隔离试跑 → 受审 Git merge → 固定 package/digest → 有期限管理员固定包 fallback 或选用的 Registry 交接。Skill 静态合同与 Runner 准备可与 Knowledge 链并行；固定包、最小消费、版本/digest 归因和回滚须在 P4/N3 一起验收，但 Knowledge 消费/反馈可先行，不等待真实 Registry、TeamAI 或 DSH/Harness Provider。

**主要工作**：

- 一个 Workflow 对应一个主 Skill；
- Workflow Draft、Skill Draft 和结构化追问；
- `SKILL.md`、`skill.yaml`、input/output/effects contract；
- 确需知识查询时才声明获授权的 Knowledge ID/version、用途及零结果/无权/失效的用户核实和停止判断路径；
- golden、boundary、exception、regression、security 静态契约；未经批准 Draft 的可执行试跑必须待隔离非生产 Runner 安全准入和负向测试通过，不能用浏览器演练或普通 Tool 调用代替；
- 指定审核人/CI 通过并核验 canonical protected main merge 后，该固定 Skill 版本才 `已发布`；审核已批准但未合并仍 `审核中`；
- 从固定 merge commit 构建可重复 package；
- 有期限、可审计的管理员固定包 fallback 或按独立 Registry 需求选用的 SkillHub/等价 Registry release/read-back；两者均与 Git 发布、目标安装、DSH load、实际消费分开记。

**退出证据**：Git 审核/合并与包构建状态分列；契约和回归门禁可执行，未通过隔离 Runner 门前不试跑未批准 Draft；package digest 与固定 source commit 一致；禁止 `latest` 和未提交工作区构建；digest mismatch 阻断交接；管理员 fallback、可选 Registry 和真实 Provider 状态清晰分开。

### 阶段 P5：消费、反馈与最小指标闭环

**目标**：Knowledge 已读回版本的消费与独立反馈可在 P3 后先行，不依赖 Skill 或 Creation Session；P4 固定包产出后补验 Skill 消费、digest 归因及反馈。N4 双资产整体验收在这两部分和只读 Tool Demo 均完成后收敛。

**主要工作**：

- 最小 Knowledge query/zero-result/retrieval/citation 与 Skill invocation/attempt 事件；可信开始/查询底账、观测覆盖和版本归因不足时相应总体率为“不可计算”；
- `invocation` 与 `attempt` 分离；
- technical/contract/business 三层状态；
- 独立 Feedback Candidate：报告/受理/分流/关闭不建会话、不改正式资产，明确修订并重鉴权后才关联新会话；
- 可靠性、采用指标和低覆盖率保护；
- unknown、digest mismatch、handoff pending 对账。

**退出证据**：Knowledge 反馈不直接覆盖正式资产且无须先有消费事件/会话；事件按实际有权版本/digest 关联，重试不重复计为调用；无可信底账时总体率不可计算，无业务证据时业务状态为 `unknown`。N4 的 Skill 部分还须固定 Skill version/package digest、最小消费结果、反馈分流和回滚证据。

### 阶段 P6：真实 Provider 交接与非生产 Pilot Beta

**目标**：按选型门分别验证可选 Registry、优先验证的 TeamAI 多端分发（若选用）、TeamLab（如纳入目标路径）和 DSH/Harness 的固定 digest 真实交接；不建设 Harness Runtime。

**按选型结果走相应路径，且逐层读回**：

```text
canonical Git 已审 merge → 固定 commit package/digest
  ├→ 独立 Registry 需求获批：SkillHub/等价 Registry release/version/digest read-back
  └→ 未选 Registry：有期限、审计的管理员固定包 fallback（非 Registry release）
→（如选用多端分发）TeamAI pinned digest/逐目标 installed files read-back（先验证同仓或经审镜像、首次 init、目标 Hook/主动 pull）
→（如纳入目标路径）TeamLab target binding/install read-back
→ DSH discovery/explicit load/profile/loaded digest read-back
→ 低风险任务 smoke → feedback reference
```

TeamAI 未选用时记录选型原因与 `readiness_only/non_blocking`；需要多端分发时优先验证其目标仓库/实际安装/DSH load 契约，不预设自动下发。TeamLab 未纳入本期目标路径时同样非阻塞；纳入后必须固定版本、digest、目标、撤回和回滚。已选 Registry 失败不能由管理员 fallback 冒充真实 release。
每个 Provider 都必须重复：

```text
build → package → digest → fresh-profile install
→ restart → load report/read-back → functional smoke
→ disable/uninstall → rollback
```

**Pilot Beta 前提**：阶段 0 的真实业务场景、真实用户、人工基线、业务结果 Owner、采用指标、至少一个价值指标、恢复和回滚证据齐全。

### 阶段 P7：按需建设 User-authored Plugin、Gateway 与生产能力

只有出现以下触发条件，才进入本阶段：

- 第二个外部系统需要适配；
- 多个 Skill 复用同一工具；
- 需要集中凭据、权限、沙箱或进程隔离；
- 模块化单体已经无法接受地维护安装、健康和运行归因。

可能建设：User-authored Plugin 的创建、代码/manifest/capability/permission contract、测试与受控发布，受控 Plugin runtime、Gateway、低风险 MCP、签名事件、生产部署、多租户增强。高风险生产写入、开放 Marketplace、跨团队 Agent 联邦仍需单独 Go/No-Go。

| 方案阶段 5：Knowledge-first 垂直切片 | P1 → P3 Knowledge 链路 | N2 要求 merge、ingest、逐文档读回及检索后才 published；合成材料沿真实非生产链进入大盘并核撤权/旧索引；链接抓取、材料覆盖和时效各自守门 |
| 方案阶段 6：消费、反馈与三层指标 | P3 后 P5 Knowledge 消费/独立反馈，P4 后补 Skill 部分 | 不需等待 Skill 才受理 Knowledge/无会话反馈；N4 双资产验收在 Skill 固定包最小消费与 Tool Demo 后整体完成；底账不可信则总体率不可计算 |
| 方案阶段 7：Skill 契约、测试与打包 | P4 Skill MVP | N3 要求受审 canonical Git merge 后才已发布；未经批准 Draft 的执行须获隔离 Runner 准入，包/digest、安装或管理员 fallback、最小消费和回滚各留证 |
| 方案阶段 8：选用的 Registry/TeamAI/TeamLab 与 DSH Provider | P6 真实 Provider 交接 | N5；多端分发优先验证 TeamAI，SkillHub 仅有独立 Registry 需求且经选型时纳入；未选用的 Provider 非阻塞，目标安装与 DSH load 分别读回 |
| 方案阶段 9：非生产试点与成熟度决策 | P6/P7 Pilot Beta 与发布候选 | N6；需要真实用户、业务结果 Owner、基线、指标、恢复和 Go/No-Go |
| 方案 N0：工程骨架 | P1 工程骨架 | 不等同于 `P0-Workbench-Product-Package-Spike`，包含 Backend、Worker、Workbench client、配置和健康检查；N0 整体完成还要求 Workbench product package 安装子项通过，Spike blocked 时可继续其他隔离开发，但 N0 保持 `no_go` |
| 方案 N1：控制面与隔离 | P2 | 身份、ACL、outbox、审计、双 asset-space 和 Worker 恢复通过后，才允许真实资产写入 |
| 方案 N2：Knowledge 发布链 | P3 | 真实非生产 Git/WeKnora 检索与撤权/旧索引负向读回；合成知识经入口②至入口⑤的真实链有证据才可通过对应大盘子项 |
| 方案 N3：Skill MVP | P4 | Git 发布与 package/目标安装分列；不得因 Registry/TeamAI/DSH real_verified 延期或删减 Skill 本身 |
| 方案 N4：消费与反馈、Tool Demo | P3/P5 Knowledge 先行，P4 后补 Skill | 独立反馈、最小消费和可信底账/“不可计算”、三层指标、隐私门禁，以及获准只读合成 Tool 的非生产真实调用 |
| 方案 N5：Provider 交接 | P6 | Registry 仅经独立需求选型后接入，TeamAI 多端分发优先验证，TeamLab 按目标路径选用；所有纳入节点固定 digest 并分别读回 release、install 和 load |
| 方案 N6：MVP 发布候选 | P6/P7 | 双资产、ACL、旧版、指标、回滚、证据和责任链齐全 |

`P0-Workbench-Product-Package-Spike` 是 P0 内的早期交付标签，不占用方案 `N0`。它可以与 P1 fake contract、Provider readiness 和云端部署侦察并行。为避免门禁歧义，四个状态独立记录：`P0-Workbench-Product-Package-Spike` 表示本项目产品安装实验结果；`N0 Workbench product package 安装子项` 表示 N0 内的安装/load 验收；`N0 overall` 只有工程骨架和安装子项都通过才可为 `go`；`formal Workbench installation dependency` 表示后续业务阶段是否允许依赖该产品安装契约。Spike 为 `blocked/fallback_only` 时，P1 隔离 fake contract 可以继续，但安装子项、`N0 overall` 和正式安装依赖均保持 `no_go`。User-authored Plugin 的创建、发布和运行不属于这些 P0/N0 状态，需在后续阶段独立验收。

## 5. Provider readiness matrix

| Provider | in_scope 默认值与切换规则 | P0 必须登记 | 最低 read-back | fallback 与回滚 | owner/状态规则 |
|---|---|---|---|---|---|
| Git | `true` | 版本/仓库/受保护 ref/签名方式 | merge commit、changed paths、actor、event id、canonical content | fake/admin 可用于开发；保留旧 commit、撤销 MR/事件并对账 | `pending/blocked/fallback_only/contract_verified/real_verified` |
| WeKnora | `true` | 版本/测试 space/ACL/凭据边界 | document、version、source、repo_path、ACL、retrieval | fake/admin 可用于开发；保留旧索引，停止 published 并重试/对账 | 同上 |
| SkillHub/等价 Registry | 仅独立 Registry 需求成立且经 ADR 选用为 `true`；否则 `not_selected`（选型结果，非 integration status） | 选用理由/目标版本/API/发布审批；未选记录决定 | 选用时 release id、version、immutable digest、状态 | 未选走有期限、审计的管理员固定包 fallback，非 Registry release；已选则固定旧 digest、撤回未确认 release | 仅选用时成为 N5/P6 的真实 release 门禁；Git 发布不受其替代 |
| TeamAI | 多端分发优先验证；经选型纳入目标路径才 `in_scope: true` | 目标 workspace、同仓/经审镜像、首次 init/Hook 或 pull 的版本证据 | 实际目标、installed revision、file list、digest、离线和撤回残留 | 未选时 `readiness_only/non_blocking`；选用后失败保留目标 blocked/回滚旧 pinned digest | 仓库可拉取不等于逐目标安装或 DSH load |
| TeamLab | `false`；纳入本期目标分发路径时改为 `true` | 目标 API/版本/服务身份 | target binding、package/digest、安装/撤回状态 | `false` 时 `readiness_only/non_blocking`；`true` 时管理员 fallback 需固定版本并审计 | `true` 时成为 N5/P6 正式门禁；否则不阻断 |
| DSH/Harness | `true` | 目标制品/commit/profile/工具策略 | discovery、explicit load、profile、loaded digest、权限策略 | fake/admin/contract fallback；清理 profile、回退旧版本并对账 | 同上 |
| Tool/MCP Demo（隔离非生产） | 合同设计先 fake，真实 Demo 验收另有目标授权 | 标准契约、仅测试身份、只读合成目标及字段/环境权限 | 目录/详情、真实受控调用结果、来源、审计与拒绝/失败回执 | 未获准目标时真实调用项 `blocked`；不以 fake/预置卡片替代 | 真实 Demo 是 N4 子项，不推断生产业务数据源授权 |
| 大盘合成知识真实链 | 与 N2 一起验证真实非生产 Git/Worker/WeKnora 测试空间 | 明确合成 fixture、审核/merge/索引目标与空间 | 逐文档 ACL 检索、资产 ID/版本去重、项目×产品线、具体文档有权深链 | 仅预置卡片保持 `fixture`；旧索引/撤权不明保持 unknown/阻断 | 不推断生产内容质量或价值 |

“服务可访问”不能代替最终 read-back。只有 `provider_mode: real`、目标版本/环境固定且最终状态 read-back 完整时，才可标记对应范围 `real_verified`；fake/admin 只能标记 `fallback_only` 或 `contract_verified`。未选 Registry 的 `not_selected` 仅记选型决定。

```text
Git canonical merge（Skill 已发布）→ 固定 package/digest
  ├─ Registry 需求成立并选用 → SkillHub/等价 release/read-back
  └─ 未选用 → 限期管理员固定包 fallback（非 Registry release）
固定 package/digest → TeamAI 逐目标安装读回（仅选用多端分发时）
                    → DSH 指定 profile discovery/load/read-back（独立门禁）
```
## 6. 阶段依赖关系

```text
工程基线 → P0 设计/产品安装 Spike 与 Provider/安全侦察（并行）
  ├→ P1 fake contract：Inbox 私有边界、只读核证、按需正式会话、Knowledge 及 Tool 契约
  │    └→ P2 持久化 Worker、身份/ACL、撤权、双空间和 reconciliation 硬门禁
  │         ├→ P3 真实非生产 Knowledge 发布/修订/撤权/三方对账/合成知识→大盘
  │         │    └→ P5 Knowledge 消费（不等 P4 Skill）
  │         └→ P4 Skill 静态契约/隔离 Runner 可并行；Git 发布/固定包与最小消费在同一 MVP 收敛
  │              └→ P5 补验 Skill 事件/反馈，收敛 N4 双资产验收
  ├→ P1/P5 无会话反馈：独立受理/分流/回访；正式修订时再重鉴权关联创作
  └→ 只读合成 Tool Demo 真实非生产目标 Spike（独立授权/读回，N4 子项）
固定包 + 选型门 + 对应目标准入 → P6 可选 Registry/分发/DSH 逐层验证 → Pilot → P7 按需演进
```

真实团队资产、真实 Git 或真实 WeKnora 写入前，P2 的可信身份/ACL、双资产隔离、权限撤销、Worker restart/recovery、secret/path 负向测试和 reconciliation 必须通过。`blocked`、`fallback_only` 或 `unknown/reconciling` 只能保留在隔离 fake/admin 路径，不能作为 N1/N2、真实发布或 Pilot 的通过依据。P6 可选 Registry/TeamAI 与真实 DSH 不成为 P3/P4 的反向硬依赖；P4 的 Git 发布、固定包/digest、限期 fallback 或获准目标安装、最小消费和回滚仍不可省略。Inbox、反馈和评论在各自受限范围可先行；受限链接获取、未批准 Skill Draft 试跑分别受目标安全与 Runner 准入门禁约束。

## 7. DSH 能力对象必须分开验收

| 对象 | 运行位置 | P0/P1 关系 | 成功意味着什么 | 不意味着什么 |
|---|---|---|---|---|
| DSH Desktop Workbench product package | 用户电脑 | P0-Workbench-Product-Package-Spike 尽早验证，方案 N0 仍是工程骨架 | Workbench product package 可安装、启动、显示和卸载 | 不证明资产发布、WeKnora 索引或 Harness load |
| DSH/Harness 服务端 | 腾讯云非生产环境（若具备部署制品） | P0 侦察，P6 固定 digest 交接 | 服务端可部署、健康检查、profile/discovery/load 能力有证据 | 不证明 Workbench product package 已安装或业务价值已验证 |
| DSH profile | DSH 运行环境 | P0/P6 按契约验证 | 固定 Skill/工具策略/知识 profile 的目标组合可读回 | 不等于 SkillHub release 或一次任务成功 |
| Harness runtime | DSH/Harness 下游 | 本项目不实现 | 运行下游 Session/Run/Tool Call 和业务结果 | 不属于 Workbench 控制面 |

## 8. 所有阶段的统一证据要求

每个阶段都要保存：

- 目标版本、commit、环境和 provider mode；
- fixture/artifact/package digest；
- 实际命令、退出码和结果摘要；
- API/provider read-back；
- 失败、timeout、unknown、reconciliation 和回滚结果；
- `requested_by`、`approved_by`、`released_by`、`executed_by`、复核人；
- evidence manifest 自身 digest；
- Go/No-Go 决策、阻塞项、fallback 到期日和下一步。

`go_with_expiry` 必须同时记录 `fallback_expires_at`、`decision_owner`、`reviewer` 和 `rollback_or_next_action`。到期未复审时，状态自动回到 `pending` 或 `blocked`，不能继续作为当前 Go 依据。

没有这些证据时，只能保持 `pending`、`fallback_only`、`contract_verified` 或 `blocked`，不能标记 `real_verified`、Pilot Beta 或 Stable。

## 10. 明确延期内容

首期不做：

- DeepSeek Harness 的 Workspace/Session/Task/Run/Tool Call/运行时人工 gate/完整 trace；
- 生产写入、不可逆外部发送、高风险 MCP；
- 自动从任意聊天批量生成 Stable Skill；
- TeamAI 多端分发的目标读回优先验证，但未选用的自动分发不作为 Knowledge MVP 硬依赖；
- 无独立 Registry 需求时不建设 SkillHub release 链路；
- User-authored Plugin 的创建、发布、运行时和 Marketplace；
- 通用可视化 DAG、多 Skill 动态规划、Agent 联邦；
- 完整 SaaS 多租户、计费和组织平台；
- 复杂 Console 和市场能力。
