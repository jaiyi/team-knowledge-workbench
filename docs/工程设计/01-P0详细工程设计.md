# P0 详细工程设计：Workbench Product Package 安装与非生产能力侦察

> 本文是 P0 的工程设计与验收基线。P0 的目标不是完成 Knowledge/Skill 业务闭环，而是冻结系统边界、Provider contract、最小 Workbench product package 和非生产部署验证路径，优先确认 `team-knowledge-workbench` 能否在 DSH Desktop 上安装并运行。这里的 Workbench product package 是本项目自身的产品安装包，不是未来用户通过 Workbench 创建的 User-authored Plugin。

## 1. P0 目标

P0 必须回答四个问题：

1. 我们是否有一个可构建、可测试、可打包的 Workbench 工程骨架？
2. 最小 `team-knowledge-workbench` package 是否能在固定版本的 DSH Desktop fresh profile 中安装、重启、加载、显示、禁用、卸载和回滚？
3. Workbench 后端、Worker、PostgreSQL、对象存储、WeKnora 测试空间和 DSH/Harness 服务端是否具备腾讯云非生产部署条件？
4. 后续 Knowledge-first 和 Skill MVP 所需要的领域边界、Provider contract、状态、审计、失败和人工 fallback 是否已经可以编码和验收？

P0 通过后只能说明工程骨架、安装契约和非生产能力侦察通过，不能说明正式 Knowledge 已发布、SkillHub 已 release、DSH 已 loaded 或业务价值已验证。

## 2. P0 范围与非目标

### 2.1 P0 范围

- 工程 monorepo、TypeScript、测试、构建和本地启动基线；
- API、Worker、Provider adapter、domain、validation、audit 的模块边界；
- 核心对象、状态机、错误码、事件、幂等和追踪字段的设计；
- fake Git、fake WeKnora、fake DSH/distribution provider contract；
- 最小 Workbench product package manifest、server entry、client entry、版本和 digest；
- Workbench product package 在 DSH Desktop 中的安装/重启/load report/UI/health/disable/uninstall/rollback Spike（内部节点名为 `P0-Workbench-Product-Package-Spike`，不占用方案文档 `N0`）；
- DSH 官方 Workbench product package 宿主安装契约取证：固定 commit/profile，读取 package、类型、README、fixture、Loader 和安装 E2E，区分 `fact`、`candidate`、`pending_checks`、`warning`；
- 腾讯云非生产部署拓扑、网络、凭据、日志、备份和健康检查设计；
- Provider readiness matrix、证据 manifest、故障注入和 Go/No-Go 模板；
- 本地 artifact verifier 必须同时校验 payload 文件 digest 与包含 package identity/version/source commit/entry points/evidence level 的 manifest metadata digest；manifest 可读但被篡改时必须失败；artifact reader 必须拒绝 symlink 或非 regular payload file。

### 2.2 P0 非目标

- Knowledge 从材料到正式发布的完整业务闭环；
- Workflow 到 Skill 的完整生成、测试、发布和运行；
- DeepSeek Harness 的 Workspace、Session、Task、Run、Step、Tool Call 和 runtime human gate；
- 生产环境和生产凭据；
- 高风险工具、生产写入、不可逆外部发送和高风险 MCP；
- TeamAI 自动分发作为硬依赖；
- User-authored Plugin Registry/Runtime/Marketplace 和通用 Gateway；
- 完整 Console、通用 DAG 编排和复杂多租户平台。

## 3. 工程拓扑

P0 采用模块化单体，不拆微服务：

```text
team-knowledge-workbench
├── apps/
│   ├── api/                  # HTTP/API 或 application facade
│   ├── worker/               # 后续持久化任务消费入口
│   └── console/              # 后续最小业务界面
├── packages/
│   ├── domain/               # 不依赖 Provider 的领域对象和状态机
│   ├── contracts/            # API、Provider、事件和错误契约
│   ├── validation/           # 输入、路径、secret、ACL、schema 门禁
│   ├── audit/                # 脱敏审计与 correlation 链
│   ├── git-provider/         # Git/MR/merge event adapter
│   ├── weknora-adapter/      # Knowledge index/search/read-back adapter
│   ├── dsh-adapter/          # DSH profile/install/load/run contract
│   └── distribution-adapter/ # package/digest/target distribution contract
├── tests/
│   ├── unit/
│   ├── contract/
│   ├── integration/
│   └── e2e/
├── infra/
│   ├── local/
│   ├── ci/
│   └── deployment/
└── docs/
    ├── 方案/
    ├── 验证/
    └── 工程设计/
```

依赖方向必须保持：

```text
apps → application/domain/contracts
adapters → contracts/validation
contracts → domain-neutral serializable types
 domain → 不依赖具体 Provider SDK、HTTP 框架或数据库
```

P0 不引入真实 Provider SDK 作为领域层依赖。真实 Provider 只能通过 adapter 实现 contract。

## 4. 核心对象与追踪字段

P0 只冻结后续实现所需的最小对象，不要求一次性建完全部数据库表。

### 4.1 组织与身份

- `principal`：来自 DSH 认证上下文的已验证主体；
- `team`：团队边界；
- `asset_space`：团队资产域；
- `team_membership`：主体与团队关系；
- `role_binding`：创作、审核、发布、对账等责任；
- `service_identity`：Git bot、WeKnora adapter、publisher、Worker 等技术执行身份；
- `asset_repository`：团队 asset-space 与 canonical Git repository 的服务端绑定。

客户端提交的 `team_id`、`asset_space_id`、owner、approver 或 publisher 只能表达意图，不能替代服务端授权事实。

### 4.2 创作与资产

- `creation_session`：知识或 Skill 的独立创作上下文；
- `draft` / `draft_revision`：会话内候选和修订；
- `approval` / `review_task`：人工确认、审核和待处理事项；
- `asset` / `asset_revision`：正式资产及不可变版本；
- `source_reference`：材料、来源和引用位置的最小引用；
- `knowledge_dependency`：Skill 对已批准 Knowledge ID/version 的固定依赖。

每个 draft revision 至少关联：

```yaml
session_id: cs_<id>
draft_id: <id>
draft_revision_id: <id>
base_asset_id: <optional>
base_revision: <optional>
state_version: <integer>
correlation_id: <id>
```

### 4.3 外部操作与证据

- `operation`：外部 ingest/release/distribution/handoff 操作；
- `job` / `worker_attempt` / `lease`：异步任务、租约和尝试；
- `integration_event` / `merge_event`：外部事件及去重事实；
- `readback`：WeKnora、SkillHub、TeamAI、DSH 的最终状态证据；
- `reconciliation_record`：unknown、迟到、漂移和半成功对账；
- `audit_event`：责任人与技术执行归因；
- `evidence_manifest`：阶段验证本身的不可变证据索引。

每个写操作使用 `idempotency_key`，外部回调必须校验 `expected_state_version`、`operation_id`、`correlation_id` 和资产范围。

## 5. 状态机设计

### 5.1 Creation Session

```text
active → paused → active
   ├→ archived
   ├→ forked
   └→ read_only
```

- `active`：允许会话成员编辑和发起受授权动作；
- `paused`：保留上下文，不启动新的生成或发布动作；
- `archived`：不可编辑，保留审计和恢复依据；
- `forked`：创建新的 `session_id` 和 draft revision；
- `read_only`：可查看证据，不可修改或发起外部写入。

### 5.2 Knowledge 与 Skill

Knowledge：

```text
captured → candidate → reviewing → approved → publishing → published
```

异常或终态：

```text
index_failed | index_unknown | stale | deprecated | rejected | manual_required
```

Skill：

```text
requested → scaffolded → authoring → validating → reviewing → approved → released
released → beta → stable
authorized exception: blocked | rejected | withdrawn | deprecated | retired
```

P0 不实现完整业务转换，但必须为合法/非法转换和错误码写测试设计。

### 5.3 Provider Operation

```text
queued → running → waiting_readback → succeeded
                         ├→ failed
                         ├→ unknown
                         └→ reconciling
```

请求已发送、HTTP 200、任务入队或 Provider 接受请求，都不能直接推进 `succeeded`。`unknown` 必须保留查询、人工对账和回滚路径。

### 5.4 Workbench product package 的安装状态与资产发布状态分开

Workbench product package 的安装状态与资产发布状态分开：

```text
package_built → packaged → install_requested → installed
                                      ├→ failed
                                      └→ unknown → reconciling
```

只有 DSH Desktop 的真实 install/restart/load report 能证明 `installed`；它不能改变 Knowledge、Skill、WeKnora 或 SkillHub 状态。

## 6. Provider contract 设计

P0 先定义接口和可序列化输入输出，不把 HTTP SDK 或 Provider 原始响应泄露给领域层。

### 6.1 Git Provider

最小能力：

- 创建受控 branch/change artifact；
- 读取 change/MR；
- 验证 protected ref；
- 接收并验签 merge event；
- 读取指定 merge commit 的 canonical 内容。

约束：fake provider 不能允许 protected main 直写；真实 merge event 必须包含稳定 repository identity、protected ref、merge commit、changed paths、actor、event id、签名和时间。

### 6.2 WeKnora Provider

最小能力：

- approved Knowledge ingest；
- document/version/source/repo_path/ACL read-back；
- retrieval smoke；
- 旧版本保留、失败和对账。

Fake provider 支持重复 index 幂等、timeout、failed、unknown、ACL mismatch 和 read-back mismatch。

### User-authored Plugin 的后续扩展边界

P0 不实现用户自建业务 Plugin 的创建、代码生成、权限授予、registry、发布或运行时。P0 只为未来的 Plugin asset 预留可扩展边界：

- asset type 与 Creation Session 扩展点；
- manifest、capability、permission 和 dependency contract；
- immutable package/digest；
- distribution target 与安装/加载 read-back；
- disable、uninstall、rollback 和安全审查/审批模型。

未来 User-authored Plugin 必须拥有独立的创建、测试、审核、发布和安装证据。它不得与 `team-knowledge-workbench` 的 Workbench product package 安装状态混用，也不能因为 P0 的宿主安装 Spike 通过而被视为已经可以创建、发布或运行。

### 6.3 Workbench product package 的 DSH Desktop 宿主安装契约

P0-Workbench-Product-Package-Spike 要确认或登记以下字段，未知项不得猜测；方案文档的 `N0` 仍专指工程骨架，不在这里复用：

```yaml
contract_evidence_level: fact | candidate | pending_checks | warning
package_identity: <待确认>
package_version: <待确认>
package_digest: sha256:<hex>
dsh_desktop_version: <待确认>
dsh_commit_or_build: <待确认>
profile: <fresh-profile>
server_entry: <待确认>
client_entry: <待确认>
exports: <待确认>
manifest_fields: <待确认>
ui_registration: <待确认>
load_report: <待确认>
install_method: market | local_bundle | admin_fallback
```

`fact` 只能来自目标 commit 的官方源码、类型、README、fixture 或真实安装读回；`candidate` 只能进入隔离实验；`pending_checks` 必须绑定 owner/date；`warning` 必须有额外测试或人工审批。开发模式热加载、源码 import、社区 Skill 或接口可访问都不能替代正式安装契约。

1. 被 DSH Desktop 识别；
2. 加载 server entry；
3. 加载 client entry 或最小 UI；
4. 显示 Workbench 名称、版本和 digest；
5. 连接最小 Backend `/healthz`；
6. 生成可读 boot/load report；
7. disable、uninstall 和 rollback。

### 6.4 DSH/Harness 服务端 contract

DSH/Harness 服务端是腾讯云非生产环境中的独立验证对象，不等同于本地 DSH Desktop 上的 Workbench product package。P0 只验证目标版本和环境是否具备：

- 服务健康检查；
- profile 读取或创建方式；
- Skill discovery；
- explicit load；
- profile/tool policy read-back；
- loaded digest read-back；
- 受控低风险任务的最小 smoke（若目标制品可用）。

若没有可确认的部署制品、目标版本或 API，只记录 `blocked`/`fallback_only`，不将接口可访问写成已集成。

### 6.5 Provider readiness matrix

P0 必须分别登记以下 Provider；“可访问”不等于“已集成”。TeamAI 和 TeamLab 默认是 `in_scope: false`、`readiness_only/non_blocking`；只有被选入本期目标分发路径并将 `in_scope` 改为 `true` 时，才成为 N5/P6 的实际交接门禁。Git、WeKnora、SkillHub、DSH/Harness 默认属于本期主链路。每行至少包含目标版本/环境、provider mode、integration status、健康检查、最终 read-back、fallback、回滚路径、owner、decision owner、reviewer 和复审日期。下表是能力摘要，完整状态以统一 evidence manifest 为准。

| Provider | 默认 scope | 最低 read-back | P0 允许的 fallback | 真实集成通过条件 |
|---|---|---|---|---|
| Git | `true` | protected ref、merge commit、changed paths、actor、event id、canonical content | fake/admin branch/MR/merge fixture | 目标仓库、签名和 merge commit 可重复验证 |
| WeKnora | `true` | document、version、source、repo_path、ACL、retrieval | fake/admin ingest/read-back | 独立测试 space 中最终索引和检索可读回 |
| SkillHub | `true` | release id、version、immutable digest、状态 | fake/admin release | 目标版本真实 release/read-back 与 package digest 一致 |
| TeamAI | `false`；纳入目标分发路径时改为 `true` | target、installed revision、file list、digest | `false` 时 readiness-only；`true` 时管理员 pinned-digest 操作或 fake | `true` 时只接受固定 digest，目标安装和清理可读回 |
| TeamLab | `false`；纳入目标分发路径时改为 `true` | target binding、package/digest、安装/撤回状态 | `false` 时 readiness-only；`true` 时管理员 fallback | `true` 时目标 API/版本、服务身份和撤回 read-back 已验证 |
| DSH/Harness | `true` | discovery、explicit load、profile/tool policy、loaded digest | fake/admin/contract fallback | 目标制品、profile 和 loaded digest 最终读回完整 |

fake/admin 只能标记 `fallback_only` 或 `contract_verified`，不能标记真实 release、distribution 或 loaded 成功。

## 7. Workbench product package 安装 Spike

### 7.1 本地/桌面 Workbench product package 链路

```text
DSH Desktop
└── team-knowledge-workbench package
    ├── client UI
    └── server entry
          │
          └── Team Knowledge API
                └── GET /healthz
```

P0 可以使用本地 API、fake backend 和内存状态。此时不要求 PostgreSQL、WeKnora 或 SkillHub 已接通。

### 7.2 腾讯云非生产拓扑

```text
腾讯云非生产 VPC
├── Team Knowledge API
├── Team Knowledge Worker
├── PostgreSQL
├── 加密对象存储
├── 日志/监控/告警
├── WeKnora 独立测试 space（若已存在）
└── DSH/Harness 服务端（仅在有明确制品和版本时部署）
```

用户电脑上的 DSH Desktop 不部署到腾讯云。腾讯云只承载服务端组件；Workbench product package 通过宿主安装在用户设备上。

P0 的云端要求：

- 非生产网络和安全组；
- TLS/私网边界；
- Secret Manager 引用；
- 不使用生产 Token、Cookie、密码或业务原文；
- 日志、trace 和错误响应脱敏；
- PostgreSQL 备份/恢复演练入口；
- API/Worker/DB/Provider 健康检查；
- 目标版本、环境、负责人和回滚路径可记录。

## 8. Workbench product package 安装 Spike 实施步骤

### Step 0：冻结验证身份

在开始真实安装前填写：

```yaml
dsh_desktop_version: <固定版本>
dsh_commit_or_build: <固定值>
os: <macOS/Linux/Windows>
node_version: <固定版本>
profile_type: fresh
install_method: local_bundle | market | admin_fallback
backend_mode: local | nonprod
provider_mode: fake | admin | real
```

若无法填写固定版本和 profile，P0-Workbench-Product-Package-Spike 只能保持 `pending` 或 `blocked`。

### Step 1：构建最小 Workbench package

输出：

- server/client bundle；
- manifest/package metadata；
- version；
- package digest；
- 脱敏安装说明；
- health/read-back contract。

### Step 2：安装到 fresh profile

执行：

```text
build → package → digest → create fresh profile → install → restart
```

记录实际命令、退出码、安装前后 package 状态和宿主版本。

### Step 3：读取加载和健康状态

验证：

- server entry；
- client entry；
- UI registration；
- boot/load report；
- `/healthz`；
- package version/digest；
- 无敏感信息泄漏。

### Step 4：故障与清理

至少验证：

- 错误 package 被拒绝；
- server/client load failure 可见；
- backend 不可用显示 degraded/unknown，而不是成功；
- disable；
- uninstall 后残留清理；
- rollback 到旧 package 或空 profile。

### Step 5：形成证据与 Go/No-Go

将结果写入 evidence manifest，并由指定责任人决定：

```text
go | no_go | go_with_expiry
```

`go_with_expiry` 只允许用于已登记 `owner`、`decision_owner`、`reviewer`、`fallback_expires_at` 和 `rollback_or_next_action` 的 fallback；到期未复审自动回到 `pending` 或 `blocked`，不能继续作为 Go 依据。

## 9. P0 验收矩阵

| 编号 | 验收项 | 必须证据 | 阻塞条件 |
|---|---|---|---|
| P0-01 | 工程可安装、typecheck、build、test | 命令、版本、退出码 | 基线命令不可重复执行 |
| P0-02 | package 可构建并计算 digest | artifact 和 digest | 构建不可重复或依赖未提交工作区 |
| P0-03 | DSH 官方 Workbench product package 安装契约取证 | 固定 commit/profile、源码/类型/README/fixture/Loader 证据及 `fact/candidate/pending_checks/warning` 表 | 猜测字段进入正式契约，或没有 owner/date 的 pending 项 |
| P0-04 | fresh profile 安装 | 安装前后状态、安装日志 | 目标版本或 profile 不固定 |
| P0-05 | Desktop 重启后仍加载 | restart/load report | 只能热加载、无法重启验证 |
| P0-06 | server entry 成功 | server load report、health | 只证明文件存在 |
| P0-07 | client/UI 成功 | UI/read-back 或截图/日志 | UI 未注册或安全边界被绕过 |
| P0-08 | package/version/digest 可读回 | manifest、宿主 read-back | digest 缺失或漂移 |
| P0-09 | backend health 可达 | `/healthz` 请求和响应 | 将连接失败显示成成功 |
| P0-10 | disable 可用 | disable read-back | 后台任务无 owner/取消语义 |
| P0-11 | uninstall 清理完整 | 文件/注册表/profile 对比 | 残留可执行内容或配置 |
| P0-12 | rollback 可重复 | 旧版本 digest 和结果 | 只能手工猜测恢复 |
| P0-13 | fake Provider contract | contract/unit/integration tests | fake 与真实边界不清 |
| P0-14 | 真实资产前隔离与恢复硬门禁 | principal/ACL、双 asset-space、撤权、Worker restart/recovery、reconciliation、secret/path 负向测试 | 任一越权、丢任务、重复副作用或伪成功 |
| P0-15 | Provider readiness | Git、WeKnora、SkillHub、TeamAI、TeamLab、DSH/Harness 各自版本、健康、read-back、fallback、回滚和 owner；TeamLab 若非目标路径标记 `readiness_only/non_blocking` | 用“服务可访问”代替最终 read-back |
| P0-16 | 安全边界 | secret/path/ACL/越权负向测试 | 生产凭据、业务原文或越权成功 |
| P0-17 | 腾讯云非生产可行性 | 部署版本、健康检查、网络/备份记录 | 无制品、无 owner 或无法回滚 |
| P0-18 | DSH Desktop 与云端 Harness 分开结论 | 两类证据分别登记 | 用 Desktop 证据冒充云端能力，反之亦然 |

## 9.1 当前实现状态与未完成缺口

本节是截至当前代码仓库状态的 review 结果，不是 P0 通过声明。状态只依据已提交/当前工作树中的代码、测试和实际验证命令；没有外部环境 read-back 的事项保持 `missing` 或 `blocked`。

### 当前必须保持的边界

- 本地 package build、digest、`/healthz`、fake/admin contract 和测试通过，只能证明 `contract_verified` 或 `readiness_only`。
- 没有固定 DSH version/commit/profile 和真实 install/restart/load/read-back，不得标记 P0-03 至 P0-12 为通过。
- fake/admin 不能标记 `real_verified`，服务可访问不能标记 Provider 已集成，安装成功不能标记 Knowledge、SkillHub、Harness 或业务成功。
- P0-14、P0-15、P0-16、P0-17 任一硬门禁未通过时，不允许真实团队资产写入、真实 Provider 发布或 Pilot。
- User-authored Plugin creation/release/runtime 仍不属于 P0；TeamAI 默认 `readiness_only/non_blocking`，不能成为本阶段已完成能力。

## 11. 风险与处理

| 风险 | 处理 |
|---|---|
| DSH package/manifest/exports 未确认 | 先读取固定版本官方契约；保持 `pending/blocked`，不猜字段 |
| 只能开发模式热加载 | 不视为安装成功；必须 fresh profile + restart |
| server/client load 部分成功 | 分开记录；整体进入 `unknown` 或 `reconciling` |
| API health 成功但 Provider 未验证 | 只标记 backend healthy，不标记资产或 Provider 成功 |
| DSH Desktop 可安装但云端 Harness 无制品 | 两条结论分开；云端标记 `blocked`，保留 fake/admin fallback |
| Package digest 漂移 | 阻断后续交接，重新构建并对账 |
| 日志泄露凭据或业务材料 | 立即停止验证、清理证据并修复脱敏；不得提交仓库 |
| 安装失败无法卸载 | P0 No-Go，保留 fresh profile 和回滚记录，不进入业务实现依赖 |

## 12. P0 退出条件

P0 的总体决策必须与 Spike 子项分开记录：`P0 overall_go` 仅在 Workbench product package 安装、重启、load/read-back 等硬门禁通过后成立；`blocked/fallback_only` 只能记录为 `P0 transition_allowed_with_no_go`，允许隔离的 fake/admin contract 开发继续，但不能解除 N0 安装子项、N0 overall 或正式安装依赖的 `no_go`。

- P0 总体决策为 `P0 overall_go`，或明确记录为 `P0 transition_allowed_with_no_go` 并限制后续仅能进行隔离的 fake/admin 开发；
- DSH Workbench product package 官方安装契约取证已形成固定 commit/profile 绑定的 `fact/candidate/pending_checks/warning` 证据表；
- 真实 Provider 或真实团队资产写入前的身份映射、ACL、双 asset-space 隔离、权限撤销、Worker 重启恢复、reconciliation、secret/path 负向测试已通过；若未通过，只能继续隔离的 fake/admin 开发，不能以 `blocked/fallback_only` 解除真实写入、真实发布或 Pilot 硬阻塞；
- Git、WeKnora、SkillHub、TeamAI、TeamLab、DSH/Harness 各自有版本、环境、健康、最终 read-back、fallback、回滚和 owner；若 TeamLab 不在本期分发路径，必须标记 `readiness_only/non_blocking`；
- fake Provider 支持成功、重复、失败、timeout、unknown、read-back mismatch；
- Workbench package 在固定 DSH Desktop/profile 上完成安装、重启、server/client load、UI/health、disable、uninstall 和 rollback，或有完整的 `blocked/fallback_only` 证据；
- 腾讯云非生产后端部署边界、网络、凭据、日志、备份和回滚已明确；
- DSH Desktop Workbench product package 与腾讯云 DSH/Harness 服务端的结论分开记录；
- P0 不把 User-authored Plugin 的创建、发布或运行能力标记为已实现；这些能力保留到后续独立阶段设计；
- `decision`、`decision_date`、`expiry_or_review_date`、`rollback_or_next_action` 和 `decision_record_id` 与阶段 Go/No-Go 记录保持一致；
- `fallback_expires_at` 到期后由后续控制面审核/对账任务将 fallback 状态回退为 `pending` 或 `blocked`，在该任务实现前不得把到期自动转换写成已实现能力；

P0 完成后，下一份实现任务应进入 Knowledge domain/state/contract 的 TDD，而不是直接建设完整 SkillHub、TeamAI 或 Harness Runtime。
